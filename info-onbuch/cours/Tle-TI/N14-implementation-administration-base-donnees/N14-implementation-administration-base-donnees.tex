\coursec{Du MCD au schéma relationnel}

Le lycée bilingue de Bafoussam gère encore ses 2\,400 élèves dans des cahiers : notes, paiements de scolarité, absences. À chaque conseil de classe, le censeur passe trois jours à recouper les informations, et les erreurs se multiplient : un élève radié reçoit encore des bulletins, deux élèves portent le même matricule. Le proviseur mandate ton groupe TI : modéliser ces données, les implémenter dans un SGBD et permettre au secrétariat d'extraire en quelques secondes la liste des élèves de Tle TI n'ayant pas soldé la scolarité.

Problématique : \textbf{comment passer d'un cahier papier à une base de données fiable, interrogeable et sauvegardable ?}

La réponse commence par une étape décisive : transformer le \cle{MCD} (Modèle Conceptuel de Données), conçu lors de l'analyse, en un \cle{schéma relationnel}, c'est-à-dire en un plan précis de tables qu'un SGBD comme MySQL saura créer. C'est l'objet de cette section.

\courssub{Rappel : le Modèle Conceptuel de Données (MCD)}

\courssub{Pourquoi un modèle conceptuel ?}

Avant d'écrire la moindre ligne de SQL, il faut \emph{comprendre} les données du monde réel. Le MCD est un schéma graphique, indépendant de tout logiciel, qui représente les objets manipulés par l'organisation et leurs liens. Il sert de contrat entre le client (le proviseur) et l'informaticien (toi) : tant que le MCD n'est pas validé, on ne code rien.

\begin{definition}[Les briques du MCD]
\begin{itemize}
  \item Une \cle{entité} représente un objet du monde réel, doté d'une existence propre (ex. : \texttt{ELEVE}, \texttt{CLASSE}, \texttt{MATIERE}).
  \item Un \cle{attribut} est une propriété d'une entité (ex. : \texttt{nom}, \texttt{dateNaissance}, \texttt{coefficient}).
  \item L'\cle{identifiant} est l'attribut (ou le groupe d'attributs) qui distingue de façon unique chaque occurrence de l'entité (ex. : \texttt{matricule}). On le \emph{souligne}.
  \item Une \cle{association} est un lien sémantique entre entités (ex. : \texttt{INSCRIRE} relie \texttt{ELEVE} et \texttt{CLASSE}).
  \item Les \cle{cardinalités} indiquent, pour chaque patte de l'association, le nombre minimal et maximal de participations d'une occurrence de l'entité : $(1,1)$, $(0,1)$, $(1,n)$, $(0,n)$.
\end{itemize}
\end{definition}

\begin{exemplebox}[Lire des cardinalités]
Dans le MCD du lycée : un élève est inscrit dans \emph{une et une seule} classe (cardinalité $1,1$ côté \texttt{ELEVE}), et une classe accueille \emph{au moins un, au plus plusieurs} élèves (cardinalité $1,n$ côté \texttt{CLASSE}). L'association \texttt{INSCRIRE} est donc de type $(1,1)-(1,n)$.
\end{exemplebox}

\courssub{Le schéma relationnel : le plan des tables}

Un SGBD relationnel (MySQL, PostgreSQL\dots) ne connaît qu'une seule structure : la \textbf{table}. Il faut donc traduire le MCD en un ensemble de tables reliées entre elles. C'est le schéma relationnel.

\begin{definition}[Schéma relationnel, clé primaire, clé étrangère]
\begin{itemize}
  \item Un \cle{schéma relationnel} est la description des tables d'une base : pour chaque table, son nom suivi de la liste de ses colonnes, avec la clé primaire soulignée et les clés étrangères repérées par \texttt{\#}.
  \item La \cle{clé primaire} d'une table est une colonne (ou un groupe de colonnes) dont la valeur identifie de manière unique chaque ligne : jamais nulle, jamais dupliquée.
  \item Une \cle{clé étrangère} est une colonne d'une table qui reprend la clé primaire d'une \emph{autre} table, afin de matérialiser un lien entre les deux.
\end{itemize}
Notation : \texttt{CLASSE(\underline{idClasse}, libelle, niveau)} et \texttt{ELEVE(\underline{matricule}, nom, \#idClasse)}.
\end{definition}

\begin{savaistu}[Edgar F. Codd, père du modèle relationnel]
Le modèle relationnel a été inventé en 1970 par le Britannique \textbf{Edgar F. Codd}, chercheur chez IBM, dans son article \emph{« A Relational Model of Data for Large Shared Data Banks »}. Son idée révolutionnaire : représenter toutes les données sous forme de tables mathématiques (relations) et les manipuler avec une algèbre rigoureuse. IBM n'y crut pas immédiatement ; c'est Oracle qui commercialisa le premier SGBD relationnel en 1979. Codd reçut le prix Turing en 1981. Aujourd'hui, MySQL, PostgreSQL, Oracle et SQL Server — qui font tourner les systèmes de MTN Mobile Money ou des impôts en ligne — appliquent tous son modèle.
\end{savaistu}

\courssub{Les trois règles de passage du MCD au relationnel}

Le passage du MCD au schéma relationnel n'est pas un art : c'est un \textbf{algorithme} composé de trois règles mécaniques. Appliquées correctement, elles garantissent un schéma sans redondance ni perte d'information.

\begin{methode}[Les 3 règles de transformation du MCD en schéma relationnel]
\begin{enumerate}
  \item \textbf{Règle 1 — Entité.} Toute entité devient une \textbf{table}. Ses attributs deviennent les colonnes, et son identifiant devient la \textbf{clé primaire} (soulignée).
  \item \textbf{Règle 2 — Association $(x,1)-(x,n)$.} Une association binaire dont une patte a une cardinalité maximale de 1 ne devient \emph{pas} une table. On fait \textbf{migrer la clé primaire du côté « n » vers le côté « 1 »} : elle devient une \textbf{clé étrangère} dans la table du côté « 1 ». Les éventuels attributs de l'association migrent avec elle.
  \item \textbf{Règle 3 — Association $(x,n)-(x,n)$.} Une association dont les deux pattes ont une cardinalité maximale « n » devient une \textbf{table} dont la clé primaire est la \textbf{concaténation des clés primaires} des entités reliées (ces colonnes sont à la fois clé primaire composée et clés étrangères). Ses attributs propres deviennent des colonnes de cette table.
\end{enumerate}
\end{methode}

\begin{attention}[Erreur fréquente : créer une table pour une association $(1,n)$]
Beaucoup d'élèves créent systématiquement une table par association. C'est \textbf{faux} pour une association $(x,1)-(x,n)$ : créer une table \texttt{INSCRIRE} avec sa propre clé primaire ajouterait une table inutile, des jointures supplémentaires et des risques d'incohérence (un élève pourrait apparaître dans deux classes !). La clé étrangère migrée impose naturellement qu'un élève n'a \emph{qu'une seule} valeur de \texttt{\#idClasse} : la contrainte $(1,1)$ est ainsi garantie par construction. Réserve la création d'une table aux associations $(n,n)$ — et aux cas particuliers vus plus bas.
\end{attention}

\courssub{Cas particuliers : associations porteuses et associations réflexives}

\textbf{Association porteuse de données.} Une association peut posséder ses propres attributs. Par exemple, \texttt{EVALUER} relie un élève à une matière et porte l'attribut \texttt{note} (la note obtenue) : cette note n'appartient ni à l'élève seul, ni à la matière seule, mais bien au \emph{couple}. Selon la règle 3, ces attributs deviennent des colonnes de la table issue de l'association : \texttt{NOTE(\underline{\#matricule, \#idMat}, note, trimestre)}. Pour une association $(1,n)$ porteuse, les attributs migrent avec la clé étrangère (règle 2).

\textbf{Association unaire (réflexive).} Une entité peut être en relation avec \emph{elle-même}. Exemple : \texttt{ELEVE} — \texttt{PARRAINER} — \texttt{ELEVE} (un élève parraine au plus un nouvel élève ; un nouvel élève est parrainé par au plus un ancien). On applique les mêmes règles : ici, cardinalités $(0,1)-(0,1)$, donc on migre la clé d'un côté. La table devient \texttt{ELEVE(\underline{matricule}, nom, \#matriculeParrain)} : la clé étrangère référence la clé primaire \emph{de la même table}. Si l'association réflexive est $(n,n)$ (ex. : \texttt{AMITIE} entre élèves), elle devient une table à deux clés étrangères vers la même entité, renommées pour être distinguées : \texttt{AMITIE(\underline{\#matricule1, \#matricule2})}.

\courssub{Exemple fil rouge : le MCD « Lycée » traduit en schéma relationnel}

Reprenons la situation du lycée de Bafoussam. L'analyse a produit le MCD suivant :
\begin{itemize}
  \item \texttt{ELEVE}(\underline{matricule}, nom, prenom, dateNaissance, sexe) ;
  \item \texttt{CLASSE}(\underline{idClasse}, libelle, niveau) ;
  \item \texttt{MATIERE}(\underline{idMatiere}, libelle, coefficient) ;
  \item \texttt{INSCRIRE} : association $(1,1)-(1,n)$ entre \texttt{ELEVE} et \texttt{CLASSE}, porteuse de \texttt{anneeScolaire} ;
  \item \texttt{EVALUER} : association $(1,n)-(1,n)$ entre \texttt{ELEVE} et \texttt{MATIERE}, porteuse de \texttt{note} et \texttt{trimestre}.
\end{itemize}

\begin{exemplebox}[Transformation complète du MCD « Lycée » en 4 tables]
\textbf{Étape 1 (règle 1)} — les trois entités deviennent trois tables :
\begin{itemize}
  \item \texttt{ELEVE(\underline{matricule}, nom, prenom, dateNaissance, sexe)}
  \item \texttt{CLASSE(\underline{idClasse}, libelle, niveau)}
  \item \texttt{MATIERE(\underline{idMatiere}, libelle, coefficient)}
\end{itemize}
\textbf{Étape 2 (règle 2)} — \texttt{INSCRIRE} est de type $(1,1)-(1,n)$ : la clé \texttt{idClasse} migre dans \texttt{ELEVE}, avec l'attribut porté :
\begin{itemize}
  \item \texttt{ELEVE(\underline{matricule}, nom, prenom, dateNaissance, sexe, anneeScolaire, \#idClasse)}
\end{itemize}
\textbf{Étape 3 (règle 3)} — \texttt{EVALUER} est de type $(n,n)$ : elle devient la table \texttt{NOTE}, dont la clé primaire est la concaténation des deux clés :
\begin{itemize}
  \item \texttt{NOTE(\underline{\#matricule, \#idMatiere, trimestre}, note)}
\end{itemize}
Remarque : comme un élève peut avoir une note par trimestre dans la même matière, on ajoute \texttt{trimestre} à la clé primaire composée pour garantir l'unicité.
\end{exemplebox}

\begin{exoresolu}[Appliquer les règles à un mini-MCD]
Énoncé. Une bibliothèque scolaire est modélisée ainsi : \texttt{LIVRE}(\underline{isbn}, titre, auteur) ; \texttt{ADHERENT}(\underline{idAdherent}, nom) ; l'association \texttt{EMPRUNTER} relie \texttt{ADHERENT} $(0,n)$ à \texttt{LIVRE} $(0,n)$ et porte les attributs \texttt{dateEmprunt} et \texttt{dateRetour}. Donne le schéma relationnel complet.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
  \item Règle 1 : chaque entité devient une table.\\
  \texttt{LIVRE(\underline{isbn}, titre, auteur)}\\
  \texttt{ADHERENT(\underline{idAdherent}, nom)}
  \item Règle 3 : \texttt{EMPRUNTER} est de type $(n,n)$ des deux côtés, donc elle devient une table. Sa clé primaire est la concaténation des clés des entités reliées, et ses attributs propres deviennent des colonnes.\\
  \texttt{EMPRUNTER(\underline{\#idAdherent, \#isbn, dateEmprunt}, dateRetour)}
\end{enumerate}
On ajoute \texttt{dateEmprunt} à la clé primaire composée car un même adhérent peut emprunter le même livre à plusieurs reprises : le couple $(\texttt{\#idAdherent}, \texttt{\#isbn})$ seul ne serait pas unique. C'est exactement le même raisonnement que pour le trimestre dans la table \texttt{NOTE} du lycée.
\end{exoresolu}

\begin{aretenir}[L'essentiel de la section]
\begin{itemize}
  \item Le \cle{schéma relationnel} est la traduction du MCD en tables ; il se note \texttt{TABLE(\underline{clePrimaire}, col2, \#cleEtrangere)}.
  \item \textbf{Règle 1} : entité $\rightarrow$ table, identifiant $\rightarrow$ clé primaire.
  \item \textbf{Règle 2} : association $(x,1)-(x,n)$ $\rightarrow$ clé étrangère migrée du côté « n » vers le côté « 1 » (avec ses attributs portés).
  \item \textbf{Règle 3} : association $(n,n)$ $\rightarrow$ table dont la clé primaire est la concaténation des clés reliées ; les attributs portés deviennent des colonnes.
  \item Les associations réflexives suivent les mêmes règles, avec des clés étrangères renommées qui référencent la même table.
  \item La clé primaire composée doit garantir l'unicité : on y ajoute parfois un attribut discriminant (trimestre, date\dots).
\end{itemize}
\end{aretenir}

\begin{exercice}[À toi de jouer]
Le cybercafé « Connect+ » de Ngaoundéré veut gérer ses locations de postes. Le MCD comprend : \texttt{CLIENT}(\underline{idClient}, nom, telephone), \texttt{POSTE}(\underline{numPoste}, marque, etat), et l'association \texttt{UTILISER} de type $(0,n)-(1,n)$ portant \texttt{heureDebut} et \texttt{duree}. Transforme ce MCD en schéma relationnel en justifiant chaque règle appliquée.
\end{exercice}

\begin{corrige}[Exercice 1]
Règle 1 : \texttt{CLIENT(\underline{idClient}, nom, telephone)} et \texttt{POSTE(\underline{numPoste}, marque, etat)}. L'association \texttt{UTILISER} est de type $(0,n)-(1,n)$ : les deux cardinalités maximales valent « n », donc la règle 3 s'applique (et non la règle 2 : il faut une patte à maximum 1). On obtient \texttt{UTILISER(\underline{\#idClient, \#numPoste, heureDebut}, duree)}, en ajoutant \texttt{heureDebut} à la clé primaire car un client peut utiliser le même poste plusieurs fois dans la journée.
\end{corrige}

Nous disposons désormais d'un plan de tables rigoureux. Dans la section suivante, nous étudierons le logiciel qui donnera vie à ce plan : le \cle{SGBD}.

\coursec{SGBD : rôle, caractéristiques et exemples}

Dans la section précédente, nous avons appris à transformer un MCD en schéma relationnel : nous sommes donc capables, sur le papier, de décrire les tables de la bibliothèque du lycée ou de la boutique d'un commerçant de Douala. Mais un schéma relationnel n'est qu'un \emph{plan}. Pour que ce plan devienne une base de données vivante, capable d'enregistrer des milliers d'emprunts, de répondre en une fraction de seconde à la question « quels élèves n'ont pas rendu leur livre ? » et de survivre à une coupure de courant, il faut un logiciel spécialisé : le \cle{SGBD}. Cette section répond à trois questions : qu'est-ce qu'un SGBD, que fait-il exactement, et lequel choisir ?

\courssub{Pourquoi un SGBD ? Le problème à résoudre}

Imaginons que la bibliothèque du lycée gère ses emprunts dans des fichiers texte ou des classeurs Excel enregistrés sur l'ordinateur du surveillant. Très vite, les problèmes s'accumulent :

\begin{itemize}
\item \textbf{Redondance} : le nom et la classe d'un élève sont recopiés sur chaque fiche d'emprunt ; s'il change de classe, il faut corriger des dizaines de lignes, et on en oublie toujours une.
\item \textbf{Incohérence} : on retrouve « 6\textsuperscript{ème} A », « 6e A » et « Sixième A » pour la même classe.
\item \textbf{Conflits d'accès} : deux surveillants ne peuvent pas saisir en même temps dans le même fichier.
\item \textbf{Perte de données} : une panne de courant pendant l'enregistrement corrompt le fichier, sans possibilité de récupération.
\item \textbf{Absence de sécurité} : n'importe qui ouvrant le fichier peut modifier ou effacer les données.
\end{itemize}

C'est précisément pour résoudre ces cinq problèmes que les SGBD ont été inventés dans les années 1970.

\begin{definition}[Base de données et SGBD]
Une \cle{base de données} (BD) est un ensemble structuré et organisé de données relatives à un même domaine, stockées de façon persistante et accessibles à plusieurs utilisateurs.

Un \cle{Système de Gestion de Base de Données} (SGBD) est un logiciel qui assure la \textbf{description}, la \textbf{manipulation}, l'\textbf{interrogation} et l'\textbf{administration} des données d'une ou plusieurs bases de données. Il fait l'intermédiaire entre les utilisateurs (ou les programmes) et les fichiers physiques où sont réellement stockées les données.
\end{definition}

\begin{attention}[SGBD $\neq$ base de données]
C'est la confusion la plus fréquente à l'examen. Le \textbf{SGBD} est le \emph{logiciel} (MySQL, PostgreSQL, Oracle...) ; la \textbf{base de données} est le \emph{contenu} (les tables \texttt{eleve}, \texttt{livre}, \texttt{emprunt} avec leurs enregistrements). On ne dit donc pas « j'ai installé une base de données MySQL » mais « j'ai installé le SGBD MySQL, puis j'y ai créé une base de données ». Un même SGBD peut héberger plusieurs bases de données indépendantes.
\end{attention}

\courssub{Les fonctions d'un SGBD et le langage SQL}

Pour dialoguer avec le SGBD, on utilise un langage normalisé : \cle{SQL} (\emph{Structured Query Language}), standard international depuis 1986. Toutes les instructions que nous écrirons dans les sections suivantes seront en SQL. Ce langage se divise en trois familles, qui correspondent aux trois grandes fonctions du SGBD.

\begin{propriete}[Les trois familles du langage SQL (admise)]
Toute instruction SQL appartient à l'une des trois familles suivantes :
\begin{enumerate}
\item le \cle{LDD} (Langage de Définition de Données) : création et modification de la \emph{structure} — instructions \texttt{CREATE}, \texttt{ALTER}, \texttt{DROP} ;
\item le \cle{LMD} (Langage de Manipulation de Données) : gestion du \emph{contenu} — instructions \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}, \texttt{SELECT} ;
\item le \cle{LCD} (Langage de Contrôle des Données) : gestion des \emph{droits d'accès} — instructions \texttt{GRANT} (accorder) et \texttt{REVOKE} (retirer).
\end{enumerate}
\end{propriete}

Concrètement, le SGBD remplit les fonctions suivantes :

\begin{itemize}
\item \textbf{Définition des données (LDD)} : il permet de créer ou supprimer une base ou une table, d'ajouter une colonne, de changer un type, de déclarer des contraintes d'intégrité (clé primaire, unicité...).
\item \textbf{Manipulation et interrogation (LMD)} : il insère, modifie, supprime et surtout \emph{recherche} les données. C'est le SGBD qui optimise la recherche grâce aux index : trouver un élève parmi 50\,000 prend quelques millisecondes.
\item \textbf{Contrôle des accès (LCD)} : il gère des comptes utilisateurs et des droits. Le surveillant peut consulter les emprunts mais pas les supprimer ; seul l'administrateur a tous les droits.
\end{itemize}

\begin{exemplebox}[Un aperçu des trois familles]
\begin{lstlisting}[language=SQL]
-- LDD : definition de la structure
CREATE TABLE emprunt (
    id_emprunt INT PRIMARY KEY AUTO_INCREMENT,
    date_emprunt DATE NOT NULL
);

-- LMD : manipulation du contenu
INSERT INTO emprunt (date_emprunt) VALUES ('2025-01-15');
SELECT * FROM emprunt;

-- LCD : controle des droits
GRANT SELECT, INSERT ON bibliotheque.* TO 'surveillant'@'localhost';
REVOKE INSERT ON bibliotheque.* FROM 'surveillant'@'localhost';
\end{lstlisting}
\end{exemplebox}

\courssub{Les caractéristiques d'un bon SGBD}

Un SGBD digne de ce nom garantit six propriétés fondamentales. Retiens-les : elles reviennent souvent dans les questions de cours.

\begin{aretenir}[Les six caractéristiques d'un SGBD]
\begin{enumerate}
\item \textbf{Indépendance données/programmes} : on peut modifier la structure des données (ajouter une colonne) sans réécrire les programmes qui les utilisent, et inversement.
\item \textbf{Non-redondance} : chaque information n'est stockée qu'une seule fois (grâce à la décomposition en tables reliées par des clés), ce qui économise l'espace et évite les contradictions.
\item \textbf{Cohérence (intégrité)} : le SGBD refuse toute opération qui violerait une contrainte — impossible d'enregistrer un emprunt pour un élève qui n'existe pas, ou deux élèves avec le même matricule.
\item \textbf{Sécurité et confidentialité} : accès protégé par comptes et mots de passe, droits différenciés par utilisateur.
\item \textbf{Accès concurrents} : plusieurs utilisateurs peuvent travailler simultanément ; le SGBD gère les verrous pour éviter que deux écritures simultanées ne se corrompent mutuellement.
\item \textbf{Reprise après panne} : grâce au \emph{journal des transactions} (\emph{log}), le SGBD restaure un état cohérent après une coupure de courant ou un plantage.
\end{enumerate}
\end{aretenir}

\begin{savaistu}[MySQL, le SGBD du Web]
MySQL, créé en 1995 par la société suédoise MySQL AB, est l'un des SGBD les plus utilisés au monde. Gratuit, rapide et fiable, il équipe la majorité des sites web hébergés en mutualisé — y compris la plupart des sites camerounais (journaux en ligne, plateformes de e-commerce, sites d'établissements scolaires). Après son rachat par Oracle, sa communauté a créé \textbf{MariaDB}, un dérivé 100 \% libre et compatible, qui le remplace progressivement. Les grandes plateformes de Mobile Money et les applications bancaires s'appuient, elles, sur des SGBD propriétaires comme Oracle, capables de traiter des millions de transactions par jour.
\end{savaistu}

\courssub{Architecture client/serveur d'un SGBD}

Un SGBD comme MySQL fonctionne selon le modèle \cle{client/serveur}. Le \textbf{serveur} (le programme \texttt{mysqld}) est le seul à lire et écrire dans les fichiers physiques de la base. Les \textbf{clients} — un script PHP, l'interface PhpMyAdmin, la console \texttt{mysql} — envoient des requêtes SQL au serveur (par défaut sur le port 3306) et reçoivent les résultats. Cette séparation permet à des dizaines de clients, y compris distants, d'interroger la même base en même temps.

\courssub{L'environnement de travail : WAMP/XAMPP et PhpMyAdmin}

Pour pratiquer, nous utiliserons un \emph{paquetage} qui installe en une fois tout le nécessaire sur ton poste : \textbf{WAMP} (Windows) ou \textbf{XAMPP} (multiplateforme). Ces logiciels regroupent : le serveur web \textbf{Apache}, le SGBD \textbf{MySQL/MariaDB}, le langage \textbf{PHP} et l'interface \textbf{PhpMyAdmin}. \cle{PhpMyAdmin} est une application web écrite en PHP qui permet d'administrer MySQL depuis le navigateur (créer des bases et des tables, saisir des données, exécuter des requêtes SQL, exporter) sans taper de commandes système.

\begin{experience}[Découvrir PhpMyAdmin et exécuter sa première requête]
\textbf{Objectif} : vérifier la distinction client/serveur et exécuter une requête SQL.

\textbf{Matériel} : un poste avec XAMPP (ou WAMP) installé.

\textbf{Manipulation} :
\begin{enumerate}
\item Lance le panneau de contrôle XAMPP et démarre les modules \texttt{Apache} et \texttt{MySQL} (ils doivent passer au vert).
\item Ouvre le navigateur à l'adresse \texttt{http://localhost/phpmyadmin} : PhpMyAdmin (le client) apparaît.
\item Clique sur l'onglet \textbf{SQL} et saisis la requête suivante, puis clique sur \textbf{Exécuter} :
\begin{lstlisting}[language=SQL]
SHOW DATABASES;   -- liste les bases hébergées par le serveur
\end{lstlisting}
\item Dans le panneau de contrôle XAMPP, clique sur \textbf{Stop} devant MySQL, puis réexécute la requête dans PhpMyAdmin.
\end{enumerate}

\textbf{Observations} : à l'étape 3, la liste des bases s'affiche ; à l'étape 4, PhpMyAdmin affiche une erreur de connexion.

\textbf{Interprétation} : PhpMyAdmin n'est qu'un \emph{client} ; sans le \emph{serveur} MySQL actif, aucune requête ne peut aboutir. Cela illustre concrètement l'architecture client/serveur.
\end{experience}

\begin{exoresolu}[Identifier SGBD, base de données et famille SQL]
\textbf{Énoncé.} Le CENADI héberge sur un serveur MySQL trois applications : impôts, état civil et douanes. Pour chaque affirmation, dis si elle est correcte et justifie : (a) « Le serveur contient trois SGBD » ; (b) « \texttt{CREATE TABLE} relève du LMD » ; (c) « \texttt{GRANT} relève du LCD ».
\tcblower
\textbf{Solution.}
\begin{enumerate}
\item (a) \textbf{Faux} : il y a \emph{un seul} SGBD (MySQL, le logiciel serveur) qui héberge \emph{trois bases de données} distinctes. On confond ici le logiciel et son contenu.
\item (b) \textbf{Faux} : \texttt{CREATE TABLE} définit la \emph{structure} d'une table ; c'est une instruction du \textbf{LDD} (Langage de Définition de Données). Le LMD concerne le contenu (\texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}, \texttt{SELECT}).
\item (c) \textbf{Vrai} : \texttt{GRANT} accorde des droits d'accès ; c'est une instruction du \textbf{LCD} (Langage de Contrôle des Données), comme \texttt{REVOKE}.
\end{enumerate}
\end{exoresolu}

\coursec{Définition des données : tables, types et contraintes d'intégrité}

Dans la section précédente, nous avons découvert ce qu'est un \cle{SGBD} (MySQL, PostgreSQL, MariaDB\ldots) et pourquoi il est indispensable pour stocker, protéger et interroger les données d'un système d'information. Mais un SGBD installé est comme un immense entrepôt vide : avant d'y ranger la moindre information, il faut \emph{construire les rayonnages}. C'est précisément l'objet de cette section : apprendre à \cle{définir} la structure d'une base de données — créer la base, créer les tables, choisir les bons types de données et poser des verrous de sécurité appelés \cle{contraintes d'intégrité} — grâce au langage \cle{SQL} et à l'outil \cle{PhpMyAdmin}.

\courssub{Éléments caractéristiques d'une table}

Imagine le registre papier des élèves de ton lycée : chaque page est un tableau dont les colonnes sont toujours les mêmes (matricule, nom, date de naissance, classe\ldots) et chaque ligne correspond à un élève. Une \cle{table} dans une base de données relationnelle fonctionne exactement pareil.

\begin{definition}[Table, champ, enregistrement]
Une \cle{table} (ou \emph{relation}) est un ensemble de données organisé en deux dimensions :
\begin{itemize}
  \item les \cle{colonnes}, appelées aussi \cle{champs} ou \emph{attributs}, décrivent les propriétés des objets stockés (ex. \texttt{nom}, \texttt{moyenne}) ; chaque colonne possède un \textbf{nom} et un \textbf{type de données} ;
  \item les \cle{lignes}, appelées aussi \cle{enregistrements} ou \emph{tuples}, représentent chacune une occurrence concrète (un élève précis, une classe précise).
\end{itemize}
\end{definition}

Deux colonnes jouent un rôle particulier :

\begin{definition}[Clé primaire et clé étrangère]
\begin{itemize}
  \item La \cle{clé primaire} (\texttt{PRIMARY KEY}) est un champ (ou un groupe de champs) dont la valeur \textbf{identifie de manière unique} chaque enregistrement de la table. Deux lignes ne peuvent jamais avoir la même valeur de clé primaire, et cette valeur ne peut pas être vide (\texttt{NOT NULL} implicite).
  \item La \cle{clé étrangère} (\texttt{FOREIGN KEY}) est un champ d'une table qui \textbf{référence la clé primaire d'une autre table}. C'est elle qui matérialise les liens entre tables : le champ \texttt{id\_classe} de la table \texttt{ELEVE} pointe vers la clé primaire de la table \texttt{CLASSE}.
\end{itemize}
\end{definition}

\end{attention}

\courssub{Les types de données courants en MySQL}

Pourquoi déclarer un type pour chaque colonne ? Parce que le type détermine \textbf{l'espace de stockage}, les \textbf{opérations autorisées} (on peut additionner deux nombres, pas deux textes) et constitue un premier filtre contre les erreurs de saisie (une lettre dans un champ \texttt{INT} sera rejetée).

\begin{center}
\begin{tabularx}{\linewidth}{|l|X|X|}
\hline
\rowcolor{popblueL} \textbf{Type} & \textbf{Rôle} & \textbf{Exemple d'usage} \\
\hline
\texttt{INT} & Nombre entier (environ $-2$ milliards à $+2$ milliards) & identifiant, effectif d'une classe \\
\hline
\texttt{DECIMAL(M,D)} & Nombre décimal exact, $M$ chiffres au total dont $D$ après la virgule & \texttt{DECIMAL(4,2)} pour une moyenne sur 20 \\
\hline
\texttt{VARCHAR(n)} & Texte de longueur \textbf{variable}, au plus $n$ caractères & nom, prénom, adresse \\
\hline
\texttt{CHAR(n)} & Texte de longueur \textbf{fixe} (complété par des espaces) & code pays « CM », sexe « M »/« F » \\
\hline
\texttt{DATE} & Date au format \texttt{AAAA-MM-JJ} & date de naissance \\
\hline
\texttt{TEXT} & Texte long (jusqu'à 65 535 caractères) & observation, appréciation du bulletin \\
\hline
\texttt{BOOLEAN} & Valeur vraie/fausse (stockée 1/0) & élève boursier ou non \\
\hline
\end{tabularx}
\end{center}

\begin{methode}[Choisir le bon type de données pour un attribut]
Pour chaque attribut du schéma relationnel, pose-toi trois questions dans l'ordre :
\begin{enumerate}
  \item \textbf{Quelle est la nature de la valeur ?} Nombre entier (\texttt{INT}), nombre avec virgule (\texttt{DECIMAL}), texte (\texttt{VARCHAR}), date (\texttt{DATE}), vrai/faux (\texttt{BOOLEAN}) ?
  \item \textbf{Quelle est la taille maximale réaliste ?} Un nom camerounais dépasse rarement 50 caractères : \texttt{VARCHAR(50)} suffit, inutile de gaspiller avec \texttt{TEXT}.
  \item \textbf{Fera-t-on des calculs dessus ?} Un matricule comme « TI-001 » contient des lettres : c'est un \texttt{VARCHAR}, jamais un entier, même s'il contient des chiffres — on ne calcule jamais la moyenne de deux matricules !
\end{enumerate}
Exemples types : \texttt{matricule} $\rightarrow$ \texttt{VARCHAR(10)} ; \texttt{moyenne} $\rightarrow$ \texttt{DECIMAL(4,2)} (de 00,00 à 20,00) ; \texttt{date\_naissance} $\rightarrow$ \texttt{DATE} ; \texttt{est\_boursier} $\rightarrow$ \texttt{BOOLEAN}.
\end{methode}

\begin{attention}[Les pièges des types]
\begin{itemize}
  \item Ne stocke \textbf{jamais} un numéro de téléphone en \texttt{INT} : le zéro initial de « 690123456 » disparaîtrait et les numéros internationaux contiennent « + ». Utilise \texttt{VARCHAR(20)}.
  \item Pour l'argent (montants Mobile Money, frais de scolarité), préfère \texttt{DECIMAL} à \texttt{FLOAT} : \texttt{FLOAT} arrondit et peut faire perdre des francs dans les calculs.
  \item Une date s'écrit \texttt{'2007-03-15'} entre apostrophes, au format année-mois-jour (ISO 8601).
\end{itemize}
\end{attention}

\courssub{Créer, sélectionner et supprimer une base de données}

Avant de créer des tables, il faut un contenant : la \cle{base de données}. Trois ordres SQL suffisent.

\begin{propriete}[Syntaxe : gestion d'une base de données]
\begin{itemize}
  \item Création : \texttt{CREATE DATABASE nom\_base ;}
  \item Sélection (rendre la base « active » pour les commandes suivantes) : \texttt{USE nom\_base ;}
  \item Suppression : \texttt{DROP DATABASE nom\_base ;}
\end{itemize}
Chaque instruction SQL se termine par un point-virgule \texttt{;}. SQL n'est pas sensible à la casse pour les mots-clés, mais la convention est de les écrire en MAJUSCULES.
\end{propriete}

\begin{lstlisting}[language=SQL]
-- Création de la base du lycée (jeu de caractères accentués acceptés)
CREATE DATABASE lycee CHARACTER SET utf8mb4;

-- On se place dans la base : toutes les tables créées ensuite iront dedans
USE lycee;

-- Suppression complète de la base (DANGER : tout est perdu)
-- DROP DATABASE lycee;
\end{lstlisting}

\courssub{Créer une table : CREATE TABLE et contraintes d'intégrité}

Voici le cœur de la section. Une base de données scolaire qui accepterait une moyenne de 47/20, un élève sans nom ou deux fois le même matricule serait \textbf{pire qu'inutile : dangereuse}. Les \cle{contraintes d'intégrité} sont les gardiennes qui empêchent ces aberrations.

\begin{definition}[Contrainte d'intégrité]
Une \cle{contrainte d'intégrité} est une règle déclarée au SGBD, qui \textbf{rejette automatiquement} toute insertion ou modification violant cette règle. Elle garantit la cohérence et la fiabilité des données, quelle que soit l'application qui écrit dans la base. Les six contraintes au programme sont :
\begin{enumerate}
  \item \textbf{Clé primaire} (\texttt{PRIMARY KEY}) : identifiant unique et non nul de chaque ligne ;
  \item \textbf{Valeur nulle} (\texttt{NOT NULL} / \texttt{NULL}) : le champ doit-il obligatoirement être rempli ? Par défaut, un champ peut être vide (\texttt{NULL}) ;
  \item \textbf{Valeur par défaut} (\texttt{DEFAULT}) : valeur automatiquement attribuée si l'utilisateur ne précise rien ;
  \item \textbf{Unicité} (\texttt{UNIQUE}) : deux lignes ne peuvent pas avoir la même valeur pour ce champ (ex. matricule) ;
  \item \textbf{Valeur autorisée} (\texttt{CHECK}) : condition que la valeur doit vérifier (ex. moyenne entre 0 et 20) ;
  \item \textbf{Format / domaine} : imposé par le type de données lui-même (un \texttt{DATE} refuse « 32 janvier », un \texttt{INT} refuse « abc »).
\end{enumerate}
On ajoute à cette liste la \textbf{clé étrangère} (\texttt{FOREIGN KEY ... REFERENCES}), qui garantit qu'une valeur référencée existe bien dans l'autre table (intégrité référentielle).
\end{definition}

\begin{propriete}[Syntaxe générale de CREATE TABLE]
\begin{lstlisting}[language=SQL]
CREATE TABLE nom_table (
    colonne1 TYPE [contraintes de colonne],
    colonne2 TYPE [contraintes de colonne],
    ...,
    PRIMARY KEY (colonne),
    FOREIGN KEY (colonne) REFERENCES autre_table(colonne)
);
\end{lstlisting}
Les contraintes peuvent être écrites au niveau de la colonne (\texttt{NOT NULL}, \texttt{DEFAULT}, \texttt{UNIQUE}) ou en fin de liste (\texttt{PRIMARY KEY}, \texttt{FOREIGN KEY}, \texttt{CHECK}).
\end{propriete}

\begin{exemplebox}[Script complet : création des tables CLASSE et ELEVE]
\begin{lstlisting}[language=SQL]
-- La table référencée (CLASSE) doit être créée AVANT la table ELEVE
CREATE TABLE CLASSE (
    id_classe   INT AUTO_INCREMENT,
    nom_classe  VARCHAR(20) NOT NULL UNIQUE,  -- ex. 'Tle TI A'
    effectif    INT DEFAULT 0,                -- 0 élève au départ
    PRIMARY KEY (id_classe)
);

CREATE TABLE ELEVE (
    id_eleve        INT AUTO_INCREMENT,
    matricule       VARCHAR(10) NOT NULL UNIQUE,  -- unicité du matricule
    nom             VARCHAR(50) NOT NULL,         -- nom obligatoire
    date_naissance  DATE,                         -- peut être inconnue
    moyenne         DECIMAL(4,2) DEFAULT 0.00,
    est_boursier    BOOLEAN DEFAULT FALSE,
    id_classe       INT NOT NULL,                 -- clé étrangère
    PRIMARY KEY (id_eleve),
    CHECK (moyenne BETWEEN 0 AND 20),             -- valeur autorisée
    FOREIGN KEY (id_classe) REFERENCES CLASSE(id_classe)
);
\end{lstlisting}
Grâce à \texttt{AUTO\_INCREMENT}, MySQL numérote lui-même les lignes (1, 2, 3\ldots) : on n'a jamais à choisir l'identifiant à la main.
\end{exemplebox}

\begin{attention}[Erreurs fréquentes à la création]
\begin{itemize}
  \item \textbf{Oublier la clé primaire} : MySQL accepte la table, mais tu perds toute garantie d'unicité et les jointures futures seront impossibles à fiabiliser. Vérifie toujours la présence du \texttt{PRIMARY KEY}.
  \item \textbf{Déclarer une clé étrangère vers une table inexistante} : l'ordre de création compte ! \texttt{CLASSE} doit être créée \emph{avant} \texttt{ELEVE}, sinon MySQL renvoie l'erreur \emph{Cannot add foreign key constraint}.
  \item \textbf{Types incompatibles} : la clé étrangère \texttt{ELEVE.id\_classe} doit avoir le \textbf{même type} que la clé primaire référencée \texttt{CLASSE.id\_classe} (ici \texttt{INT} des deux côtés).
  \item Oublier le point-virgule final ou les virgules entre colonnes : erreur de syntaxe immédiate.
\end{itemize}
\end{attention}

\courssub{Modifier la structure d'une table : ALTER TABLE}

En cours d'année, le proviseur décide d'ajouter le numéro de téléphone des parents dans le fichier des élèves. Faut-il tout recréer ? Non : l'ordre \cle{ALTER TABLE} modifie la structure d'une table \textbf{sans perdre les données} qu'elle contient.

\begin{propriete}[Syntaxe : ALTER TABLE]
\begin{itemize}
  \item Ajouter une colonne : \texttt{ALTER TABLE t ADD col TYPE [contraintes] ;}
  \item Supprimer une colonne : \texttt{ALTER TABLE t DROP COLUMN col ;}
  \item Renommer une colonne : \texttt{ALTER TABLE t RENAME COLUMN ancien TO nouveau ;}
  \item Modifier le type d'une colonne : \texttt{ALTER TABLE t MODIFY col NOUVEAU\_TYPE ;}
\end{itemize}
\end{propriete}

\begin{lstlisting}[language=SQL]
-- Ajout du téléphone du parent d'élève
ALTER TABLE ELEVE ADD tel_parent VARCHAR(20);

-- Le nom peut être plus long que prévu : on élargit à 80 caractères
ALTER TABLE ELEVE MODIFY nom VARCHAR(80) NOT NULL;

-- Renommage d'une colonne
ALTER TABLE ELEVE RENAME COLUMN tel_parent TO contact_parent;

-- Suppression d'une colonne devenue inutile
ALTER TABLE ELEVE DROP COLUMN est_boursier;
\end{lstlisting}

\begin{attention}[MODIFY et DROP COLUMN : prudence]
Réduire la taille d'un type (\texttt{VARCHAR(80)} $\rightarrow$ \texttt{VARCHAR(10)}) peut \textbf{tronquer} les données existantes ; convertir un texte en \texttt{INT} peut échouer ou produire des zéros. Quant à \texttt{DROP COLUMN}, les données de la colonne sont \textbf{définitivement perdues}. Avant toute modification de structure sur une base en production, fais une sauvegarde (nous verrons comment dans la section 6).
\end{attention}

\courssub{Supprimer et renommer une table}

\begin{propriete}[DROP TABLE et RENAME TABLE]
\begin{itemize}
  \item Renommer : \texttt{RENAME TABLE ancien\_nom TO nouveau\_nom ;}
  \item Supprimer : \texttt{DROP TABLE nom\_table ;} — la structure \textbf{et toutes les données} sont détruites.
\end{itemize}
\end{propriete}

\begin{attention}[DROP TABLE et DROP DATABASE sont irréversibles]
Contrairement à une corbeille Windows, MySQL ne propose \textbf{aucune annulation} : un \texttt{DROP TABLE ELEVE;} exécuté par inadvertance un vendredi soir efface instantanément le fichier de 1 500 élèves. De plus, on ne peut pas supprimer une table référencée par une clé étrangère (il faut d'abord supprimer \texttt{ELEVE} avant \texttt{CLASSE}). \textbf{Règle d'or de l'administrateur : toujours exporter une sauvegarde de la base avant toute opération destructive.} Dans PhpMyAdmin, c'est l'onglet « Exporter » — deux clics qui peuvent sauver ton année scolaire.
\end{attention}

\begin{savaistu}[Le modèle relationnel, une invention française ?]
C'est Edgar Frank \textbf{Codd}, un chercheur britannique travaillant pour IBM à San José, qui pose en 1970 les bases mathématiques du modèle relationnel (algèbre relationnelle, clés, normalisation). Mais c'est une équipe française de l'INRIA (Institut National de Recherche en Informatique et en Automatique), autour de \textbf{Michel Scholl} et \textbf{Françoise Fabret}, qui développe dans les années 80 le SGBD relationnel \textbf{MISTRAL}, puis contribue activement à la standardisation SQL (norme SQL-92). Aujourd'hui encore, la recherche française (équipes de l'INRIA, LIP6, IRISA) est à la pointe sur les bases de données distribuées, le \emph{NoSQL} et la gestion des données massives (\emph{Big Data}) — des compétences clés pour les futurs ingénieurs camerounais formés en TI.
\end{savaistu}

\courssub{Réalisation guidée : créer la base « lycee » dans PhpMyAdmin}

\begin{experience}[TP : création de la base « lycee » et de ses tables]
\textbf{Objectif :} déployer la base \texttt{lycee} avec les tables \texttt{CLASSE} et \texttt{ELEVE} sous WampServer.\\
\textbf{Matériel :} un poste avec WampServer (ou XAMPP) démarré (icône verte), un navigateur.
\begin{enumerate}
  \item Ouvre le navigateur et saisis l'adresse \texttt{http://localhost/phpmyadmin}. Connecte-toi avec l'utilisateur \texttt{root} (mot de passe vide par défaut sous WampServer).
  \item Clique sur l'onglet \textbf{SQL} dans le menu supérieur : c'est la console où l'on tape directement les requêtes.
  \item Saisis \texttt{CREATE DATABASE lycee CHARACTER SET utf8mb4;} puis clique sur \textbf{Exécuter}. La base apparaît dans la colonne de gauche.
  \item Clique sur la base \texttt{lycee} à gauche pour la sélectionner (équivalent de \texttt{USE lycee;}).
  \item Rouvre l'onglet \textbf{SQL} et colle le script complet de création des tables \texttt{CLASSE} puis \texttt{ELEVE} (voir l'exemple ci-dessus), puis \textbf{Exécuter}.
  \item \textbf{Observations :} dans la colonne de gauche, les deux tables apparaissent. Clique sur \texttt{ELEVE} puis sur l'onglet \textbf{Structure} : tu vois chaque colonne, son type, et les contraintes (clé primaire signalée par une clé jaune, index \texttt{UNIQUE} sur \texttt{matricule}).
  \item \textbf{Vérification des contraintes :} dans l'onglet \textbf{Insérer}, tente d'enregistrer un élève avec une moyenne de 25, puis un élève avec \texttt{id\_classe = 99} (classe inexistante).
  \item \textbf{Interprétation :} MySQL rejette les deux insertions : la contrainte \texttt{CHECK} bloque la moyenne invalide, et la clé étrangère bloque la référence vers une classe inexistante. Les contraintes d'intégrité fonctionnent !
\end{enumerate}
\end{experience}

\begin{exoresolu}[Modifier la structure d'une table existante]
Énoncé : le lycée bilingue de Nkolbisson souhaite désormais enregistrer le genre des élèves (« M » ou « F », obligatoire) et porter la taille du champ \texttt{nom\_classe} de 20 à 30 caractères. Écris les requêtes SQL correspondantes.
\tcblower
Solution détaillée : on utilise deux ordres \texttt{ALTER TABLE} distincts (un par modification, pour plus de clarté) :
\begin{lstlisting}[language=SQL]
-- 1. Ajout de la colonne genre : CHAR(1), obligatoire, valeur contrôlée
ALTER TABLE ELEVE ADD genre CHAR(1) NOT NULL DEFAULT 'M';
ALTER TABLE ELEVE ADD CHECK (genre IN ('M', 'F'));

-- 2. Élargissement du nom de classe (aucune perte : on agrandit)
ALTER TABLE CLASSE MODIFY nom_classe VARCHAR(30) NOT NULL UNIQUE;
\end{lstlisting}
Remarque : le \texttt{DEFAULT 'M'} est indispensable à l'ajout, car les lignes déjà présentes recevraient sinon une valeur vide, ce qui violerait le \texttt{NOT NULL}. Agrandir un \texttt{VARCHAR} est sans risque ; le réduire pourrait tronquer des données.
\end{exoresolu}

\begin{aretenir}[L'essentiel de la section]
\begin{itemize}
  \item Une table = des \textbf{colonnes} (champs typés) et des \textbf{lignes} (enregistrements) ; la \textbf{clé primaire} identifie chaque ligne, la \textbf{clé étrangère} relie deux tables.
  \item Le type de données (\texttt{INT}, \texttt{DECIMAL}, \texttt{VARCHAR(n)}, \texttt{CHAR(n)}, \texttt{DATE}, \texttt{TEXT}, \texttt{BOOLEAN}) se choisit selon la nature, la taille et l'usage de l'attribut.
  \item \texttt{CREATE DATABASE} / \texttt{USE} / \texttt{DROP DATABASE} gèrent la base ; \texttt{CREATE TABLE} définit les tables avec leurs contraintes.
  \item Les contraintes d'intégrité (\texttt{PRIMARY KEY}, \texttt{NOT NULL}, \texttt{DEFAULT}, \texttt{UNIQUE}, \texttt{CHECK}, domaine du type, clé étrangère) protègent automatiquement la cohérence des données.
  \item \texttt{ALTER TABLE} (ADD, DROP COLUMN, RENAME COLUMN, MODIFY) fait évoluer la structure ; \texttt{DROP TABLE} et \texttt{RENAME TABLE} suppriment ou renomment une table.
  \item Toute suppression est \textbf{irréversible} : sauvegarde toujours avant.
\end{itemize}
\end{aretenir}

\begin{exercice}[À toi de jouer]
La startup doualaise « EduPay » gère les paiements de scolarité par Mobile Money. Écris le script SQL créant la base \texttt{edupay} puis la table \texttt{PAIEMENT} avec les champs : \texttt{id\_paiement} (clé primaire auto-incrémentée), \texttt{montant} (décimal positif obligatoire), \texttt{date\_paiement} (date du jour par défaut n'étant pas exigée, laisser sans défaut), \texttt{operateur} (« MTN » ou « OM » uniquement), et \texttt{id\_eleve} (clé étrangère vers \texttt{ELEVE}). Puis écris la requête qui ajoute ensuite une colonne \texttt{reference\_transaction} unique de 25 caractères.
\end{exercice}

\begin{corrige}[Exercice : EduPay]
\begin{lstlisting}[language=SQL]
CREATE DATABASE edupay CHARACTER SET utf8mb4;
USE edupay;

-- On suppose que la table ELEVE existe déjà dans cette base
CREATE TABLE PAIEMENT (
    id_paiement     INT AUTO_INCREMENT,
    montant         DECIMAL(10,2) NOT NULL,
    date_paiement   DATE NOT NULL,
    operateur       VARCHAR(4) NOT NULL,
    id_eleve        INT NOT NULL,
    PRIMARY KEY (id_paiement),
    CHECK (montant > 0),
    CHECK (operateur IN ('MTN', 'OM')),
    FOREIGN KEY (id_eleve) REFERENCES ELEVE(id_eleve)

ALTER TABLE PAIEMENT

\end{lstlisting}
Points de vigilance : la table \texttt{ELEVE} doit exister avant la création de \texttt{PAIEMENT} ; \texttt{DECIMAL(10,2)} permet des montants jusqu'à 99 999 999,99 FCFA ; le \texttt{CHECK} sur l'opérateur empêche toute faute de frappe (« mtn », « Orange »).
\end{corrige}

La structure de notre base est désormais solide et protégée. Mais une base vide ne sert à rien : dans la prochaine section, nous apprendrons à la \emph{manipuler} — insérer, modifier, supprimer et surtout interroger les données avec \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE} et le puissant \texttt{SELECT}.

\coursec{Manipulation des données : INSERT, UPDATE, DELETE, SELECT}

Dans la section précédente, nous avons appris à \emph{définir} la structure d'une base de données : créer les tables, choisir les types de colonnes et poser les contraintes d'intégrité. Mais une table vide ne sert à rien. Le lycée bilingue de Nkolndongo qui vient de créer sa table \texttt{ELEVE} veut maintenant y \emph{inscrire} les élèves, \emph{corriger} une erreur de saisie, \emph{radier} un élève parti, et surtout \emph{interroger} la base : « quels sont les élèves de Yaoundé ? », « qui a payé moins de 50\,000 FCFA de scolarité ? ». C'est exactement le rôle du \cle{LMD} (Langage de Manipulation de Données), qui regroupe quatre ordres SQL fondamentaux : \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE} et \texttt{SELECT}.

\begin{definition}[Requête]
Une \cle{requête} est un ordre écrit en SQL, envoyé au SGBD, qui demande d'effectuer une opération sur les données : les insérer, les modifier, les supprimer ou les extraire. Le SGBD analyse la requête, l'exécute et renvoie un résultat (un message de confirmation ou une table de résultats).
\end{definition}

\courssub{Insertion d'enregistrements : INSERT INTO}

\textbf{Intuition.} La table est une armoire à tiroirs vide : \texttt{INSERT} est le geste qui consiste à y ranger une fiche. Sans insertion, aucune donnée n'existe.

\begin{propriete}[Syntaxe de INSERT]
\begin{lstlisting}[language=SQL]
-- Insertion d'une seule ligne (colonnes nommées : recommandé)
INSERT INTO nom_table (col1, col2, col3)
VALUES (val1, val2, val3);

-- Insertion de plusieurs lignes en une seule requête
INSERT INTO nom_table (col1, col2, col3)
VALUES (val1, val2, val3),
       (val4, val5, val6);
\end{lstlisting}
Les valeurs textuelles et les dates s'écrivent entre apostrophes ; les nombres sans apostrophes. L'ordre des valeurs doit correspondre à l'ordre des colonnes déclarées.
\end{propriete}

\begin{exemplebox}[Remplir la table ELEVE]
\begin{lstlisting}[language=SQL]
-- Deux inscriptions au lycée, en une seule requête
INSERT INTO ELEVE (id, nom, prénom, âge, ville, scolarité)
VALUES (1, 'Ngo Bell', 'Amina', 17, 'Yaoundé', 75000),
       (2, 'Etoundi', 'Jean', 18, 'Douala', 50000);
\end{lstlisting}
Si la colonne \texttt{id} est en \texttt{AUTO\_INCREMENT}, on l'omet simplement de la liste des colonnes : le SGBD la numérote tout seul.
\end{exemplebox}

\begin{attention}[Pièges fréquents à l'insertion]
\begin{itemize}
\item Oublier les apostrophes autour d'une chaîne : \texttt{VALUES (Ngo Bell)} provoque une erreur de syntaxe.
\item Insérer une valeur qui viole une contrainte (doublon de clé primaire, \texttt{NOT NULL} non renseigné, clé étrangère inexistante) : le SGBD \emph{refuse} la ligne. C'est la preuve que les contraintes de la section précédente protègent réellement les données.
\end{itemize}
\end{attention}

\courssub{Modification : UPDATE ... SET ... WHERE}

\textbf{Intuition.} Amina déménage de Yaoundé à Douala : il ne faut ni supprimer sa fiche ni tout réécrire, juste \emph{corriger} un champ. C'est le rôle de \texttt{UPDATE}.

\begin{propriete}[Syntaxe de UPDATE]
\begin{lstlisting}[language=SQL]
UPDATE nom_table
SET col1 = nouvelle_valeur1, col2 = nouvelle_valeur2
WHERE condition;
\end{lstlisting}
La clause \texttt{WHERE} désigne \emph{les lignes à modifier}. Toutes les lignes qui satisfont la condition sont mises à jour ; les autres restent intactes.
\end{propriete}

\begin{lstlisting}[language=SQL]
-- Amina (id = 1) déménage à Douala
UPDATE ELEVE
SET ville = 'Douala'
WHERE id = 1;

-- Le lycée augmente la scolarité de 5 000 FCFA pour tous les élèves de Douala
UPDATE ELEVE
SET scolarité = scolarité + 5000
WHERE ville = 'Douala';
\end{lstlisting}

\begin{attention}[Erreur fréquente : UPDATE ou DELETE sans WHERE]
Si tu oublies la clause \texttt{WHERE}, la modification ou la suppression s'applique à \textbf{toutes les lignes de la table}, sans demande de confirmation ! \texttt{UPDATE ELEVE SET ville = 'Douala';} déclare subitement que les 8 élèves habitent Douala. En entreprise, cette faute de frappe a déjà détruit des bases entières. \textbf{Réflexe de survie} : écris toujours le \texttt{WHERE} \emph{avant} le \texttt{UPDATE}, et teste d'abord ta condition avec un \texttt{SELECT} portant le même \texttt{WHERE} pour vérifier quelles lignes seront touchées.
\end{attention}

\courssub{Suppression : DELETE FROM ... WHERE}

\textbf{Intuition.} Steve (id = 8) quitte définitivement le lycée : on retire sa fiche de l'armoire. \texttt{DELETE} supprime des \emph{lignes}, pas la table.

\begin{propriete}[Syntaxe de DELETE]
\begin{lstlisting}[language=SQL]
DELETE FROM nom_table
WHERE condition;
\end{lstlisting}
Seules les lignes vérifiant la condition sont supprimées. La structure de la table (colonnes, contraintes) est conservée.
\end{propriete}

\begin{lstlisting}[language=SQL]
-- Radiation de Steve
DELETE FROM ELEVE
WHERE id = 8;
\end{lstlisting}

\begin{aretenir}[DELETE ou DROP TABLE ?]
\texttt{DELETE FROM ELEVE;} vide la table de \emph{tous} ses enregistrements mais la table (vide) existe toujours. \texttt{DROP TABLE ELEVE;} détruit la table \emph{elle-même} : structure et données disparaissent. Pour repartir à zéro on utilise DELETE ; pour supprimer définitivement l'objet, DROP.
\end{aretenir}

\courssub{Interrogation : SELECT, projection et restriction}

\textbf{Intuition.} C'est la requête la plus utilisée (plus de 80 \% des requêtes en pratique). Interroger une table, c'est répondre à deux questions : \emph{quelles colonnes} veux-tu voir ? \emph{quelles lignes} veux-tu garder ?

\begin{definition}[Projection et restriction]
La \cle{projection} est le choix des \textbf{colonnes} affichées dans le résultat (liste après \texttt{SELECT}). La \cle{restriction} (ou sélection) est le choix des \textbf{lignes} conservées, exprimé par la condition du \texttt{WHERE}. Le résultat d'un \texttt{SELECT} est toujours une \emph{nouvelle table temporaire}, sans modifier la table d'origine.
\end{definition}

\begin{propriete}[Syntaxe générale de SELECT]
\begin{lstlisting}[language=SQL]
SELECT col1, col2        -- projection : les colonnes (ou * pour toutes)
FROM nom_table
WHERE condition;         -- restriction : les lignes (facultatif)
\end{lstlisting}
\end{propriete}

\begin{lstlisting}[language=SQL]
-- Toutes les colonnes, toutes les lignes
SELECT * FROM ELEVE;

-- Projection : seulement nom et ville, pour tous les élèves
SELECT nom, ville FROM ELEVE;

-- Projection + restriction : nom et âge des élèves de Yaoundé
SELECT nom, âge
FROM ELEVE
WHERE ville = 'Yaoundé';
\end{lstlisting}

\courssub{Construire la condition du WHERE}

\textbf{Opérateurs de comparaison et opérateurs logiques}\par

Les opérateurs de comparaison sont : \texttt{=} (égal), \texttt{<>} (différent, parfois \texttt{!=}), \texttt{<}, \texttt{<=}, \texttt{>}, \texttt{>=}. On les combine avec les opérateurs logiques \texttt{AND} (les deux conditions vraies), \texttt{OR} (au moins une vraie), \texttt{NOT} (négation).

\begin{methode}[Construire une clause WHERE correcte]
\begin{enumerate}
\item \textbf{Formule la question en français} : « les élèves de Douala qui ont moins de 18 ans ».
\item \textbf{Découpe en conditions élémentaires} : \texttt{ville = 'Douala'} et \texttt{âge < 18}.
\item \textbf{Choisis le connecteur} : « et » $\rightarrow$ \texttt{AND} ; « ou » $\rightarrow$ \texttt{OR}.
\item \textbf{Respecte les priorités} : \texttt{NOT} est évalué d'abord, puis \texttt{AND}, puis \texttt{OR}. Dès qu'il y a un mélange de \texttt{AND} et de \texttt{OR}, \textbf{mets des parenthèses} pour imposer ton intention.
\item \textbf{Teste mentalement} sur deux ou trois lignes de la table avant d'exécuter.
\end{enumerate}
\end{methode}

\begin{attention}[Priorité de AND sur OR]
\texttt{WHERE ville = 'Douala' OR ville = 'Yaoundé' AND âge < 18} ne signifie \emph{pas} « (Douala ou Yaoundé) et moins de 18 ans » : le \texttt{AND} étant prioritaire, cela se lit « Douala, ou bien (Yaoundé et moins de 18 ans) ». Écris toujours : \texttt{WHERE (ville = 'Douala' OR ville = 'Yaoundé') AND âge < 18}.
\end{attention}

\textbf{Recherche de motifs : LIKE, intervalles : BETWEEN, listes : IN}\par

\begin{propriete}[Opérateurs spécialisés du WHERE]
\begin{itemize}
\item \texttt{LIKE 'motif'} : recherche sur du texte. Le joker \texttt{\%} remplace \emph{zéro ou plusieurs} caractères ; le joker \texttt{\_} remplace \emph{exactement un} caractère.
\item \texttt{BETWEEN a AND b} : valeur comprise entre \texttt{a} et \texttt{b}, \emph{bornes incluses} (équivaut à \texttt{>= a AND <= b}).
\item \texttt{IN (v1, v2, ...)} : appartenance à une liste de valeurs ; \texttt{NOT IN} : n'appartient pas à la liste.
\end{itemize}
\end{propriete}

\begin{lstlisting}[language=SQL]
-- Noms commençant par 'N' : Ngo Bell, Nkoulou, Ndi, Ngassa
SELECT nom FROM ELEVE WHERE nom LIKE 'N%';

-- Noms dont la 2e lettre est 'g' (un caractère quelconque puis 'g')
SELECT nom FROM ELEVE WHERE nom LIKE '_g%';

-- Scolarité entre 40 000 et 60 000 FCFA (bornes incluses)
SELECT nom, scolarité FROM ELEVE
WHERE scolarité BETWEEN 40000 AND 60000;

-- Élèves de Douala ou Bafoussam (équivalent à deux OR)
SELECT nom, ville FROM ELEVE
WHERE ville IN ('Douala', 'Bafoussam');

-- Élèves qui ne sont NI de Douala NI de Yaoundé
SELECT nom FROM ELEVE
WHERE ville NOT IN ('Douala', 'Yaoundé');
\end{lstlisting}

\begin{attention}[Position du joker \% dans LIKE]
\texttt{LIKE 'N\%'} trouve les noms \emph{commençant} par N ; \texttt{LIKE '\%N'} ceux \emph{finissant} par N ; \texttt{LIKE '\%N\%'} ceux \emph{contenant} un N n'importe où. Inverser la position du joker change complètement le résultat. Autre piège : \texttt{=} ne tolère aucun joker ; pour un motif, c'est obligatoirement \texttt{LIKE}.
\end{attention}

\textbf{Valeurs nulles : IS NULL / IS NOT NULL}\par

Larissa Ngassa n'a pas encore de scolarité enregistrée : son champ vaut \texttt{NULL} (absence de valeur, ce n'est ni 0 ni une chaîne vide). Or \texttt{NULL} n'est comparable à rien : \texttt{WHERE scolarité = NULL} ne renvoie \textbf{jamais} aucune ligne, même celles qui sont nulles !

\begin{propriete}[Tester la nullité]
On teste une valeur nulle exclusivement avec \texttt{IS NULL} ou \texttt{IS NOT NULL} :
\begin{lstlisting}[language=SQL]
-- Élèves dont la scolarité n'est pas encore renseignée
SELECT nom FROM ELEVE WHERE scolarité IS NULL;

-- Élèves dont la scolarité est connue
SELECT nom FROM ELEVE WHERE scolarité IS NOT NULL;
\end{lstlisting}
\end{propriete}

\courssub{Alias et DISTINCT : présenter le résultat}

\begin{propriete}[Alias avec AS et suppression des doublons avec DISTINCT]
Le mot-clé \texttt{AS} renomme une colonne (ou la table) dans le résultat, sans toucher à la base. Le mot-clé \texttt{DISTINCT}, placé juste après \texttt{SELECT}, élimine les lignes en double du résultat.
\begin{lstlisting}[language=SQL]
-- Alias : la colonne s'affiche sous le nom "Nom de famille"
SELECT nom AS 'Nom de famille', âge AS 'Âge (ans)'
FROM ELEVE;

-- Villes représentées au lycée, sans doublons : Yaoundé, Douala, Bafoussam
SELECT DISTINCT ville FROM ELEVE;
\end{lstlisting}
Sans \texttt{DISTINCT}, la dernière requête afficherait Yaoundé trois fois et Douala trois fois.
\end{propriete}

\begin{exemplebox}[Six requêtes progressives sur la table ÉLÈVE]
\begin{lstlisting}[language=SQL]
-- R1 : tous les élèves (aucune restriction)
SELECT * FROM ELEVE;

-- R2 : les élèves de 17 ans exactement -> Ngo Bell, Ndi
SELECT nom, prénom FROM ELEVE WHERE âge = 17;

-- R3 : les élèves de Douala de 18 ans ou plus -> Etoundi, Abena
SELECT nom FROM ELEVE WHERE ville = 'Douala' AND âge >= 18;

-- R4 : les noms commençant par 'N' -> Ngo Bell, Nkoulou, Ndi, Ngassa
SELECT nom FROM ELEVE WHERE nom LIKE 'N%';

-- R5 : scolarité entre 45 000 et 75 000 FCFA -> ids 1, 2, 3, 5, 8
SELECT nom, scolarité FROM ELEVE
WHERE scolarité BETWEEN 45000 AND 75000;

-- R6 : élèves de Yaoundé ou Bafoussam sans scolarité renseignée,
--      ou mineurs de Yaoundé (parenthèses obligatoires !)
SELECT nom, ville, âge FROM ELEVE
WHERE ville IN ('Yaoundé', 'Bafoussam')
  AND (scolarité IS NULL OR âge < 17);
\end{lstlisting}
\end{exemplebox}

\begin{exoresolu}[De la demande du proviseur à la requête]
Énoncé. Le proviseur demande : « la liste des noms et villes des élèves majeurs (18 ans ou plus) qui n'habitent ni Yaoundé ni Douala ». Écris la requête et donne son résultat sur notre table.
\tcblower
\textbf{Étape 1 — découpage.} Conditions élémentaires : \texttt{âge >= 18} ; ville différente de Yaoundé ; ville différente de Douala. Connecteur : « et » partout, donc \texttt{AND}. La liste négative se condense avec \texttt{NOT IN}.

\textbf{Étape 2 — requête.}
\begin{lstlisting}[language=SQL]
SELECT nom, ville
FROM ELEVE
WHERE âge >= 18
  AND ville NOT IN ('Yaoundé', 'Douala');
\end{lstlisting}

\textbf{Étape 3 — vérification ligne par ligne.} Mbarga (19 ans, Bafoussam) : retenu. Fotso (18 ans, Bafoussam) : retenu. Etoundi et Abena sont majeurs mais de Douala : exclus. Résultat : \textbf{Mbarga — Bafoussam} et \textbf{Fotso — Bafoussam}.
\end{exoresolu}

\begin{exercice}[À toi de jouer]
Sur la table \texttt{ELEVE}, écris les requêtes suivantes :
\begin{enumerate}
\item Nom et âge des élèves de moins de 18 ans habitant Yaoundé.
\item Les élèves dont le prénom se termine par « e ».
\item Les villes des élèves dont la scolarité est strictement inférieure à 60\,000 FCFA, sans doublons.
\item Corrige l'erreur de saisie : la scolarité de Larissa Ngassa (id = 7) est en réalité de 75\,000 FCFA.
\end{enumerate}
\end{exercice}

\begin{corrige}[Exercice 1]
\begin{lstlisting}[language=SQL]
-- 1. Mineurs de Yaoundé -> Nkoulou, Ngassa
SELECT nom, âge FROM ELEVE
WHERE âge < 18 AND ville = 'Yaoundé';

-- 2. Prénoms finissant par 'e' -> Marie, Chantal
SELECT nom, prénom FROM ELEVE
WHERE prénom LIKE '%e';

-- 3. Villes concernées, sans doublons -> Douala, Bafoussam
SELECT DISTINCT ville FROM ELEVE
WHERE scolarité < 60000;

-- 4. Correction ciblée : le WHERE sur la clé primaire garantit
--    qu'une seule ligne est modifiée
UPDATE ELEVE
SET scolarité = 75000
WHERE id = 7;
\end{lstlisting}
Remarque pour la question 3 : la condition \texttt{scolarité < 60000} exclut automatiquement Larissa, car toute comparaison avec \texttt{NULL} est fausse — d'où l'importance de la question 4 avant toute statistique.
\end{corrige}

\begin{aretenir}[L'essentiel de la section]
\begin{itemize}
\item \texttt{INSERT INTO ... VALUES} ajoute des lignes ; \texttt{UPDATE ... SET} les modifie ; \texttt{DELETE FROM} les supprime ; \texttt{SELECT} les interroge sans jamais modifier la base.
\item Sans \texttt{WHERE}, \texttt{UPDATE} et \texttt{DELETE} frappent \textbf{toute la table} : danger maximal.
\item \texttt{SELECT} = projection (colonnes) + restriction (lignes via \texttt{WHERE}).
\item Conditions : comparaisons (\texttt{=}, \texttt{<>}, \texttt{<}...), logique (\texttt{AND} prioritaire sur \texttt{OR}, parenthèses !), \texttt{LIKE} avec \texttt{\%} et \texttt{\_}, \texttt{BETWEEN} (bornes incluses), \texttt{IN}/\texttt{NOT IN}, et \texttt{IS NULL} pour les valeurs absentes.
\item \texttt{AS} renomme l'affichage ; \texttt{DISTINCT} supprime les doublons du résultat.
\end{itemize}
\end{aretenir}

Maintenant que tu sais extraire des lignes précises d'une table, il reste à apprendre à en tirer des \emph{synthèses} — combien d'élèves par ville ? quelle scolarité moyenne ? — et à croiser plusieurs tables entre elles : ce sera l'objet de la section suivante, consacrée à l'agrégation, au tri, au regroupement et aux jointures.

\coursec{Agrégation, tri, regroupement et jointures}

Dans la section précédente, nous avons appris à insérer, modifier et supprimer des lignes, ainsi qu'à sélectionner des données brutes avec \texttt{SELECT ... FROM ... WHERE}. Mais une base de données ne sert pas seulement à stocker des données : elle doit permettre de \textbf{répondre à des questions décisionnelles}. Combien d'élèves par classe ? Quelle est la moyenne de la classe de Terminale A ? Quel est le montant total des factures impayées pour un client donné ? Pour répondre à ces questions, nous devons \textbf{agréger}, \textbf{trier}, \textbf{regrouper} et \textbf{croiser} les données de plusieurs tables. C'est l'objet de cette section.

\courssub{Fonctions d'agrégation : résumer des ensembles de lignes}

\noindent
Une \cle{fonction d'agrégation} (ou fonction de groupe) calcule une valeur unique à partir d'un ensemble de lignes (un groupe). Elle ignore généralement les valeurs \texttt{NULL} (sauf \texttt{COUNT(*)}).

\begin{definition}[Fonctions d'agrégation standards (SQL:1999)]
Les cinq fonctions d'agrégation fondamentales sont :
\begin{itemize}
    \item \texttt{COUNT(expr)} : nombre de lignes (ou valeurs non nulles de \texttt{expr}). \texttt{COUNT(*)} compte toutes les lignes, \texttt{NULL} inclus.
    \item \texttt{SUM(expr)} : somme des valeurs (types numériques).
    \item \texttt{AVG(expr)} : moyenne arithmétique (types numériques).
    \item \texttt{MIN(expr)} / \texttt{MAX(expr)} : valeur minimale / maximale (numérique, date, chaîne).
\end{itemize}
\textbf{Comportement avec \texttt{NULL} :} \texttt{SUM}, \texttt{AVG}, \texttt{MIN}, \texttt{MAX} ignorent les \texttt{NULL}. \texttt{COUNT(colonne)} ignore les \texttt{NULL} ; \texttt{COUNT(*)} les compte.
\end{definition}

\begin{exemplebox}[Agrégation sur la table \texttt{NOTE} (contexte : bulletin scolaire)]
Soit la table \texttt{NOTE(id\_eleve, id\_matiere, note\_sur\_20)}.
\begin{lstlisting}[language=SQL]
-- 1. Nombre total de notes enregistrées
SELECT COUNT(*) AS total_notes FROM NOTE;

-- 2. Nombre de notes saisies pour les mathématiques (id_matiere = 3)
--    COUNT(note_sur_20) ignore les notes NULL (absences non justifiées)
SELECT COUNT(note_sur_20) AS notes_saisies_maths
FROM NOTE WHERE id_matiere = 3;

-- 3. Moyenne, min, max, somme des notes de l'élève n° 105
SELECT 
    AVG(note_sur_20) AS moyenne,
    MIN(note_sur_20) AS note_min,
    MAX(note_sur_20) AS note_max,
    SUM(note_sur_20) AS somme_notes
FROM NOTE WHERE id_eleve = 105;
\end{lstlisting}
\emph{Résultat typique :} \texttt{moyenne=12,50, note\_min=5, note\_max=19, somme\_notes=250}.
\end{exemplebox}

\begin{attention}[Piège : \texttt{COUNT(*)} vs \texttt{COUNT(colonne)}]
Si la colonne \texttt{note\_sur\_20} contient des \texttt{NULL} (élève absent), \texttt{COUNT(note\_sur\_20)} ne les comptera \textbf{pas}, alors que \texttt{COUNT(*)} comptera la ligne. Pour un effectif d'élèves présents à l'épreuve, utilisez \texttt{COUNT(note\_sur\_20)}. Pour l'effectif total d'inscrits (présents + absents), utilisez \texttt{COUNT(*)}.
\end{attention}

\courssub{Tri des résultats : \texttt{ORDER BY}}

\noindent
Par défaut, l'ordre des lignes retournées par \texttt{SELECT} est \textbf{indéterminé} (dépend du moteur de stockage, des index, etc.). Pour garantir un ordre, on utilise \texttt{ORDER BY}.

\begin{propriete}[Syntaxe \texttt{ORDER BY}]
\begin{lstlisting}[language=SQL]
SELECT liste_colonnes
FROM table
[WHERE condition]
ORDER BY colonne1 [ASC|DESC], colonne2 [ASC|DESC], ... ;
\end{lstlisting}
\begin{itemize}
    \item \texttt{ASC} (ascendant) : par défaut (A→Z, 0→9, date ancienne→récente).
    \item \texttt{DESC} (descendant) : ordre inverse (Z→A, 9→0, date récente→ancienne).
    \item Tri multi-critères : on trie d'abord par \texttt{colonne1}, puis \emph{à l'intérieur des égalités} par \texttt{colonne2}, etc.
    \item On peut trier par un \textbf{alias} défini dans le \texttt{SELECT} ou par le \textbf{numéro de colonne} (1 pour la 1ère colonne du SELECT), mais l'alias est plus lisible.
\end{itemize}
\end{propriete}

\begin{exemplebox}[Tri des élèves par classe puis par moyenne décroissante]
\begin{lstlisting}[language=SQL]
SELECT 
    e.nom, e.prenom, c.libelle AS classe, 
    AVG(n.note_sur_20) AS moyenne
FROM ELEVE e
JOIN CLASSE c ON e.id_classe = c.id_classe
JOIN NOTE n ON e.id_eleve = n.id_eleve
GROUP BY e.id_eleve, e.nom, e.prenom, c.libelle
ORDER BY c.libelle ASC, moyenne DESC;
\end{lstlisting}
\emph{Interprétation :} Les élèves sont groupés par classe (ordre alphabétique), et \emph{à l'intérieur de chaque classe}, classés du meilleur au plus faible.
\end{exemplebox}

\courssub{Regroupement : \texttt{GROUP BY} et filtrage des groupes : \texttt{HAVING}}

\noindent
Jusqu'ici, les fonctions d'agrégation s'appliquaient sur \emph{toute} la table (ou le sous-ensemble \texttt{WHERE}). \texttt{GROUP BY} permet de les appliquer \textbf{séparément pour chaque groupe} de lignes partageant une même valeur.

\begin{definition}[Clause \texttt{GROUP BY}]
\begin{lstlisting}[language=SQL]
SELECT colonne_groupe, fonction_agreg(colonne_cible), ...
FROM table
[WHERE condition_lignes]
GROUP BY colonne_groupe [, colonne_groupe2 ...] ;
\end{lstlisting}
\textbf{Règle stricte (SQL standard) :} Toute colonne apparaissant dans le \texttt{SELECT} (hors fonctions d'agrégation) \textbf{doit} figurer dans le \texttt{GROUP BY}. Sinon : erreur \texttt{ONLY\_FULL\_GROUP\_BY} (MySQL strict, PostgreSQL, SQL Server).
\end{definition}

\begin{propriete}[Différence fondamentale \texttt{WHERE} vs \texttt{HAVING}]
\begin{center}
\begin{tabularx}{\linewidth}{|l|X|X|}
\hline
\rowcolor{popblueL}
\textbf{Critère} & \textbf{WHERE} & \textbf{HAVING} \\ \hline
\textbf{Moment} & Filtre \textbf{avant} le regroupement (lignes brutes) & Filtre \textbf{après} le regroupement (groupes constitués) \\ \hline
\textbf{Colonnes autorisées} & Colonnes de la table (pas d'agrégats) & Colonnes du \texttt{GROUP BY} \textbf{et} fonctions d'agrégation \\ \hline
\textbf{Usage typique} & « Notes $> 10$ », « Classe = 'Terminale A' » & « Moyenne $> 12$ », « Effectif $> 30$ » \\ \hline
\end{tabularx}
\end{center}
\end{propriete}

\begin{methode}[Écrire une requête avec regroupement et \texttt{HAVING}]
\begin{enumerate}
    \item Identifier la \textbf{colonne de regroupement} (ex. \texttt{id\_classe}).
    \item Écrire le \texttt{SELECT} : colonne de regroupement + fonctions d'agrégation (+ alias).
    \item Ajouter \texttt{FROM} et les \texttt{JOIN} nécessaires.
    \item Ajouter \texttt{WHERE} pour filtrer les \textbf{lignes sources} (ex. ne garder que les notes du 1er trimestre).
    \item Ajouter \texttt{GROUP BY} avec la/les colonne(s) de regroupement.
    \item Ajouter \texttt{HAVING} pour filtrer les \textbf{groupes résultants} (ex. classes ayant plus de 40 élèves).
    \item Ajouter \texttt{ORDER BY} pour trier le résultat final.
\end{enumerate}
\end{methode}

\begin{exemplebox}[Effectif et moyenne par classe (uniquement classes $> 30$ élèves)]
Contexte : Proviseur du Lycée Bilingue d'Essos veut les classes surchargées.
\begin{lstlisting}[language=SQL]
SELECT 
    c.libelle AS classe,
    COUNT(e.id_eleve) AS effectif,
    ROUND(AVG(n.note_sur_20), 2) AS moyenne_classe
FROM CLASSE c
JOIN ELEVE e ON c.id_classe = e.id_classe
JOIN NOTE n ON e.id_eleve = n.id_eleve
WHERE n.id_trimestre = 1  -- Filtre lignes : seulement notes T1
GROUP BY c.id_classe, c.libelle
HAVING COUNT(e.id_eleve) > 30  -- Filtre groupes : classes > 30 élèves
ORDER BY effectif DESC;
\end{lstlisting}
\end{exemplebox}

\begin{attention}[Erreur classique : colonne « orpheline » dans le SELECT]
\begin{lstlisting}[language=SQL]
-- ERREUR (mode strict) : 'nom' n'est ni dans GROUP BY ni agrégé
SELECT c.libelle, e.nom, COUNT(*) 
FROM CLASSE c JOIN ELEVE e ON c.id_classe = e.id_classe
GROUP BY c.libelle;

-- CORRECT : soit on groupe par les deux, soit on agrège 'nom'
SELECT c.libelle, GROUP_CONCAT(e.nom), COUNT(*) 
FROM CLASSE c JOIN ELEVE e ON c.id_classe = e.id_classe
GROUP BY c.libelle;
\end{lstlisting}
\emph{Astuce MySQL :} \texttt{GROUP\_CONCAT(col)} concatène les valeurs du groupe. PostgreSQL : \texttt{STRING\_AGG(col, ',')}.
\end{attention}

\courssub{Données calculées et alias : enrichir le résultat}

\noindent
Le \texttt{SELECT} n'est pas limité aux colonnes de la table. On peut y placer des \textbf{expressions} (arithmétiques, chaînes, dates, conditions) et leur donner un nom (\textbf{alias}) avec \texttt{AS} (optionnel mais recommandé).

\begin{propriete}[Expressions dans le SELECT]
\begin{itemize}
    \item \textbf{Arithmétique :} \texttt{+ - * /} (priorités usuelles, parenthèses). \emph{Attention :} division entière en SQL Server / PostgreSQL si les deux opérandes sont entiers $\rightarrow$ caster : \texttt{col::numeric} ou \texttt{CAST(col AS DECIMAL)}.
    \item \textbf{Concaténation :} \texttt{||} (standard, PostgreSQL, Oracle) ou \texttt{CONCAT()} (MySQL, SQL Server).
    \item \textbf{Conditionnel :} \texttt{CASE WHEN ... THEN ... ELSE ... END} (standard).
    \item \textbf{Alias :} \texttt{AS nom\_alias} (ou juste \texttt{nom\_alias}). L'alias est utilisable dans \texttt{ORDER BY}, \texttt{HAVING}, \texttt{GROUP BY} (selon SGBD), mais \textbf{pas} dans \texttt{WHERE} (évalué avant le SELECT).
\end{itemize}
\end{propriete}

\begin{exemplebox}[Calcul du montant restant dû par élève (contexte : gestion scolarité)]
Tables : \texttt{INSCRIPTION(id\_eleve, id\_annee, montant\_du)}, \texttt{PAIEMENT(id\_eleve, id\_annee, montant\_payé)}.
\begin{lstlisting}[language=SQL]
SELECT 
    e.matricule,
    CONCAT(e.nom, ' ', e.prenom) AS eleve,
    i.montant_du AS total_du,
    COALESCE(SUM(p.montant_paye), 0) AS total_paye,
    (i.montant_du - COALESCE(SUM(p.montant_paye), 0)) AS reste_du,
    CASE 
        WHEN (i.montant_du - COALESCE(SUM(p.montant_paye), 0)) <= 0 THEN 'Soldé'
        ELSE 'Impayé'
    END AS statut
FROM ELEVE e
JOIN INSCRIPTION i ON e.id_eleve = i.id_eleve AND i.id_annee = 2024
LEFT JOIN PAIEMENT p ON e.id_eleve = p.id_eleve AND p.id_annee = 2024
GROUP BY e.id_eleve, e.matricule, e.nom, e.prenom, i.montant_du
HAVING reste_du > 0
ORDER BY reste_du DESC;
\end{lstlisting}
\emph{Notes :} \texttt{COALESCE} gère les \texttt{NULL} (aucun paiement). \texttt{LEFT JOIN} garde les élèves n'ayant rien payé. Alias \texttt{reste\_du} réutilisé dans \texttt{HAVING} (MySQL) et \texttt{ORDER BY}.
\end{exemplebox}

\courssub{Jointures : croiser les tables via les clés étrangères}

\noindent
Une base de données relationnelle \textbf{normalisée} éparpille l'information dans plusieurs tables pour éviter la redondance. La \cle{jointure} (JOIN) permet de \textbf{reconstituer l'information complète} en reliant les tables via leurs clés (primaire $\leftrightarrow$ étrangère).

\begin{definition}[Jointure interne (\texttt{INNER JOIN} ou \texttt{JOIN})]
Ne retourne que les lignes pour lesquelles la condition de jointure est vraie \textbf{dans les deux tables}. Si un élève n'a pas de classe affectée (\texttt{id\_classe} NULL) ou si une classe n'a pas d'élève, ils n'apparaissent pas.
\begin{lstlisting}[language=SQL]
-- Syntaxe explicite (recommandée : lisible, standard SQL-92)
SELECT e.nom, e.prenom, c.libelle AS classe
FROM ELEVE e
INNER JOIN CLASSE c ON e.id_classe = c.id_classe;

-- Syntaxe implicite (ancienne, à éviter : risque de produit cartésien oublié)
SELECT e.nom, e.prenom, c.libelle
FROM ELEVE e, CLASSE c
WHERE e.id_classe = c.id_classe;
\end{lstlisting}
\end{definition}

\begin{methode}[Écrire une jointure en 3 étapes]
\begin{enumerate}
    \item \textbf{Identifier les tables} nécessaires pour répondre à la question (ex. \texttt{ELEVE} pour le nom, \texttt{CLASSE} pour le libellé, \texttt{NOTE} pour les notes).
    \item \textbf{Identifier les clés de liaison} : pour chaque paire de tables, quelle colonne (FK) dans l'une correspond à quelle colonne (PK) dans l'autre ? (ex. \texttt{ELEVE.id\_classe = CLASSE.id\_classe}).
    \item \textbf{Écrire la requête} : \texttt{SELECT} les colonnes voulues (préfixées par l'alias de table si ambiguïté), \texttt{FROM} table\_principale, puis \texttt{JOIN} table\_secondaire \texttt{ON} condition, \texttt{WHERE} filtres métiers, \texttt{GROUP BY} / \texttt{HAVING} / \texttt{ORDER BY} si besoin.
\end{enumerate}
\end{methode}

\courssub{Jointures sur plus de deux tables et alias de tables}

\noindent
Pour croiser $N$ tables, on enchaîne $N-1$ clauses \texttt{JOIN}. L'ordre logique n'importe pas pour le résultat (l'optimiseur s'en charge), mais l'ordre d'écriture aide la lecture : commencez par la table « centrale » (souvent celle qui a les FK vers les autres) ou celle du \texttt{WHERE} principal.

\begin{propriete}[Qualification des colonnes et alias de tables]
\begin{itemize}
    \item \textbf{Qualification obligatoire :} Si une colonne existe dans plusieurs tables de la requête (ex. \texttt{id\_classe} dans \texttt{ELEVE} et \texttt{CLASSE}), on \textbf{doit} la préfixer : \texttt{e.id\_classe} ou \texttt{c.id\_classe}.
    \item \textbf{Alias de table :} Court (1-3 lettres), significatif (\texttt{e} pour \texttt{ELEVE}, \texttt{c} pour \texttt{CLASSE}, \texttt{n} pour \texttt{NOTE}). Utilisé pour qualifier les colonnes et raccourcir l'écriture.
    \item \textbf{Auto-jointure :} Une table jointe à elle-même (ex. hiérarchie employeur/employé). Nécessite \textbf{deux alias distincts} pour la même table.
\end{itemize}
\end{propriete}

\begin{exemplebox}[Jointure 4 tables : Bulletin complet (Élève, Classe, Matière, Note)]
\begin{lstlisting}[language=SQL]
SELECT 
    e.matricule,
    CONCAT(e.nom, ' ', e.prenom) AS eleve,
    cl.libelle AS classe,
    m.libelle AS matiere,
    n.note_sur_20,
    n.coefficient
FROM ELEVE e
JOIN CLASSE cl ON e.id_classe = cl.id_classe
JOIN NOTE n ON e.id_eleve = n.id_eleve
JOIN MATIERE m ON n.id_matiere = m.id_matiere
WHERE e.id_eleve = 101  -- Filtre sur un élève précis
  AND n.id_trimestre = 1
ORDER BY m.libelle;
\end{lstlisting}
\emph{Résultat :} Une ligne par note de l'élève 101 au T1, avec le nom de la matière et sa classe.
\end{exemplebox}

\begin{exoresolu}[Moyenne pondérée par élève et par matière (coefficient)]
\textbf{Énoncé :} Calculer la moyenne pondérée de chaque élève pour chaque matière au 1er trimestre. Afficher : Matricule, Nom, Prénom, Matière, Moyenne\_ponderee (arrondie à 2 décimales). Trier par Élève puis Matière.
\tcblower
\textbf{Solution détaillée :}
La moyenne pondérée = $\frac{\sum(note \times coef)}{\sum(coef)}$.
\begin{lstlisting}[language=SQL]
SELECT 
    e.matricule,
    e.nom, e.prenom,
    m.libelle AS matiere,
    ROUND(SUM(n.note_sur_20 * n.coefficient) / SUM(n.coefficient), 2) AS moyenne_ponderee
FROM ELEVE e
JOIN NOTE n ON e.id_eleve = n.id_eleve
JOIN MATIERE m ON n.id_matiere = m.id_matiere
WHERE n.id_trimestre = 1
GROUP BY e.id_eleve, e.matricule, e.nom, e.prenom, m.id_matiere, m.libelle
ORDER BY e.nom, e.prenom, m.libelle;
\end{lstlisting}
\emph{Points clés :} Utilisation d'expressions dans \texttt{SUM()}. \texttt{GROUP BY} sur toutes les colonnes non agrégées du SELECT. Qualification \texttt{n.coefficient} (la note porte son propre coef, souvent défini au niveau matière mais stocké en redondance contrôlée dans NOTE pour l'historique).
\end{exoresolu}

\begin{aretenir}[Checklist pour une requête SELECT complexe réussie]
\begin{enumerate}
    \item \textbf{SELECT} : Liste explicite (pas de \texttt{*}). Alias clair pour chaque expression/agrégat.
    \item \textbf{FROM / JOIN} : Tables nécessaires, alias courts, conditions \texttt{ON} exactes (PK=FK). \texttt{LEFT JOIN} si optionnel.
    \item \textbf{WHERE} : Filtres métiers sur colonnes brutes (\texttt{date}, \texttt{statut}, \texttt{id}). \textbf{Jamais} d'agrégats ni d'alias du SELECT.
    \item \textbf{GROUP BY} : Toutes les colonnes du SELECT non agrégées. Clé primaire de l'entité principale souvent suffisante (ex. \texttt{e.id\_eleve}) si SGBD supporte la dépendance fonctionnelle (MySQL 5.7+, PostgreSQL 9.1+), sinon lister toutes.
    \item \textbf{HAVING} : Filtres sur les groupes (agrégats, \texttt{COUNT}, \texttt{AVG}...). Alias du SELECT souvent utilisables.
    \item \textbf{ORDER BY} : Tri final. Alias du SELECT \textbf{toujours} utilisables. \texttt{ASC/DESC} explicite.
    \item \textbf{LIMIT} : Pour la pagination (ex. \texttt{LIMIT 20 OFFSET 40} page 3).
\end{enumerate}
\end{aretenir}

\begin{experience}[TP Guidé : Tableau de bord « Scolarité » sur PhpMyAdmin / MySQL]
\textbf{Objectif :} Produire trois requêtes décisionnelles sur la base \texttt{ecole\_db}.
\textbf{Prérequis :} Base \texttt{ecole\_db} peuplée (tables \texttt{ELEVE, CLASSE, MATIERE, NOTE, INSCRIPTION, PAIEMENT}). Script SQL fourni en ressource.
\textbf{Matériel :} Navigateur web, serveur WampServer/XAMPP, PhpMyAdmin (onglet SQL).

\begin{enumerate}
    \item \textbf{Requête 1 : « Top 5 des élèves par moyenne générale T1 »} \\
    Écrire la requête calculant la moyenne pondérée (coefficient dans \texttt{NOTE}) par élève pour \texttt{id\_trimestre=1}, triée décrochante, limitée à 5.
    \begin{lstlisting}[language=SQL]
SELECT e.matricule, CONCAT(e.nom,' ',e.prenom) AS eleve,
       ROUND(SUM(n.note_sur_20 * n.coefficient)/SUM(n.coefficient),2) AS moy_gen
FROM ELEVE e
JOIN NOTE n ON e.id_eleve = n.id_eleve
WHERE n.id_trimestre = 1
GROUP BY e.id_eleve, e.matricule, e.nom, e.prenom
ORDER BY moy_gen DESC
LIMIT 5;
    \end{lstlisting}
    \textit{Observation :} Vérifier que les élèves sans note au T1 n'apparaissent pas (INNER JOIN). Noter l'usage de l'alias \texttt{moy\_gen} dans ORDER BY.

    \item \textbf{Requête 2 : « Classes en situation d'échec (moyenne classe < 10) »} \\
    Afficher \texttt{libelle\_classe}, \texttt{effectif}, \texttt{moyenne\_classe} pour les classes dont la moyenne générale (toutes matières, tous élèves, T1) est strictement inférieure à 10.
    \begin{lstlisting}[language=SQL]
SELECT c.libelle AS classe, COUNT(DISTINCT e.id_eleve) AS effectif,
       ROUND(AVG(n.note_sur_20), 2) AS moyenne_classe
FROM CLASSE c
JOIN ELEVE e ON c.id_classe = e.id_classe
JOIN NOTE n ON e.id_eleve = n.id_eleve
WHERE n.id_trimestre = 1
GROUP BY c.id_classe, c.libelle
HAVING AVG(n.note_sur_20) < 10
ORDER BY moyenne_classe ASC;
    \end{lstlisting}
    \textit{Interprétation :} \texttt{COUNT(DISTINCT e.id\_eleve)} évite de compter un élève multiple fois s'il a plusieurs notes. \texttt{HAVING} filtre sur l'agrégat \texttt{AVG}.

    \item \textbf{Requête 3 : « Situation financière par élève (Inscription 2024) »} \\
    Lister tous les élèves inscrits en 2024 avec : Matricule, Nom, Montant\_du, Total\_payé, Reste\_du, Statut (Soldé/Impayé). Inclure les élèves n'ayant rien payé. Trier par Reste\_du décroissant.
    \begin{lstlisting}[language=SQL]
SELECT e.matricule, CONCAT(e.nom,' ',e.prenom) AS eleve,
       i.montant_du,
       COALESCE(SUM(p.montant_paye),0) AS total_paye,
       (i.montant_du - COALESCE(SUM(p.montant_paye),0)) AS reste_du,
       CASE WHEN (i.montant_du - COALESCE(SUM(p.montant_paye),0)) <= 0 THEN 'Soldé' ELSE 'Impayé' END AS statut
FROM ELEVE e
JOIN INSCRIPTION i ON e.id_eleve = i.id_eleve AND i.id_annee = 2024
LEFT JOIN PAIEMENT p ON e.id_eleve = p.id_eleve AND p.id_annee = 2024
GROUP BY e.id_eleve, e.matricule, e.nom, e.prenom, i.montant_du
ORDER BY reste_du DESC;
    \end{lstlisting}
    \textit{Point clé :} \texttt{LEFT JOIN} sur \texttt{PAIEMENT} + \texttt{COALESCE(SUM(...),0)}. Sans \texttt{LEFT JOIN}, les élèves sans paiement disparaîtraient. Sans \texttt{COALESCE}, \texttt{SUM} renverrait \texttt{NULL} et le calcul \texttt{reste\_du} deviendrait \texttt{NULL}.
\end{enumerate}
\textbf{Bilan :} Vous maîtrisez maintenant l'extraction d'indicateurs synthétiques (KPIs) à partir de données relationnelles normalisées.
\end{experience}

\coursec{Administration : exportation, importation et sauvegarde}

Dans la section précédente, tu as appris à interroger ta base avec des requêtes puissantes : agrégations, tris, regroupements et jointures. Ta base du lycée est maintenant vivante : elle contient des élèves, des notes, des classes, et tu sais en extraire des bulletins. Mais une question de survie demeure : \textbf{que deviennent toutes ces données le jour où le serveur tombe en panne ?} Un disque dur qui lâche en pleine année scolaire, une coupure ENEO brutale pendant une écriture, un virus, une mauvaise manipulation (un \texttt{DELETE} sans \texttt{WHERE}...), et des mois de saisie s'évaporent. L'administration d'une base de données, c'est précisément l'ensemble des gestes qui garantissent que les données \emph{survivront} à n'importe quel incident. C'est le dernier maillon de la chaîne — et souvent le plus négligé.

\courssub{Pourquoi administrer une base de données ?}

Trois situations concrètes justifient à elles seules cette section :

\begin{itemize}
\item \textbf{Sécurité et continuité de service.} Les données d'un établissement scolaire (notes, effectifs, paiements) sont critiques. Une sauvegarde régulière permet de restaurer la base en quelques minutes après un incident, au lieu de tout ressaisir.
\item \textbf{Migration.} Le lycée change d'hébergeur, ou l'application développée sur le poste du club informatique doit être déployée sur le serveur du CENADI. Il faut alors \emph{transporter} la base d'une machine à une autre : on exporte sur l'ancienne, on importe sur la nouvelle.
\item \textbf{Archivage.} En fin d'année scolaire, on fige la base (notes définitives, effectifs) dans un fichier daté, conservé précieusement. L'année suivante démarre sur une base « propre », mais l'historique reste consultable.
\end{itemize}

\begin{definition}[Sauvegarde, exportation, importation]
Une \cle{sauvegarde} (ou \emph{backup}) est une copie de sécurité des données, stockée séparément du serveur, permettant de restaurer la base en cas de perte ou de corruption.
L'\cle{exportation} est l'opération qui consiste à extraire le contenu d'une base (structure et/ou données) vers un \textbf{fichier} (SQL, CSV...) lisible et transportable.
L'\cle{importation} est l'opération inverse : on recharge un fichier d'exportation dans un SGBD pour recréer la structure et les données.
\end{definition}

\begin{aretenir}[Le cycle de vie d'une sauvegarde]
Une sauvegarde n'a de valeur que si elle forme un cycle complet : \textbf{base} $\rightarrow$ \textbf{exportation} $\rightarrow$ \textbf{fichier} $\rightarrow$ \textbf{stockage sûr} $\rightarrow$ (un jour) \textbf{restauration}. Si un maillon manque — par exemple un fichier jamais testé — la sauvegarde est illusoire.
\end{aretenir}

\courssub{Exportation dans PhpMyAdmin}

PhpMyAdmin, l'interface web de MySQL/MariaDB installée avec WampServer ou XAMPP, propose un onglet \textbf{Exporter} accessible à deux niveaux :

\begin{itemize}
\item en sélectionnant \textbf{une table} puis « Exporter » : seule cette table est extraite ;
\item en sélectionnant \textbf{la base entière} (ou sans rien sélectionner, depuis la page d'accueil) : toutes les tables sont extraites.
\end{itemize}

Deux méthodes sont proposées : \textbf{Rapide} (options par défaut, suffisantes dans la plupart des cas) et \textbf{Personnalisée} (choix des tables, du format, de la compression, export de la structure seule ou des données seules). Les formats les plus utiles au programme sont :

\begin{center}
\begin{tabularx}{\linewidth}{|l|X|X|}
\hline
\rowcolor{popblueL} \textbf{Format} & \textbf{Contenu exporté} & \textbf{Usage typique} \\
\hline
SQL & Structure (CREATE TABLE, clés, contraintes) \textbf{et} données (INSERT) & Sauvegarde complète, migration, archivage fidèle \\
\hline
CSV & Données seules, une ligne par enregistrement, valeurs séparées par des points-virgules & Échange avec un tableur (Excel), statistiques \\
\hline
\end{tabularx}
\end{center}

\begin{attention}[CSV : les données sans la structure]
Exporter en \cle{CSV} ne conserve \textbf{que les données brutes} : ni les types de colonnes, ni les clés primaires, ni les clés étrangères, ni les contraintes d'intégrité ne sont sauvegardés. Réimporter un CSV exige de recréer la table à la main, au bon format, colonne par colonne. \textbf{Seul le format SQL conserve tout} (structure + données + contraintes) et permet une restauration fidèle en une seule opération. Pour une sauvegarde de sécurité, choisis toujours SQL.
\end{attention}

Un fichier d'exportation SQL n'est rien d'autre qu'un long script texte. En voici un extrait réaliste :

\begin{lstlisting}[language=SQL]
-- Exportation de la base `lycee` -- 10/06/2025
CREATE DATABASE IF NOT EXISTS `lycee`;
USE `lycee`;

CREATE TABLE `eleve` (
  `id_eleve` INT NOT NULL AUTO_INCREMENT,
  `nom` VARCHAR(50) NOT NULL,
  `date_naiss` DATE NOT NULL,
  `id_classe` INT NOT NULL,
  PRIMARY KEY (`id_eleve`),
  FOREIGN KEY (`id_classe`) REFERENCES `classe`(`id_classe`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO `eleve` (`id_eleve`, `nom`, `date_naiss`, `id_classe`) VALUES
(1, 'Ngo Bell Amina', '2007-03-14', 2),
(2, 'Etoundi Paul',   '2006-11-02', 2),
(3, 'Mbarga Solange', '2007-07-25', 3);
\end{lstlisting}

On y reconnaît tout ce que tu as appris : création de la base, création des tables avec leurs contraintes, puis insertion des enregistrements. Réimporter ce fichier revient simplement à \textbf{rejouer le script}, instruction par instruction, dans l'ordre du fichier.

\courssub{Importation dans PhpMyAdmin}

L'importation se fait via l'onglet \textbf{Importer} : on choisit le fichier sur son poste (bouton « Parcourir »), on vérifie le format détecté (SQL en général), puis on clique sur « Exécuter ». PhpMyAdmin rejoue le script et affiche le nombre de requêtes exécutées.

\begin{attention}[Erreurs fréquentes à l'importation]
\begin{itemize}
\item \textbf{Fichier trop volumineux} : PhpMyAdmin limite la taille des envois (souvent 2 Mio ou 8 Mio, directives \texttt{upload\_max\_filesize} et \texttt{post\_max\_size} de PHP). Solution : compresser le fichier en \texttt{.zip} (PhpMyAdmin l'accepte) ou passer par la ligne de commande.
\item \textbf{Problème d'encodage} : si le fichier a été enregistré en Latin-1 et importé en UTF-8, les accents deviennent des caractères bizarres (par exemple \texttt{Ngo BÃ©ll} au lieu de \texttt{Ngo Béll}). Exporte et importe toujours en \textbf{UTF-8} (\texttt{utf8mb4}).
\item \textbf{Base déjà existante} : réimporter un script contenant \texttt{CREATE TABLE} sur une base non vide provoque des erreurs « table already exists ». Avant une restauration, supprime (ou vide) l'ancienne base.
\end{itemize}
\end{attention}

\begin{methode}[Exporter puis restaurer une base dans PhpMyAdmin]
\textbf{Exportation (sauvegarde) :}
\begin{enumerate}
\item Ouvre PhpMyAdmin et sélectionne la base \texttt{lycee} dans la colonne de gauche.
\item Clique sur l'onglet \textbf{Exporter}, méthode « Rapide », format \textbf{SQL}.
\item Clique sur « Exécuter » : le navigateur télécharge un fichier \texttt{lycee.sql}.
\item \textbf{Renomme-le immédiatement} avec la date : \texttt{lycee\_2025-06-10.sql}, et copie-le sur un support externe.
\end{enumerate}
\textbf{Restauration (après incident) :}
\begin{enumerate}
\item Crée une base vide de même nom (ou supprime l'ancienne base corrompue puis recrée-la).
\item Sélectionne cette base, ouvre l'onglet \textbf{Importer}.
\item Choisis le fichier \texttt{lycee\_2025-06-10.sql}, vérifie l'encodage UTF-8.
\item Clique sur « Exécuter » et contrôle le message de succès (nombre de requêtes exécutées).
\item \textbf{Vérifie} : ouvre quelques tables, compte les enregistrements, teste une requête de jointure.
\end{enumerate}
\end{methode}

\begin{attention}[Une sauvegarde non testée n'est pas une sauvegarde]
Une exportation n'est utile que si l'on a \textbf{vérifié qu'on peut la réimporter}. Un fichier corrompu, tronqué ou mal encodé ne sert à rien le jour de l'incident. Bonne habitude professionnelle : après chaque sauvegarde importante, teste la restauration sur une base \emph{vide} (par exemple \texttt{lycee\_test}) et contrôle le résultat. Cinq minutes de test valent mieux qu'une année de données perdues.
\end{attention}

\begin{experience}[TP guidé : sauvegarde et restauration complète de la base \texttt{lycee}]
\textbf{Objectif} : maîtriser le cycle complet exportation $\rightarrow$ destruction simulée $\rightarrow$ restauration.
\textbf{Matériel} : poste avec WampServer/XAMPP, PhpMyAdmin, base \texttt{lycee} remplie (tables \texttt{eleve}, \texttt{classe}, \texttt{note}).
\begin{enumerate}
\item \textbf{Exporte} la base \texttt{lycee} au format SQL ; renomme le fichier \texttt{lycee\_TP\_2025-06-10.sql} et copie-le sur une clé USB.
\item \textbf{Simule l'incident} : dans l'onglet SQL, exécute \texttt{DROP TABLE eleve;} — la table disparaît.
\item \textbf{Restaure} : onglet « Importer », choisis ton fichier, exécute.
\item \textbf{Vérifie} : \texttt{SELECT COUNT(*) FROM eleve;} doit redonner l'effectif initial ; teste une jointure \texttt{eleve}--\texttt{classe}.
\end{enumerate}
\textbf{Observations attendues} : la table restaurée contient exactement les données du jour de l'export ; les enregistrements saisis \emph{après} l'export sont perdus — d'où l'importance de sauvegarder \emph{régulièrement}.
\textbf{Interprétation} : une sauvegarde ne protège que ce qui existait au moment de l'export. La fréquence des sauvegardes détermine la perte maximale acceptable.
\end{experience}

\courssub{Complément utile au Bac : la sauvegarde en ligne de commande avec mysqldump}

PhpMyAdmin est pratique, mais limité (taille des fichiers, dépendance au navigateur). Les administrateurs professionnels utilisent l'outil en ligne de commande \cle{mysqldump}, fourni avec MySQL. \emph{Cette notion est un complément utile pour le Bac : elle n'est pas exigible, mais elle valorise une copie.}

\begin{propriete}[Syntaxe de mysqldump]
\begin{lstlisting}
-- Sauvegarder toute la base `lycee` dans un fichier :
mysqldump -u root -p lycee > lycee_2025-06-10.sql

-- Sauvegarder une seule table :
mysqldump -u root -p lycee eleve > table_eleve.sql

-- Restaurer (sens inverse, avec le client mysql) :
mysql -u root -p lycee < lycee_2025-06-10.sql
\end{lstlisting}
L'option \texttt{-u} précise l'utilisateur, \texttt{-p} demande la saisie du mot de passe, le symbole \texttt{>} redirige la sortie vers un fichier, \texttt{<} recharge un fichier.
\end{propriete}

L'avantage décisif : \texttt{mysqldump} peut être \textbf{automatisé} (tâche planifiée chaque nuit à 2 h), sans intervention humaine — impossible avec PhpMyAdmin.

\courssub{Bonnes pratiques de sauvegarde}

\begin{aretenir}[Les réflexes de l'administrateur]
\begin{itemize}
\item \textbf{Régularité} : sauvegarde quotidienne pour une base active (notes saisies chaque semaine), au minimum hebdomadaire.
\item \textbf{Nommage daté} : \texttt{lycee\_2025-06-10.sql} plutôt que \texttt{sauvegarde\_finale\_v2.sql}. Le format \texttt{AAAA-MM-JJ} se trie naturellement par ordre chronologique.
\item \textbf{Supports multiples} : une copie sur le poste ne protège ni du vol ni de la panne du disque.
\item \textbf{Tests de restauration} périodiques sur une base d'essai.
\end{itemize}
\end{aretenir}

\begin{savaistu}[La règle « 3-2-1 » des sauvegardes]
Les professionnels de l'informatique appliquent la règle \textbf{3-2-1} : conserver \textbf{3} copies de chaque donnée importante, sur \textbf{2} supports de nature différente (par exemple disque dur du serveur + clé USB), dont \textbf{1} copie \textbf{hors site} (dans un autre bâtiment, ou sur un espace cloud sécurisé). Ainsi, même un incendie de la salle informatique ne détruit pas toutes les copies. C'est cette règle qu'appliquent les hébergeurs et les administrations numérisées comme le CENADI ou impots.cm pour protéger les données des citoyens camerounais.
\end{savaistu}

\courssub{Scénario guidé : restauration après incident, de A à Z}

\textbf{Situation.} Mardi 8 h, au secrétariat du lycée : l'application de gestion affiche « Table 'lycee.note' doesn't exist ». Une mauvaise manipulation a détruit la table des notes la veille au soir. La dernière sauvegarde date de lundi 18 h : \texttt{lycee\_2025-06-09.sql}.

\begin{enumerate}
\item \textbf{Diagnostic} : dans PhpMyAdmin, onglet Structure — la table \texttt{note} a bien disparu. Pas de panique : la sauvegarde existe.
\item \textbf{Isolation} : on empêche toute nouvelle saisie pendant la restauration (sinon les nouvelles données seraient écrasées).
\item \textbf{Restauration} : onglet « Importer », fichier \texttt{lycee\_2025-06-09.sql}, exécution. Message : « 1 248 requêtes exécutées avec succès ».
\item \textbf{Vérification} : \texttt{SELECT COUNT(*) FROM note;} redonne les 1 200 notes attendues ; un bulletin test est régénéré et comparé à un bulletin imprimé.
\item \textbf{Bilan} : seules les notes saisies mardi matin avant l'incident sont perdues — elles seront ressaisies à la main. \textbf{Leçon} : passer à une sauvegarde quotidienne automatique avec \texttt{mysqldump}.
\end{enumerate}

\courssub{Survol : gestion des utilisateurs et des droits (GRANT)}

Dernier volet de l'administration : \textbf{qui a le droit de faire quoi} sur la base. Le compte \texttt{root} (super-utilisateur) ne doit jamais être utilisé par une application ni partagé. On crée des comptes dédiés avec des droits minimaux, grâce à l'instruction \cle{GRANT} (\emph{complément utile, non exigible}) :

\begin{lstlisting}[language=SQL]
-- Creer un utilisateur 'secretaire' avec mot de passe
CREATE USER 'secretaire'@'localhost' IDENTIFIED BY 'Mot2Passe!Fort';

-- Lui accorder uniquement lecture et insertion sur la base lycee
GRANT SELECT, INSERT ON lycee.* TO 'secretaire'@'localhost';

-- Retirer un droit si necessaire
REVOKE INSERT ON lycee.* FROM 'secretaire'@'localhost';
\end{lstlisting}

Ainsi, même si le mot de passe du secrétariat fuit, un attaquant ne pourra ni supprimer (\texttt{DELETE}, \texttt{DROP}) ni modifier les notes. C'est le \textbf{principe du moindre privilège} : chaque utilisateur ne reçoit que les droits strictement nécessaires à sa tâche.

\begin{exoresolu}[Choisir la bonne stratégie de sauvegarde]
\textbf{Énoncé.} Le club informatique d'un lycée de Douala gère la base des notes (environ 3 000 enregistrements modifiés chaque semaine). Le proviseur demande : « Une sauvegarde par trimestre sur le poste du secrétariat, ça suffit, non ? » Réponds en proposant une stratégie argumentée, avec nommage des fichiers et supports.
\tcblower
\textbf{Solution.} Non, cette stratégie est insuffisante pour deux raisons : (1) avec une sauvegarde trimestrielle, un incident peut faire perdre \textbf{trois mois} de saisie ; (2) une copie unique sur le poste local ne survit ni à une panne de disque, ni à un vol, ni à un incendie.
Stratégie proposée, conforme à la règle 3-2-1 :
\begin{itemize}
\item \textbf{Fréquence} : sauvegarde automatique quotidienne via \texttt{mysqldump} planifié chaque nuit ;
\item \textbf{Nommage daté} : \texttt{lycee\_2025-06-09.sql}, \texttt{lycee\_2025-06-10.sql}, etc. ;
\item \textbf{3 copies} : le fichier sur le serveur + une copie sur disque externe + une copie hebdomadaire hors site (cloud ou disque conservé au domicile de l'administrateur) ;
\item \textbf{2 supports différents} : disque dur interne et disque externe/cloud ;
\item \textbf{Test mensuel} : restauration sur une base \texttt{lycee\_test} pour vérifier que les fichiers sont exploitables.
\end{itemize}
Perte maximale en cas d'incident : une journée de saisie, au lieu d'un trimestre.
\end{exoresolu}

\begin{enumerate}

\begin{aretenir}[L'essentiel de la section]
\begin{itemize}
\item Sauvegarder = exporter la base (format \textbf{SQL}, qui conserve structure + données) vers un fichier \textbf{daté}, copié sur des \textbf{supports multiples} dont un \textbf{hors site} (règle 3-2-1).

\item Une sauvegarde n'a de valeur que si sa restauration a été \textbf{testée}.

\end{itemize}

\begin{propriete}[Règles de passage MCD $\to$ Relationnel (Mérise)]
\begin{itemize}
    \item \textbf{Entité forte} $\to$ Table (nom entité), attributs = colonnes, identifiant = \cle{PK}.
    \item \textbf{Entité faible} (identifiant relatif) $\to$ Table, PK composée : identifiant relatif + PK de l'entité propriétaire (clé étrangère).
    \item \textbf{Association 1:n} $\to$ Clé étrangère migrée vers la table du côté « n » (référence la PK du côté « 1 »).
    \item \textbf{Association n:m} $\to$ Table de liaison (PK composée des deux PK étrangères).
    \item \textbf{Attribut multi-valué} $\to$ Table séparée (PK composée : PK entité + attribut).
\end{itemize}
\end{propriete}

\begin{propriete}[Syntaxe SQL clé (MySQL/MariaDB)]
\begin{lstlisting}[language=SQL]
-- Création table avec contraintes
CREATE TABLE table_name (
    col1 TYPE CONSTRAINTS,
    col2 TYPE,
    CONSTRAINT pk_name PRIMARY KEY (col1),
    CONSTRAINT fk_name FOREIGN KEY (col_fk) 
        REFERENCES parent_table(parent_pk)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT chk_name CHECK (condition)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Insertion multiple
INSERT INTO table (col1, col2) VALUES
(val1, val2), (val3, val4);

-- Jointure externe (gauche) pour garder les lignes sans correspondance
SELECT t1.col, t2.col FROM t1 LEFT JOIN t2 ON t1.pk = t2.fk;

-- Agrégation avec regroupement
SELECT groupe, SUM(montant) AS total FROM table GROUP BY groupe ORDER BY total DESC;

-- Recherche motif (insensible casse par défaut utf8mb4_general_ci)
WHERE nom LIKE '%nga%';

-- Valeur nulle
WHERE montant IS NULL OR montant = 0; -- ou COALESCE(SUM(montant),0)=0
\end{lstlisting}
\end{propriete}

CREATE DATABASE IF NOT EXISTS scolarite
    CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;

-- 2. Table CLASSE (aucune FK entrante)

    matricule CHAR(10),

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 4. Table PAIEMENT (FK vers ELEVE)
CREATE TABLE PAIEMENT (
    idPaiement INT AUTO_INCREMENT,
    matricule CHAR(10) NOT NULL,
    datePaiement DATE NOT NULL,
    montant DECIMAL(10,2) NOT NULL DEFAULT 0.00,

\begin{attention}[Pièges classiques DDL]
\begin{itemize}
    \item Oublier \texttt{ENGINE=InnoDB} : MyISAM ne supporte pas les clés étrangères (\texttt{FOREIGN KEY} ignoré silencieusement).
    \item Inverser l'ordre de création : erreur \texttt{ERROR 1215 (HY000): Cannot add foreign key constraint}.
    \item Type de la FK différent de la PK référencée (ex: \texttt{INT} vs \texttt{BIGINT}, \texttt{CHAR(10)} vs \texttt{VARCHAR(10)}) $\to$ erreur 1215.
    \item \texttt{DEFAULT 0} sans \texttt{NOT NULL} : possible, mais \texttt{DEFAULT} ne s'applique qu'à l'insertion si la colonne est omise ; \texttt{NOT NULL} garantit l'intégrité.
    \item \texttt{CHAR(10)} pour \texttt{matricule} : les valeurs fournies font 9 caractères. MySQL complète par des espaces à droite. Préférer \texttt{VARCHAR(10)} en production pour éviter les surprises de comparaison (\texttt{'2024TI001'} = \texttt{'2024TI001 '} est vrai en comparaison mais pas en \texttt{LIKE}).
\end{itemize}
\end{attention}

ORDER BY nom;
\end{lstlisting}
\textit{Justification :} Collation \texttt{utf8mb4\_general\_ci} (ci = case insensitive) $\to$ « Nga », « Nganou », « Ngah », « Tchounga » matchent. \textit{Résultat : 4 lignes.}

\noindent\textbf{Requête 3 : Total paiements par classe (GROUP BY + SUM + Jointure + Tri)}
Il faut joindre \texttt{PAIEMENT} $\to$ \texttt{ELEVE} $\to$ \texttt{CLASSE} pour avoir le nom de la classe.
\begin{lstlisting}[language=SQL]
SELECT c.nomClasse, SUM(p.montant) AS total_encaisse
FROM PAIEMENT p
JOIN ELEVE e ON p.matricule = e.matricule
JOIN CLASSE c ON e.idClasse = c.idClasse
GROUP BY c.nomClasse
ORDER BY total_encaisse DESC;
\end{lstlisting}
\textit{Calculs attendus :}
\begin{align*}
\text{Tle TI}  &: 50000 + 25000 + 75000 + 30000 + 75000 = 255\,000 \\
\text{1ere A}  &: 60000 + 60000 + 30000 + 30000 = 180\,000 \\
\text{2nde C}  &: 55000 + 55000 = 110\,000
\end{align*}
\textit{Tri décroissant : Tle TI, 1ere A, 2nde C.}

\noindent\textbf{Requête 4 : « Nom Prénom — Montant total payé » pour TOUS les élèves (Jointure EXTERNE)}
Point crucial : les élèves sans paiement (Mbarga, Nga, Ngah) doivent apparaître avec total 0. $\to$ \texttt{LEFT JOIN} depuis \texttt{ELEVE} vers \texttt{PAIEMENT}. Gestion du \texttt{NULL} avec \texttt{COALESCE} ou \texttt{IFNULL}.
\begin{lstlisting}[language=SQL]
SELECT 
    CONCAT(e.nom, ' ', e.prenom) AS eleve,
    COALESCE(SUM(p.montant), 0) AS total_paye
FROM ELEVE e
LEFT JOIN PAIEMENT p ON e.matricule = p.matricule
GROUP BY e.matricule, e.nom, e.prenom
ORDER BY total_paye DESC;
\end{lstlisting}

\noindent\textbf{Requête 5 : Élèves n'ayant rien payé (Total = 0)}
Deux approches équivalentes. La première utilise une CTE (MySQL 8.0+), la seconde \texttt{NOT EXISTS} (compatible toutes versions, souvent plus performant).
\begin{lstlisting}[language=SQL, caption={Approche 1 : CTE + HAVING (MySQL 8.0+)}]
WITH Totaux AS (
    SELECT e.matricule, e.nom, e.prenom, COALESCE(SUM(p.montant),0) AS total
    FROM ELEVE e LEFT JOIN PAIEMENT p ON e.matricule = p.matricule
    GROUP BY e.matricule, e.nom, e.prenom
)
SELECT matricule, nom, prenom, total
FROM Totaux
WHERE total = 0;
\end{lstlisting}

\begin{lstlisting}[language=SQL, caption={Approche 2 : NOT EXISTS (toutes versions)}]
SELECT matricule, nom, prenom
FROM ELEVE e
WHERE NOT EXISTS (
    SELECT 1 FROM PAIEMENT p WHERE p.matricule = e.matricule
);
\end{lstlisting}
\textit{Résultat attendu : 3 lignes (Mbarga Paul, Nga Henriette, Ngah Julie).}
\end{exoresolu}

\begin{attention}[Piège \texttt{LEFT JOIN} + \texttt{GROUP BY}]
\begin{itemize}
    \item Si on fait \texttt{INNER JOIN} (ou \texttt{JOIN} seul), les 3 élèves sans paiement disparaissent du résultat.
    \item \texttt{SUM(p.montant)} renvoie \texttt{NULL} pour un groupe sans ligne dans \texttt{PAIEMENT} $\to$ \texttt{COALESCE(SUM(...), 0)} ou \texttt{IFNULL(SUM(...), 0)} est indispensable pour afficher 0.
    \item Le \texttt{GROUP BY} doit contenir toutes les colonnes non agrégées du \texttt{SELECT} (mode \texttt{ONLY\_FULL\_GROUP\_BY} activé par défaut dans MySQL 5.7+).
\end{itemize}
\end{attention}

    \item \textbf{DML (Data Manipulation Language) :} \texttt{INSERT} multiple, gestion des valeurs auto-incrémentées (omises dans la liste des colonnes).
    \item \textbf{DQL (Data Query Language) avancé :}
        \begin{itemize}
            \item Filtrage : opérateurs de comparaison, \texttt{LIKE} avec jokers \texttt{\%}, \texttt{IN}, \texttt{BETWEEN}.
            \item Jointures : \texttt{INNER JOIN} (correspondances strictes) vs \texttt{LEFT JOIN} (conservation lignes table gauche — crucial pour « élèves sans paiement »).
            \item Agrégation : \texttt{SUM()}, \texttt{COUNT()}, \texttt{GROUP BY} (avec colonnes non agrégées listées), \texttt{HAVING} (filtre sur agrégat), \texttt{ORDER BY} (tri sur alias ou expression).
            \item Gestion des \texttt{NULL} : \texttt{COALESCE()}/\texttt{IFNULL()} pour remplacer \texttt{NULL} par 0 dans les sommes.
            \item Alias (\texttt{AS}) pour lisibilité des colonnes résultat.
        \end{itemize}
    \item \textbf{Administration (DBA junior) :} Export (dump logique \texttt{.sql} : structure + données), suppression (\texttt{DROP DATABASE}), restauration par importation (rejouer le script), vérification d'intégrité post-restauration (comptages, requêtes métiers).
\end{itemize}
\end{aretenir}

\begin{attention}[Erreurs fréquentes observées en TP — À ne plus reproduire]
\begin{enumerate}
    \item \textbf{Oubli du \texttt{LEFT JOIN}} pour la requête « tous les élèves même sans paiement » $\to$ perte de lignes (jointure interne implicite).
    \item \textbf{\texttt{GROUP BY} incomplet} (mode \texttt{ONLY\_FULL\_GROUP\_BY}) $\to$ erreur \texttt{ERROR 1055 (42000)}. Solution : lister toutes les colonnes non agrégées du \texttt{SELECT} dans le \texttt{GROUP BY} (ou utiliser \texttt{ANY\_VALUE()} si sémantiquement justifié).
    \item \textbf{Confusion \texttt{WHERE} vs \texttt{HAVING}} : \texttt{WHERE} filtre les lignes \emph{avant} regroupement (pas de fonction d'agrégation autorisée) ; \texttt{HAVING} filtre les groupes \emph{après} agrégation.
    \item \textbf{Ordre de suppression/insertion} : On ne peut pas insérer un élève si sa classe n'existe pas (FK) ; on ne peut pas supprimer une classe si des élèves y sont rattachés (\texttt{ON DELETE RESTRICT}).
    \item \textbf{Export sans « Structure »} : ne génère que les \texttt{INSERT} $\to$ échec à l'import dans une base vide (tables inexistantes).
    \item \textbf{Encodage} : Ne pas choisir \texttt{utf8mb4} $\to$ problèmes d'accents, de caractères spéciaux (noms camerounais : « Ngà », « Été ») et tri incorrect.
\end{enumerate}
\end{attention}

\coursec{Implémentation et administration d'une base de données (SGBD, SQL)}

\courssub{Du MCD au schéma relationnel}

\begin{definition}[Modèle Conceptuel de Données (MCD) et Modèle Relationnel]
Le \textbf{MCD} (souvent représenté par le formalisme Entité-Association \emph{Merise}) décrit les données indépendamment de tout SGBD : \textbf{entités} (objets du monde réel), \textbf{propriétés} (attributs), \textbf{identifiants} (clés candidates) et \textbf{associations} (liens sémantiques avec cardinalités). Le \textbf{schéma relationnel} est la traduction logique : un ensemble de \textbf{relations} (tables) composées de \textbf{colonnes} (attributs) et de \textbf{lignes} (occurrences), liées par des \textbf{clés primaires} et \textbf{clés étrangères}.
\end{definition}

\begin{propriete}[Règles de passage MCD $\to$ Relationnel (Merise)]
\begin{enumerate}
\item \textbf{Entité $\to$ Table} : chaque entité devient une relation. Son identifiant devient la \cle{clé primaire} (soulignée ou \texttt{PRIMARY KEY}). Ses propriétés deviennent des colonnes.
\item \textbf{Association binaire (1,n) -- (1,1)} : migration de la clé primaire de l'entité côté \texttt{1} (ou \texttt{0,1}) vers la table de l'entité côté \texttt{n} comme \cle{clé étrangère} (notée \# ou \texttt{FOREIGN KEY}).
\item \textbf{Association binaire (n,m)} : l'association devient une \textbf{table de liaison} (ou table de jointure). Sa clé primaire est \textbf{composée} des deux clés primaires migrées (qui sont aussi clés étrangères). Les propriétés propres de l'association deviennent des colonnes de cette table.
\item \textbf{Association unaire (réflexive)} : même règle que binaire, la clé étrangère référence la même table (ex. \texttt{EMPLOYE(\#id\_superviseur)}).
\item \textbf{Héritage / Entités faibles} : selon la méthode (fusion, table par entité, table unique), l'identifiant de l'entité parente migre comme clé primaire (et étrangère) dans la table fille.
\end{enumerate}
\end{propriete}

\begin{methode}[Passer du MCD au schéma relationnel]
\begin{enumerate}
\item Lister toutes les entités et créer les tables correspondantes avec leur clé primaire.
\item Analyser chaque association : noter ses cardinalités (min, max des deux côtés).
\item Appliquer la règle de migration selon le type de cardinalités (voir \emph{Propriété} ci-dessus).
\item Pour chaque table, lister toutes les colonnes : clés primaires, clés étrangères (préfixées \#), attributs simples.
\item Vérifier : toute clé étrangère référence une clé primaire existante ; pas de perte d'attribut ; pas de redondance évitable.
\end{enumerate}
\textbf{Notation normalisée} : \texttt{NOM\_TABLE(\underline{cle\_primaire}, attribut1, attribut2, \#cle\_etrangere\_1, \#cle\_etrangere\_2)}.
\end{methode}

\begin{exoresolu}[MCD d'une bibliothèque municipale de Bafoussam]
La bibliothèque municipale de Bafoussam gère ses prêts avec le MCD suivant : une entité \textbf{ADHERENT} (\underline{id\_adh}, nom, quartier, telephone), une entité \textbf{LIVRE} (\underline{id\_livre}, titre, auteur, annee), et une association \textbf{EMPRUNTER} (date\_emprunt, date\_retour) de cardinalités (1,n) côté ADHERENT et (1,n) côté LIVRE (un adhérent peut emprunter plusieurs livres, un livre peut être emprunté plusieurs fois par différents adhérents à des dates différentes). Transforme ce MCD en schéma relationnel.
\tcblower
\textbf{Étape 1 — Entités $\to$ Tables.} Les identifiants deviennent clés primaires.
\begin{lstlisting}
ADHERENT(id_adh, nom, quartier, telephone)
LIVRE(id_livre, titre, auteur, annee)
\end{lstlisting}
\textbf{Étape 2 — Analyse de l'association EMPRUNTER.} Cardinalités (1,n) -- (1,n) $\equiv$ type \textbf{(n,m)}. Un adhérent emprunte $n$ livres ; un livre est emprunté par $m$ adhérents. L'association devient une \textbf{table à part entière}.
\textbf{Étape 3 — Clé primaire de la table de liaison.} Elle est composée des deux identifiants migrants : \texttt{(id\_adh, id\_livre)}. Pour distinguer deux emprunts du même livre par le même adhérent à des dates différentes, on ajoute \texttt{date\_emprunt} à la clé primaire : \texttt{(id\_adh, id\_livre, date\_emprunt)}. Les propriétés de l'association (\texttt{date\_retour}) deviennent des colonnes.
\textbf{Étape 4 — Schéma relationnel final :}
\begin{lstlisting}
ADHERENT(\underline{id_adh}, nom, quartier, telephone)
LIVRE(\underline{id_livre}, titre, auteur, annee)
EMPRUNTER(\underline{id_adh}, \underline{id_livre}, \underline{date_emprunt}, date_retour)
\end{lstlisting}
\textbf{Vérification} : chaque table a une clé primaire ; \texttt{\#id\_adh} référence \texttt{ADHERENT(id\_adh)} et \texttt{\#id\_livre} référence \texttt{LIVRE(id\_livre)} ; aucune propriété n'est perdue.
\textbf{Conclusion} : le MCD se traduit en trois relations : ADHERENT, LIVRE et EMPRUNTER, cette dernière matérialisant l'association (n,m) avec une clé primaire composée de trois attributs.
\end{exoresolu}

\courssub{SGBD : rôle, caractéristiques et exemples}

\begin{definition}[Système de Gestion de Base de Données (SGBD)]
Un \textbf{SGBD} (DBMS en anglais) est un logiciel système qui permet de \textbf{créer}, \textbf{manipuler}, \textbf{sécuriser}, \textbf{partager} et \textbf{maintenir} des bases de données. Il assure l'interface entre les utilisateurs/applications et les fichiers physiques de données.
\end{definition}

\begin{propriete}[Fonctions essentielles d'un SGBD]
\begin{itemize}
\item \textbf{Définition des données (DDL)} : création/suppression/modification de la structure (schéma).
\item \textbf{Manipulation des données (DML)} : insertion, lecture, modification, suppression des occurrences.
\item \textbf{Contrôle d'accès et sécurité} : gestion des utilisateurs, droits (GRANT/REVOKE), chiffrement.
\item \textbf{Intégrité des données} : application des contraintes (clés, domaines, unicité, référentielle).
\item \textbf{Gestion de la concurrence} : verrouillage (locks), transactions (ACID : Atomicité, Cohérence, Isolation, Durabilité).
\item \textbf{Sauvegarde et restauration} : dump, logs, réplication, récupération après panne.
\item \textbf{Optimisation} : indexation, plan d'exécution, cache, partitionnement.
\end{itemize}
\end{propriete}

\courssub{Définition des données : tables, types et contraintes d'intégrité}

\begin{definition}[Structure d'une table relationnelle]
Une \textbf{table} (relation) est un ensemble de \textbf{lignes} (enregistrements, tuples) et de \textbf{colonnes} (champs, attributs).
\begin{itemize}
\item \textbf{Clé primaire (Primary Key - PK)} : identifiant unique, non nul, immuable (ex. \texttt{id\_client}). Une seule par table.
\item \textbf{Clé étrangère (Foreign Key - FK)} : colonne(s) référençant la clé primaire d'une autre table (table \emph{parente}). Garantit l'\textbf{intégrité référentielle}.
\item \textbf{Domaine (Type de données)} : ensemble de valeurs autorisées pour une colonne (entier, chaîne, date, etc.).
\item \textbf{Contraintes d'intégrité} : règles déclaratives que le SGBD applique automatiquement.
\end{itemize}
\end{definition}

\begin{propriete}[Types de données MySQL/MariaDB courants (Choix pédagogique)]
\begin{center}
\begin{tabularx}{\linewidth}{|l|l|X|}\hline
\textbf{Catégorie} & \textbf{Type SQL} & \textbf{Usage / Précision} \\\hline
Entier & \texttt{TINYINT}, \texttt{SMALLINT}, \texttt{INT}, \texttt{BIGINT} & \texttt{INT} (4 octets, $\pm 2 \times 10^9$) suffit pour la plupart des ID. \texttt{UNSIGNED} pour n'accepter que le positif. \\\hline
Décimal exact & \texttt{DECIMAL(m,d)} ou \texttt{NUMERIC(m,d)} & \textbf{Obligatoire pour l'argent (FCFA)}. $m$=nb total chiffres, $d$=décimales. Ex: \texttt{DECIMAL(10,2)} $\to$ 99\,999\,999,99 FCFA. \\\hline
Flottant approx. & \texttt{FLOAT}, \texttt{DOUBLE} & Sciences, mesures. \textbf{Interdit pour la monnaie} (erreurs d'arrondi binaire). \\\hline
Chaîne courte & \texttt{VARCHAR(n)} & Longueur variable $\le n$ (ex. \texttt{VARCHAR(50)} pour un nom). Efficace. \\\hline
Chaîne fixe & \texttt{CHAR(n)} & Longueur fixe (ex. \texttt{CHAR(10)} pour code ISO, \texttt{CHAR(32)} pour hash MD5). \\\hline
Texte long & \texttt{TEXT}, \texttt{LONGTEXT} & Description, article, JSON brut. Pas de \texttt{DEFAULT} possible avant MySQL 8.0.13. \\\hline
Date/Heure & \texttt{DATE}, \texttt{TIME}, \texttt{DATETIME}, \texttt{TIMESTAMP} & \texttt{DATE} (YYYY-MM-DD), \texttt{DATETIME} (YYYY-MM-DD HH:MM:SS). \texttt{TIMESTAMP} = UTC, zone auto. \\\hline
Booléen & \texttt{BOOLEAN} / \texttt{TINYINT(1)} & Stocké comme 0 (faux) / 1 (vrai). \\\hline

\end{tabularx}
\end{center}
\end{propriete}

\begin{propriete}[Contraintes d'intégrité (Syntaxe MySQL)]
\begin{itemize}
\item \texttt{PRIMARY KEY (col)} : unique + not null. Une seule par table.
\item \texttt{NOT NULL} : valeur obligatoire.
\item \texttt{UNIQUE} : valeurs distinctes (autorise \texttt{NULL} sauf si \texttt{NOT NULL} combiné).
\item \texttt{DEFAULT valeur} : valeur insérée si omise (ex. \texttt{DEFAULT 'Bonanjo'}, \texttt{DEFAULT CURRENT\_TIMESTAMP}).
\item \texttt{AUTO\_INCREMENT} : entier incrémenté automatiquement (sur clé primaire \texttt{INT} ou \texttt{BIGINT}).
\item \texttt{CHECK (condition)} : \textbf{MySQL 8.0.16+} l'applique. Ex: \texttt{CHECK (solde >= 0)}, \texttt{CHECK (age BETWEEN 18 AND 100)}.
\item \texttt{FOREIGN KEY (col) REFERENCES table\_parent(col\_parent) [ON DELETE CASCADE|SET NULL] [ON UPDATE CASCADE]} : intégrité référentielle. Actions en cascade optionnelles.
\end{itemize}
\end{propriete}

\begin{methode}[Écrire un script SQL de création (CREATE DATABASE / CREATE TABLE)]
\begin{enumerate}
\item \textbf{Créer et sélectionner la base} : \texttt{CREATE DATABASE nom\_base CHARACTER SET utf8mb4 COLLATE utf8mb4\_general\_ci;} puis \texttt{USE nom\_base;} (PhpMyAdmin : panneau gauche $\to$ Nouvelle base).
\item \textbf{Ordre des tables} : créer d'abord les tables \emph{parentes} (sans clé étrangère), puis les tables \emph{enfantes}.
\item \textbf{Pour chaque colonne} : choisir le type le plus restrictif possible (ex. \texttt{TINYINT UNSIGNED} pour un âge, \texttt{VARCHAR(30)} pour un quartier).
\item \textbf{Déclarer les contraintes} : au niveau colonne (inline) ou au niveau table (après la liste des colonnes, recommandé pour clés composées et FK nommées).
\item \textbf{Exécuter et vérifier} : onglet SQL de PhpMyAdmin $\to$ Exécuter $\to$ \texttt{DESCRIBE nom\_table;} ou \texttt{SHOW CREATE TABLE nom\_table;}.
\item \textbf{Modifier la structure} : \texttt{ALTER TABLE nom\_table} avec \texttt{ADD COLUMN}, \texttt{DROP COLUMN}, \texttt{CHANGE COLUMN ancien\_nom nouveau\_nom type}, \texttt{MODIFY COLUMN nom nouveau\_type}, \texttt{ADD CONSTRAINT ... FOREIGN KEY ...}.
\end{enumerate}
\end{methode}

\begin{exoresolu}[Base de données d'un cybercafé à Douala (Bonanjo)]
Un cybercafé veut créer la base \texttt{cybercafe} contenant :
\begin{itemize}
\item Table \texttt{CLIENT} : identifiant auto-incrémenté, nom obligatoire, téléphone unique, quartier (défaut « Bonanjo »), solde en FCFA positif ou nul.
\item Table \texttt{SESSION} : identifiant auto-incrémenté, date, durée en minutes (positive), montant (défaut 0), référence au client.
\end{itemize}
Écris le script SQL complet de création.
\tcblower
\textbf{Raisonnement} : base $\to$ table parente \texttt{CLIENT} $\to$ table enfant \texttt{SESSION}. On utilise \texttt{utf8mb4} pour gérer les accents et émojis. On nomme les contraintes FK pour une maintenance aisée.
\begin{lstlisting}[language=SQL]
-- 1. Creation de la base avec encodage UTF-8 complet
CREATE DATABASE cybercafe
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_general_ci;
USE cybercafe;

-- 2. Table parente : CLIENT (aucune cle etrangere)
CREATE TABLE CLIENT (
    id_client INT UNSIGNED AUTO_INCREMENT,
    nom VARCHAR(50) NOT NULL,
    telephone VARCHAR(20) NOT NULL,
    quartier VARCHAR(30) DEFAULT 'Bonanjo',
    solde DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    date_inscription DATETIME DEFAULT CURRENT_TIMESTAMP,
    -- Contraintes de table (nommees pour diagnostic clair)
    CONSTRAINT pk_client PRIMARY KEY (id_client),
    CONSTRAINT uq_client_tel UNIQUE (telephone),
    CONSTRAINT ck_client_solde CHECK (solde >= 0)
) ENGINE=InnoDB; -- Moteur transactionnel, gere les FK

-- 3. Table enfant : SESSION (reference CLIENT)
CREATE TABLE SESSION (
    id_session INT UNSIGNED AUTO_INCREMENT,
    date_session DATE NOT NULL,
    duree SMALLINT UNSIGNED NOT NULL, -- minutes, max 65535
    montant DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    id_client INT UNSIGNED NOT NULL,
    -- Contraintes
    CONSTRAINT pk_session PRIMARY KEY (id_session),
    CONSTRAINT fk_session_client
        FOREIGN KEY (id_client) REFERENCES CLIENT(id_client)
        ON DELETE RESTRICT -- Empeche suppression client s'il a des sessions
        ON UPDATE CASCADE  -- Propagation si id_client change (rare)
) ENGINE=InnoDB;
\end{lstlisting}
\textbf{Justification des choix techniques} :
\begin{itemize}
\item \texttt{UNSIGNED} sur les ID et \texttt{duree} : double la capacité positive, interdit le négatif.
\item \texttt{DECIMAL(10,2)} pour \texttt{solde} et \texttt{montant} : exactitude monétaire (FCFA).
\item \texttt{ENGINE=InnoDB} : seul moteur supportant les clés étrangères et transactions (ACID).
\item \texttt{ON DELETE RESTRICT} : sécurité métier (on ne supprime pas un client ayant un historique).
\item \texttt{DEFAULT CURRENT\_TIMESTAMP} : horodatage automatique de l'inscription.
\end{itemize}
\textbf{Vérification} : \texttt{DESCRIBE CLIENT;} et \texttt{DESCRIBE SESSION;} confirment la structure. \verb|SHOW CREATE TABLE SESSION\G| affiche la définition complète avec les noms de contraintes.
\end{exoresolu}

\courssub{Manipulation des données : INSERT, UPDATE, DELETE}

\begin{methode}[Requêtes DML : INSERT, UPDATE, DELETE]
\begin{enumerate}
\item \textbf{INSERT} (ajout) :
\begin{lstlisting}[language=SQL]
INSERT INTO table (col1, col2, ...) VALUES (val1, val2, ...), (val3, val4, ...);
\end{lstlisting}
\begin{itemize}
\item Lister explicitement les colonnes (sécurité si ordre change).
\item Chaînes et dates entre \textbf{apostrophes simples} \texttt{'...'}.
\item Omettre les colonnes \texttt{AUTO\_INCREMENT} et celles avec \texttt{DEFAULT}.
\item Insertion multiple : plusieurs tuples séparés par des virgules (plus performant).
\end{itemize}
\item \textbf{UPDATE} (modification) :
\begin{lstlisting}[language=SQL]
UPDATE table SET col1 = expr1, col2 = expr2 WHERE condition;
\end{lstlisting}
\begin{itemize}
\item \textbf{Clause WHERE obligatoire} : sans elle, \emph{toutes} les lignes sont modifiées.
\item L'expression peut utiliser l'ancienne valeur : \texttt{SET solde = solde + 500}.
\item \textbf{Réflexe pro} : tester d'abord avec \texttt{SELECT * FROM table WHERE condition;}.
\end{itemize}
\item \textbf{DELETE} (suppression) :
\begin{lstlisting}[language=SQL]
DELETE FROM table WHERE condition;
\end{lstlisting}
\begin{itemize}
\item Même vigilance sur \texttt{WHERE}.
\item \textbf{Intégrité référentielle} : impossible de supprimer une ligne parente référencée par une enfant (erreur 1451). Solutions : supprimer les enfants d'abord, ou \texttt{ON DELETE CASCADE} (défini à la création), ou \texttt{SET NULL} (si FK nullable).
\item \texttt{TRUNCATE TABLE table;} : vide la table entièrement, réinitialise \texttt{AUTO\_INCREMENT}, plus rapide, \textbf{non transactionnel} (pas de \texttt{ROLLBACK}), ne déclenche pas les triggers.
\end{itemize}
\end{enumerate}
\end{methode}

\begin{exoresolu}[Gestion des clients du cybercafé]
Dans la base \texttt{cybercafe} : (a) insère la cliente « Amina Fotso », téléphone « 699112233 », quartier « Bali », solde 2000 FCFA ; (b) crédite son solde de 1500 FCFA ; (c) supprime le client d'identifiant 7, sachant qu'il n'a aucune session enregistrée.
\tcblower
\textbf{(a) Insertion} : on omet \texttt{id\_client} (auto) et \texttt{date\_inscription} (défaut). On respecte l'ordre des colonnes listées.
\begin{lstlisting}[language=SQL]
INSERT INTO CLIENT (nom, telephone, quartier, solde)
VALUES ('Amina Fotso', '699112233', 'Bali', 2000.00);
\end{lstlisting}
\textbf{(b) Mise à jour} : on cible par téléphone (unique). On vérifie d'abord.
\begin{lstlisting}[language=SQL]
-- 1. Verification (reflexe securite)
SELECT id_client, nom, solde FROM CLIENT WHERE telephone = '699112233';
-- 2. Mise a jour : solde = ancien + 1500
UPDATE CLIENT
SET solde = solde + 1500.00
WHERE telephone = '699112233';
-- 3. Controle post-execution
SELECT solde FROM CLIENT WHERE telephone = '699112233'; -- Doit afficher 3500.00
\end{lstlisting}
La contrainte \texttt{CHECK (solde >= 0)} est respectée ($3500 \ge 0$).
\textbf{(c) Suppression} : le client 7 n'a pas de session (FK non référencée), \texttt{RESTRICT} ne bloque pas.
\begin{lstlisting}[language=SQL]
DELETE FROM CLIENT WHERE id_client = 7;
\end{lstlisting}
\textbf{Conclusion} : insertion ciblée, mise à jour arithmétique sécurisée, suppression propre respectant l'intégrité référentielle.
\end{exoresolu}

\courssub{Interrogation des données : SELECT, opérateurs, alias et tri}

\begin{methode}[Construire une requête SELECT complète]
\begin{enumerate}
\item \textbf{Syntaxe canonique} :
\begin{lstlisting}[language=SQL]
SELECT [DISTINCT] liste_colonnes_ou_expressions
FROM table_principale
[JOIN table_secondaire ON condition_liaison]
[WHERE condition_lignes]
[GROUP BY liste_colonnes_regroupement]
[HAVING condition_groupes]
[ORDER BY col1 [ASC|DESC], col2 ...]
[LIMIT nombre [OFFSET decalage]];
\end{lstlisting}
\item \textbf{Opérateurs de comparaison} : \texttt{=}, \texttt{<>} (standard) ou \texttt{!=}, \texttt{<}, \texttt{<=}, \texttt{>}, \texttt{>=}.
\item \textbf{Opérateurs logiques} : \texttt{AND} (priorité haute), \texttt{OR} (priorité basse), \texttt{NOT}. \textbf{Utiliser des parenthèses} pour forcer l'ordre : \texttt{WHERE (A OR B) AND C}.
\item \textbf{Opérateurs spéciaux} :
\begin{itemize}
\item \texttt{LIKE} : \texttt{\%} (0 à n caractères), \texttt{\_} (exactement 1 caractère). Ex: \texttt{nom LIKE 'N\%'} (commence par N), \texttt{telephone LIKE '\%55'} (finit par 55).
\item \texttt{BETWEEN a AND b} : intervalle \textbf{inclusif} (équivalent \texttt{col >= a AND col <= b}).
\item \texttt{IN (v1, v2, ...)} / \texttt{NOT IN} : appartenance à une liste discrète.
\item \texttt{IS NULL} / \texttt{IS NOT NULL} : test de nullité (jamais \texttt{= NULL}).
\end{itemize}
\item \textbf{Alias (\texttt{AS})} : renomme une colonne ou une expression dans le résultat. \textbf{Obligatoire} pour les colonnes calculées (\texttt{solde * 1.05 AS solde\_majore}) et dans les jointures pour préfixer (\texttt{C.nom}).
\item \textbf{Tri (\texttt{ORDER BY})} : \texttt{ASC} (défaut, croissant), \texttt{DESC} (décroissant). Peut trier sur alias ou position (\texttt{ORDER BY 2 DESC}).
\end{enumerate}
\end{methode}

\begin{exoresolu}[Recherches dans la table CLIENT du cybercafé]
Écris les requêtes SQL qui : (a) affichent les clients des quartiers « Bali » ou « Akwa » dont le solde $> 1000$ ; (b) affichent les clients dont le nom commence par « N » ; (c) affichent pour chaque client le solde majoré de 5 \% sous le nom \texttt{solde\_bonus}, trié par solde décroissant ; (d) affichent les clients dont le solde est entre 500 et 5000 FCFA.
\tcblower
\textbf{(a)} Priorité \texttt{AND} > \texttt{OR} $\to$ parenthèses obligatoires sur le \texttt{OR}. Équivalent \texttt{IN} plus lisible.
\begin{lstlisting}[language=SQL]
SELECT * FROM CLIENT
WHERE (quartier = 'Bali' OR quartier = 'Akwa')
  AND solde > 1000;
-- Ou plus propre :
SELECT * FROM CLIENT
WHERE quartier IN ('Bali', 'Akwa') AND solde > 1000;
\end{lstlisting}
\textbf{(b)} Motif de début de chaîne.
\begin{lstlisting}[language=SQL]
SELECT * FROM CLIENT WHERE nom LIKE 'N%';
\end{lstlisting}
\textbf{(c)} Expression calculée + alias + tri sur colonne d'origine (ou alias).
\begin{lstlisting}[language=SQL]
SELECT nom, solde, solde * 1.05 AS solde_bonus
FROM CLIENT
ORDER BY solde DESC;
\end{lstlisting}
Exemple : solde $3500 \to 3500 \times 1.05 = 3675.00$ FCFA.
\textbf{(d)} Intervalle inclusif.
\begin{lstlisting}[language=SQL]
SELECT * FROM CLIENT WHERE solde BETWEEN 500 AND 5000;
\end{lstlisting}
\textbf{Conclusion} : ces requêtes couvrent les opérateurs logiques, les motifs, les données calculées/alias/tri, et les intervalles.
\end{exoresolu}

\courssub{Agrégation, regroupement et jointures}

\begin{methode}[Fonctions d'agrégation, GROUP BY, HAVING et Jointures]
\begin{enumerate}
\item \textbf{Fonctions d'agrégation} (retournent une valeur unique par groupe) :
\texttt{COUNT(*)} (nb lignes), \texttt{COUNT(col)} (nb non-null), \texttt{SUM(col)}, \texttt{AVG(col)}, \texttt{MIN(col)}, \texttt{MAX(col)}.
\item \textbf{Regroupement (\texttt{GROUP BY})} : divise le jeu de résultats en groupes partageant la même valeur(s) de colonne(s). Le \texttt{SELECT} ne peut contenir que : colonnes du \texttt{GROUP BY}, fonctions d'agrégation, constantes.
\item \textbf{Filtrage des groupes (\texttt{HAVING})} : condition \textbf{après} regroupement, peut contenir des agrégats. \texttt{WHERE} = avant regroupement (lignes), \texttt{HAVING} = après (groupes).
\item \textbf{Jointure interne (\texttt{INNER JOIN} ou \texttt{JOIN})} : ne garde que les lignes ayant une correspondance dans les deux tables.
\begin{lstlisting}[language=SQL]
SELECT C.nom, S.date_session
FROM CLIENT C
JOIN SESSION S ON C.id_client = S.id_client;
\end{lstlisting}
\item \textbf{Jointures externes} :
\texttt{LEFT JOIN} : toutes les lignes de la table de gauche + correspondances (NULL si absent).
\texttt{RIGHT JOIN} : symétrique.
\item \textbf{Auto-jointure} : table jointe à elle-même (alias différents obligatoires).
\item \textbf{Ordre logique d'exécution} : \texttt{FROM/JOIN} $\to$ \texttt{WHERE} $\to$ \texttt{GROUP BY} $\to$ \texttt{HAVING} $\to$ \texttt{SELECT} $\to$ \texttt{ORDER BY} $\to$ \texttt{LIMIT}.
\end{enumerate}
\end{methode}

\begin{exoresolu}[Statistiques de gestion du cybercafé]
Tables : \texttt{CLIENT(id\_client, nom, quartier, solde)} et \texttt{SESSION(id\_session, date\_session, duree, montant, \#id\_client)}.
Requêtes : (a) nb total sessions ; (b) recette totale et durée moyenne ; (c) nb clients par quartier (quartiers $\ge$ 3 clients) ; (d) nom client + total dépensé (tri décroissant).
\tcblower
\textbf{(a)} Agrégat global simple.
\begin{lstlisting}[language=SQL]
SELECT COUNT(*) AS nb_sessions FROM SESSION;
\end{lstlisting}
\textbf{(b)} Deux agrégats simultanés.
\begin{lstlisting}[language=SQL]
SELECT SUM(montant) AS recette_totale,
       AVG(duree) AS duree_moyenne_min
FROM SESSION;
\end{lstlisting}
\textbf{(c)} Regroupement + filtre sur agrégat ($\to$ \texttt{HAVING}).
\begin{lstlisting}[language=SQL]
SELECT quartier, COUNT(*) AS nb_clients
FROM CLIENT
GROUP BY quartier
HAVING COUNT(*) >= 3;
\end{lstlisting}
\textbf{(d)} Jointure + regroupement par client + agrégat somme.
\begin{lstlisting}[language=SQL]
SELECT C.nom, SUM(S.montant) AS total_depense
FROM CLIENT C
JOIN SESSION S ON C.id_client = S.id_client
GROUP BY C.id_client, C.nom -- C.nom fonctionnellement depend de C.id_client (PK)
ORDER BY total_depense DESC;
\end{lstlisting}
\textbf{Justification} : la jointure associe chaque session à son client ; \texttt{GROUP BY} forme un groupe par client ; \texttt{SUM} additionne les montants du groupe ; alias \texttt{C}, \texttt{S} pour lisibilité.
\textbf{Conclusion} : indicateurs clés (fréquentation, CA, géographie, top clients) pour le gérant.
\end{exoresolu}

\courssub{Administration : exportation, importation et sauvegarde}

\begin{methode}[Sauvegarder et restaurer une base MySQL/MariaDB]
\begin{enumerate}
\item \textbf{Exportation (Dump) via PhpMyAdmin} :
Base $\to$ Onglet \emph{Exporter} $\to$ Méthode « Rapide » (toutes tables) ou « Personnalisée » (choix tables, options : \texttt{DROP TABLE}, \texttt{AUTO\_INCREMENT}, \texttt{CREATE DATABASE}) $\to$ Format \texttt{SQL} $\to$ \emph{Exécuter}. Fichier \texttt{.sql} téléchargé.

\begin{lstlisting}[language=bash]
mysqldump -u root -p --single-transaction --routines --triggers cybercafe > cybercafe_$(date +%F).sql
\end{lstlisting}
\texttt{--single-transaction} : cohérence sans verrouiller (InnoDB). \texttt{--routines --triggers} : inclut procédures/fonctions/triggers.
\item \textbf{Importation via PhpMyAdmin} :
Créer/Sélectionner base cible $\to$ Onglet \emph{Importer} $\to$ Choisir fichier \texttt{.sql} $\to$ \emph{Exécuter}. Attention à \texttt{max\_execution\_time} et \texttt{upload\_max\_filesize} (php.ini) pour gros fichiers.
\item \textbf{Importation ligne de commande} :
\begin{lstlisting}[language=bash]
mysql -u root -p cybercafe < cybercafe_2024-05-10.sql
\end{lstlisting}
\item \textbf{Bonnes pratiques professionnelles} :
\begin{itemize}
\item Sauvegardes \textbf{quotidiennes} (incrémentielles via logs binaires) + \textbf{hebdomadaires} (complètes).
\item Stockage \textbf{externe} (disque USB, NAS, cloud \emph{Wasabi}, \emph{AWS S3}, \emph{Azure Blob}).
\item \textbf{Test de restauration} mensuel sur serveur de recette (procédure \emph{Disaster Recovery Plan}).
\item Chiffrement des dumps sensibles (\texttt{gpg -c fichier.sql}).
\end{itemize}
\end{enumerate}
\end{methode}

\begin{attention}[Les 5 erreurs fatales au Baccalauréat (et en production)]
\begin{enumerate}
\item \textbf{WHERE manquant dans UPDATE/DELETE.} $\to$ Massacre de données. \textbf{Toujours} écrire le \texttt{WHERE} et le tester par un \texttt{SELECT} préalable.
\item \textbf{Confusion WHERE / HAVING.} \texttt{WHERE} filtre lignes (pas d'agrégat). \texttt{HAVING} filtre groupes (agrégats autorisés). \texttt{WHERE COUNT(*) > 3} = \textbf{Erreur syntaxe/sémantique}.
\item \textbf{Mauvaise translation association (n,m).} Créer une seule FK dans une des tables au lieu d'une table de liaison à clé composée. Perte de la sémantique « plusieurs-à-plusieurs ».
\item \textbf{Oubli apostrophes / priorité opérateurs.} \texttt{WHERE nom = Bali} (erreur colonne inconnue) vs \texttt{WHERE nom = 'Bali'}. \texttt{WHERE ville='Yaounde' OR ville='Douala' AND solde>0} $\neq$ \texttt{WHERE (ville='Yaounde' OR ville='Douala') AND solde>0}.
\item \textbf{Jointure sans condition (Produit cartésien).} \texttt{FROM CLIENT, SESSION} sans \texttt{ON/WHERE} $\to$ $N \times M$ lignes. Toujours \texttt{JOIN ... ON PK = FK} et préfixer colonnes ambiguës (\texttt{C.nom}, \texttt{S.montant}).
\end{enumerate}
\end{attention}

\begin{exercice}[Entraînement Bac : Gestion d'un stock de pièces informatiques]
On souhaite gérer le stock d'une boutique de pièces informatiques à Yaoundé (quartier Mvog-Ada).
\textbf{MCD fourni} :
\begin{itemize}
\item Entité \textbf{FOURNISSEUR} (\underline{id\_four}, nom\_four, ville, telephone).
\item Entité \textbf{PIECE} (\underline{ref\_piece}, designation, prix\_unitaire, stock\_actuel, stock\_alerte).
\item Association \textbf{FOURNIR} (delai\_livraison\_jours) entre FOURNISSEUR (1,n) et PIECE (1,n). Une pièce a un fournisseur principal ; un fournisseur fournit plusieurs pièces.
\end{itemize}
\textbf{Travail demandé} :
\begin{enumerate}
\item Proposer le schéma relationnel normalisé (notation \texttt{TABLE(\underline{PK}, col, \#FK)}).
\item Écrire le script SQL complet de création de la base \texttt{stock\_pieces} et des tables avec contraintes adaptées (types, \texttt{CHECK}, \texttt{DEFAULT}, \texttt{FK}).
\item Insérer 2 fournisseurs (ex. « TechPlus Douala », « InfoKit Yaoundé ») et 3 pièces (ex. « SSD 1To », « RAM 16Go DDR4 », « Alim 600W ») avec leurs liaisons.
\item Écrire la requête qui affiche la désignation, le prix, le stock et le nom du fournisseur pour les pièces dont le stock est \textbf{inférieur ou égal} au stock d'alerte (rupture imminente).
\item Écrire la requête qui donne, pour chaque fournisseur, le nombre de pièces fournies et le prix moyen de ces pièces, en ne gardant que les fournisseurs proposant au moins 2 pièces.
\end{enumerate}
\end{exercice}

\begin{corrige}[Exercice : Gestion d'un stock de pièces informatiques]
\textbf{1. Schéma relationnel} \\
Association \texttt{FOURNIR} (1,n) -- (1,n) $\to$ migration clé \texttt{id\_four} dans table \texttt{PIECE} (côté n).
\begin{lstlisting}
FOURNISSEUR(\underline{id_four}, nom_four, ville, telephone)
PIECE(\underline{ref_piece}, designation, prix_unitaire, stock_actuel, stock_alerte, #id_four)
\end{lstlisting}
\textbf{2. Script SQL de création}
\begin{lstlisting}[language=SQL]
CREATE DATABASE stock_pieces CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
USE stock_pieces;

CREATE TABLE FOURNISSEUR (
    id_four INT UNSIGNED AUTO_INCREMENT,
    nom_four VARCHAR(60) NOT NULL,
    ville VARCHAR(40) NOT NULL,
    telephone VARCHAR(20),
    CONSTRAINT pk_fournisseur PRIMARY KEY (id_four)
) ENGINE=InnoDB;

CREATE TABLE PIECE (
    ref_piece VARCHAR(20) NOT NULL, -- Ex: 'SSD-1TO-SAM', 'RAM-16G-DDR4'
    designation VARCHAR(100) NOT NULL,
    prix_unitaire DECIMAL(10,2) NOT NULL CHECK (prix_unitaire > 0),
    stock_actuel INT UNSIGNED NOT NULL DEFAULT 0,
    stock_alerte INT UNSIGNED NOT NULL DEFAULT 5,
    id_four INT UNSIGNED NOT NULL,
    CONSTRAINT pk_piece PRIMARY KEY (ref_piece),
    CONSTRAINT fk_piece_fournisseur
        FOREIGN KEY (id_four) REFERENCES FOURNISSEUR(id_four)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT ck_stock_alerte CHECK (stock_alerte >= 0)
) ENGINE=InnoDB;
\end{lstlisting}
\textbf{3. Insertion de données}
\begin{lstlisting}[language=SQL]
-- Fournisseurs
INSERT INTO FOURNISSEUR (nom_four, ville, telephone) VALUES
('TechPlus Douala', 'Douala', '690112233'),
('InfoKit Yaounde', 'Yaounde', '677445566');

-- Pieces (id_four recupere: 1 pour TechPlus, 2 pour InfoKit)

('SSD-1TO-SAM', 'SSD 1To Samsung 870 EVO', 45000.00, 3, 5, 1),

\end{lstlisting}
\textbf{4. Pièces en alerte de stock (rupture imminente)} \\
Jointure + condition sur colonnes de la même table.
\begin{lstlisting}[language=SQL]
SELECT P.designation, P.prix_unitaire, P.stock_actuel, P.stock_alerte, F.nom_four
FROM PIECE P
JOIN FOURNISSEUR F ON P.id_four = F.id_four
WHERE P.stock_actuel <= P.stock_alerte;
\end{lstlisting}
\textbf{Résultat attendu} : SSD 1To (stock 3 $\le$ 5) et RAM 16Go (stock 2 $\le$ 3).
\textbf{5. Statistiques par fournisseur (min 2 pièces)}
\begin{lstlisting}[language=SQL]
SELECT F.nom_four, COUNT(P.ref_piece) AS nb_pieces, AVG(P.prix_unitaire) AS prix_moyen
FROM FOURNISSEUR F
JOIN PIECE P ON F.id_four = P.id_four
GROUP BY F.id_four, F.nom_four
HAVING COUNT(P.ref_piece) >= 2;
\end{lstlisting}
\textbf{Résultat attendu} : « TechPlus Douala » : 2 pièces (SSD, Alim), prix moyen $(45000+32000)/2 = 38500$. « InfoKit Yaounde » : 1 pièce $\to$ exclu par \texttt{HAVING}.
\end{corrige}

\begin{corrige}[Exercice 1 — QCM : SGBD et tables]
\begin{enumerate}
\item \textbf{Réponse b.} Un \cle{SGBD} (Système de Gestion de Bases de Données) est un \emph{logiciel} qui permet de créer, administrer et exploiter des bases de données (exemples : MySQL, PostgreSQL, Oracle). Ce n'est ni un langage (le langage utilisé est le SQL), ni un composant matériel, ni un protocole réseau.
\item \textbf{Réponse c.} La \cle{clé primaire} identifie de manière \emph{unique} chaque enregistrement d'une table. Elle ne peut donc jamais être \texttt{NULL} ni dupliquée, et elle peut être de tout type (souvent \texttt{INT}).
\item \textbf{Réponse b.} \texttt{DROP TABLE ELEVE ;} supprime la structure de la table \emph{et} toutes ses données, de façon définitive. \texttt{DELETE} supprime des lignes mais conserve la table ; \texttt{REMOVE} et \texttt{TRUNCATE DATABASE} n'existent pas en SQL standard.
\item \textbf{Réponse c.} \texttt{AVG()} (\emph{average}, moyenne) calcule la moyenne arithmétique des valeurs d'une colonne. \texttt{SUM()} calcule la somme, \texttt{COUNT()} compte les lignes, \texttt{MAX()} donne la plus grande valeur.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 2 — Vrai ou faux — justifier]
\begin{enumerate}
\item \textbf{Vrai.} Par définition, une \cle{clé étrangère} (\texttt{FOREIGN KEY}) est une colonne d'une table qui fait référence à la clé primaire d'une autre table (ou de la même table) ; elle garantit l'\emph{intégrité référentielle} entre les tables.
\item \textbf{Faux.} La contrainte \texttt{DEFAULT} attribue une \emph{valeur par défaut} à une colonne lorsque l'utilisateur n'en fournit pas à l'insertion. C'est la contrainte \texttt{NOT NULL} qui interdit la valeur \texttt{NULL}.
\item \textbf{Faux.} Le joker \texttt{\%} remplace \emph{zéro, un ou plusieurs caractères}. \texttt{LIKE 'A\%'} sélectionne les chaînes qui \emph{commencent} par A. Pour celles qui se terminent par A, il faudrait écrire \texttt{LIKE '\%A'}.
\item \textbf{Vrai.} MySQL et PostgreSQL sont deux \cle{SGBDR} (SGBD relationnels) libres et très répandus : les données y sont organisées en tables reliées par des clés.
\item \textbf{Vrai.} \texttt{WHERE} filtre les lignes \emph{avant} le regroupement, tandis que \texttt{HAVING} filtre les \emph{groupes} formés par \texttt{GROUP BY}, après calcul des agrégats. \texttt{HAVING} ne s'emploie donc qu'avec \texttt{GROUP BY}.
\item \textbf{Faux.} \texttt{UPDATE} modifie les \emph{données} (les valeurs des lignes). Pour ajouter une colonne, on utilise \texttt{ALTER TABLE ... ADD COLUMN}, qui appartient au langage de définition des données (LDD).
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 3 — Définitions et vocabulaire]
\begin{enumerate}
\item \textbf{Définitions.}
\begin{itemize}
\item \cle{SGBD} : logiciel qui permet de créer, décrire, manipuler, administrer et sécuriser des bases de données, en offrant un langage d'interrogation (SQL) et des mécanismes de contrôle d'accès.
\item \cle{Clé primaire} : attribut (ou ensemble d'attributs) dont la valeur identifie de manière unique chaque enregistrement d'une table ; elle est non nulle et non dupliquée.
\item \cle{Clé étrangère} : attribut d'une table qui fait référence à la clé primaire d'une autre table, afin de matérialiser un lien entre les deux tables.
\item \cle{Contrainte d'intégrité} : règle imposée aux données d'une table (clé primaire, \texttt{NOT NULL}, \texttt{UNIQUE}, \texttt{DEFAULT}, \texttt{CHECK}, clé étrangère) pour garantir la validité et la cohérence de la base.
\end{itemize}
\item Deux exemples de SGBD autres que MySQL : \textbf{PostgreSQL} et \textbf{Oracle Database} (on accepte aussi SQLite, Microsoft SQL Server, MariaDB, Access).
\item Les trois grandes familles de requêtes SQL :
\begin{itemize}
\item le \textbf{LDD} (Langage de Définition des Données) : \texttt{CREATE}, \texttt{ALTER}, \texttt{DROP} ;
\item le \textbf{LMD} (Langage de Manipulation des Données) : \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE} ;
\item le \textbf{LCD} (Langage de Contrôle des Données) : \texttt{GRANT}, \texttt{REVOKE} (l'interrogation \texttt{SELECT} est souvent classée dans le LMD ou citée à part comme DQL).
\end{itemize}
\item Un \cle{champ} (colonne) décrit une \emph{propriété} commune à tous les enregistrements (ex. la colonne \texttt{nom}) : il possède un nom et un type de données. Un \cle{enregistrement} (ligne) est une \emph{occurrence concrète} de la table : un ensemble de valeurs, une par champ (ex. la ligne \texttt{(1, 'Mbarga', 'Tle TI')}). Autrement dit, les colonnes définissent la \emph{structure}, les lignes contiennent les \emph{données}.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 5 — Du MCD au schéma relationnel]
\begin{enumerate}
\item \textbf{Schéma relationnel obtenu :}
\begin{itemize}
\item \textbf{CLIENT} (\underline{id\_client}, nom, telephone, ville) ;
\item \textbf{PRODUIT} (\underline{id\_produit}, designation, prix) ;
\item \textbf{COMMANDER} (\underline{\texttt{\#}id\_client}, \underline{\texttt{\#}id\_produit}, date\_commande, quantite).
\end{itemize}
La clé primaire de \texttt{COMMANDER} est le couple (\texttt{id\_client}, \texttt{id\_produit}) ; chacun de ses deux attributs est en même temps clé étrangère vers la table parente correspondante.
\item \textbf{Justification.} L'association \textbf{COMMANDER} relie \emph{plusieurs} clients à \emph{plusieurs} produits : c'est une association de type \emph{plusieurs-à-plusieurs} (cardinalités 1,n de part et d'autre). Or le modèle relationnel interdit les listes de valeurs dans une case : on ne peut pas stocker plusieurs produits dans une ligne de \texttt{CLIENT}, ni plusieurs clients dans une ligne de \texttt{PRODUIT}. La règle de transformation impose donc de convertir toute association plusieurs-à-plusieurs en une \emph{table supplémentaire}, dont la clé primaire est formée des clés primaires des deux entités reliées, et qui porte les attributs propres à l'association (\texttt{date\_commande}, \texttt{quantite}).
\end{enumerate}
\textbf{Point de vigilance :} ne pas oublier de reporter les attributs de l'association (\texttt{quantite}, \texttt{date\_commande}) dans la nouvelle table, et de souligner les \emph{deux} attributs de la clé primaire composée.
\end{corrige}

\begin{corrige}[Exercice 6 — Création de tables avec contraintes]
\begin{enumerate}
\item Création et sélection de la base :
\begin{lstlisting}[language=SQL]
CREATE DATABASE boutique_douala;
USE boutique_douala;
\end{lstlisting}
\item Création des tables \texttt{CLIENT} et \texttt{PRODUIT} avec les contraintes demandées :
\begin{lstlisting}[language=SQL]
CREATE TABLE CLIENT (
    id_client INT PRIMARY KEY AUTO_INCREMENT,
    nom VARCHAR(50) NOT NULL,                 -- nom obligatoire
    telephone VARCHAR(20),
    ville VARCHAR(50) DEFAULT 'Douala'        -- valeur par defaut
);

CREATE TABLE PRODUIT (
    id_produit INT PRIMARY KEY AUTO_INCREMENT,
    designation VARCHAR(80),
    prix DECIMAL(10,2) CHECK (prix > 0)       -- prix strictement positif
);
\end{lstlisting}
La contrainte \texttt{CHECK (prix > 0)} traduit la règle « valeur autorisée » : toute insertion d'un prix nul ou négatif sera rejetée par le SGBD (supporté depuis MySQL 8.0.16).
\item Ajout de la colonne \texttt{email} unique :
\begin{lstlisting}[language=SQL]
ALTER TABLE CLIENT ADD COLUMN email VARCHAR(100) UNIQUE;
\end{lstlisting}
La contrainte \texttt{UNIQUE} garantit que deux clients ne pourront jamais partager la même adresse électronique.
\end{enumerate}
\textbf{Point de vigilance :} \texttt{ALTER TABLE} (et non \texttt{UPDATE}) est l'instruction du LDD qui modifie la \emph{structure} d'une table existante.
\end{corrige}

\item Produits dont le prix est compris entre 1\,000 et 5\,000 FCFA (bornes incluses) :
\begin{lstlisting}[language=SQL]
SELECT * FROM PRODUIT WHERE prix BETWEEN 1000 AND 5000;
\end{lstlisting}
Résultat attendu sur le tableau : Savon liquide (2\,500), Riz parfumé (4\,500) et Jus de bissap (1\,000).
\item Produits des catégories « Boisson » ou « Céréale » :
\begin{lstlisting}[language=SQL]
SELECT * FROM PRODUIT WHERE categorie IN ('Boisson', 'Cereale');
\end{lstlisting}
Résultat attendu : Riz parfumé, Jus de bissap, Eau minérale (puis Maïs grain après insertion).
\item Augmentation de 10\,\% du prix des produits d'hygiène (multiplier par $1 + \frac{10}{100} = 1{,}1$) :
\begin{lstlisting}[language=SQL]
UPDATE PRODUIT SET prix = prix * 1.1 WHERE categorie = 'Hygiene';
\end{lstlisting}
Le prix du Savon liquide passe ainsi de 2\,500 à $2500 \times 1{,}1 = 2\,750$ FCFA.
\item Suppression des produits en rupture de stock :
\begin{lstlisting}[language=SQL]
DELETE FROM PRODUIT WHERE quantite = 0;
\end{lstlisting}
Sur le tableau actuel, aucun produit n'est supprimé car toutes les quantités sont strictement positives.
\item Désignations commençant par « R » :
\begin{lstlisting}[language=SQL]
SELECT designation FROM PRODUIT WHERE designation LIKE 'R%';
\end{lstlisting}
Résultat attendu : « Riz parfumé 5 kg ». Le joker \texttt{\%} placé \emph{après} le R signifie « n'importe quelle suite de caractères ».
\end{enumerate}
\textbf{Point de vigilance :} ne jamais oublier la clause \texttt{WHERE} dans un \texttt{UPDATE} ou un \texttt{DELETE} : sans elle, \emph{toutes} les lignes de la table seraient modifiées ou supprimées.
\end{corrige}

\begin{corrige}[Exercice 8 — Agrégation, tri et alias]
\begin{enumerate}
\item Nombre total de produits :
\begin{lstlisting}[language=SQL]
SELECT COUNT(*) AS nb_produits FROM PRODUIT;
\end{lstlisting}
Résultat sur le tableau initial : 5 (puis 6 après l'insertion de l'exercice 7).
\item Prix extrêmes et prix moyen avec alias :
\begin{lstlisting}[language=SQL]
SELECT MAX(prix) AS prix_max,
       MIN(prix) AS prix_min,
       AVG(prix) AS prix_moyen
FROM PRODUIT;
\end{lstlisting}
Vérification sur le tableau initial : $\text{prix\_max} = 9000$, $\text{prix\_min} = 500$, et
\[ \text{prix\_moyen} = \frac{2500 + 4500 + 1000 + 9000 + 500}{5} = \frac{17500}{5} = 3500\,\text{FCFA}. \]
\item Valeur totale du stock par catégorie (donnée calculée, regroupement, tri décroissant) :
\begin{lstlisting}[language=SQL]
SELECT categorie,
       SUM(prix * quantite) AS valeur_stock
FROM PRODUIT
GROUP BY categorie
ORDER BY valeur_stock DESC;
\end{lstlisting}
Vérification sur le tableau initial :
\begin{align*}
\text{Alimentaire} &: 9000 \times 15 = 135\,000,\\
\text{Céréale} &: 4500 \times 25 = 112\,500,\\
\text{Hygiène} &: 2500 \times 40 = 100\,000,\\
\text{Boisson} &: (1000 \times 60) + (500 \times 100) = 60\,000 + 50\,000 = 110\,000.
\end{align*}
L'ordre d'affichage est donc : Alimentaire (135\,000), Céréale (112\,500), Boisson (110\,000), Hygiène (100\,000).
\item Catégories dont la valeur de stock dépasse 100\,000 FCFA : on filtre les \emph{groupes} avec \texttt{HAVING} :
\begin{lstlisting}[language=SQL]
SELECT categorie,
       SUM(prix * quantite) AS valeur_stock
FROM PRODUIT
GROUP BY categorie
HAVING SUM(prix * quantite) > 100000;
\end{lstlisting}
Résultat attendu : Alimentaire (135\,000), Céréale (112\,500) et Boisson (110\,000). La catégorie Hygiène (exactement 100\,000) est exclue car la condition est \emph{strictement} supérieure.
\end{enumerate}
\textbf{Point de vigilance :} on ne peut pas écrire \texttt{WHERE SUM(...) > 100000} : \texttt{WHERE} s'applique aux lignes \emph{avant} le regroupement et ne connaît pas encore les agrégats ; c'est précisément le rôle de \texttt{HAVING}.
\end{corrige}

\begin{corrige}[Exercice 9 — Type Bac : Gestion d'une bibliothèque scolaire]
\textbf{Barème indicatif :} 2 + 3 + 1,5 + 2 + 1,5 = 10 points.
\begin{enumerate}
\item \textbf{Schéma relationnel (2 pts).} L'association EMPRUNT étant plusieurs-à-plusieurs (un adhérent fait plusieurs emprunts, un livre est emprunté plusieurs fois), elle devient une table :
\begin{itemize}
\item \textbf{ADHERENT} (\underline{id\_adherent}, nom, classe, telephone) ;
\item \textbf{LIVRE} (\underline{id\_livre}, titre, auteur, annee\_edition) ;
\item \textbf{EMPRUNT} (\underline{id\_emprunt}, \texttt{\#}id\_adherent, \texttt{\#}id\_livre, date\_emprunt, date\_retour\_prevue).
\end{itemize}
On introduit un identifiant propre \texttt{id\_emprunt} car un même adhérent peut emprunter le même livre à des dates différentes : le couple (\texttt{id\_adherent}, \texttt{id\_livre}) ne suffirait pas à distinguer deux emprunts successifs. \emph{Point de vigilance :} souligner les clés primaires et marquer les deux clés étrangères par \texttt{\#}.
\item \textbf{Création de la base et des tables (3 pts).}
\begin{lstlisting}[language=SQL]
CREATE DATABASE biblio_nkongsamba;
USE biblio_nkongsamba;

CREATE TABLE ADHERENT (
    id_adherent INT PRIMARY KEY AUTO_INCREMENT,
    nom VARCHAR(50) NOT NULL,          -- nom obligatoire
    classe VARCHAR(20),
    telephone VARCHAR(20)
);

CREATE TABLE LIVRE (
    id_livre INT PRIMARY KEY AUTO_INCREMENT,
    titre VARCHAR(100) NOT NULL,       -- titre obligatoire
    auteur VARCHAR(60),
    annee_edition INT CHECK (annee_edition BETWEEN 1950 AND 2025)
);

CREATE TABLE EMPRUNT (
    id_emprunt INT PRIMARY KEY AUTO_INCREMENT,
    id_adherent INT NOT NULL,
    id_livre INT NOT NULL,
    date_emprunt DATE,
    date_retour_prevue DATE,
    FOREIGN KEY (id_adherent) REFERENCES ADHERENT(id_adherent),
    FOREIGN KEY (id_livre) REFERENCES LIVRE(id_livre)
);
\end{lstlisting}
\emph{Points de vigilance :} créer les tables parentes \emph{avant} la table \texttt{EMPRUNT} (sinon les clés étrangères ne peuvent pas être déclarées) ; chaque \texttt{FOREIGN KEY} doit référencer la clé primaire de la table parente.
\item \textbf{Adhérents ayant emprunté « Les Misérables » (1,5 pt).} La condition porte sur le titre (table \texttt{LIVRE}) et le résultat sur les adhérents : il faut donc \emph{deux jointures} enchaînées.
\begin{lstlisting}[language=SQL]
SELECT AD.nom, AD.classe
FROM ADHERENT AD
JOIN EMPRUNT E ON AD.id_adherent = E.id_adherent
JOIN LIVRE L ON E.id_livre = L.id_livre
WHERE L.titre = 'Les Miserables';
\end{lstlisting}
\item \textbf{Nombre de livres empruntés par adhérent (2 pts).}
\begin{lstlisting}[language=SQL]
SELECT AD.nom, COUNT(E.id_emprunt) AS nb_emprunts
FROM ADHERENT AD
JOIN EMPRUNT E ON AD.id_adherent = E.id_adherent
GROUP BY AD.id_adherent, AD.nom
ORDER BY nb_emprunts DESC;
\end{lstlisting}
\emph{Point de vigilance :} le regroupement se fait sur l'identifiant (et le nom) de l'adhérent ; l'alias \texttt{nb\_emprunts} peut être utilisé dans \texttt{ORDER BY}.
\item \textbf{Adhérents ayant emprunté plus de 3 livres (1,5 pt).}
\begin{lstlisting}[language=SQL]
SELECT AD.nom, COUNT(E.id_emprunt) AS nb_emprunts
FROM ADHERENT AD
JOIN EMPRUNT E ON AD.id_adherent = E.id_adherent
GROUP BY AD.id_adherent, AD.nom
HAVING COUNT(E.id_emprunt) > 3;
\end{lstlisting}
La condition sur l'agrégat (\texttt{> 3}) se place obligatoirement dans \texttt{HAVING}, jamais dans \texttt{WHERE}.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 10 — Type Bac : Correction d'un script et contraintes d'intégrité]
\textbf{Barème indicatif :} 2 + 4 + 2 + 2 = 10 points.
\begin{enumerate}
\item \textbf{Définitions (2 pts).} Une \cle{clé primaire} est un attribut (ou groupe d'attributs) qui identifie de manière unique chaque enregistrement d'une table ; elle est non nulle et non dupliquée. Une \cle{clé étrangère} est un attribut d'une table qui fait référence à la clé primaire d'une autre table, assurant l'intégrité référentielle. Trois autres contraintes d'intégrité : \texttt{NOT NULL} (valeur obligatoire), \texttt{UNIQUE} (unicité), \texttt{DEFAULT} (valeur par défaut) ; on accepte aussi \texttt{CHECK} (valeur autorisée / format).
\item \textbf{Les quatre erreurs (4 pts).}
\begin{enumerate}
\item \textbf{Point-virgule manquant} à la fin de \texttt{CREATE DATABASE agromarket} : chaque instruction SQL doit se terminer par \texttt{;} ;
\item \textbf{Clé primaire absente} : ni \texttt{CATEGORIE} ni \texttt{ARTICLE} ne déclarent de \texttt{PRIMARY KEY} ;
\item \textbf{Type inadapté pour le prix} : \texttt{prix VARCHAR(20)} stocke le prix comme du texte, ce qui empêche les calculs (sommes, moyennes) et les comparaisons numériques ; il faut un type numérique (\texttt{DECIMAL} ou \texttt{INT}) ;
\item \textbf{Clé étrangère invalide} : \texttt{FOREIGN KEY (id\_cat) REFERENCES CATEGORIE(id\_cat)} ne peut fonctionner que si \texttt{CATEGORIE.id\_cat} est clé primaire (ou unique), ce qui n'est pas le cas dans le script du stagiaire.
\end{enumerate}
Script corrigé et complet :
\begin{lstlisting}[language=SQL]
CREATE DATABASE agromarket;
USE agromarket;

CREATE TABLE CATEGORIE (
    id_cat INT PRIMARY KEY AUTO_INCREMENT,
    libelle VARCHAR(50)
);

CREATE TABLE ARTICLE (
    id_art INT PRIMARY KEY AUTO_INCREMENT,
    designation VARCHAR(80) NOT NULL,
    prix DECIMAL(10,2) DEFAULT 0,
    id_cat INT,
    FOREIGN KEY (id_cat) REFERENCES CATEGORIE(id_cat)
);
\end{lstlisting}
\item \textbf{Explication de la requête (2 pts).}
\begin{itemize}
\item \texttt{SELECT libelle, COUNT(id\_art) AS nb\_articles} : on affiche le libellé de chaque catégorie et le \emph{nombre d'articles} qui lui sont rattachés ; l'alias \texttt{nb\_articles} renomme la colonne calculée pour la lisibilité du résultat ;
\item \texttt{FROM CATEGORIE C JOIN ARTICLE A ON C.id\_cat = A.id\_cat} : on réalise une \emph{jointure} entre les deux tables en faisant correspondre la clé étrangère \texttt{A.id\_cat} avec la clé primaire \texttt{C.id\_cat} ; les alias \texttt{C} et \texttt{A} sont des noms raccourcis qui évitent de réécrire les noms complets des tables et lèvent toute ambiguïté sur la colonne \texttt{id\_cat}, présente dans les deux tables ;
\item \texttt{GROUP BY libelle} : les lignes sont regroupées par catégorie afin que \texttt{COUNT} soit calculé \emph{pour chaque groupe} et non sur toute la table.
\end{itemize}
Au final, la requête affiche le nombre d'articles par catégorie.
\item \textbf{Exportation via PhpMyAdmin (2 pts).} Procédure :
\begin{enumerate}
\item ouvrir PhpMyAdmin dans le navigateur et se connecter ;
\item cliquer sur la base \texttt{agromarket} dans le panneau de gauche ;
\item cliquer sur l'onglet \textbf{Exporter}, choisir la méthode \emph{Rapide} (ou \emph{Personnalisée}) et le format \textbf{SQL} ;
\item cliquer sur \textbf{Exécuter} : le fichier \texttt{agromarket.sql} est téléchargé ;
\item copier ce fichier sur le disque dur externe.
\end{enumerate}
Deux avantages de la sauvegarde régulière : \textbf{(1)} pouvoir \emph{restaurer rapidement} les données en cas de panne, de suppression accidentelle ou d'attaque (rançongiciel) ; \textbf{(2)} \emph{limiter les pertes} : avec une sauvegarde quotidienne, on perd au maximum une journée de données. On accepte aussi : archivage, migration vers un autre serveur, conservation de l'historique.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 11 — Type Bac : Incident et restauration au lycée de Bafoussam]
\textbf{Barème indicatif :} 2 + 1,5 + 2 + 1,5 + 1 = 8 points.
\begin{enumerate}
\item \textbf{Procédure de restauration (2 pts).}
\begin{enumerate}
\item installer et démarrer MySQL sur le nouveau serveur, ouvrir PhpMyAdmin et se connecter ;
\item créer une base vide : onglet \emph{Bases de données}, saisir le nom \texttt{notes\_lycee}, cliquer sur \emph{Créer} ;
\item sélectionner cette base dans le panneau de gauche, puis cliquer sur l'onglet \textbf{Importer} ;
\item cliquer sur \emph{Choisir un fichier}, sélectionner \texttt{notes\_lycee.sql} (format SQL), puis cliquer sur \textbf{Exécuter} : les tables \texttt{ELEVE}, \texttt{MATIERE}, \texttt{NOTE} sont recréées et remplies ;
\item \textbf{vérifier} : contrôler la présence des trois tables, le nombre d'enregistrements (\texttt{SELECT COUNT(*)}) et exécuter quelques requêtes de test pour valider l'intégrité des données.
\end{enumerate}
\item \textbf{Justification de la sauvegarde quotidienne et externalisée (1,5 pt).} Une sauvegarde \emph{quotidienne} limite la perte de données à une journée au maximum (ici, les notes saisies la veille), alors qu'une sauvegarde hebdomadaire pourrait faire perdre jusqu'à une semaine de saisies. Une sauvegarde \emph{externalisée} (serveur distant) survit à la destruction du serveur local. Deux risques évités : \textbf{(1)} la perte totale des données en cas de panne matérielle du disque (cas présent) ; \textbf{(2)} la destruction simultanée des données \emph{et} de leur sauvegarde en cas d'incendie, de vol ou de dégât des eaux dans la salle serveur.
\item \textbf{Requête du proviseur (2 pts).} Il faut joindre les trois tables, filtrer sur la classe et la matière, regrouper par élève, puis filtrer les groupes sur la moyenne :
\begin{lstlisting}[language=SQL]
SELECT E.nom, AVG(N.valeur) AS moyenne_info
FROM ELEVE E
JOIN NOTE N ON E.id_eleve = N.id_eleve
JOIN MATIERE M ON N.id_matiere = M.id_matiere
WHERE E.classe = 'Terminale TI'
  AND M.intitule = 'Informatique'
GROUP BY E.id_eleve, E.nom
HAVING AVG(N.valeur) >= 12
ORDER BY E.nom ASC;
\end{lstlisting}
\emph{Points de vigilance :} la condition sur la matière et la classe (lignes) va dans \texttt{WHERE} ; la condition sur la moyenne (agrégat) va dans \texttt{HAVING} ; le tri alphabétique s'obtient avec \texttt{ORDER BY E.nom ASC}.
\item \textbf{Noms contenant « nga » (1,5 pt).} Le joker \texttt{\%} est placé \emph{des deux côtés} de la syllabe, car elle peut apparaître n'importe où dans le nom :
\begin{lstlisting}[language=SQL]
SELECT * FROM ELEVE WHERE nom LIKE '%nga%';
\end{lstlisting}
Cette requête retrouve par exemple Nganou (\emph{début}), Tchoupo-Ngassa (\emph{milieu}) ou Manga (\emph{fin}).
\item \textbf{Mesures complémentaires (1 pt).} Deux propositions parmi :
\begin{itemize}
\item installer un \textbf{onduleur (UPS)} pour protéger le serveur des coupures et surtensions électriques, fréquentes dans nos localités ;
\item mettre en place un \textbf{second disque en miroir (RAID 1)} pour que la panne d'un disque n'interrompe pas le service ;
\item \textbf{automatiser} la sauvegarde par une tâche planifiée (script \texttt{mysqldump} quotidien) plutôt qu'une copie manuelle ;
\item définir des \textbf{comptes et privilèges} MySQL distincts (\texttt{GRANT}) pour limiter les suppressions accidentelles.
\end{itemize}
\end{enumerate}
\end{corrige}

\courssub{Définitions Clés}

\begin{definition}[Modèle Conceptuel de Données (MCD)]
Représentation graphique (Entités-Associations) indépendante du SGBD, décrivant la structure des données : entités (rectangles), associations (losanges), identifiants (soulignés), cardinalités (0,1 ; 1,1 ; 0,n ; 1,n).
\end{definition}

\begin{definition}[Schéma Relationnel (Modèle Logique de Données - MLD)]
Ensemble de relations (tables) issues de la transformation du MCD. Notation : \texttt{NomRelation(\underline{PK}, attribut1, attribut2, \dots, \#FK\_TableRef)}.
\end{definition}

\begin{definition}[SGBD (Système de Gestion de Base de Données)]
Logiciel serveur (ex. \textbf{MySQL/MariaDB}, PostgreSQL) gérant le stockage, la sécurité, la concurrence et l'accès aux données via le langage SQL. Architecture Client-Serveur (port 3306 par défaut pour MySQL).
\end{definition}

\begin{definition}[Clé Primaire (Primary Key - PK)]
Attribut ou groupe d'attributs identifiant \textbf{uniquement} chaque enregistrement (ligne). Contraintes : \cle{NOT NULL} + \cle{UNIQUE}. Une seule PK par table.
\end{definition}

\begin{definition}[Clé Étrangère (Foreign Key - FK)]
Attribut d'une table référençant la PK d'une autre table (table parente). Garantit l'\textbf{intégrité référentielle} : toute valeur de FK doit exister comme PK dans la table parente (ou être \cle{NULL} si autorisé).
\end{definition}

\courssub{Commandes SQL Essentielles (À connaître par cœur)}

\begin{center}
\begin{tabularx}{\linewidth}{|>{\bfseries}l|X|X|}
\hline
\rowcolor{popblueL}
\textbf{Catégorie} & \textbf{Commande / Syntaxe} & \textbf{Exemple / Note} \\
\hline
\textbf{DDL (Définition)} & \texttt{CREATE DATABASE nom;} & \texttt{CREATE DATABASE ecole\_db CHARACTER SET utf8mb4;} \\
& \texttt{DROP DATABASE nom;} & Suppression définitive (attention !) \\
& \texttt{CREATE TABLE t (c1 TYPE CONTRAINTES, \dots);} & \texttt{id INT AUTO\_INCREMENT PRIMARY KEY} \\
& \texttt{ALTER TABLE t ADD COLUMN c TYPE;} & Ajout colonne \\
& \texttt{ALTER TABLE t DROP COLUMN c;} & Suppression colonne \\
& \texttt{ALTER TABLE t MODIFY c NEW\_TYPE;} & Changement type (risque perte données) \\
& \texttt{ALTER TABLE t ADD CONSTRAINT fk\_name FOREIGN KEY (c) REFERENCES parent(pk);} & Ajout FK explicite \\
\hline
\textbf{DML (Manipulation)} & \texttt{INSERT INTO t (c1, c2) VALUES (v1, v2);} & Ordre colonnes = ordre valeurs. \texttt{DEFAULT} ou \texttt{NULL} si absent. \\
& \texttt{UPDATE t SET c1=v1, c2=v2 WHERE cond;} & \textbf{Obligatoire : clause WHERE} sinon MAJ toute la table ! \\
& \texttt{DELETE FROM t WHERE cond;} & \textbf{Obligatoire : clause WHERE} sinon vidage table (TRUNCATE plus rapide). \\
\hline
\textbf{DQL (Interrogation)} & \texttt{SELECT [DISTINCT] c1, c2 AS alias FROM t WHERE cond ORDER BY c1 [DESC] LIMIT n;} & \texttt{AS} optionnel. \texttt{LIMIT} pour pagination. \\
& \texttt{SELECT c1, COUNT(*) AS nb FROM t GROUP BY c1 HAVING COUNT(*) > 1;} & \texttt{WHERE} filtre lignes \textbf{avant} groupement, \texttt{HAVING} filtre groupes \textbf{après}. \\
\hline
\textbf{Jointures} & \texttt{SELECT * FROM A INNER JOIN B ON A.fk = B.pk;} & \textbf{INNER} : intersection (correspondances only). \\
& \texttt{SELECT * FROM A LEFT JOIN B ON A.fk = B.pk;} & \textbf{LEFT} : tout A + B correspondantes (NULL si absent). \\
\hline
\textbf{Agrégation} & \texttt{COUNT(*)}, \texttt{COUNT(col)}, \texttt{SUM(col)}, \texttt{AVG(col)}, \texttt{MIN(col)}, \texttt{MAX(col)} & \texttt{COUNT(*)} compte lignes (même NULL). \texttt{COUNT(col)} ignore NULL. \\
\hline

\courssub{Méthodes Express}

\begin{methode}[Transformer un MCD en Schéma Relationnel (Règles standards)]
\begin{enumerate}
\item \textbf{Entité forte} $\to$ Table. Identifiant $\to$ Clé Primaire (PK). Attributs $\to$ Colonnes.
\item \textbf{Entité faible (identifiant relatif)} $\to$ Table. Clé primaire \textbf{composée} : (PK entité propriétaire, identifiant relatif).
\item \textbf{Association 1:n (ou 0:n / 1:1)} $\to$ Clé étrangère dans la table côté \textbf{"n"} (ou côté "1" pour 1:1), référençant la PK du côté "1".
\item \textbf{Association n:m} $\to$ \textbf{Table de liaison} (table de jointure). PK composée = (FK\_TableA, FK\_TableB). Deux FK vers les deux tables parentes.
\item \textbf{Association avec attributs} $\to$ Table (même si 1:n ou 1:1). Attributs de l'association deviennent colonnes de cette table.
\item \textbf{Héritage (IS-A)} $\to$ Soit table unique (attributs nullable + type), soit table par classe concrète, soit table par classe (PK commune = FK).
\end{enumerate}
\end{methode}

\begin{methode}[Écrire une Requête SELECT Complexe (Jointure + Agrégation)]
\begin{enumerate}
\item Identifier les \textbf{tables nécessaires} (d'après les colonnes demandées dans SELECT/WHERE/ORDER BY).
\item Déterminer les \textbf{jointures} (INNER pour correspondances obligatoires, LEFT pour garder lignes table gauche).
\item Écrire la clause \texttt{FROM} + \texttt{JOIN ... ON ...}.
\item Ajouter \texttt{WHERE} pour filtres sur lignes brutes (ex. date, statut).
\item Lister colonnes \texttt{SELECT} : colonnes de groupement + fonctions d'agrégation. Utiliser \texttt{AS} pour alias lisibles.
\item Ajouter \texttt{GROUP BY} sur toutes les colonnes non agrégées du SELECT.
\item Ajouter \texttt{HAVING} pour filtres sur résultats agrégés (ex. \texttt{HAVING COUNT(*) > 5}).
\item Ajouter \texttt{ORDER BY} (alias ou position ou expression) et \texttt{LIMIT} si besoin.
\end{enumerate}
\end{methode}

\begin{methode}[Sauvegarder et Restaurer une Base MySQL (Ligne de commande / Terminal)]
\begin{enumerate}
\item Ouvrir un terminal (invite de commandes Windows, Bash Linux, ou Git Bash).
\item \textbf{Export (Dump)} : \texttt{mysqldump -u root -p --databases ma\_base > C:/sauvegardes/ma\_base\_\$(date +\%F).sql} (saisir mot de passe).
\item Vérifier le fichier \texttt{.sql} (texte lisible : \texttt{CREATE TABLE}, \texttt{INSERT}).
\item \textbf{Import (Restauration)} : Créer la BD vide si besoin (\texttt{CREATE DATABASE ma\_base;}). Puis : \texttt{mysql -u root -p ma\_base < C:/sauvegardes/ma\_base\_2025-01-15.sql}.
\item \textbf{Bonnes pratiques} : Automatiser via \texttt{cron} (Linux) / Planificateur de tâches (Windows). Stocker hors serveur (NAS, Cloud). Tester la restauration régulièrement.
\end{enumerate}
\end{methode}

\begin{aretenir}[Checklist avant le Bac : Leçon 14 — BDD \& SQL]
$\square$ Savoir transformer un MCD (entités, associations 1:n, n:m, identifiants relatifs, héritage) en schéma relationnel textuel et créer les tables SQL correspondantes (PK, FK, types adaptés : \texttt{INT}, \texttt{VARCHAR(n)}, \texttt{DATE}, \texttt{DECIMAL(p,s)}, \texttt{ENUM}, \texttt{BOOLEAN}).
$\square$ Maîtriser la syntaxe exacte de \texttt{CREATE TABLE} avec contraintes : \texttt{PRIMARY KEY}, \texttt{FOREIGN KEY (...) REFERENCES ...}, \texttt{NOT NULL}, \texttt{UNIQUE}, \texttt{DEFAULT 'valeur'}, \texttt{CHECK (condition)}.
$\square$ Différencier \texttt{WHERE} (filtre lignes \textbf{avant} groupement) et \texttt{HAVING} (filtre groupes \textbf{après} \texttt{GROUP BY}).
$\square$ Écrire une jointure \texttt{INNER JOIN} (intersection) et \texttt{LEFT JOIN} (tout gauche + correspondance droite) avec condition \texttt{ON} correcte (FK = PK).
$\square$ Utiliser les fonctions d'agrégation : \texttt{COUNT(*)} vs \texttt{COUNT(colonne)}, \texttt{SUM}, \texttt{AVG}, \texttt{MIN}, \texttt{MAX} ; regrouper avec \texttt{GROUP BY} (toutes colonnes non agrégées du SELECT).
$\square$ Gérer les opérateurs : \texttt{LIKE} (\%, \_), \texttt{BETWEEN ... AND ...}, \texttt{IN (..., ...)}, \texttt{IS NULL / IS NOT NULL}, \texttt{AND / OR / NOT} (priorité : NOT > AND > OR, utiliser parenthèses).
$\square$ Savoir ordonner (\texttt{ORDER BY col ASC/DESC}), limiter (\texttt{LIMIT n OFFSET m}), aliaser (\texttt{AS alias} ou \texttt{col alias}).
$\square$ Connaître les commandes d'administration : \texttt{mysqldump} (export structure + données), \texttt{mysql < fichier.sql} (import), gestion utilisateurs (\texttt{CREATE USER}, \texttt{GRANT}, \texttt{REVOKE}, \texttt{FLUSH PRIVILEGES}).
$\square$ \textbf{Piège UPDATE/DELETE} : \textbf{Jamais} sans clause \texttt{WHERE} (sauf intention explicite de tout modifier/supprimer). Tester d'abord avec un \texttt{SELECT * FROM table WHERE ...}.
$\square$ \textbf{Intégrité référentielle} : On ne peut insérer une FK qui n'existe pas en PK parente ; on ne peut supprimer une PK parente si des lignes filles existent (sauf \texttt{ON DELETE CASCADE/SET NULL} défini à la création FK).
$\square$ Types de données : Choisir \texttt{DECIMAL(10,2)} pour l'argent (pas \texttt{FLOAT}/\texttt{DOUBLE} -- imprécision binaire), \texttt{DATE} pour date seule, \texttt{DATETIME} pour date+heure, \texttt{VARCHAR} pour texte variable, \texttt{TEXT} pour long texte.
$\square$ Encodage : Toujours \texttt{CHARACTER SET utf8mb4 COLLATE utf8mb4\_unicode\_ci} (ou \texttt{utf8mb4\_general\_ci}) à la création de la BD et des tables pour supporter accents, émojis, langues africaines.
\end{aretenir}
