\coursec{Serveur web, service web et hébergeur}

La coopérative des jeunes diplômés de Bafoussam vient de créer un site de vente en ligne de produits agricoles : plantains, haricots, huile de palme, livrés dans tout l'Ouest. Avant de payer un hébergement coûteux chez un prestataire étranger, le développeur du groupe veut d'abord tester le site entièrement sur son propre ordinateur, hors connexion Internet. Comment transformer un simple PC en véritable serveur web capable d'exécuter des pages dynamiques et de gérer une base de données ? Quels logiciels installer, comment les configurer, et comment rendre le site accessible dans un navigateur ? C'est toute la problématique de cette leçon.

Pour y répondre, il faut d'abord comprendre trois notions que le langage courant mélange sans cesse : le \cle{serveur web}, le \cle{service web} et l'\cle{hébergeur web}. C'est l'objet de cette première section.

\courssub{Le serveur web : une machine et un logiciel}

\textbf{Intuition : à quoi sert un serveur web ?}

Quand tu tapes une adresse dans ton navigateur, par exemple \texttt{http://www.exemple.cm/index.php}, ton ordinateur envoie une demande à travers le réseau. Quelque part, une machine reçoit cette demande, retrouve le fichier demandé (ou le fabrique à la volée), puis te le renvoie. Cette machine, et surtout le programme qui tourne dessus, c'est le serveur web. Sans lui, pas de site : tes fichiers HTML resteraient enfermés sur ton disque dur, invisibles pour le reste du monde.

\begin{definition}[Serveur web]
Un \cle{serveur web} désigne à la fois :
\begin{itemize}
\item un \textbf{équipement matériel} : un ordinateur (souvent puissant, allumé en permanence et connecté au réseau) qui stocke les fichiers d'un ou plusieurs sites web ;
\item un \textbf{logiciel} installé sur cette machine, qui \emph{écoute} les requêtes \cle{HTTP} arrivant du réseau, les traite et renvoie en réponse des \textbf{ressources} : pages HTML, images, feuilles de style, scripts, ou le résultat de l'exécution d'un programme (PHP, Python\ldots).
\end{itemize}
Au Baccalauréat, quand on parle de « serveur web » sans précision, on désigne le plus souvent le \emph{logiciel} (Apache, Nginx\ldots).
\end{definition}

Le fonctionnement repose sur le modèle \cle{client-serveur} : le \textbf{client} (ton navigateur : Chrome, Firefox\ldots) formule une \emph{requête}, le \textbf{serveur} la traite et renvoie une \emph{réponse}. Ce dialogue suit des règles précises : le protocole HTTP, que nous détaillerons plus bas.

\begin{savaistu}[D'où vient le nom « Apache » ?]
Le serveur Apache, créé en 1995, a longtemps hébergé plus de la moitié des sites web mondiaux. Son nom vient d'un jeu de mots anglais : au départ, il s'agissait d'une collection de correctifs (\emph{patches}) appliqués au serveur NCSA, donc \emph{« a patchy server »} — littéralement « un serveur rafistolé ». Ce bricolage ingénieux est devenu l'un des logiciels libres les plus importants de l'histoire d'Internet.
\end{savaistu}

\courssub{Le protocole HTTP : la langue du dialogue client-serveur}

\textbf{Intuition.} Pour que ton navigateur et le serveur se comprennent, il faut une convention commune : comment formuler une demande, comment annoncer que tout s'est bien passé ou que la page n'existe pas. Cette convention, c'est le protocole \cle{HTTP} (\emph{HyperText Transfer Protocol}).

\begin{propriete}[Requête et réponse HTTP]
Le protocole HTTP fonctionne en deux temps :
\begin{enumerate}
\item le client envoie une \textbf{requête} précisant la \emph{méthode} (\texttt{GET} pour demander une page, \texttt{POST} pour envoyer des données de formulaire) et le \emph{chemin de la ressource} ;
\item le serveur renvoie une \textbf{réponse} commençant par un \textbf{code de statut} à trois chiffres, suivi du contenu demandé.
\end{enumerate}
HTTP est un protocole \emph{sans état} : chaque requête est indépendante des précédentes.
\end{propriete}

Les \textbf{codes de statut} usuels à connaître pour le Bac :

\begin{center}
\begin{tabularx}{\linewidth}{|l|l|X|}
\hline
\rowcolor{popblueL} \textbf{Code} & \textbf{Signification} & \textbf{Interprétation} \\
\hline
\texttt{200} & OK & La requête a réussi, la ressource est renvoyée. \\
\hline
\texttt{404} & Not Found & La ressource demandée n'existe pas sur le serveur (adresse erronée, fichier supprimé). \\
\hline
\texttt{500} & Internal Server Error & Erreur interne du serveur, souvent un bug dans un script PHP. \\
\hline
\end{tabularx}
\end{center}

\begin{exemplebox}[Une requête HTTP complète, pas à pas]
Lorsque tu saisis l'adresse \texttt{http://www.exemple.cm/index.php} dans ton navigateur, voici ce qui se passe réellement :
\begin{enumerate}
\item Le navigateur décompose l'URL : protocole \texttt{http}, nom de domaine \texttt{www.exemple.cm}, ressource \texttt{/index.php}.
\item Le nom de domaine est traduit en adresse IP grâce au service DNS.
\item Le navigateur ouvre une connexion TCP vers le serveur, sur le \textbf{port 80} (port standard de HTTP).
\item Il envoie la requête :
\begin{lstlisting}
GET /index.php HTTP/1.1
Host: www.exemple.cm
\end{lstlisting}
\item Le serveur Apache de l'hébergeur exécute le script PHP, puis renvoie la réponse :
\begin{lstlisting}
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8

<!DOCTYPE html>
<html>...</html>
\end{lstlisting}
\item Le navigateur affiche la page reçue.
\end{enumerate}
Si le fichier \texttt{index.php} n'existait pas, la première ligne de la réponse serait \texttt{HTTP/1.1 404 Not Found}.
\end{exemplebox}

\courssub{Le service web : des fonctionnalités pour les programmes}

\textbf{Intuition.} Un site web est fait pour être \emph{lu par un humain} dans un navigateur. Mais parfois, ce n'est pas un humain qui se connecte : c'est un \emph{autre programme}. Quand ton application mobile de messagerie consulte le solde de ton compte Mobile Money, ce n'est pas une page HTML joliment décorée qu'elle demande : ce sont des \emph{données brutes} (un solde, un numéro de transaction). C'est exactement le rôle d'un service web.

\begin{definition}[Service web et hébergeur web]
Un \cle{service web} est une \textbf{application accessible via le web qui offre des fonctionnalités à d'autres programmes}, en échangeant des données structurées (souvent au format XML ou JSON) au moyen de protocoles standard (HTTP, SOAP, REST).

Un \cle{hébergeur web} est une \textbf{entreprise qui met à disposition, moyennant paiement ou gratuitement, des serveurs connectés en permanence à Internet}, sur lesquels ses clients déposent leurs sites et applications. Exemples : OVH, Hostinger, ou des hébergeurs locaux camerounais qui proposent des serveurs proches des utilisateurs et un support en français.
\end{definition}

La différence entre site web et service web est donc le \emph{destinataire} : le site s'adresse à un humain (pages HTML), le service web s'adresse à un programme (données). Un même serveur peut héberger les deux : le site vitrine de la coopérative de Bafoussam pour les clients, et un service web qui permet à l'application mobile du livreur de consulter les commandes du jour.

\begin{attention}[Ne pas confondre serveur web et hébergeur]
Piège classique du Baccalauréat : le \textbf{serveur web} est un \emph{logiciel} (comme Apache) ou la machine qui l'exécute ; l'\textbf{hébergeur} est une \emph{entreprise} qui loue des serveurs et la connectivité Internet. Dire « mon site est sur Apache » n'a pas le même sens que « mon site est chez OVH » : Apache est le programme qui sert les pages, OVH est l'entreprise qui fournit la machine, l'électricité et la connexion permanente. De même, ne confonds pas \emph{service web} (fonctionnalités pour programmes) et \emph{site web} (pages pour humains).
\end{attention}

\courssub{Rôles respectifs : synthèse comparative}

\begin{center}
\begin{tabularx}{\linewidth}{|l|X|X|}
\hline
\rowcolor{popblueL} \textbf{Notion} & \textbf{Nature} & \textbf{Rôle} \\
\hline
Serveur web & Machine + logiciel (Apache, Nginx\ldots) & \textbf{Stocke} les fichiers du site et \textbf{sert} les ressources en réponse aux requêtes HTTP. \\
\hline
Service web & Application accessible via le web & \textbf{Fournit des fonctionnalités} et des données à d'autres programmes (API Mobile Money, météo\ldots). \\
\hline
Hébergeur web & Entreprise (OVH, Hostinger\ldots) & \textbf{Loue l'espace disque}, la machine et la connectivité permanente à Internet. \\
\hline
\end{tabularx}
\end{center}

\begin{aretenir}[L'essentiel]
\begin{itemize}
\item Le \cle{serveur web} (logiciel comme Apache) reçoit les requêtes HTTP et renvoie les ressources.
\item Le \cle{service web} expose des fonctionnalités aux programmes, pas des pages aux humains.
\item L'\cle{hébergeur web} est l'entreprise qui loue serveurs et connexion permanente.
\item Codes HTTP à retenir : \texttt{200} (succès), \texttt{404} (introuvable), \texttt{500} (erreur serveur).
\end{itemize}
\end{aretenir}

\courssub{Hébergement local ou hébergement distant ?}

Revenons à notre coopérative de Bafoussam. Deux stratégies s'offrent à elle :

\begin{itemize}
\item \textbf{Hébergement local} : le site tourne sur la machine du développeur (ou un PC de la coopérative). Avantages : gratuit, fonctionne \emph{hors connexion Internet}, idéal pour développer et tester. Inconvénients : le site disparaît dès que le PC s'éteint, et il n'est pas accessible au public sans configuration réseau avancée (redirection de port, DNS dynamique).
\item \textbf{Hébergement distant} : le site est déposé chez un hébergeur professionnel. Avantages : accessible 24 h/24 partout dans le monde, nom de domaine propre, sauvegardes gérées. Inconvénients : coût récurrent, dépendance à la connexion Internet.
\end{itemize}

La démarche professionnelle est donc toujours la même : on \textbf{développe et teste en local} (sur \texttt{localhost} ou \texttt{127.0.0.1}), puis on \textbf{déploie chez un hébergeur} quand le site est prêt. C'est exactement ce que veut faire le développeur de la coopérative — et c'est pourquoi les sections suivantes te montreront comment installer un environnement intégré (WampServer, XAMPP\ldots) qui transforme ton PC en serveur web complet.

\begin{exoresolu}[Identifier les acteurs d'une mise en ligne]
Énoncé. La startup « AgroMarket » de Bafoussam a développé son site avec Apache et PHP sur le portable de son développeur. Une fois les tests terminés, elle dépose les fichiers chez un hébergeur camerounais. Un client tape l'adresse du site et reçoit le message « Erreur 404 ». Pour chaque élément suivant, indique s'il s'agit du serveur web, du service web ou de l'hébergeur, puis explique la cause probable de l'erreur : (a) Apache qui tourne sur la machine louée ; (b) l'entreprise qui loue la machine ; (c) l'API qui permet à l'application mobile de passer commande.
\tcblower
Solution détaillée.
\begin{enumerate}
\item (a) Apache est le \textbf{serveur web} au sens logiciel : il reçoit les requêtes HTTP et renvoie les pages.
\item (b) L'entreprise qui loue la machine est l'\textbf{hébergeur web} : elle fournit l'espace disque et la connectivité permanente.
\item (c) L'API de commande est un \textbf{service web} : elle offre des fonctionnalités à un programme (l'application mobile), pas des pages à un humain.
\end{enumerate}
L'erreur \texttt{404 Not Found} signifie que le serveur fonctionne (il répond !) mais que la \emph{ressource demandée n'existe pas} à l'adresse indiquée. Causes probables : le fichier n'a pas été transféré chez l'hébergeur, il a été déposé dans le mauvais répertoire (hors du répertoire racine), ou l'URL saisie contient une faute de frappe. La première vérification à faire est donc le contenu du répertoire racine du serveur — notion que nous étudierons dans la section 5.
\end{exoresolu}

\begin{exercice}[À toi de jouer]
\begin{enumerate}
\item Donne la double définition d'un serveur web (aspect matériel et aspect logiciel).
\item Cite trois logiciels serveurs web et précise celui qui est intégré à WampServer.
\item Ton ami affirme : « Mon site est hébergé par Apache ». Corrige sa formulation en distinguant serveur web et hébergeur.
\item Un navigateur affiche « 500 Internal Server Error » alors que la page s'affichait hier. Le problème vient-il de l'adresse saisie ou d'un script du site ? Justifie.
\item La coopérative de Bafoussam hésite entre tester son site en local ou le mettre directement en ligne chez un hébergeur. Donne deux arguments en faveur du test local préalable.
\end{enumerate}
\end{exercice}

\begin{corrige}[Exercice 1]
\begin{enumerate}
\item Matériellement, c'est un ordinateur connecté en permanence au réseau qui stocke les fichiers des sites. Logiquement, c'est le logiciel qui écoute les requêtes HTTP et renvoie les ressources demandées (pages, images).
\item Apache HTTP Server, Nginx, Microsoft IIS (ou Lighttpd). WampServer intègre \textbf{Apache}.
\item Apache est un \emph{logiciel serveur web}, pas un hébergeur. Formulation correcte : « Mon site est servi par Apache, sur une machine louée chez mon hébergeur (OVH, Hostinger\ldots) ».
\item Le code \texttt{500} signale une erreur \emph{interne du serveur}, typiquement un bug dans un script PHP (erreur de syntaxe, base de données injoignable). Ce n'est pas un problème d'adresse : une adresse fausse donnerait un \texttt{404}.
\item Tester en local est (1) \textbf{gratuit} — aucun abonnement à payer pendant le développement — et (2) \textbf{possible hors connexion Internet} — le développeur peut travailler même sans forfait data, ce qui est précieux à Bafoussam comme ailleurs. On ne paie l'hébergement distant qu'une fois le site validé.
\end{enumerate}
\end{corrige}

\coursec{Environnements intégrés de développement web}

Dans la section précédente, nous avons vu qu'un \cle{serveur web} (comme Apache ou Nginx) est le logiciel qui écoute les requêtes HTTP et sert les pages, qu'un \cle{service web} expose des fonctionnalités à travers le réseau, et qu'un \cle{hébergeur web} met ces machines à disposition. Une question pratique se pose alors immédiatement : pour développer et tester notre application web (par exemple le site de gestion des notes de notre lycée), faut-il louer tout de suite un hébergement payant chez un prestataire ? Non. La bonne pratique consiste à d'abord \emph{simuler un vrai serveur sur son propre ordinateur}. C'est précisément le rôle des environnements intégrés de développement web que nous étudions ici.

\courssub{Pourquoi un environnement intégré ?}

\textbf{Le problème concret.} Une application web dynamique en PHP a besoin de \emph{trois} logiciels qui collaborent :
\begin{itemize}
\item un \cle{serveur web} (Apache) qui reçoit les requêtes HTTP du navigateur ;
\item un \cle{préprocesseur} (PHP) qui exécute les scripts et génère le HTML ;
\item un \cle{serveur de données} (MySQL ou MariaDB) qui stocke et interroge les données en SQL.
\end{itemize}

Installer ces trois logiciels \emph{séparément} est une tâche longue et délicate : il faut télécharger chaque programme dans une version compatible avec les autres, éditer à la main plusieurs fichiers de configuration (\texttt{httpd.conf} d'Apache, \texttt{php.ini}, \texttt{my.ini} de MySQL), déclarer à Apache où se trouve l'interpréteur PHP (via le module \texttt{mod\_php} ou \texttt{FastCGI}), configurer les ports d'écoute, créer le service de base de données\ldots{} Une seule erreur de version ou de chemin et rien ne fonctionne, avec des messages d'erreur souvent obscurs pour un débutant.

\textbf{La solution.} Les éditeurs ont donc créé des \emph{paquetages tout-en-un} : un seul installeur dépose les trois composants, les configure pour qu'ils se reconnaissent mutuellement, et fournit un panneau de contrôle pour tout démarrer ou arrêter d'un clic.

\begin{definition}[Environnement intégré de développement web]
Un \cle{environnement intégré de développement web} est un \textbf{paquetage logiciel tout-en-un} qui installe et pré-configure, en une seule opération, les composants nécessaires au fonctionnement d'un serveur web local : un serveur HTTP (généralement Apache), un interpréteur de scripts (généralement PHP) et un serveur de bases de données (généralement MySQL ou MariaDB), accompagnés d'outils d'administration (panneau de contrôle, phpMyAdmin). Il permet de développer et tester un site \emph{en local}, sans connexion Internet ni hébergement payant.
\end{definition}

\begin{aretenir}[Les quatre environnements au programme]
Le programme officiel retient quatre environnements intégrés : \cle{EasyPHP}, \cle{WampServer}, \cle{XAMPP} et \cle{LAMP}. Les trois premiers sont des installeurs tout-en-un pour Windows (principalement) ; LAMP est une \emph{pile logicielle} installée par paquets sous Linux.
\end{aretenir}

\courssub{Présentation des quatre environnements au programme}

\paragraph{WampServer : la référence sous Windows.}
\cle{WampServer} est l'environnement le plus répandu dans les salles informatiques des lycées camerounais, car la quasi-totalité des machines y fonctionnent sous Windows.

\begin{exemplebox}[Décoder le sigle WAMP]
Le nom \textbf{WAMP} est un acronyme qui décrit exactement le contenu du paquetage :
\begin{itemize}
\item \textbf{W} = \textbf{Windows} (le système d'exploitation hôte) ;
\item \textbf{A} = \textbf{Apache} (le serveur web) ;
\item \textbf{M} = \textbf{MySQL} (le serveur de bases de données ; MariaDB est aussi proposé) ;
\item \textbf{P} = \textbf{PHP} (le préprocesseur / interpréteur de scripts).
\end{itemize}
On retrouve la même logique de nommage dans LAMP (Linux), MAMP (macOS) et XAMPP (multiplateforme).
\end{exemplebox}

Une fois installé, WampServer se pilote depuis une \textbf{icône de la zone de notification} (à côté de l'horloge Windows). Cette icône est un véritable tableau de bord lumineux :

\begin{center}
\begin{tabularx}{\linewidth}{|l|X|}
\hline
\rowcolor{popblueL} \textbf{Couleur de l'icône} & \textbf{Signification} \\
\hline
\textcolor{popgreen}{\textbf{Verte}} & Tous les services (Apache et MySQL/MariaDB) sont démarrés : le serveur local est opérationnel. \\
\hline
\textcolor{poporange}{\textbf{Orange}} & Au moins un service n'a pas démarré (souvent Apache, à cause d'un conflit de port 80 avec Skype, IIS ou un autre serveur). \\
\hline
\textcolor{poppink}{\textbf{Rouge}} & Aucun service n'est démarré : le serveur est arrêté. \\
\hline
\end{tabularx}
\end{center}

Un clic gauche sur l'icône ouvre un menu permettant de démarrer/arrêter les services, d'ouvrir \texttt{phpMyAdmin}, d'accéder au répertoire racine \texttt{www} et de modifier les fichiers de configuration (\texttt{httpd.conf}, \texttt{php.ini}, \texttt{my.ini}). WampServer permet aussi de \emph{changer de version de PHP} à la volée (menu \texttt{PHP \$\rightarrow\$ Version}), ce qui est précieux pour tester la compatibilité d'un projet avec PHP 7.4, 8.1, 8.2, etc.

\paragraph{XAMPP : la solution multiplateforme.}
\cle{XAMPP}, développé par Apache Friends, est l'environnement le plus téléchargé au monde. Sa grande force : il fonctionne de manière quasi identique sous \textbf{Windows, Linux et macOS}, ce qui le rend idéal pour une équipe dont les machines sont hétérogènes.

\begin{exemplebox}[Décoder le sigle XAMPP]
\begin{itemize}
\item \textbf{X} = \textbf{cross-platform} (multiplateforme : le « X » symbolise n'importe quel OS) ;
\item \textbf{A} = \textbf{Apache} ;
\item \textbf{M} = \textbf{MariaDB} (remplace MySQL depuis la version 5.5.30) ;
\item \textbf{P} = \textbf{PHP} ;
\item \textbf{P} = \textbf{Perl} (second langage de script inclus, utile pour certains scripts système ou CGI).
\end{itemize}
\end{exemplebox}

XAMPP se pilote depuis le \textbf{panneau de contrôle XAMPP} (\texttt{xampp-control.exe} sous Windows) : une petite fenêtre liste les modules (Apache, MySQL, FileZilla FTP, Mercury Mail, Tomcat) avec, pour chacun, les boutons \texttt{Start}, \texttt{Stop}, \texttt{Config} et \texttt{Logs}. On y lit aussi les \textbf{ports d'écoute} effectivement utilisés (par exemple \texttt{80, 443} pour Apache et \texttt{3306} pour la base de données), ce qui facilite le diagnostic des conflits.

\begin{attention}[XAMPP installe MariaDB, pas MySQL]
Depuis la version 5.5.30, XAMPP embarque \textbf{MariaDB} et non plus MySQL, bien que le bouton du panneau de contrôle s'appelle encore « MySQL ». Ce n'est pas un problème : MariaDB est un \emph{fork} de MySQL, créé par les développeurs originaux de MySQL après son rachat par Oracle, et il est \textbf{compatible} avec MySQL pour l'essentiel des usages (même protocole, même port 3306, même client \texttt{mysqlnd} en PHP). Toutes vos requêtes SQL (\texttt{SELECT}, \texttt{INSERT}, \texttt{CREATE TABLE}\ldots), vos identifiants (\texttt{root} sans mot de passe par défaut) fonctionnent exactement pareil. Au Baccalauréat, on considère donc les deux comme interchangeables dans ce contexte.
\end{attention}

\paragraph{EasyPHP : le pionnier portable.}
\cle{EasyPHP} est historiquement le \emph{premier} environnement tout-en-un sous Windows (créé en 1999, en France). Il a formé des générations de développeurs PHP. Ses particularités :
\begin{itemize}
\item une approche \textbf{portable} : certaines versions (notamment \texttt{EasyPHP Devserver}) peuvent fonctionner depuis une clé USB, sans installation profonde dans le système (pas de clés de registre, pas de services Windows) — pratique dans une salle informatique où l'on n'a pas les droits administrateur ;
\item une distinction entre un \textbf{serveur local} (développement personnel, accessible uniquement via \texttt{127.0.0.1}) et un \textbf{serveur de développement} (accessible depuis le réseau local via l'IP LAN, pour tester avec ses camarades sur mobile) ;
\item des modules complémentaires (WebGrind pour profilage, PostgreSQL, MongoDB, etc.) gérables via une interface web.
\end{itemize}
Moins activement maintenu que ses concurrents ces dernières années, EasyPHP reste cité au programme et illustre parfaitement le concept de portabilité.

\paragraph{LAMP : la pile logicielle sous Linux.}
Contrairement aux trois précédents, \cle{LAMP} n'est pas un installeur unique téléchargeable : c'est une \textbf{pile logicielle} (\emph{software stack}) que l'on assemble sous Linux à l'aide du gestionnaire de paquets. Le sigle signifie \textbf{L}inux + \textbf{A}pache + \textbf{M}ySQL/MariaDB + \textbf{P}HP.

Sous une distribution Debian ou Ubuntu (très utilisées sur les serveurs camerounais, ex. serveurs CAMTEL, ANTIC), l'installation complète tient en quelques commandes :

\begin{lstlisting}[language=bash]
# 1. Mise a jour du catalogue des paquets
sudo apt update

# 2. Installation du serveur web Apache
sudo apt install apache2

# 3. Installation du serveur de bases de donnees MariaDB (remplace MySQL)
sudo apt install mariadb-server

# 4. Securisation de base de MariaDB (definir mot de passe root, supprimer utilisateurs anonymes, etc.)
sudo mysql_secure_installation

# 5. Installation de PHP et du module d'integration Apache (mod_php) + extension MySQL
sudo apt install php libapache2-mod-php php-mysql php-cli php-common php-json php-opcache php-readline php-mbstring php-xml php-gd php-curl php-zip

# 6. Verification : demarrage et etat du service Apache
sudo systemctl start apache2
sudo systemctl enable apache2   # demarrage automatique au boot
sudo systemctl status apache2
\end{lstlisting}

Le gestionnaire de paquets \texttt{apt} résout automatiquement les \emph{dépendances} (il installe tout ce dont chaque logiciel a besoin : bibliothèques SSL, zlib, etc.) et configure les services systemd. C'est la méthode utilisée sur les \textbf{serveurs de production réels} : la grande majorité des serveurs web d'Internet tournent sous Linux (Ubuntu Server, Debian, CentOS/Rocky Linux).

\begin{savaistu}[LAMP, la pile qui a propulsé le web dynamique]
Dans les années 2000, la pile LAMP — entièrement \textbf{libre et gratuite} — a rendu la création de sites dynamiques accessible à tous, sans licence coûteuse (contrairement à IIS/ASP.NET ou Oracle/WebLogic à l'époque). C'est sur LAMP qu'ont été bâtis \textbf{Wikipédia}, \textbf{WordPress} (qui propulse encore aujourd'hui plus de 40\,\% des sites web mondiaux) et même \textbf{Facebook à ses débuts} (Mark Zuckerberg codait en PHP/MySQL dans sa chambre d'étudiant). Au Cameroun, la plupart des applications des administrations en ligne (\texttt{impots.cm}, \texttt{anten.cm}, portails ministériels) et des startups (Kiro'o Games, GiftedMom, Ejara) utilisent encore aujourd'hui des variantes de cette pile, souvent avec MariaDB, Nginx (au lieu d'Apache) et des frameworks PHP modernes comme Laravel ou Symfony.
\end{savaistu}

\courssub{Installation et configuration d'un environnement intégré}

L'installation d'un installeur tout-en-un (WampServer, XAMPP, EasyPHP) sous Windows suit une procédure standard qu'il faut maîtriser pour le Bac.

\begin{methode}[Installer et configurer WampServer / XAMPP sous Windows]
\begin{enumerate}
\item \textbf{Télécharger} l'installeur officiel (site \texttt{wampserver.aviatechno.net} ou \texttt{apachefriends.org}). Choisir la version \textbf{64 bits} (standard actuel) et la version de PHP souhaitée (ex. PHP 8.2.x).
\item \textbf{Exécuter en tant qu'administrateur} (clic droit $\rightarrow$ « Exécuter en tant qu'administrateur ») pour permettre l'écriture dans \texttt{C:\textbackslash wamp64} (ou \texttt{C:\textbackslash xampp}) et l'enregistrement des services Windows.
\item \textbf{Accepter la licence}, choisir le répertoire de destination (conserver le défaut \texttt{C:\textbackslash wamp64} ou \texttt{C:\textbackslash xampp} pour éviter les problèmes de chemins avec espaces).
\item \textbf{Choisir le navigateur par défaut} (laissé par défaut : \texttt{msedge.exe} ou \texttt{chrome.exe}) et l'éditeur de texte (Notepad++ ou VS Code recommandés).
\item \textbf{Autoriser l'accès réseau} dans la fenêtre « Alerte de sécurité Windows » (pare-feu) pour \texttt{httpd.exe} (Apache) et \texttt{mysqld.exe} (MariaDB) : cocher « Réseaux privés » et « Réseaux publics » si vous voulez tester depuis un autre poste du LAN.
\item \textbf{Lancer le panneau de contrôle} et démarrer les services (Apache, MySQL/MariaDB). Vérifier l'icône verte (WampServer) ou les PID/Ports verts (XAMPP).
\item \textbf{Tester} : ouvrir le navigateur à \texttt{http://localhost} (page d'accueil WampServer/XAMPP) et \texttt{http://localhost/phpmyadmin} (interface d'administration BDD).
\end{enumerate}
\end{methode}

\begin{attention}[Pièges classiques à l'installation]
\begin{itemize}
\item \textbf{Conflit de port 80} : Si l'icône WampServer reste orange ou XAMPP affiche « Port 80 in use by "System" / PID 4 », c'est souvent le service « Publication sur le Web » (IIS) de Windows ou Skype. \textbf{Solution} : Désactiver IIS (\texttt{services.msc \$\rightarrow\$ World Wide Web Publishing Service \$\rightarrow\$ Désactiver}) ou changer le port d'Apache (voir section suivante).
\item \textbf{Droits d'écriture} : Si vous installez hors \texttt{Program Files} (ex. \texttt{D:\textbackslash MonServeur}), assurez-vous que l'utilisateur Windows a les droits \emph{Modification} sur le dossier.
\item \textbf{Visual C++ Redistributables} : WampServer/XAMPP en ont besoin. L'installeur les propose souvent ; sinon, téléchargez « Microsoft Visual C++ Redistributable for Visual Studio 2015-2022 » (x64).
\item \textbf{Antivirus} : Certains (Avast, Kaspersky) bloquent \texttt{mysqld.exe} ou \texttt{httpd.exe}. Ajoutez le dossier d'installation aux exclusions.
\end{itemize}
\end{attention}

\courssub{Répertoire racine (DocumentRoot) et fichiers de configuration}

C'est une notion clé du programme : \textbf{où poser ses fichiers ?} et \textbf{comment changer le port ?}

\begin{definition}[Répertoire racine / DocumentRoot]
Le \cle{répertoire racine} (directive Apache \texttt{DocumentRoot}) est le dossier physique sur le disque dur qui correspond à l'URL racine \texttt{http://localhost/}. Tout fichier ou sous-dossier placé à l'intérieur devient accessible publiquement via le navigateur.
\end{definition}

\begin{propriete}[Emplacements standards du DocumentRoot]
\begin{center}
\begin{tabularx}{\linewidth}{|l|l|X|}
\hline
\rowcolor{popblueL} \textbf{Environnement} & \textbf{DocumentRoot par défaut} & \textbf{Accès rapide} \\
\hline
WampServer & \texttt{C:\textbackslash wamp64\textbackslash www} & Clic gauche icône $\rightarrow$ « Répertoire www » \\
\hline
XAMPP (Windows) & \texttt{C:\textbackslash xampp\textbackslash htdocs} & Panneau de contrôle $\rightarrow$ bouton « Explorer » \\
\hline
EasyPHP (Devserver) & \texttt{C:\textbackslash EasyPHP\textbackslash devserver\textbackslash eds-www} & Menu « Local Web » \\
\hline
LAMP (Ubuntu/Debian) & \texttt{/var/www/html} & \texttt{cd /var/www/html} (droits \texttt{www-data}) \\
\hline
\end{tabularx}
\end{center}
\end{propriete}

\begin{exemplebox}[Organiser ses projets dans le DocumentRoot]
Ne mettez pas vos fichiers \emph{directement} dans \texttt{www} ou \texttt{htdocs} (mélange avec les fichiers système de phpMyAdmin, etc.). Créez un sous-dossier par projet :
\begin{lstlisting}[language=bash]
# Exemple structure WampServer
C:\wamp64\www\
├── index.php          # (page par défaut WampServer, ne pas supprimer)
├── phpmyadmin/        # (fourni)
├── mon_projet_lycee/  # <--- VOTRE PROJET
│   ├── index.php
│   ├── config/
│   ├── public/
│   └── src/
└── portfolio/         # <--- AUTRE PROJET
    └── index.html
\end{lstlisting}
Accès navigateur : \texttt{http://localhost/mon\_projet\_lycee/}
\end{exemplebox}

\begin{propriete}[Fichiers de configuration principaux à connaître]
\begin{center}
\begin{tabular}{|l|l|l|}
\hline
\rowcolor{popblueL} \textbf{Composant} & \textbf{Fichier (Windows)} & \textbf{Fichier (Linux LAMP)} \\
\hline
Apache (core) & \texttt{C:\textbackslash wamp64\textbackslash bin\textbackslash apache\textbackslash apache2.4.x\textbackslash conf\textbackslash httpd.conf} & \texttt{/etc/apache2/apache2.conf} (ou \texttt{httpd.conf}) \\
Apache (vhosts/ports) & \texttt{httpd-vhosts.conf}, \texttt{httpd-ssl.conf} (dossier \texttt{extra}) & \texttt{/etc/apache2/sites-available/000-default.conf} \\

\hline
\end{tabular}

\end{propriete}

\begin{methode}[Changer le port d'écoute d'Apache (ex. 80 $\rightarrow$ 8080)]
\begin{enumerate}
\item Ouvrir \texttt{httpd.conf} (via menu WampServer $\rightarrow$ Apache $\rightarrow$ httpd.conf, ou \texttt{Config} dans XAMPP).
\item Chercher la ligne \texttt{Listen 80} (vers ligne 50-60). La modifier : \texttt{Listen 8080}.
\item Chercher la ligne \texttt{ServerName localhost:80} (vers ligne 220). La modifier : \texttt{ServerName localhost:8080}.
\item \textbf{Si VirtualHosts utilisés} : modifier aussi \texttt{<VirtualHost *:80>} en \texttt{<VirtualHost *:8080>} dans \texttt{httpd-vhosts.conf}.
\item Sauvegarder, puis \textbf{Redémarrer Apache} (menu « Restart All Services » ou bouton \texttt{Restart} XAMPP).
\item Tester : \texttt{http://localhost:8080} (le port est maintenant obligatoire dans l'URL).
\end{enumerate}
\end{methode}

\begin{attention}[Ne pas confondre php.ini (Apache) et php.ini (CLI)]
Sous WampServer/XAMPP, il y a souvent \textbf{deux} fichiers \texttt{php.ini} :
\begin{itemize}
\item Celui utilisé par \textbf{Apache} (pour le web) : \texttt{.../apache/bin/php.ini} ou lien symbolique.
\item Celui utilisé par \textbf{PHP en ligne de commande (CLI)} : \texttt{.../php/php.ini}.
\end{itemize}
Si vous modifiez \texttt{upload\_max\_filesize} ou \texttt{memory\_limit} pour un upload web, modifiez celui d'Apache et \textbf{redémarrez Apache}. La commande \texttt{php -i | findstr "Loaded Configuration File"} (Windows) ou \texttt{php --ini} (Linux) vous dit lequel est chargé.
\end{attention}

\courssub{Hébergement local et déploiement d'une application}

Une fois l'environnement prêt, voici la procédure complète pour mettre en ligne (en local) une application PHP/MySQL (ex. gestion de bibliothèque, notes, cybercafé).

\begin{methode}[Déployer une application web en local (procédure type Bac)]
\begin{enumerate}
\item \textbf{Préparer la base de données} :
      \begin{itemize}
      \item Ouvrir \texttt{http://localhost/phpmyadmin}.
      \item Créer la BDD (ex. \texttt{CREATE DATABASE biblio\_lycee CHARSET utf8mb4;}).
      \item Importer le fichier \texttt{structure.sql} (tables) puis \texttt{donnees.sql} (jeu de test) via l'onglet « Importer ».
      \item Créer un utilisateur dédié (ex. \texttt{user\_biblio} / \texttt{motdepasse\_fort}) avec privilèges \texttt{SELECT, INSERT, UPDATE, DELETE} sur \texttt{biblio\_lycee.*} (pas \texttt{root} en prod !).
      \end{itemize}
\item \textbf{Copier les fichiers du projet} dans un sous-dossier du \texttt{DocumentRoot} (ex. \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash biblio\_lycee}).
\item \textbf{Configurer la connexion BDD} dans le fichier de config du projet (ex. \texttt{config/database.php} ou \texttt{.env}) :
\begin{lstlisting}[language=php]
<?php
// Exemple config PDO (bonnes pratiques)
$host = '127.0.0.1';      // ou 'localhost'
$dbname = 'biblio_lycee';
$charset = 'utf8mb4';
$user = 'user_biblio';    // PAS 'root' !
$pass = 'motdepasse_fort';

$dsn = "mysql:host=$host;dbname=$dbname;charset=$charset";
$options = [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,
];
try {
    $pdo = new PDO($dsn, $user, $pass, $options);
} catch (\PDOException $e) {
    die("Erreur connexion BDD : " . $e->getMessage());
}
\end{lstlisting}
\item \textbf{Tester l'application} : Ouvrir \texttt{http://localhost/biblio\_lycee/} (ou \texttt{http://localhost:8080/biblio\_lycee/} si port changé). Vérifier la page d'accueil, la connexion, l'affichage des données.
\item \textbf{Vérifier les logs en cas d'erreur} :
      \begin{itemize}
      \item Apache : \texttt{logs/error.log} (WampServer : menu $\rightarrow$ Apache $\rightarrow$ Error logs).
      \item PHP : \texttt{php\_error.log} (défini dans \texttt{php.ini} : \texttt{error\_log = "..."}).
      \item MySQL : \texttt{data/\textless hostname\textgreater.err}.
      \end{itemize}
\end{enumerate}
\end{methode}

\begin{experience}[Déployer un mini-site "Gestion de notes" sous WampServer]
\textbf{Objectif :} Mettre en œuvre la procédure complète de déploiement local.
\textbf{Matériel :} Poste Windows 10/11 avec WampServer 3.3+ installé, archive \texttt{gestion\_notes.zip} (fournie : \texttt{index.php}, \texttt{config.php}, \texttt{notes.sql}).
\textbf{Manipulation :}
\begin{enumerate}
\item Démarrer WampServer (icône verte).
\item Créer la BDD : \texttt{http://localhost/phpmyadmin} $\rightarrow$ « Nouvelle base » \texttt{notes\_db} $\rightarrow$ Importer \texttt{notes.sql}.
\item Créer dossier \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash notes\_app}. Extraire l'archive dedans.
\item Modifier \texttt{config.php} : \texttt{\$pdo = new PDO('mysql:host=127.0.0.1;dbname=notes\_db;charset=utf8mb4', 'root', '');} (utilisateur root sans mdp en local dev uniquement).
\item Ouvrir \texttt{http://localhost/notes\_app/}. Vérifier l'affichage de la liste des élèves et notes.
\item \textbf{Test d'erreur} : Renommer \texttt{config.php} en \texttt{config.php.bak}. Recharger la page. Observer l'erreur PHP (chemin introuvable). Consulter \texttt{Apache error.log} pour voir la trace. Remettre le fichier.
\end{enumerate}
\textbf{Observations :} Le site est accessible immédiatement. L'erreur 500 ou page blanche correspond souvent à une erreur PHP non affichée (vérifier \texttt{display\_errors=On} dans \texttt{php.ini} dev).
\textbf{Interprétation :} Cette procédure simule exactement le déploiement chez un hébergeur (OVH, Ionos, hébergeur camerounais), sauf que le DocumentRoot est local et l'URL est \texttt{localhost}.
\end{experience}

\begin{attention}[Sécurité : Environnement de développement $\neq$ Production]
WampServer, XAMPP, EasyPHP sont configurés par défaut pour la \textbf{commodité du développeur}, pas pour la sécurité :
\begin{itemize}
\item Utilisateur \texttt{root} MySQL \textbf{sans mot de passe} (ou \texttt{root/root}).
\item \texttt{display\_errors = On} : fuites d'infos (chemins, structure BDD) dans le navigateur.
\item \texttt{phpMyAdmin} accessible sans authentification forte (par défaut).
\item Services tournant souvent avec des privilèges élevés (SYSTEM ou Administrateur).
\end{itemize}
\textbf{Ne JAMAIS exposer un tel environnement sur Internet public} (ouverture port 80 sur box/routeur) sans durcissement extrême (mots de passe forts, restriction IP, HTTPS, désactivation phpMyAdmin, utilisateur Windows dédié non-admin). Pour la mise en production, on utilise un serveur Linux (LAMP/LEMP) durci, géré via SSH, avec déploiement Git/CI-CD.
\end{attention}

\begin{methode}[Choisir son environnement selon son système et ses besoins]
\begin{enumerate}
\item \textbf{Identifier le système d'exploitation} de la machine : sous Windows, WampServer, XAMPP ou EasyPHP sont possibles ; sous Linux, on installe la pile LAMP (ou XAMPP pour Linux) ; sous macOS, XAMPP (ou MAMP natif).
\item \textbf{Évaluer le besoin de portabilité} : si l'on travaille sur des machines différentes sans droits administrateur (salle informatique du lycée), privilégier une version portable (EasyPHP Devserver, ou XAMPP « Portable » sur clé USB).
\item \textbf{Considérer la simplicité d'usage} : pour un débutant sous Windows, WampServer et son icône verte/orange/rouge offrent le diagnostic le plus intuitif ; le changement de version PHP natif est un atout majeur pour le programme (test compatibilité).
\item \textbf{Penser à la cible de déploiement} : si le site sera hébergé en production sur un serveur Linux (cas le plus fréquent, ex. VPS OVH, Scaleway, Cloud CAMTEL), développer dans des conditions proches (mêmes versions de PHP, MariaDB, Apache/Nginx, sensible à la casse des noms de fichiers) évite les mauvaises surprises (ex. \texttt{include 'Fichier.php'} vs \texttt{fichier.php}).
\item \textbf{Vérifier les besoins du projet} : versions de PHP exigées par le framework (Laravel 10+ $\rightarrow$ PHP 8.1+), modules supplémentaires (Redis, Elasticsearch, Node.js pour assets), base PostgreSQL (plus facile sur LAMP/XAMPP).
\end{enumerate}
\end{methode}

\begin{exoresolu}[Identifier un environnement et ses composants]
\textbf{Énoncé.} Dans la salle informatique du Lycée de Nkolbisson, les machines tournent sous Windows 10. L'enseignant lance un logiciel : une icône apparaît près de l'horloge, d'abord rouge, puis orange, puis verte. Le menu de cette icône propose « Apache », « MySQL », « PHP » et « phpMyAdmin ». (a) De quel environnement s'agit-il ? Justifie. (b) Donne la signification de chaque lettre de son sigle. (c) Que signifie la phase « orange » et quelle en est la cause la plus fréquente ? (d) Comment accéder au fichier \texttt{httpd.conf} pour changer le port d'écoute ?
\tcblower
\textbf{Solution.}
\begin{itemize}
\item[(a)] Il s'agit de \textbf{WampServer}. Indices caractéristiques : système Windows, icône de la zone de notification à trois états colorés (rouge/orange/vert), menu donnant accès à Apache, MySQL, PHP et phpMyAdmin.
\item[(b)] \textbf{W} = Windows (OS hôte), \textbf{A} = Apache (serveur web), \textbf{M} = MySQL (serveur de bases de données), \textbf{P} = PHP (préprocesseur).

La cause la plus fréquente est un \textbf{conflit sur le port 80} : une autre application (service IIS « Publication sur le Web » de Windows, Skype, VMware Workstation) écoute déjà ce port, empêchant Apache de s'y attacher. La solution consiste à arrêter le service fautif (\texttt{services.msc}) ou à changer le port d'écoute d'Apache dans \texttt{httpd.conf} (\texttt{Listen 8080}).
\item[(d)] Clic gauche sur l'icône WampServer $\rightarrow$ \texttt{Apache} $\rightarrow$ \texttt{httpd.conf} (ouvre le fichier dans l'éditeur de texte associé). Modifier \texttt{Listen 80} en \texttt{Listen 8080} et \texttt{ServerName localhost:80} en \texttt{ServerName localhost:8080}, puis « Redémarrer les services ».
\end{itemize}

\begin{aretenir}[L'essentiel de la leçon : Environnements intégrés]
\begin{itemize}
\item Un \textbf{environnement intégré} (WampServer, XAMPP, EasyPHP, LAMP) installe d'un coup le trio \textbf{Apache + PHP + MySQL/MariaDB} (+ phpMyAdmin).
\item \textbf{WampServer} (Windows) : icône systray verte/orange/rouge, multi-version PHP natif, standard lycée.
\item \textbf{XAMPP} (Multi-OS) : panneau de contrôle GUI, MariaDB, modules extras (FTP, Mail, Tomcat).
\item \textbf{EasyPHP} : portable (clé USB), distinction Local/Dev LAN, historique.
\item \textbf{LAMP} (Linux) : pile installée via \texttt{apt} (\texttt{apache2}, \texttt{mariadb-server}, \texttt{php libapache2-mod-php php-mysql}), standard \textbf{production}.
\item \textbf{DocumentRoot} : dossier racine du site (\texttt{www}, \texttt{htdocs}, \texttt{/var/www/html}). On y crée un sous-dossier par projet.
\item \textbf{Fichiers config} : \texttt{httpd.conf} (Apache, ports, vhosts), \texttt{php.ini} (PHP, extensions, limites), \texttt{my.ini/cnf} (MariaDB).
\item \textbf{Déploiement local} : 1) Créer BDD/user via phpMyAdmin, 2) Copier fichiers dans DocumentRoot/projet, 3) Configurer \texttt{PDO} (DSN, user, pass), 4) Tester \texttt{http://localhost/projet}, 5) Lire logs si erreur.
\item \textbf{Sécurité} : Config par défaut = \textbf{insécurisée} (root sans mdp, errors on, phpMyAdmin ouvert). \textbf{Jamais en production direct}.
\end{itemize}
\end{aretenir}

\coursec{Architecture d'un environnement intégré}

Dans la section précédente, nous avons découvert les environnements intégrés de développement web — EasyPHP, WampServer, XAMPP, LAMP — et compris pourquoi ils existent : installer séparément Apache, PHP et MySQL serait long et délicat pour un débutant, alors ces « paquets » regroupent tout en une seule installation. Mais une question demeure : \emph{que contient exactement un tel environnement, et comment ses composants coopèrent-ils pour afficher une page web dynamique ?} C'est toute l'architecture que nous allons maintenant démonter, brique par brique, comme un mécanicien qui ouvre le capot d'un moteur.

\courssub{Les trois éléments constitutifs}

Ouvre le panneau de contrôle de WampServer ou de XAMPP : tu y verras toujours les mêmes trois services. Ce n'est pas un hasard. Tout environnement intégré de développement web repose sur \cle{trois éléments constitutifs} complémentaires :

\begin{itemize}
\item un \cle{serveur web} : \textbf{Apache} (le plus répandu au monde) ;
\item un \cle{serveur de données} : \textbf{MySQL} ou son dérivé libre \textbf{MariaDB} ;
\item un \cle{préprocesseur} : \textbf{PHP}, l'interpréteur de scripts exécutés côté serveur.
\end{itemize}

C'est d'ailleurs de ces trois briques que viennent les noms des environnements : \textbf{WAMP} = Windows + Apache + MySQL + PHP, \textbf{LAMP} = Linux + Apache + MySQL + PHP, et le « X » de \textbf{XAMPP} signifie « multiplateforme » (Windows, Linux, macOS).

\begin{definition}[Préprocesseur]
Un \cle{préprocesseur} est un programme qui \textbf{interprète (exécute) des scripts côté serveur}, avant que la page ne soit envoyée au client. Dans nos environnements, le préprocesseur est \textbf{PHP} : il lit le code PHP contenu dans un fichier \texttt{.php}, l'exécute (calculs, accès à la base de données, tests, boucles) et produit en sortie du code \textbf{HTML pur}, qui est le seul langage que le navigateur sache afficher. Le préfixe « pré » indique que ce traitement a lieu \emph{avant} la livraison de la page au client.
\end{definition}

\courssub{Rôle du serveur web : Apache}

Imagine un restaurant. Le serveur (au sens restauration !) accueille les clients, prend les commandes et apporte les plats. \textbf{Apache} joue exactement ce rôle dans l'architecture web : c'est le \emph{maître d'hôtel} de ton application.

Concrètement, Apache remplit \cle{trois missions} :

\begin{enumerate}
\item \textbf{Recevoir les requêtes HTTP} envoyées par les navigateurs (par exemple « donne-moi la page \texttt{index.php} ») ;
\item \textbf{Servir directement les fichiers statiques} : pages \texttt{.html}, images \texttt{.png}/\texttt{.jpg}, feuilles de style \texttt{.css}, scripts \texttt{.js}. Ces fichiers n'ont pas besoin d'être transformés : Apache les lit sur le disque et les envoie tels quels ;
\item \textbf{Transmettre les scripts au préprocesseur} : lorsque le fichier demandé porte l'extension \texttt{.php}, Apache ne l'envoie \emph{pas} au client. Il le confie à PHP, attend le résultat (du HTML), puis envoie ce résultat au navigateur.
\end{enumerate}

\begin{propriete}[Page statique vs page dynamique — admise]
Une \cle{page statique} (fichier \texttt{.html}, image, CSS) est servie \textbf{directement par Apache}, sans aucune transformation : son contenu est identique pour tous les visiteurs. Une \cle{page dynamique} (fichier \texttt{.php}) \textbf{transite obligatoirement par le préprocesseur PHP} avant d'être servie : son contenu peut varier selon l'utilisateur, l'heure ou le contenu de la base de données.
\end{propriete}

\courssub{Rôle du préprocesseur PHP}

Pourquoi un préprocesseur ? Parce qu'une page dynamique doit être \emph{fabriquée sur mesure} au moment de la demande. Quand tu consultes ton relevé de notes sur la plateforme de ton lycée, la page affiche \emph{tes} notes, pas celles de ton voisin : quelqu'un doit aller chercher les bonnes données et assembler le HTML correspondant. Ce « quelqu'un », c'est PHP.

PHP \textbf{exécute les scripts côté serveur} : calculs, conditions, boucles, connexion à la base de données, puis \textbf{génère du HTML dynamique} qui sera renvoyé à Apache. Observons un script minimal :

\begin{lstlisting}[language=Php]
<?php
// Ce script est exécuté sur le serveur, jamais dans le navigateur
$eleve = "Amina";                       // donnée (souvent issue de MySQL)
$moyenne = 14.5;
echo "<h1>Bulletin de $eleve</h1>";     // génération de HTML
if ($moyenne >= 10) {
    echo "<p>Admise au trimestre.</p>";
} else {
    echo "<p>Redouble d'efforts.</p>";
}
?>
\end{lstlisting}

Le navigateur du client ne recevra \textbf{jamais} ce code PHP. Il recevra uniquement le HTML produit :

\begin{lstlisting}[language=HTML]
<h1>Bulletin de Amina</h1>
<p>Admise au trimestre.</p>
\end{lstlisting}

\begin{attention}[PHP ne s'exécute jamais dans le navigateur]
Piège classique du Bac et des débutants : croire que le client « voit » ou « exécute » le PHP. \textbf{PHP s'exécute côté serveur, toujours.} Le client ne reçoit que du HTML (plus éventuellement du CSS et du JavaScript, qui, eux, s'exécutent côté navigateur). Conséquence pratique : si tu ouvres un fichier \texttt{.php} en double-cliquant dessus (\texttt{file:///...}), le navigateur ne peut pas l'interpréter — il faut passer par le serveur via \texttt{http://localhost/...}. Autre conséquence : le code source PHP (identifiants de base de données, logique métier) reste invisible pour les visiteurs, ce qui est une protection naturelle.
\end{attention}

\courssub{Rôle du serveur de données : MySQL/MariaDB}

Revenons à notre restaurant : Apache est le maître d'hôtel, PHP est le cuisinier… mais où sont stockés les ingrédients ? Dans la réserve : c'est le \cle{serveur de données}.

\textbf{MySQL} (ou \textbf{MariaDB}, son équivalent libre installé par défaut dans les versions récentes de XAMPP) est un \textbf{système de gestion de bases de données} (SGBD). Son rôle est triple :

\begin{itemize}
\item \textbf{Stocker} les données de l'application de façon organisée et durable (tables d'élèves, de notes, de produits, de commandes…) ;
\item \textbf{Interroger} ces données grâce au langage \textbf{SQL} (\emph{Structured Query Language}) : \texttt{SELECT}, \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE} ;
\item \textbf{Gérer} les bases : droits d'accès, utilisateurs, sauvegardes, cohérence des données.
\end{itemize}

PHP ne manipule pas les fichiers de données directement : il envoie des \textbf{requêtes SQL} à MySQL, qui exécute la recherche et renvoie les résultats. Par exemple, la requête suivante récupère les élèves de Terminale TI :

\begin{lstlisting}[language=SQL]
-- Requête exécutée par le serveur MySQL/MariaDB
SELECT nom, moyenne
FROM eleves
WHERE classe = 'Terminale TI'
ORDER BY moyenne DESC;
\end{lstlisting}

Pour administrer les bases sans taper de commandes, les environnements intégrés fournissent \textbf{phpMyAdmin} : une \cle{interface web} (écrite en PHP, justement !) accessible à l'adresse \texttt{http://localhost/phpmyadmin}, qui permet de créer des bases et des tables, d'insérer des données et de tester des requêtes SQL à la souris.

\courssub{Chaîne complète de traitement d'une page dynamique}

Assemblons maintenant le puzzle. Que se passe-t-il, exactement, entre le moment où un élève tape \texttt{http://localhost/bulletin.php} et l'affichage de son bulletin ?

\begin{methode}[Les six étapes de traitement d'une page PHP]
\begin{enumerate}
\item Le \textbf{navigateur} envoie une requête HTTP \texttt{GET /bulletin.php} au serveur web ;
\item \textbf{Apache} reçoit la requête, repère l'extension \texttt{.php} et transmet le script au préprocesseur ;
\item \textbf{PHP} exécute le script ; celui-ci envoie une requête SQL au serveur de données ;
\item \textbf{MySQL/MariaDB} exécute la requête et renvoie les résultats (les notes de l'élève) à PHP ;
\item \textbf{PHP} assemble le HTML final (le bulletin mis en forme) et le rend à Apache ;
\item \textbf{Apache} envoie la réponse HTTP contenant le HTML au navigateur, qui l'affiche.
\end{enumerate}
\end{methode}

\courssub{Le répertoire racine (DocumentRoot)}

Jusqu'ici, nous avons vu \emph{comment} les composants traitent une requête. Reste une question essentielle : \emph{où} Apache cherche-t-il les fichiers sur le disque dur ? C'est le rôle du \cle{répertoire racine}, appelé \texttt{DocumentRoot} dans la configuration d'Apache.

\begin{definition}[Répertoire racine (DocumentRoot)]
Le \cle{DocumentRoot} est le \textbf{dossier physique sur le disque dur} qui correspond à la racine de l'espace web public (\texttt{/} dans l'URL). Tout fichier ou dossier placé à l'intérieur de ce répertoire devient accessible via une URL \texttt{http://localhost/...}. Les fichiers en dehors ne sont \emph{pas} accessibles par le navigateur (sécurité).
\end{definition}

\begin{exemplebox}[Emplacements typiques du DocumentRoot]
\begin{itemize}
\item \textbf{WampServer} : \texttt{C:\textbackslash wamp64\textbackslash www} (ou \texttt{C:\textbackslash wamp\textbackslash www} sur anciennes versions) ;
\item \textbf{XAMPP} : \texttt{C:\textbackslash xampp\textbackslash htdocs} ;
\item \textbf{Linux (LAMP)} : \texttt{/var/www/html}.
\end{itemize}
Si tu places un fichier \texttt{test.php} dans \texttt{www} (WampServer), tu y accèdes par \texttt{http://localhost/test.php}. Si tu crées un sous-dossier \texttt{projet}, l'URL devient \texttt{http://localhost/projet/}.
\end{exemplebox}

\courssub{Ports d'écoute et boucle locale}

Dernière pièce de l'architecture : comment plusieurs services cohabitent-ils sur la même machine sans se mélanger ? Ton PC fait tourner simultanément Apache et MySQL ; quand une requête arrive, comment le système sait-il si elle s'adresse à l'un ou à l'autre ? Réponse : grâce aux \cle{ports d'écoute}.

\begin{definition}[Port d'écoute]
Un \cle{port d'écoute} est un \textbf{numéro (de 0 à 65535) identifiant un service précis sur une machine}. Une adresse IP désigne la machine ; le port désigne le service au sein de cette machine. On dit qu'un serveur « écoute » sur un port lorsqu'il attend des connexions sur ce numéro. L'adresse complète d'un service s'écrit \texttt{IP:port}, par exemple \texttt{127.0.0.1:80}.
\end{definition}

Les numéros à connaître pour le Bac :

\begin{center}
\begin{tabularx}{\linewidth}{|l|c|X|}
\hline
\rowcolor{popblueL} \textbf{Service} & \textbf{Port par défaut} & \textbf{Rôle} \\
\hline
HTTP (Apache) & 80 & Pages web non chiffrées \\
\hline
HTTPS (Apache) & 443 & Pages web chiffrées (TLS) — complément utile au Bac \\
\hline
MySQL / MariaDB & 3306 & Connexions au serveur de bases de données \\
\hline
\end{tabularx}
\end{center}

\begin{exemplebox}[Exemple chiffré : changer de port]
Si le port 80 est déjà occupé (par Skype, IIS ou une autre instance d'Apache), on configure Apache pour écouter sur le port \textbf{8080}. L'URL \texttt{http://localhost:8080} interroge alors le serveur web local sur le port 8080 \emph{au lieu} du port 80. Sans le \texttt{:8080}, le navigateur interrogerait le port 80 par défaut et obtiendrait… une erreur de connexion. De même, PHP se connecte à MySQL en précisant \texttt{localhost:3306} (souvent implicite dans la configuration).
\end{exemplebox}

Reste une dernière question : quelle est l'adresse IP de « ta propre machine » ? Toute machine possède une adresse spéciale, l'\cle{adresse de boucle locale} \texttt{127.0.0.1}, associée au nom d'hôte \texttt{localhost}. Une requête envoyée à \texttt{127.0.0.1} ne sort jamais sur le réseau : elle « boucle » à l'intérieur de la machine. C'est ce qui rend possible l'hébergement local : ton navigateur et ton serveur Apache sont sur le même PC, et dialoguent via \texttt{http://localhost} ou \texttt{http://127.0.0.1}.

\begin{exoresolu}[Identifier les composants et les ports d'une architecture]
Énoncé. Une startup de Douala développe un site de vente en ligne avec XAMPP. Le site affiche le catalogue des produits stockés dans une base MariaDB. (a) Citer les trois briques de l'environnement et leur rôle. (b) Sur quels ports ces briques écoutent-elles par défaut ? (c) Décrire le trajet d'une requête lorsqu'un client consulte \texttt{catalogue.php}.
\tcblower
Solution. (a) Les trois briques sont : \textbf{Apache} (serveur web : reçoit les requêtes HTTP et sert les pages), \textbf{PHP} (préprocesseur : exécute les scripts et génère le HTML), \textbf{MariaDB} (serveur de données : stocke le catalogue et répond aux requêtes SQL). (b) Apache écoute sur le port \textbf{80} (HTTP, ou 443 en HTTPS) ; MariaDB écoute sur le port \textbf{3306}. (c) Le navigateur envoie la requête HTTP à Apache (1) ; Apache transmet \texttt{catalogue.php} à PHP (2) ; PHP interroge MariaDB en SQL (3) ; MariaDB renvoie les produits (4) ; PHP génère le HTML du catalogue (5) ; Apache renvoie la réponse au navigateur qui l'affiche (6).
\end{exoresolu}

\begin{experience}[Observer la chaîne de traitement en vrai]
\textbf{Objectif :} vérifier expérimentalement que PHP s'exécute côté serveur. \textbf{Matériel :} un PC avec WampServer ou XAMPP démarré (icône verte). \textbf{Manipulation :} (1) crée dans le répertoire racine (\texttt{www} ou \texttt{htdocs}) un fichier \texttt{test.php} contenant \texttt{<?php echo "Serveur OK : " . date("H:i:s"); ?>} ; (2) ouvre \texttt{http://localhost/test.php} dans le navigateur ; (3) affiche le code source de la page reçue (clic droit $\rightarrow$ « Code source de la page »). \textbf{Observations :} l'heure s'affiche et se met à jour à chaque rechargement ; le code source ne contient \emph{aucune} balise \texttt{<?php}, uniquement du texte HTML. \textbf{Interprétation :} PHP a exécuté le script sur le serveur (port 80 de \texttt{127.0.0.1}) et n'a transmis que le résultat. Essaie maintenant d'ouvrir le même fichier en double-cliquant : le navigateur affiche le code brut ou propose un téléchargement, preuve que sans serveur, pas d'exécution PHP.
\end{experience}

\begin{aretenir}[L'essentiel de l'architecture]
Un environnement intégré = \textbf{Apache} (serveur web, port 80/443, racine \texttt{DocumentRoot}) + \textbf{PHP} (préprocesseur, exécution côté serveur) + \textbf{MySQL/MariaDB} (serveur de données, port 3306, administré via phpMyAdmin). Une page statique est servie directement ; une page dynamique suit la chaîne navigateur $\rightarrow$ Apache $\rightarrow$ PHP $\rightarrow$ MySQL $\rightarrow$ PHP $\rightarrow$ Apache $\rightarrow$ navigateur. Le client ne reçoit que du HTML. En local, tout se passe sur la boucle locale \texttt{127.0.0.1} (\texttt{localhost}), chaque service étant identifié par son port d'écoute.
\end{aretenir}

Maintenant que l'architecture n'a plus de secret pour toi, la prochaine étape sera concrète : installer et configurer toi-même un environnement intégré, puis régler son fichier de configuration et son port d'écoute.

\coursec{Installation et configuration d'un environnement intégré}

Après avoir compris l'\emph{architecture} d'un environnement intégré (serveur web Apache, SGBD MySQL/MariaDB, préprocesseur PHP) et le rôle de chaque composant, nous allons maintenant passer à la pratique : \textbf{installer, configurer et valider} cet environnement sur votre machine. C'est l'étape où l'abstraction devient concrète : vous transformez votre ordinateur personnel en un véritable serveur de développement local.

\courssub{Choix de l'environnement : WampServer, XAMPP ou LAMP ?}

Au Cameroun, comme dans la majorité des lycées et centres de formation technique, trois solutions dominent selon le système d'exploitation : \textbf{WampServer} (Windows, développé par Romain Bourdon), \textbf{XAMPP} (multi-plateforme, Apache Friends) et \textbf{LAMP} (Linux, installation via gestionnaire de paquets). Les trois sont gratuits, open source pour les composants cœur, et fournissent une pile \textbf{AMP} (Apache, MySQL/MariaDB, PHP) prête à l'emploi.

\begin{propriete}[Critères de choix WampServer vs XAMPP vs LAMP]
\begin{itemize}
    \item \textbf{WampServer (Windows)} : Interface via une icône unique dans la zone de notification (systray). Gestion fine des versions multiples de PHP, Apache, MySQL via des menus contextuels. Idéal pour apprendre la gestion de versions (ex. : basculer de PHP 8.3 à 7.4 pour un vieux projet). Fichiers de configuration accessibles via menus. \textbf{Recommandé pour la Terminale TI} car il force à comprendre la notion de \emph{service Windows} et la gestion des versions, compétences exigées au Baccalauréat.
    \item \textbf{XAMPP (Windows/Linux/macOS)} : Panneau de contrôle graphique (\texttt{xampp-control.exe}) avec boutons \texttt{Start}/\texttt{Stop} explicites. Plus simple pour un premier démarrage. Inclut \texttt{FileZilla} (FTP), \texttt{Mercury} (Mail), \texttt{Tomcat} (Java) — souvent inutiles en TI. Dossier unique \texttt{C:\textbackslash xampp} par défaut.
    \item \textbf{LAMP (Linux - Ubuntu/Debian/Mint)} : Installation native via \texttt{sudo apt install apache2 mysql-server php php-mysql libapache2-mod-php phpmyadmin}. Pas d'interface graphique unifiée ; gestion via \texttt{systemctl} (services) et édition manuelle des fichiers \texttt{/etc/apache2/}, \texttt{/etc/php/}, \texttt{/etc/mysql/}. C'est l'environnement de \textbf{production} réel (serveurs CAMTEL, hébergeurs cloud).
    \item \textbf{EasyPHP} : Historiquement utilisé dans les lycées camerounais, mais moins maintenu et moins flexible sur la gestion des versions PHP récentes. À connaître pour la culture générale (cité au programme), mais WampServer ou XAMPP sont préférables aujourd'hui.
\end{itemize}
\end{propriete}

\courssub{Prérequis indispensables : les redistribuables Visual C++}

\begin{attention}[Le piège n°1 : DLL manquantes au lancement]
Avant même de télécharger WampServer ou XAMPP, votre Windows \textbf{doit} posséder les \emph{Visual C++ Redistributables} (VC++). Apache et PHP sont compilés avec Visual Studio ; sans ces bibliothèques partagées (\texttt{msvcrxxx.dll}, \texttt{vcruntimexxx.dll}), les services refusent de démarrer (icône WampServer bloquée à l'orange, erreur \texttt{0xc000007b} ou \texttt{The program can't start because VCRUNTIME140.dll is missing}).
\end{attention}

\begin{methode}[Installer les prérequis VC++ (à faire une seule fois)]
\begin{enumerate}
    \item Téléchargez \textbf{« Visual C++ Redistributable for Visual Studio 2015-2022 »} (architecture \texttt{x64} pour Windows 64 bits, \texttt{x86} si 32 bits) depuis le site officiel Microsoft (\texttt{learn.microsoft.com/fr-fr/cpp/windows/latest-supported-vc-redist}).
    \item Exécutez \texttt{vc\_redist.x64.exe} en \textbf{Administrateur} (clic droit $\to$ Exécuter en tant qu'administrateur).
    \item Acceptez la licence, installez, redémarrez l'ordinateur si demandé.
    \item \emph{Astuce avancée} : Installez aussi le pack communautaire « All in One » (disponible sur GitHub \texttt{abbodi1406/vcredist}) qui installe toutes les versions (2005 à 2022) d'un coup, utile pour d'anciens projets.
\end{enumerate}
\end{methode}

\courssub{Installation pas à pas de XAMPP (alternative Windows)}

\begin{methode}[Procédure d'installation de XAMPP]
\begin{enumerate}
    \item \textbf{Téléchargement} : Site officiel \texttt{apachefriends.org/download.html}. Prenez la version PHP 8.2+ (ex. \texttt{8.2.12}) pour Windows 64 bits.

\begin{attention}[Conflit de port 80 : l'icône bloquée à l'orange]
C'est \textbf{le} problème n°1 en TP. Si l'icône WampServer reste orange après \texttt{Start All Services}, c'est qu'Apache n'a pas pu s'accrocher au port \texttt{80} (HTTP) ou \texttt{443} (HTTPS).
\begin{itemize}
    \item \textbf{Coupables fréquents} : \textbf{Skype} (option « Utiliser les ports 80 et 443 » activée par défaut dans anciennes versions), \textbf{IIS} (Internet Information Services, serveur web Windows installé par défaut sur Windows Pro/Entreprise/Education), \textbf{VMware Workstation}, \textbf{TeamViewer}, \textbf{antivirus} (proxy HTTPS).
    \item \textbf{Diagnostic rapide} : Ouvrez \texttt{cmd} (Admin) $\to$ \texttt{netstat -ano | findstr :80}. Notez le \texttt{PID} (dernière colonne). Puis \texttt{tasklist | findstr <PID>} pour nommer le processus.
    \item \textbf{Résolution} :
    \begin{enumerate}
        \item Skype : Outils $\to$ Options $\to$ Avancé $\to$ Connexion $\to$ Décocher « Utiliser les ports 80 et 443 » $\to$ Redémarrer Skype.
        \item IIS : Panneau de configuration $\to$ Programmes $\to$ Activer/désactiver fonctionnalités Windows $\to$ Décocher « Services Internet (IIS) » $\to$ Redémarrer Windows.
        \item \textbf{Alternative sans désinstaller} : Changer le port d'écoute d'Apache (voir Section 5 : Fichier de configuration \texttt{httpd.conf}, directive \texttt{Listen 8080}).
    \end{enumerate}
\end{itemize}
\end{attention}

\courssub{Lancement automatique au démarrage de Windows (optionnel)}

Pour éviter de démarrer manuellement les services à chaque session, on peut les configurer en \textbf{Démarrage Automatique} (type de service Windows).

\begin{methode}[Configurer le démarrage automatique des services (WampServer)]
\begin{enumerate}
    \item Ouvrez \texttt{services.msc} (Win+R $\to$ \texttt{services.msc} $\to$ Entrée).
    \item Cherchez \texttt{wampapache64} et \texttt{wampmysqld64} (ou \texttt{wampmariadb64}).
    \item Clic droit sur chacun $\to$ \texttt{Propriétés} $\to$ \texttt{Type de démarrage} : \textbf{Automatique} (ou \textbf{Automatique (Différé)} pour ne pas ralentir le boot).
    \item Cliquez \texttt{Appliquer} $\to$ \texttt{OK}.

\begin{attention}[Démarrage auto et sécurité]
Sur un poste de développement personnel, le démarrage auto est confortable. Sur un poste partagé (salle TP, cybercafé) ou un serveur de production, \textbf{ne l'activez pas} : cela expose le port 80/3306 dès l'ouverture de session, sans votre contrôle conscient. Préférez le démarrage manuel (icône WampServer $\to$ Start All Services) qui ritue de vérifier l'état avant de coder.
\end{attention}

\courssub{Premier test de validation : le script \texttt{phpinfo()}}

Une page d'accueil WampServer/XAMPP qui s'affiche prouve qu'Apache sert des fichiers \emph{statiques} (HTML, CSS, images). Il reste à prouver que le \textbf{module PHP} est chargé et exécuté correctement par Apache.

\begin{exemplebox}[Créer et exécuter \texttt{info.php}]
\begin{enumerate}
    \item Ouvrez votre éditeur (VS Code, Notepad++).
    \item Créez un fichier nommé \texttt{info.php} (extension \textbf{.php} obligatoire).
    \item Collez ce code unique :
\begin{lstlisting}[language=Php]
<?php
// Fichier : info.php
// Objectif : Valider l'installation PHP + modules + configuration
// ATTENTION : Ne JAMAIS laisser ce fichier en production (faille infoleak massive)

phpinfo();
?>
\end{lstlisting}
    \item Enregistrez-le dans le \textbf{répertoire racine} (DocumentRoot) :
    \begin{itemize}
        \item WampServer : \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash info.php}
        \item XAMPP : \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash info.php}
    \end{itemize}
    \item Dans le navigateur : \texttt{http://localhost/info.php} (ou \texttt{http://127.0.0.1/info.php}).
    \item \textbf{Résultat attendu} : Une page violette/rose détaillée « PHP Version 8.x.x », tableaux \texttt{System}, \texttt{Build Date}, \texttt{Server API (Apache 2.0 Handler)}, \texttt{Configuration File (php.ini) Path}, modules \texttt{mysqli}, \texttt{pdo\_mysql}, \texttt{gd}, \texttt{curl}, \texttt{mbstring}, \texttt{openssl}, etc.
\end{enumerate}
\end{exemplebox}

\begin{savaistu}[Le rite de passage \texttt{phpinfo()}]
Depuis 1995 (PHP/FI 2.0), \texttt{phpinfo()} est \emph{le} premier script exécuté par tout développeur PHP. Il révèle la signature complète du serveur : version Zend Engine, directives \texttt{php.ini} (\texttt{memory\_limit}, \texttt{upload\_max\_filesize}, \texttt{post\_max\_size}, \texttt{date.timezone}), variables d'environnement \texttt{\_SERVER}, \texttt{\_ENV}. Au Cameroun, dans les cybercafés de Yaoundé ou Douala où l'on apprend le PHP « sur le tas », afficher cette page sur l'écran du gérant était la preuve qu'on avait « installé le serveur » correctement. Aujourd'hui encore, c'est le test d'acceptation standard avant d'écrire la première ligne de code métier.
\end{savaistu}

\begin{attention}[Danger \texttt{phpinfo()} en production]
\begin{itemize}
    \item \textbf{Faille de sécurité critique} : \texttt{phpinfo()} expose \textbf{tous} les secrets du serveur : chemins absolus, versions exactes (pour cibler exploits), variables d'environnement (parfois mots de passe BD, clés API), configuration \texttt{open\_basedir}, \texttt{disable\_functions}.
    \item \textbf{Règle d'or} : \textbf{Supprimez \texttt{info.php} immédiatement après validation} ou protégez-le par \texttt{.htaccess} (authentification basique) / restriction IP.
    \item En production, \texttt{disable\_functions = phpinfo} dans \texttt{php.ini} est recommandé.
\end{itemize}
\end{attention}

\begin{exoresolu}[Icône WampServer orange, page \texttt{localhost} inaccessible]
\textbf{Énoncé} : Après installation de WampServer 3.3.5 sur Windows 11 Pro, l'icône reste orange. \texttt{http://localhost} affiche « Impossible d'accéder au site ». \texttt{netstat -ano | findstr :80} retourne :
\begin{lstlisting}[language=bash]
TCP    0.0.0.0:80             0.0.0.0:0              LISTENING       4132
TCP    [::]:80                [::]:0                 LISTENING       4132
\end{lstlisting}
\texttt{tasklist | findstr 4132} retourne :
\begin{lstlisting}[language=bash]

\end{lstlisting}
\textbf{Diagnostiquez et résolvez.}

\tcblower
\textbf{Solution détaillée} :
\begin{enumerate}
    \item \textbf{Analyse} : Le port 80 est occupé par le PID 4132, processus \texttt{w3wp.exe} (Worker Process IIS). C'est le moteur d'applications d'\textbf{IIS (Internet Information Services)}, activé par défaut sur Windows 11 Pro/Entreprise.
    \item \textbf{Résolution définitive (recommandée pour poste dév)} : Désactiver IIS.

        \item Cliquer OK $\to$ Windows applique les changements $\to$ \textbf{Redémarrer l'ordinateur}.

Modifier \texttt{C:\textbackslash wamp64\textbackslash bin\textbackslash apache\textbackslash apache2.4.xx\textbackslash conf\textbackslash httpd.conf} : remplacer \texttt{Listen 80} par \texttt{Listen 8080} et \texttt{ServerName localhost:80} par \texttt{ServerName localhost:8080}. Redémarrer services WampServer. Accéder via \texttt{http://localhost:8080}.
    \item \textbf{Vérification post-fix} : Icône WampServer \textcolor{popgreen}{\textbf{verte}}. \texttt{http://localhost} affiche la page WampServer. \texttt{http://localhost/info.php} affiche la table PHP.
\end{enumerate}
\end{exoresolu}

\coursec{Répertoire racine et fichier de configuration}

Dans la section précédente, tu as installé WampServer (ou XAMPP), démarré les services et vérifié que l'icône passe au vert. Le serveur Apache tourne donc sur ta machine. Mais une question fondamentale se pose immédiatement : \emph{où faut-il placer les fichiers de ton site pour qu'ils soient accessibles via un navigateur ?} Et une seconde question, tout aussi pratique : \emph{comment modifier le comportement du serveur}, par exemple le port sur lequel il écoute ? Les réponses à ces deux questions tiennent en deux notions que tout développeur web doit maîtriser : le \cle{répertoire racine} (DocumentRoot) et le \cle{fichier de configuration} du serveur web. C'est l'objet de cette section.

\courssub{Le répertoire racine (DocumentRoot)}

\textbf{Intuition : le problème à résoudre.}\par
Imagine une startup doualaise qui développe une application de gestion de cybercafé. Sur le disque dur du développeur, il y a des milliers de fichiers : documents personnels, photos, factures, code source, etc. Le serveur web ne doit évidemment \emph{pas} exposer tout le disque dur aux visiteurs ! Il faut donc délimiter précisément \textbf{une zone du disque} — un dossier bien identifié — dont le contenu, et uniquement lui, sera servi aux clients HTTP. Cette zone, c'est le répertoire racine.

\begin{definition}[Répertoire racine (DocumentRoot)]
Le \cle{répertoire racine} d'un serveur web, appelé \cle{DocumentRoot} dans la terminologie d'Apache, est le dossier du disque dur dont le contenu (fichiers et sous-dossiers) est \textbf{exposé par le serveur web} aux clients qui s'y connectent. Tout fichier placé dans ce dossier (ou dans un de ses sous-dossiers) devient accessible via une URL ; tout fichier situé en dehors est invisible pour les visiteurs du site.
\end{definition}

\textbf{Emplacements par défaut selon l'environnement.}\par
Chaque environnement intégré choisit un emplacement par défaut pour son DocumentRoot. Il est indispensable de les connaître :

\begin{center}
\rowcolors{1}{popblueL}{white}
\begin{tabularx}{\linewidth}{|l|X|}
\hline
\rowcolor{popblue} \textcolor{white}{\textbf{Environnement}} & \textcolor{white}{\textbf{DocumentRoot par défaut}} \\
\hline
WampServer (Windows) & \texttt{C:\textbackslash wamp64\textbackslash www} \\
XAMPP (Windows) & \texttt{C:\textbackslash xampp\textbackslash htdocs} \\
LAMP (Linux Debian/Ubuntu) & \texttt{/var/www/html} \\
\hline
\end{tabularx}
\end{center}

\begin{attention}[Deux conventions d'écriture des chemins]
Sous Windows, les chemins utilisent la barre oblique inverse : \texttt{C:\textbackslash wamp64\textbackslash www}. Sous Linux, on utilise la barre oblique simple : \texttt{/var/www/html}. Dans le fichier de configuration d'Apache, on écrit souvent les chemins Windows avec des barres obliques simples (\texttt{C:/wamp64/www}), ce qui est accepté par Apache. Ne mélange pas les deux conventions dans un même chemin.
\end{attention}

\courssub{Correspondance entre URL et fichier sur le disque}

\textbf{Le principe fondamental.}\par
La règle qui relie une URL à un fichier est d'une simplicité remarquable : le serveur \textbf{concatène} le DocumentRoot avec le chemin demandé dans l'URL. Ainsi, si le DocumentRoot est \texttt{C:\textbackslash wamp64\textbackslash www}, alors :

\begin{center}
\rowcolors{1}{popgreenL}{white}
\begin{tabularx}{\linewidth}{|X|X|}
\hline
\rowcolor{popgreen} \textcolor{white}{\textbf{URL saisie dans le navigateur}} & \textcolor{white}{\textbf{Fichier réellement lu sur le disque}} \\
\hline
\texttt{http://localhost/} & \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash index.php} \\
\texttt{http://localhost/monsite/} & \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash monsite\textbackslash index.php} \\
\texttt{http://localhost/monsite/page.html} & \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash monsite\textbackslash page.html} \\
\texttt{http://localhost/monsite/img/logo.png} & \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash monsite\textbackslash img\textbackslash logo.png} \\
\hline
\end{tabularx}
\end{center}

\begin{propriete}[Règle de correspondance URL $\leftrightarrow$ fichier]
Pour un serveur dont le DocumentRoot est le dossier $D$, l'URL \texttt{http://localhost/chemin/fichier} correspond au fichier $D$\texttt{/chemin/fichier} sur le disque. Autrement dit :
\[ \text{fichier servi} = \text{DocumentRoot} + \text{chemin de l'URL} \]
Si l'URL désigne un dossier sans préciser de fichier, Apache cherche automatiquement un fichier \emph{d'index} dans ce dossier, par défaut \texttt{index.php} puis \texttt{index.html} (directive \texttt{DirectoryIndex}).
\end{propriete}

\end{popfigure}

\begin{exemplebox}[Créer son premier site local]
Pour tester la correspondance URL $\leftrightarrow$ fichier, crée le dossier \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash monsite}, puis places-y le fichier \texttt{index.html} suivant :
\begin{lstlisting}[language=HTML]
<!DOCTYPE html>
<html lang="fr">
<head>
    <meta charset="UTF-8">
    <title>Mon premier site local</title>
</head>
<body>
    <h1>Bienvenue sur monsite !</h1>
    <p>Ce fichier est servi par Apache depuis C:\wamp64\www\monsite.</p>
</body>
</html>
\end{lstlisting}
Ouvre ensuite ton navigateur à l'adresse \texttt{http://localhost/monsite/} : la page s'affiche. Tu viens d'héberger localement ton premier site.
\end{exemplebox}

\begin{attention}[Fichiers sensibles : le DocumentRoot est une vitrine publique]
Tout fichier placé dans le DocumentRoot est \textbf{potentiellement téléchargeable par n'importe quel visiteur}. Ne place donc \textbf{jamais} directement dans le DocumentRoot des fichiers contenant des mots de passe, des clés d'API (par exemple les identifiants d'une intégration MTN Mobile Money ou Orange Money) ou des sauvegardes de base de données, sans protection explicite (fichier \texttt{.htaccess}, déplacement hors du DocumentRoot, ou refus d'accès par configuration). Un fichier \texttt{config.php} est généralement protégé parce que son code PHP est exécuté et non affiché, mais sa copie de sauvegarde \texttt{config.php.bak}, elle, serait servie \emph{en clair} : piège classique !
\end{attention}

\courssub{Le fichier de configuration d'Apache : httpd.conf}

\textbf{Intuition.}\par
Un serveur web est un logiciel, et comme tout logiciel, son comportement est piloté par des paramètres : sur quel port écouter ? Où se trouve le DocumentRoot ? Quel nom de serveur annoncer ? Plutôt que de coder ces choix « en dur », Apache les lit au démarrage dans un fichier texte : le \cle{fichier de configuration}.

\begin{definition}[Fichier de configuration httpd.conf]
\texttt{httpd.conf} est le \cle{fichier de configuration principal} du serveur web Apache. C'est un fichier texte composé de \cle{directives} (instructions de la forme \texttt{Directive argument1 argument2...}) qu'Apache lit \textbf{au moment de son démarrage} pour fixer son comportement : port d'écoute, répertoire racine, modules chargés, etc.
\end{definition}

\textbf{Où le trouver ?} Deux accès possibles :
\begin{itemize}
  \item \textbf{Via le menu de l'environnement} (le plus simple) : clic gauche sur l'icône de WampServer dans la zone de notification, puis \texttt{Apache} $\rightarrow$ \texttt{httpd.conf}. Sous XAMPP : bouton \texttt{Config} en face d'Apache dans le panneau de contrôle.
  \item \textbf{Directement sur le disque} : \texttt{C:\textbackslash wamp64\textbackslash bin\textbackslash apache\textbackslash apache2.4.x\textbackslash conf\textbackslash httpd.conf} pour WampServer, \texttt{C:\textbackslash xampp\textbackslash apache\textbackslash conf\textbackslash httpd.conf} pour XAMPP, \texttt{/etc/apache2/apache2.conf} sous Debian/Ubuntu (LAMP).
\end{itemize}

\textbf{Les directives essentielles.}\par
Le fichier fait plusieurs centaines de lignes, mais trois directives suffisent pour l'essentiel de la configuration de base :

\begin{center}
\rowcolors{1}{popgoldL}{white}
\begin{tabularx}{\linewidth}{|l|X|}
\hline
\rowcolor{popgold} \textcolor{white}{\textbf{Directive}} & \textcolor{white}{\textbf{Rôle}} \\
\hline
\texttt{Listen 80} & Port TCP sur lequel Apache \textbf{écoute} les requêtes HTTP entrantes. \\
\texttt{DocumentRoot "..."} & Chemin du \textbf{répertoire racine} exposé par le serveur. \\
\texttt{ServerName localhost:80} & \textbf{Nom} (et port) sous lequel le serveur s'identifie. \\
\hline
\end{tabularx}
\end{center}

\begin{exemplebox}[Extrait annoté de httpd.conf]
\begin{lstlisting}
# =====================================================
#  Extrait du fichier httpd.conf (Apache)
#  Les lignes commençant par # sont des commentaires
# =====================================================

# Port d'écoute : Apache attend les requêtes HTTP
# sur le port TCP 80 (port standard du Web)
Listen 80

# Nom du serveur : utilisé pour se nommer lui-même
ServerName localhost:80

# Répertoire racine : dossier du disque exposé
# aux clients. C'est ici qu'on dépose les sites !
DocumentRoot "C:/wamp64/www"

# Droits d'accès appliqués au DocumentRoot
<Directory "C:/wamp64/www">
    Options Indexes FollowSymLinks
    AllowOverride All
    Require all granted
</Directory>
\end{lstlisting}
Les deux lignes à retenir absolument : \texttt{Listen 80} (le port d'écoute) et \texttt{DocumentRoot "C:/wamp64/www"} (le répertoire racine). Le bloc \texttt{<Directory>} précise les droits d'accès appliqués à ce dossier.
\end{exemplebox}

\courssub{Modifier le port d'écoute d'Apache}

\textbf{Pourquoi changer de port ?}\par
Le port 80 est le port standard du protocole HTTP. Mais il arrive qu'il soit \textbf{déjà occupé} par un autre logiciel (IIS de Windows, Skype, un autre serveur web, un service de l'administration CENADI sur un poste mutualisé...). Dans ce cas, Apache refuse de démarrer et l'icône de WampServer reste bloquée à l'orange. La solution : faire écouter Apache sur un autre port, par exemple \textbf{8080}.

\begin{methode}[Changer le port d'écoute d'Apache en 4 étapes]
\begin{enumerate}
  \item \textbf{Ouvrir} le fichier \texttt{httpd.conf} (icône WampServer $\rightarrow$ \texttt{Apache} $\rightarrow$ \texttt{httpd.conf}) dans un éditeur de texte.
  \item \textbf{Modifier} la directive \texttt{Listen} : remplacer \texttt{Listen 80} par \texttt{Listen 8080}. Adapter aussi \texttt{ServerName localhost:80} en \texttt{ServerName localhost:8080} pour rester cohérent.
  \item \textbf{Sauvegarder} le fichier (Ctrl+S) puis fermer l'éditeur.
  \item \textbf{Redémarrer} le service Apache (icône WampServer $\rightarrow$ \texttt{Redémarrer tous les services}, ou bouton \texttt{Stop} puis \texttt{Start} sous XAMPP). L'icône doit repasser au vert.
\end{enumerate}
Le site est désormais accessible à l'adresse \texttt{http://localhost:8080}.
\end{methode}

\begin{exemplebox}[Exemple chiffré : avant et après le changement de port]
Supposons \texttt{Listen 8080} dans \texttt{httpd.conf} et Apache redémarré.
\begin{itemize}
  \item \texttt{http://localhost} (sans port) $\rightarrow$ le navigateur tente le port \textbf{80} par défaut : \textbf{aucune réponse}, erreur « site inaccessible », car Apache n'écoute plus sur ce port.
  \item \texttt{http://localhost:8080} $\rightarrow$ le navigateur contacte le port \textbf{8080} : la page d'accueil s'affiche correctement.
  \item \texttt{http://localhost:8080/monsite/} $\rightarrow$ affiche le fichier \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash monsite\textbackslash index.php}.
\end{itemize}
Règle pratique : dès que le port n'est pas 80, il faut l'\textbf{écrire explicitement} dans l'URL, après deux-points.
\end{exemplebox}

\begin{attention}[L'erreur n°1 : oublier de redémarrer Apache]
Apache lit \texttt{httpd.conf} \textbf{une seule fois, à son démarrage}. Toute modification du fichier de configuration n'a donc \textbf{aucun effet} tant que le service n'a pas été redémarré : l'ancienne configuration reste active en mémoire. C'est l'erreur la plus fréquente des débutants (et une question classique au Baccalauréat !) : tu modifies \texttt{Listen}, tu sauvegardes, tu recharges la page... et rien ne change. Réflexe à acquérir : \textbf{modifier $\rightarrow$ sauvegarder $\rightarrow$ redémarrer $\rightarrow$ tester}.
\end{attention}

\begin{experience}[TP guidé : reconfigurer le port d'écoute de WampServer]
\textbf{Objectif} : faire écouter Apache sur le port 8080 et vérifier la prise en compte de la configuration.\par
\textbf{Matériel} : un poste Windows avec WampServer installé et fonctionnel (icône verte).\par
\textbf{Manipulation} :
\begin{enumerate}
  \item Vérifie d'abord que \texttt{http://localhost} affiche la page d'accueil de WampServer.
  \item Ouvre \texttt{httpd.conf} via le menu de WampServer et repère la ligne \texttt{Listen 80} (raccourci Ctrl+F).
  \item Remplace-la par \texttt{Listen 8080}, sauvegarde, mais \textbf{ne redémarre pas encore} : recharge \texttt{http://localhost} et observe que l'ancienne configuration est toujours active.
  \item Redémarre tous les services depuis l'icône de WampServer et attends le retour à l'icône verte.
  \item Teste \texttt{http://localhost} : constate l'échec. Teste ensuite \texttt{http://localhost:8080} : la page s'affiche.
\end{enumerate}
\textbf{Observations et interprétation} : avant redémarrage, la modification est lettre morte ; après redémarrage, Apache écoute exclusivement sur le port 8080, ce qui impose de suffixer l'URL par \texttt{:8080}. Ce TP illustre concrètement le cycle \emph{configuration $\rightarrow$ redémarrage $\rightarrow$ prise d'effet}.
\end{experience}

\begin{exoresolu}[Diagnostiquer un conflit de port]
\textbf{Énoncé.} Sur le poste d'un élève, l'icône de WampServer reste orange. Le test du port 80 (menu Apache $\rightarrow$ Service $\rightarrow$ Tester le port 80) indique que le port est utilisé par un autre programme. L'élève souhaite faire fonctionner son site \texttt{monsite} situé dans \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash monsite}. Décris la solution complète et donne l'URL finale à saisir.
\tcblower
\textbf{Solution détaillée.} Le port 80 étant occupé, on fait écouter Apache sur un port libre, par exemple 8080 :
\begin{enumerate}
  \item Ouvrir \texttt{httpd.conf} (icône WampServer $\rightarrow$ Apache $\rightarrow$ \texttt{httpd.conf}).
  \item Remplacer \texttt{Listen 80} par \texttt{Listen 8080} et \texttt{ServerName localhost:80} par \texttt{ServerName localhost:8080}.
  \item Sauvegarder le fichier.
  \item Redémarrer tous les services : l'icône passe au vert, preuve qu'Apache a démarré.
\end{enumerate}
L'URL finale à saisir dans le navigateur est : \texttt{http://localhost:8080/monsite/}. Le serveur concatène alors le DocumentRoot (\texttt{C:\textbackslash wamp64\textbackslash www}) avec le chemin \texttt{/monsite/} et sert le fichier d'index du dossier.
\end{exoresolu}

\begin{aretenir}[L'essentiel de la section]
\begin{itemize}
  \item Le \cle{DocumentRoot} est le dossier du disque exposé par le serveur web : \texttt{C:\textbackslash wamp64\textbackslash www} (WampServer), \texttt{C:\textbackslash xampp\textbackslash htdocs} (XAMPP), \texttt{/var/www/html} (LAMP).
  \item Correspondance fondamentale : \texttt{http://localhost/chemin/fichier} $\leftrightarrow$ \texttt{DocumentRoot/chemin/fichier}.
  \item \texttt{httpd.conf} est le fichier de configuration d'Apache ; directives clés : \texttt{Listen} (port d'écoute), \texttt{DocumentRoot} (répertoire racine), \texttt{ServerName} (nom du serveur).
  \item Toute modification de \texttt{httpd.conf} exige un \textbf{redémarrage} du service Apache pour être prise en compte.
  \item Avec \texttt{Listen 8080}, l'accès se fait obligatoirement via \texttt{http://localhost:8080}.
  \item Ne jamais exposer de fichiers sensibles non protégés dans le DocumentRoot.
\end{itemize}
\end{aretenir}

  \item Un administrateur du CENADI configure Apache avec \texttt{Listen 8000}. Quelle URL un usager doit-il saisir pour atteindre la page d'accueil ? Justifie.
  \item Cite, dans l'ordre, les quatre étapes à suivre pour changer le port d'écoute d'Apache, et explique pourquoi la dernière est indispensable.
\end{enumerate}
\end{exercice}

\begin{corrige}[Exercice n°1]
\begin{enumerate}
  \item Sous XAMPP, le DocumentRoot est \texttt{C:\textbackslash xampp\textbackslash htdocs}. Le chemin d'URL \texttt{/lycee/notes.html} se traduit par le chemin disque \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash lycee\textbackslash notes.html}. Il faut donc créer le dossier \texttt{lycee} dans \texttt{htdocs} et y placer le fichier.
  \item L'URL est \texttt{http://localhost:8000} (ou l'adresse IP du serveur suivie de \texttt{:8000}). Le port 8000 n'étant pas le port HTTP standard (80), il doit figurer explicitement dans l'URL, sinon le navigateur interroge le port 80 où rien n'écoute.
  \item (1) Ouvrir \texttt{httpd.conf} ; (2) modifier la directive \texttt{Listen} ; (3) sauvegarder ; (4) redémarrer le service Apache. La dernière étape est indispensable car Apache ne lit sa configuration qu'au démarrage : sans redémarrage, l'ancienne configuration reste active en mémoire.
\end{enumerate}
\end{corrige}

\coursec{Hébergement local et déploiement d'une application}

Dans la section précédente, nous avons appris à localiser le \cle{répertoire racine} (\texttt{DocumentRoot}) et à modifier le \cle{fichier de configuration} d'Apache, notamment son port d'écoute. Nous disposons donc maintenant d'un serveur web correctement installé et configuré. Il reste la question finale, celle qui donne tout son sens à ce cours : \emph{comment faire vivre concrètement une application web sur ce serveur ?} C'est l'objet de cette dernière section : décrire la \cle{procédure d'hébergement local} d'un site, du dépôt des fichiers jusqu'au test dans le navigateur, puis ouvrir la perspective vers l'\cle{hébergement distant} chez un professionnel.

\courssub{Procédure complète d'hébergement local d'un site}

\textbf{Intuition.} Héberger localement un site, c'est comme ouvrir un restaurant chez soi avant d'ouvrir une vraie salle en ville : on installe la cuisine (l'environnement intégré), on allume les fourneaux (les services), on range les plats dans la salle (les fichiers dans le \texttt{DocumentRoot}), on prépare la réserve (la base de données), puis on invite un client à goûter (le navigateur). Tant que tout fonctionne à la maison, on peut corriger tranquillement les erreurs sans que personne ne les voie.

\begin{definition}[Hébergement local]
L'\cle{hébergement local} consiste à installer et exécuter une application web sur le serveur web de sa propre machine, accessible via l'adresse \texttt{http://localhost} (ou \texttt{http://127.0.0.1}), sans passer par Internet. On parle aussi de \emph{serveur de test} ou d'\emph{environnement de préproduction}.
\end{definition}

\begin{methode}[Procédure type d'hébergement local d'un site dynamique — à connaître pour le Bac]
Pour héberger localement un site dynamique (HTML/PHP + base de données), on suit rigoureusement les étapes suivantes :
\begin{enumerate}
  \item \textbf{Installer} un environnement intégré de développement web (WampServer, XAMPP, EasyPHP) ;
  \item \textbf{Démarrer les services} (Apache et MySQL/MariaDB) depuis l'icône de l'environnement et vérifier que l'icône passe au vert ;
  \item \textbf{Copier les fichiers du site} (pages \texttt{.php}, \texttt{.html}, images, CSS, JavaScript) dans un sous-dossier du répertoire racine, par exemple \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash mon\_site} (WampServer) ou \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash mon\_site} (XAMPP) ;
  \item \textbf{Créer et importer la base de données} via phpMyAdmin (\texttt{http://localhost/phpmyadmin}) ;
  \item \textbf{Adapter les identifiants de connexion} à la base dans le code de l'application (hôte, utilisateur, mot de passe, nom de la base) ;
  \item \textbf{Tester} l'application dans le navigateur en saisissant \texttt{http://localhost/mon\_site} et corriger les erreurs éventuelles.
\end{enumerate}
\end{methode}

\courssub{Démarrage d'une application hébergée et rôle du fichier index}

Une fois les fichiers copiés dans le répertoire racine, le démarrage de l'application est d'une simplicité déconcertante : il suffit d'ouvrir un navigateur et de saisir l'URL pointant vers le dossier de l'application :

\begin{center}
\texttt{http://localhost/monapplication}
\end{center}

Le navigateur envoie une requête HTTP au serveur Apache, qui cherche le dossier \texttt{monapplication} dans son \texttt{DocumentRoot}. Mais une question se pose : un dossier contient souvent des dizaines de fichiers ; lequel Apache doit-il afficher ?

\begin{propriete}[Fichier d'index : page chargée par défaut]
Lorsqu'une URL désigne un \emph{dossier} et non un fichier précis, le serveur web recherche automatiquement, dans un ordre configurable (directive \texttt{DirectoryIndex} d'Apache), un \cle{fichier d'index} : typiquement \texttt{index.php}, puis \texttt{index.html}. Le premier trouvé est exécuté (s'il s'agit de PHP) puis envoyé au navigateur. Si aucun fichier d'index n'existe, Apache affiche, selon sa configuration, la liste des fichiers du dossier ou une erreur \emph{403 Forbidden}.
\end{propriete}

\begin{attention}[Piège classique : le fichier d'index mal nommé]
Si ta page d'accueil s'appelle \texttt{accueil.php} ou \texttt{Index.php} avec une majuscule sur un serveur Linux (sensible à la casse), Apache ne la trouvera pas et affichera la liste des fichiers du dossier — ce qui est à la fois inesthétique et dangereux pour la sécurité, car n'importe qui peut alors explorer tes fichiers. Nomme toujours ta page d'entrée \texttt{index.php} ou \texttt{index.html}, en minuscules.
\end{attention}

\courssub{Import de la base de données et connexion de l'application}

Un site dynamique sans sa base de données est comme un élève sans son cahier de notes : l'application démarre, mais elle ne retrouve aucune information. Le développeur livre généralement sa base sous forme d'un \cle{fichier d'export SQL} (extension \texttt{.sql}), qui contient les instructions \texttt{CREATE TABLE}, \texttt{INSERT}, etc.

\begin{methode}[Importer une base de données avec phpMyAdmin]
\begin{enumerate}
  \item Ouvrir le navigateur et saisir \texttt{http://localhost/phpmyadmin} ;
  \item Cliquer sur l'onglet \textbf{Bases de données}, saisir le nom de la base (par exemple \texttt{gestion\_notes}), choisir l'interclassement \texttt{utf8mb4\_general\_ci} (recommandé pour le support complet d'Unicode, y compris les émojis), puis cliquer sur \textbf{Créer} ;
  \item Sélectionner la base nouvellement créée dans la colonne de gauche ;
  \item Cliquer sur l'onglet \textbf{Importer}, puis sur \textbf{Choisir un fichier} et sélectionner le fichier \texttt{.sql} fourni avec l'application ;
  \item Laisser le format \textbf{SQL} et cliquer sur \textbf{Exécuter} ;
  \item Vérifier que les tables apparaissent dans la colonne de gauche et que les données sont présentes (onglet \textbf{Afficher}).
\end{enumerate}
\end{methode}

Reste alors à \emph{brancher} l'application sur cette base. En PHP, la connexion s'écrit typiquement avec l'extension PDO (PHP Data Objects), qui est la méthode moderne, portable et sécurisée (préparation des requêtes) :

\begin{lstlisting}[language=Php]
<?php
// connexion.php : connexion de l'application a la base de donnees
$hote        = "localhost";       // le serveur MySQL/MariaDB est sur la meme machine
$utilisateur = "root";            // utilisateur par defaut de WampServer / XAMPP
$motdepasse  = "";                // mot de passe vide par defaut en local
$base        = "gestion_notes";   // nom de la base creee dans phpMyAdmin

try {
    // DSN : mysql:host=...;dbname=...;charset=utf8mb4
    $bdd = new PDO("mysql:host=$hote;dbname=$base;charset=utf8mb4",
                   $utilisateur, $motdepasse);
    // Mode d'erreur : exceptions (permettent un try/catch propre)
    $bdd->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
    // Mode de fetch par defaut : tableau associatif (plus lisible que FETCH_BOTH)
    $bdd->setAttribute(PDO::ATTR_DEFAULT_FETCH_MODE, PDO::FETCH_ASSOC);
} catch (PDOException $e) {
    // En production, on loguerait l'erreur au lieu de l'afficher (securite)
    die("Erreur de connexion a la base : " . $e->getMessage());
}
?>
\end{lstlisting}

\begin{attention}[Adapter les identifiants lors du passage chez un hébergeur]
Le trio \texttt{localhost} / \texttt{root} / mot de passe vide ne fonctionne \textbf{qu'en local}. Chez un hébergeur professionnel, celui-ci te fournit ses propres identifiants : un nom d'hôte (parfois différent de \texttt{localhost}, ex. \texttt{sql.monhebergeur.cm}), un utilisateur du type \texttt{c12345\_notes} et un mot de passe obligatoire. Si tu oublies de modifier le fichier de connexion, l'application affichera une erreur de connexion à la base. Bonne pratique : regrouper ces identifiants dans un seul fichier (comme \texttt{connexion.php} ci-dessus) inclus partout via \texttt{require\_once}, pour ne les modifier qu'à un seul endroit lors du déploiement.
\end{attention}

\courssub{Exemple guidé : déployer un mini-site de gestion des notes}

\begin{exemplebox}[Déploiement complet d'un site de gestion des notes sous WampServer]
Un élève de Terminale TI a développé un mini-site de gestion des notes de sa classe. Voici son déploiement local :
\begin{enumerate}
  \item Il démarre WampServer ; l'icône passe au vert (Apache et MySQL/MariaDB actifs) ;
  \item Il copie le dossier du projet dans \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash gestion\_notes} ; ce dossier contient \texttt{index.php}, \texttt{eleves.php}, \texttt{connexion.php} et un sous-dossier \texttt{css} ;
  \item Dans phpMyAdmin, il crée la base \texttt{gestion\_notes} (interclassement \texttt{utf8mb4\_general\_ci}) et importe le fichier \texttt{gestion\_notes.sql} (tables \texttt{eleve}, \texttt{matiere}, \texttt{note}) ;
  \item Il vérifie que \texttt{connexion.php} utilise \texttt{localhost}, \texttt{root}, mot de passe vide, et \texttt{charset=utf8mb4} ;
  \item Il ouvre son navigateur et saisit \texttt{http://localhost/gestion\_notes} : Apache exécute automatiquement \texttt{index.php}, qui affiche la liste des élèves avec leurs moyennes.
\end{enumerate}
Le site est désormais \textbf{hébergé localement} : il fonctionne même sans connexion Internet, puisque tout se passe sur sa machine.
\end{exemplebox}

\courssub{Test et débogage : comprendre les erreurs fréquentes}

Tester, c'est chercher volontairement les fautes avant que les utilisateurs ne les trouvent. Trois symptômes reviennent sans cesse :

\begin{center}
\begin{tabularx}{\linewidth}{|l|X|X|}
\hline
\rowcolor{popblueL} \textbf{Symptôme} & \textbf{Cause probable} & \textbf{Remède} \\
\hline
Erreur 404 (Not Found) & Fichier ou dossier absent du \texttt{DocumentRoot}, faute de frappe dans l'URL (casse) & Vérifier le chemin exact et l'orthographe (respecter la casse) \\
\hline
Page blanche & Erreur de syntaxe PHP ou erreur fatale non affichée (\texttt{display\_errors=Off}) & Activer \texttt{display\_errors = On} dans \texttt{php.ini} (via menu WampServer) et \texttt{error\_reporting = E\_ALL}, redémarrer Apache, ou consulter \texttt{php\_error.log} \\
\hline
« Access denied » / Erreur connexion PDO & Mauvais identifiants MySQL, base non créée, service MySQL arrêté, ou mauvais hôte & Vérifier \texttt{connexion.php}, l'icône WampServer (MySQL vert), l'import de la base \\
\hline
Liste des fichiers affichée & Aucun \texttt{index.php} / \texttt{index.html} dans le dossier visé & Ajouter un fichier d'index (ex. \texttt{index.php}) en minuscules \\
\hline
\end{tabularx}
\end{center}

\begin{exoresolu}[Diagnostic d'une page blanche]
\textbf{Énoncé.} Après avoir copié son site dans \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash biblio}, un élève saisit \texttt{http://localhost/biblio} et obtient une page totalement blanche, sans aucun message. Identifier la démarche de diagnostic et la cause la plus probable si le fichier \texttt{index.php} contient la ligne : \texttt{\$bdd = new PDO("mysql:host=localhost;dbname=biblio;charset=utf8mb4", "root", "")} alors que la base n'a pas encore été importée.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
  \item Une page blanche signifie qu'une erreur PHP s'est produite mais que l'affichage des erreurs est désactivé (configuration par défaut de certains packs ou \texttt{php.ini} de production). On ouvre donc \texttt{php.ini} (via l'icône WampServer > PHP > php.ini) et on vérifie que \texttt{display\_errors = On} et \texttt{error\_reporting = E\_ALL}, puis on redémarre Apache (clic gauche > Redémarrer les services). On peut aussi consulter directement le fichier \texttt{C:\textbackslash wamp64\textbackslash logs\textbackslash php\_error.log}.
  \item Après rechargement de la page, le message d'erreur apparaît : \emph{SQLSTATE[HY000] [1049] Unknown database 'biblio'}.
  \item Diagnostic : la connexion au serveur MySQL fonctionne (hôte \texttt{localhost}, utilisateur \texttt{root}, mot de passe vide corrects), mais la base \texttt{biblio} n'existe pas car le fichier \texttt{biblio.sql} n'a pas été importé dans phpMyAdmin.
  \item Correction : créer la base \texttt{biblio} dans phpMyAdmin (interclassement \texttt{utf8mb4\_general\_ci}), importer le fichier \texttt{biblio.sql}, puis recharger la page \texttt{http://localhost/biblio}. Le site s'affiche normalement.
\end{enumerate}
\end{exoresolu}

\begin{experience}[TP : héberger localement un site dynamique complet]
\textbf{Objectif :} mettre en œuvre la procédure complète d'hébergement local.\par
\textbf{Matériel :} un poste Windows avec WampServer (ou XAMPP) installé, un dossier de site contenant \texttt{index.php}, \texttt{connexion.php} et un fichier \texttt{site.sql}.\par
\textbf{Manipulation :}
\begin{enumerate}
  \item Lancer WampServer et attendre l'icône verte (services Apache et MySQL démarrés) ;
  \item Copier le dossier du site dans \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash} (ou \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash}) ;
  \item Ouvrir \texttt{http://localhost/phpmyadmin}, créer la base (interclassement \texttt{utf8mb4\_general\_ci}), importer \texttt{site.sql} ;
  \item Ouvrir \texttt{connexion.php} dans un éditeur de code (VS Code, Notepad++) et vérifier les quatre paramètres de connexion (\texttt{localhost}, \texttt{root}, \texttt{""}, nom de la base) ;
  \item Saisir \texttt{http://localhost/nom\_du\_dossier} dans le navigateur ;
  \item Provoquer volontairement une erreur (modifier le nom de la base dans \texttt{connexion.php} par un nom inexistant), observer l'exception PDO affichée, puis corriger.
\end{enumerate}
\textbf{Observations attendues :} le site s'affiche correctement après l'étape 5 ; l'étape 6 produit une erreur \texttt{PDOException : SQLSTATE[HY000] [1049] Unknown database '...'} explicite.\par
\textbf{Interprétation :} l'hébergement local repose sur la cohérence de trois piliers : les fichiers au bon endroit (\texttt{DocumentRoot}), la base importée et structurellement identique au code, et les identifiants de connexion exacts dans le fichier de configuration.
\end{experience}

\courssub{Ouverture : de l'hébergement local à l'hébergement distant}

L'hébergement local est parfait pour développer, mais ton site n'est visible que sur ta machine (ou ton réseau local si configuré). Pour le rendre accessible au monde entier — par exemple le site d'une startup doualaise ou la plateforme de notes d'un lycée —, il faut le \cle{déployer} chez un \cle{hébergeur web}. La procédure reprend les mêmes étapes, transposées :

\begin{enumerate}
  \item \textbf{Souscrire} à une offre d'hébergement (mutualisé, VPS, cloud) ; l'hébergeur fournit un espace disque, une base MySQL/MariaDB et des identifiants (FTP, base de données, panneau de contrôle) ;
  \item \textbf{Transférer les fichiers} du site vers le serveur distant à l'aide d'un client \cle{FTP} (FileZilla, WinSCP) ou \cle{SFTP}, en utilisant l'hôte, l'identifiant et le mot de passe FTP fournis ; les fichiers sont déposés dans le répertoire racine distant (souvent \texttt{public\_html}, \texttt{www} ou \texttt{htdocs}) ;
  \item \textbf{Exporter la base locale} depuis phpMyAdmin (onglet \emph{Exporter}, format SQL, option \emph{Structure et données}) puis l'\textbf{importer} dans la base de l'hébergeur via son phpMyAdmin distant (ou Adminer) ;
  \item \textbf{Adapter le fichier de connexion} (\texttt{connexion.php}) avec les identifiants fournis par l'hébergeur (hôte SQL distant, utilisateur préfixé, mot de passe fort, nom de base préfixé) ;
  \item \textbf{Tester} le site en ligne via le nom de domaine (ex. \texttt{http://www.monlycee.cm}) et vérifier les logs en cas d'erreur.
\end{enumerate}

\begin{savaistu}[Pourquoi les professionnels testent d'abord en local]
La quasi-totalité des développeurs professionnels — y compris dans les startups tech de Douala (Silicon Mountain) et Yaoundé — testent leurs applications en local (ou sur un serveur de \emph{préproduction} / \emph{staging}) avant toute mise en ligne. Exposer directement au public une application non testée, c'est risquer d'afficher des messages d'erreur qui révèlent la structure de la base de données, les chemins du serveur ou des secrets de configuration : une aubaine pour les cyberattaquants. La règle d'or du métier est donc : \emph{on développe en local, on teste en local, on ne déploie en production que du code validé et sécurisé}.
\end{savaistu}

\begin{aretenir}[Synthèse de la section]
\begin{itemize}
  \item Héberger localement un site dynamique suit six étapes : installer l'environnement, démarrer les services (Apache, MySQL/MariaDB), copier les fichiers dans le \texttt{DocumentRoot}, créer et importer la base via phpMyAdmin (interclassement \texttt{utf8mb4\_general\_ci}), adapter les identifiants de connexion (PDO), tester dans le navigateur ;
  \item On démarre une application via \texttt{http://localhost/monapplication} ; le serveur charge automatiquement \texttt{index.php} ou \texttt{index.html} (directive \texttt{DirectoryIndex}) ;
  \item En local, la connexion PDO utilise typiquement \texttt{localhost} / \texttt{root} / mot de passe vide / \texttt{charset=utf8mb4} ; ces identifiants \textbf{doivent} être remplacés par ceux de l'hébergeur lors de la mise en ligne ;
  \item Le déploiement distant reprend la même logique : transfert des fichiers par \cle{FTP}/\cle{SFTP}, export puis import de la base, adaptation de la configuration (\texttt{connexion.php}), test via le nom de domaine (HTTPS recommandé).
\end{itemize}
\end{aretenir}

\begin{exercice}[À toi de jouer]
Ton ami a copié son site dans \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash cybercafe} et a importé sa base, mais \texttt{http://localhost/cybercafe} affiche la liste des fichiers du dossier au lieu de la page d'accueil. De plus, un clic sur \texttt{membres.php} produit l'erreur \emph{SQLSTATE[HY000] [1045] Access denied for user 'root'@'localhost' (using password: YES)}. Propose un diagnostic complet et les corrections à apporter.
\end{exercice}

\begin{corrige}[Exercice 1]
Deux problèmes distincts se superposent :
\begin{enumerate}
  \item \textbf{Liste des fichiers affichée} : le dossier \texttt{cybercafe} ne contient aucun fichier d'index (\texttt{index.php} ou \texttt{index.html}). Apache affiche donc l'index du répertoire (configuration par défaut \texttt{Options Indexes}).
  \item \textbf{Correction} : renommer la page d'accueil en \texttt{index.php} (en minuscules, respect de la casse) ou créer un \texttt{index.php} qui inclut/redirige vers la page voulue.
  \item \textbf{Access denied (using password: YES)} : le message \texttt{(using password: YES)} indique qu'un mot de passe a été fourni dans \texttt{connexion.php} pour l'utilisateur \texttt{root}, or sous XAMPP (comme sous WampServer), l'utilisateur \texttt{root} n'a \textbf{pas de mot de passe} par défaut (chaîne vide \texttt{""}).
  \item \textbf{Correction} : ouvrir \texttt{connexion.php}, mettre \texttt{\$motdepasse = "";} (chaîne vide), vérifier que \texttt{\$hote = "localhost";}, \texttt{\$utilisateur = "root";} et que \texttt{\$base} correspond exactement au nom de la base importée. Vérifier aussi que le service MySQL est bien "Running" dans le panneau de contrôle XAMPP.
\end{enumerate}
Après corrections, recharger \texttt{http://localhost/cybercafe} : la page d'accueil (\texttt{index.php}) s'affiche et la page \texttt{membres.php} accède normalement aux données.
\end{corrige}

\courssub{Objectifs de l'activité}

À l'issue de cette activité d'intégration, tu seras capable de mobiliser \emph{simultanément} l'ensemble des savoir-faire de la leçon dans une situation professionnelle réaliste :

\item créer une base de données via phpMyAdmin et y importer un script SQL ;

Cette activité te place dans la peau d'un technicien en herbe : tu ne récites pas des définitions, tu \emph{fais fonctionner} un serveur, comme le ferait l'équipe technique d'une vraie entreprise camerounaise.

\courssub{Situation}

\textbf{Cybercafé 2.0 : héberger localement le site de la coopérative.}

La coopérative des producteurs de café de Bafoussam (Ouest-Cameroun), qui regroupe 120 exploitants, souhaite moderniser sa vitrine. Elle a fait développer par un stagiaire un petit site dynamique présentant ses produits (café arabica, café robusta, miel de montagne, huile de palme). Avant de payer un hébergeur web professionnel, le président de la coopérative veut d'abord \textbf{tester le site en local} dans le cybercafé de la commune, géré par un ancien élève de Terminale TI.

Le cybercafé dispose d'un poste sous Windows 10, relié au réseau local de la salle. Sur ce poste, un logiciel de visioconférence occupe déjà le \textbf{port 80}, ce qui empêche tout serveur web de démarrer sur ce port. L'administrateur décide donc de faire écouter le futur serveur web sur le \textbf{port 8080}.

Le stagiaire a remis deux fichiers :
\begin{itemize}
\item un script \texttt{produits.sql} contenant la table \texttt{produits} (champs : \texttt{id}, \texttt{nom}, \texttt{prix}, \texttt{stock}) et 4 enregistrements ;
\item la maquette de la page d'accueil : une page \texttt{index.php} qui se connecte à la base \texttt{coop\_db} et affiche la liste des produits sous forme de tableau HTML.
\end{itemize}

Ton groupe (3 à 4 élèves) incarne l'équipe technique du cybercafé. Votre mission : \textbf{installer, configurer et exploiter un environnement intégré complet} pour héberger localement le site de la coopérative, puis rédiger la fiche de procédure qui servira de documentation au gérant.

\courssub{Consignes}

\begin{enumerate}
\item \textbf{Choix et installation.} Citez deux environnements intégrés de développement web adaptés à un poste Windows, puis installez celui retenu (WampServer ou XAMPP) sur le poste de la salle informatique. Justifiez votre choix en nommant les trois éléments constitutifs qu'il embarque.
\item \textbf{Démarrage des services.} Lancez l'environnement, démarrez les services Apache et MySQL, puis indiquez comment vous vérifiez visuellement que les deux services fonctionnent (état de l'icône, page \texttt{http://localhost}).
\item \textbf{Résolution du conflit de port.} Apache refuse de démarrer car le port 80 est occupé. Identifiez le fichier de configuration du serveur web, ouvrez-le, modifiez le port d'écoute pour passer à 8080, puis redémarrez le service. Recopiez les lignes modifiées.
\item \textbf{Déploiement de l'application.} Localisez le répertoire racine (DocumentRoot) du serveur. Créez-y un dossier \texttt{cooperative} et placez-y la page \texttt{index.php} fournie ci-dessous.
\item \textbf{Base de données.} Ouvrez phpMyAdmin, créez une base nommée \texttt{coop\_db}, puis importez le fichier \texttt{produits.sql}. Vérifiez que la table \texttt{produits} contient bien 4 lignes.
\item \textbf{Test et documentation.} Saisissez dans le navigateur l'adresse complète permettant d'accéder au site (attention au port !). Capturez le résultat, puis rédigez une \textbf{fiche de procédure d'hébergement local en 6 étapes}, claire et numérotée, destinée au gérant du cybercafé.
\item \textbf{Présentation.} Chaque groupe présente sa fiche en 5 minutes et justifie ses choix de configuration (environnement choisi, port retenu, emplacement des fichiers).
\end{enumerate}

\courssub{Ressources à mobiliser}

\begin{aretenir}[Boîte à outils de la leçon]
\begin{itemize}
\item Un \cle{serveur web} est un logiciel (Apache, Nginx, IIS) qui reçoit les requêtes HTTP d'un client et retourne des pages web ; un \cle{hébergeur web} est une entreprise qui met des serveurs à disposition ; un \cle{service web} est une application accessible via le web offrant des données à d'autres programmes.
\item Un environnement intégré (WampServer, XAMPP, EasyPHP, LAMP) réunit : un \cle{serveur web} (Apache), un \cle{serveur de données} (MySQL/MariaDB) et un \cle{préprocesseur} (PHP).
\item Le \cle{DocumentRoot} est le répertoire racine publié par le serveur : \texttt{C:\textbackslash wamp64\textbackslash www} (WampServer) ou \texttt{C:\textbackslash xampp\textbackslash htdocs} (XAMPP).
\item Le fichier de configuration d'Apache est \texttt{httpd.conf} ; la directive \texttt{Listen} fixe le port d'écoute (80 par défaut).
\item Toute modification de \texttt{httpd.conf} n'est prise en compte qu'après \textbf{redémarrage} du service.
\item Une URL locale avec port non standard s'écrit : \texttt{http://localhost:8080/mon\_dossier}.
\end{itemize}
\end{aretenir}

\courssub{Démarche et corrigé commenté}

\begin{exoresolu}[Hébergement local du site de la coopérative]
Énoncé : installer et configurer WampServer, faire écouter Apache sur le port 8080, déployer l'application \texttt{cooperative} avec sa base \texttt{coop\_db}, et rédiger la procédure d'hébergement local.

\tcblower

\textbf{Étape 1 — Choix et installation de l'environnement intégré.}

Sous Windows, deux environnements sont candidats : \textbf{WampServer} et \textbf{XAMPP}. Nous retenons WampServer car il est léger, entièrement graphique et très répandu dans les salles informatiques camerounaises. Il embarque les trois éléments constitutifs attendus :
\begin{itemize}
\item \textbf{Apache} : le serveur web, qui écoute les requêtes HTTP ;
\item \textbf{MySQL} : le serveur de données, qui héberge les bases ;
\item \textbf{PHP} : le préprocesseur, qui exécute les scripts dynamiques.
\end{itemize}
Installation : télécharger \texttt{wampserver3.x.x\_x64.exe} sur le site officiel, exécuter l'installeur \emph{en tant qu'administrateur}, accepter le répertoire par défaut \texttt{C:\textbackslash wamp64}.

\textbf{Étape 2 — Démarrage des services.}

On lance WampServer : une icône apparaît dans la zone de notification. Elle passe du rouge (services arrêtés) à l'orange (démarrage partiel) puis au \textbf{vert} lorsque Apache et MySQL fonctionnent tous les deux. Vérification complémentaire : ouvrir \texttt{http://localhost} dans le navigateur, la page d'accueil de WampServer doit s'afficher.

\textbf{Étape 3 — Résolution du conflit de port.}

Ici, l'icône reste \textbf{orange} : Apache ne démarre pas car le logiciel de visioconférence occupe déjà le port 80. On ouvre le fichier de configuration via le menu de WampServer : \emph{Apache} $\rightarrow$ \emph{httpd.conf}. On recherche la directive \texttt{Listen} et on modifie :

\begin{lstlisting}
# Avant (configuration par defaut)
Listen 80
ServerName localhost:80

# Apres (port d'ecoute 8080)
Listen 8080
ServerName localhost:8080
\end{lstlisting}

On enregistre le fichier, puis on redémarre Apache (\emph{clic gauche sur l'icône} $\rightarrow$ \emph{Apache} $\rightarrow$ \emph{Redémarrer le service}). L'icône devient verte. La modification n'aurait \textbf{aucun effet sans ce redémarrage} : Apache ne relit sa configuration qu'au démarrage.

\textbf{Étape 4 — Déploiement dans le DocumentRoot.}

Le répertoire racine de WampServer est \texttt{C:\textbackslash wamp64\textbackslash www}. On y crée le dossier \texttt{cooperative} et on y place le fichier \texttt{index.php} :

\begin{lstlisting}[language=Php]
<?php
// Connexion au serveur de donnees MySQL local
$cnx = new mysqli("localhost", "root", "", "coop_db");
if ($cnx->connect_error) {
    die("Echec de connexion : " . $cnx->connect_error);
}

\begin{enumerate}
\item Installer WampServer en tant qu'administrateur (répertoire \texttt{C:\textbackslash wamp64}).
\item Lancer WampServer et vérifier que l'icône est verte (Apache + MySQL actifs).
\item Si Apache refuse de démarrer, ouvrir \texttt{httpd.conf}, remplacer \texttt{Listen 80} par \texttt{Listen 8080}, puis redémarrer le service Apache.
\item Copier le dossier du site dans \texttt{C:\textbackslash wamp64\textbackslash www} (le DocumentRoot).
\item Créer la base dans phpMyAdmin et importer le script SQL fourni.
\item Ouvrir le site dans le navigateur à l'adresse \texttt{http://localhost:8080/nom\_du\_dossier}.
\end{enumerate}
\end{exoresolu}

\begin{attention}[Pièges fréquents rencontrés pendant l'activité]
\begin{itemize}
\item \textbf{Oublier le port dans l'URL} : après le passage au port 8080, taper \texttt{http://localhost/cooperative} aboutit à une erreur, car le navigateur interroge le port 80 par défaut. Il faut écrire \texttt{http://localhost:8080/cooperative}.
\item \textbf{Modifier \texttt{httpd.conf} sans redémarrer} : Apache ne relit jamais sa configuration à chaud.
\item \textbf{Déposer le site hors du DocumentRoot} : un dossier placé sur le Bureau n'est pas publié par le serveur ; seuls les fichiers situés sous \texttt{www} (ou \texttt{htdocs}) sont accessibles via HTTP.
\item \textbf{Faute de frappe dans le nom de la base} : \texttt{coop\_db} dans le script PHP doit correspondre exactement au nom créé dans phpMyAdmin, sinon la connexion échoue.
\end{itemize}
\end{attention}

\courssub{Bilan de l'activité}

Cette activité t'a permis de mettre en évidence plusieurs idées essentielles de la leçon. D'abord, un environnement intégré comme WampServer n'est pas un logiciel unique mais une \textbf{architecture à trois composants} — serveur web, serveur de données, préprocesseur — qui coopèrent : Apache reçoit la requête HTTP, PHP exécute le script, MySQL fournit les données. Ensuite, tu as constaté concrètement qu'un serveur web est un \textbf{service} qu'on démarre, qu'on arrête et qu'on configure : le conflit de port, problème très réel dans les cybercafés et les entreprises, se résout par une simple directive \texttt{Listen} dans \texttt{httpd.conf}, à condition de redémarrer le service. Enfin, tu as compris le rôle central du \textbf{DocumentRoot} : héberger localement un site, c'est fondamentalement déposer ses fichiers au bon endroit et y accéder par une URL locale. La fiche de procédure en 6 étapes que tu as rédigée est exactement le type de document qu'un technicien remet à son client : tu as ainsi développé, au-delà des savoir-faire techniques, un véritable savoir-être professionnel — rigueur, documentation et justification des choix.

\coursec{Mise en place d'un environnement de développement et de déploiement web}

\courssub{Serveur web, service web et hébergeur}

\begin{definition}[Serveur web (logiciel et machine)]
Un \cle{serveur web} est un logiciel (ex. \cle{Apache HTTP Server}, \cle{Nginx}, \cle{Microsoft IIS}) qui écoute les requêtes \cle{HTTP/HTTPS} sur un port réseau (par défaut 80 pour HTTP, 443 pour HTTPS) et y répond en servant des ressources (fichiers HTML, images, scripts exécutés). Par métonymie, on appelle aussi « serveur web » la \emph{machine physique ou virtuelle} qui héberge ce logiciel.
\end{definition}

\begin{definition}[Service web]
Un \cle{service web} est une application accessible via le web qui expose des fonctionnalités ou des données à d'autres logiciels (clients) à travers des API standardisées (REST, SOAP, GraphQL), généralement en \cle{JSON} ou \cle{XML}. Exemple : l'API \texttt{MTN Mobile Money} permettant à un site e-commerce d'initier un paiement.
\end{definition}

\begin{definition}[Hébergeur web]
Un \cle{hébergeur web} est une \emph{entreprise} (ex. \cle{OVHcloud}, \cle{Hostinger}, \cle{CAMTEL} via ses offres Cloud, ou des revendeurs locaux camerounais) qui loue de l'espace disque, de la bande passante et des ressources serveur (mutualisé, VPS, dédié, cloud) pour rendre un site accessible en permanence sur Internet.
\end{definition}

\begin{propriete}[Distinction fondamentale]
\begin{itemize}
\item \textbf{Serveur web} = Logiciel (Apache, Nginx) \textbf{OU} Matériel (la machine).
\item \textbf{Service web} = Application métier exposant une API (ex. API de paiement, API météo).
\item \textbf{Hébergeur} = Fournisseur de service d'hébergement (entreprise).
\end{itemize}
Ne jamais confondre ces trois notions dans une réponse d'examen.
\end{propriete}

\begin{savaistu}[Le paysage de l'hébergement au Cameroun]
Historiquement, les sites camerounais étaient hébergés en Europe (France) ou aux USA pour la bande passante. Depuis le déploiement de la \textbf{dorsale nationale en fibre optique} par \textbf{CAMTEL} et l'arrivée des \textbf{data centers locaux} (ex. \textbf{CENADI}, \textbf{MTN Business}, \textbf{Orange Cameroun}), l'hébergement \emph{on-premise} ou en \emph{cloud souverain} se développe. Cela réduit la latence (ping < 10 ms local vs > 150 ms vers Paris) et facilite la conformité RGPD / loi camerounaise sur les données personnelles. Les API \textbf{MTN MoMo} et \textbf{Orange Money} sont des services web critiques pour le e-commerce local (ex. \emph{Jumia CM}, \emph{KmerSoft}, startups \emph{Silicon Mountain} à Buea).
\end{savaistu}

\courssub{Environnements intégrés de développement web}

\begin{methode}[Citer des exemples de serveurs web et d'environnements intégrés de développement web]
C'est le savoir-faire le plus simple de la leçon, mais il exige de la précision : le correcteur attend des \cle{noms exacts} et des \cle{catégories bien distinguées}.
\begin{enumerate}
\item \textbf{Identifier la catégorie demandée} dans l'énoncé : serveur web (logiciel qui écoute et répond en HTTP), serveur de bases de données, environnement intégré (paquet tout-en-un), ou hébergeur (entreprise).
\item \textbf{Citer des serveurs web} : \cle{Apache HTTP Server} (le plus utilisé, open source), \cle{Nginx} (haute performance, reverse proxy), \cle{Microsoft IIS} (intégré Windows Server), \cle{LiteSpeed}, \cle{Caddy} (HTTPS automatique). Précise toujours une caractéristique technique.
\item \textbf{Citer des environnements intégrés (stacks tout-en-un)} :
\begin{itemize}
\item \cle{WampServer} (Windows) : Apache + MySQL/MariaDB + PHP.
\item \cle{XAMPP} (Multiplateforme : Windows, Linux, macOS) : Apache + MariaDB + PHP + Perl.
\item \cle{EasyPHP} (Windows) : Apache + MySQL/MariaDB + PHP + PhpMyAdmin (orienté portable).
\item \cle{LAMP} (Linux) : Linux + Apache + MySQL/MariaDB + PHP (installé via gestionnaire de paquets \texttt{apt}, \texttt{dnf}, \texttt{pacman}).
\item \cle{MAMP} (macOS/Windows) : Apache/Nginx + MySQL + PHP/Python/Perl.
\end{itemize}
\item \textbf{Décoder les acronymes} quand c'est demandé :
\begin{align*}
\text{WAMP} &= \text{Windows} + \text{Apache} + \text{MySQL/MariaDB} + \text{PHP} \\
\text{XAMPP} &= \text{X (Cross-platform)} + \text{Apache} + \text{MariaDB} + \text{PHP} + \text{Perl} \\
\text{LAMP} &= \text{Linux} + \text{Apache} + \text{MySQL/MariaDB} + \text{PHP}
\end{align*}
\item \textbf{Ne pas confondre} : un hébergeur web (OVH, société camerounaise) est une \emph{entreprise}, pas un logiciel.
\end{enumerate}
\textbf{Réflexe Bac} : une réponse du type « Apache, MySQL, PHP » à la question « citer deux environnements intégrés » est \emph{fausse} : ce sont les \emph{composants}, pas les environnements. Les réponses attendues : WampServer, XAMPP, EasyPHP, LAMP.
\end{methode}

\begin{exoresolu}[QCM de connaissances — type Bac]
\textbf{Énoncé.} Une startup de Douala développe un site de vente en ligne payé par MTN Mobile Money. (1) Citer deux serveurs web qu'elle peut utiliser. (2) Citer deux environnements intégrés de développement web adaptés à un poste de travail sous Windows. (3) Donner la signification de l'acronyme XAMPP. (4) Dire si PHP est un environnement intégré de développement web ; justifier.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
\item \textbf{Serveurs web} : \textbf{Apache HTTP Server} (serveur HTTP libre, le plus répandu, défaut dans WampServer/XAMPP) et \textbf{Nginx} (performant en forte charge, souvent utilisé comme reverse proxy devant Apache ou Node.js). Microsoft IIS accepté.
\item \textbf{Environnements intégrés sous Windows} : \textbf{WampServer} et \textbf{EasyPHP}. \textbf{XAMPP} convient également (multiplateforme). Chacun embarque en une seule installation : serveur web (Apache), serveur de données (MySQL/MariaDB), préprocesseur (PHP).
\item \textbf{Signification de XAMPP} : \textbf{X} = multiplateforme, \textbf{A} = Apache, \textbf{M} = MariaDB (successeur de MySQL dans XAMPP), \textbf{P} = PHP, \textbf{P} = Perl.
\item \textbf{PHP est-il un environnement intégré ?} \textbf{Non.} PHP est un \emph{langage de script} côté serveur : c'est le \emph{préprocesseur}, un \textbf{composant} d'un environnement intégré. Un environnement intégré regroupe \emph{au minimum trois éléments} : serveur web, serveur de données, préprocesseur.
\end{enumerate}
\textbf{Conclusion.} La startup peut développer localement avec WampServer ou XAMPP (Apache + MariaDB + PHP) avant de déployer chez un hébergeur.
\end{exoresolu}

\courssub{Architecture d'un environnement intégré}

\begin{methode}[Décrire l'architecture d'un environnement intégré et le rôle du répertoire racine]
\begin{enumerate}
\item \textbf{Énumérer les trois éléments constitutifs} :
\begin{itemize}
\item \cle{Serveur web} (\cle{Apache}) : reçoit les requêtes HTTP, gère les connexions, sert les fichiers statiques, délègue l'exécution des scripts au préprocesseur.
\item \cle{Serveur de données} (\cle{MySQL} / \cle{MariaDB}) : stocke les données structurées, exécute les requêtes \cle{SQL} (SELECT, INSERT, UPDATE, DELETE), assure l'intégrité (ACID).
\item \cle{Préprocesseur} (\cle{PHP}) : interprète les scripts \texttt{.php}, accède aux superglobales (\texttt{\$\_GET}, \texttt{\$\_POST}, \texttt{\$\_SESSION}), interroge la base via \texttt{PDO} ou \texttt{mysqli}, génère le flux HTML envoyé au client.
\end{itemize}
\item \textbf{Décrire la chaîne de traitement d'une requête dynamique} :
\[
\text{Navigateur} \xrightarrow{\text{Requête HTTP}} \text{Apache} \xrightarrow{\text{si .php}} \text{PHP} \xrightarrow{\text{SQL}} \text{MySQL} \xrightarrow{\text{Résultat}} \text{PHP} \xrightarrow{\text{HTML}} \text{Apache} \xrightarrow{\text{Réponse HTTP}} \text{Navigateur}
\]
\item \textbf{Définir le DocumentRoot} : répertoire racine du serveur d'hébergement (\texttt{DocumentRoot} dans \texttt{httpd.conf}). C'est le dossier de base à partir duquel Apache sert les fichiers. L'URL \texttt{http://localhost/dossier/fichier.php} correspond au chemin physique \texttt{DocumentRoot\textbackslash dossier\textbackslash fichier.php}.
\item \textbf{Justifier son rôle de sécurité} : les fichiers situés \emph{hors} du DocumentRoot ne sont jamais accessibles par HTTP, protégeant le reste du disque (fichiers de config, logs, scripts sensibles).
\end{enumerate}
\textbf{Formule à retenir} : URL locale $=$ \texttt{http://localhost/} $+$ chemin relatif du fichier \emph{par rapport au DocumentRoot}.
\end{methode}

\begin{exoresolu}[Correspondance URL / arborescence — type Bac]
\textbf{Énoncé.} Sous WampServer, le DocumentRoot est \texttt{C:\textbackslash wamp64\textbackslash www}. (1) Un fichier est enregistré en \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash projets\textbackslash tle\textbackslash accueil.php} : donner l'URL permettant de l'exécuter. (2) L'URL \texttt{http://localhost/rapport/stage.html} est saisie : donner le chemin complet du fichier correspondant sur le disque. (3) Expliquer le rôle joué par chacun des trois composants de WampServer lors de l'affichage de \texttt{accueil.php}, page qui lit la liste des élèves dans une base de données. (4) Un fichier \texttt{secret.txt} est placé en \texttt{C:\textbackslash wamp64\textbackslash secret.txt} : est-il accessible par HTTP ? Justifier.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
\item \textbf{URL} : on supprime la partie correspondant au DocumentRoot et on remplace les antislashs par des slashs :
\[ \texttt{http://localhost/projets/tle/accueil.php} \]
\item \textbf{Chemin disque} : on ajoute le chemin relatif après le DocumentRoot :
\[ \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash rapport\textbackslash stage.html} \]
\item \textbf{Rôle des trois composants} lors de l'affichage de \texttt{accueil.php} :
\begin{itemize}
\item \textbf{Apache (serveur web)} : reçoit la requête HTTP sur le port 80, localise \texttt{accueil.php} dans le DocumentRoot, voit l'extension \texttt{.php} et transmet le script au module PHP.
\item \textbf{PHP (préprocesseur)} : exécute le script ligne par ligne, établit la connexion PDO à MySQL, prépare et exécute la requête \texttt{SELECT * FROM eleves}.
\item \textbf{MySQL (serveur de données)} : analyse la requête SQL, lit les données dans les fichiers de la base (moteur InnoDB), renvoie le jeu de résultats à PHP. PHP boucle sur les résultats pour construire le HTML final ; Apache l'envoie au navigateur.
\end{itemize}
\item \textbf{Accessibilité de \texttt{secret.txt}} : \textbf{Non}. Le fichier est \emph{au-dessus} du DocumentRoot (\texttt{C:\textbackslash wamp64\textbackslash} vs \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash}). Apache ne sert que l'arborescence \emph{sous} DocumentRoot. C'est son rôle protecteur.
\end{enumerate}
\textbf{Conclusion.} La correspondance URL $\leftrightarrow$ disque s'obtient en ajoutant/retirant le préfixe DocumentRoot. La séparation des rôles (Apache/PHP/MySQL) explique le traitement complet d'une page dynamique.
\end{exoresolu}

\courssub{Installation et configuration d'un environnement intégré}

\begin{methode}[Installer et configurer un environnement intégré (WampServer / XAMPP)]
\begin{enumerate}
\item \textbf{Choisir l'environnement} selon l'OS : WampServer ou EasyPHP (Windows), XAMPP (partout), LAMP (Linux natif via \texttt{sudo apt install apache2 mariadb-server php libapache2-mod-php}).
\item \textbf{Télécharger l'installateur} depuis le site officiel (\texttt{wampserver.com}, \texttt{apachefriends.org}) en vérifiant l'architecture (64 bits standard aujourd'hui). \textbf{Prérequis Windows} : installer les \textbf{Visual C++ Redistributable} (VC15/VC16/VC17) requis par Apache/PHP (liens fournis sur la page de téléchargement WampServer).
\item \textbf{Installer dans un chemin sans espace ni accent} (idéalement \texttt{C:\textbackslash wamp64} ou \texttt{C:\textbackslash xampp}). Éviter \texttt{Program Files} (espace + droits UAC).
\item \textbf{Vérifier la disponibilité du port 80} avant premier démarrage : Skype, IIS, VMware Workstation peuvent l'occuper. Commande :
\begin{lstlisting}[language=bash]
netstat -ano | findstr :80
\end{lstlisting}
\item \textbf{Lancer les services} : icône WampServer (zone notif) $\rightarrow$ \emph{Démarrer les services} / XAMPP Control Panel $\rightarrow$ \emph{Start} Apache \& MySQL.
\item \textbf{Tester l'installation} : navigateur $\rightarrow$ \texttt{http://localhost} (page d'accueil WampServer/XAMPP) puis \texttt{http://localhost/phpmyadmin} (interface BDD).
\item \textbf{Sécuriser immédiatement} : dans phpMyAdmin, onglet \emph{Comptes utilisateurs} $\rightarrow$ modifier \texttt{root} @ localhost $\rightarrow$ définir un mot de passe fort. Mettre à jour le fichier \texttt{config.inc.php} de phpMyAdmin (\texttt{\$cfg['Servers'][\$i]['password'] = '...';}).
\end{enumerate}
\textbf{Réflexe} : Icône WampServer \textbf{verte} = tout actif ; \textbf{orange} = un service en échec (souvent port 80) ; \textbf{rouge} = aucun service démarré.
\end{methode}

\begin{exoresolu}[Installation de WampServer — type Bac]
\textbf{Énoncé.} Le club informatique du lycée de Nkongsamba veut installer WampServer 64 bits sur un poste Windows 10 pour développer une application de gestion de la bibliothèque. (1) Donner les trois composants installés automatiquement par WampServer. (2) Après installation, l'icône de WampServer reste orange. Proposer une cause probable et une vérification à effectuer. (3) Décrire le test permettant de valider l'installation. (4) Expliquer pourquoi il est déconseillé d'installer WampServer dans \texttt{C:\textbackslash Program Files}.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
\item \textbf{Composants} : \textbf{Apache} (serveur web, écoute HTTP), \textbf{MySQL/MariaDB} (serveur de données, SQL), \textbf{PHP} (préprocesseur, exécution scripts). Sens de l'acronyme : \textbf{W}indows + \textbf{A}pache + \textbf{M}ySQL + \textbf{P}HP.
\item \textbf{Cause probable (icône orange)} : le port 80 est occupé (Skype, IIS, autre serveur). \textbf{Vérification} :
\begin{lstlisting}[language=bash]
netstat -ano | findstr :80
\end{lstlisting}
Si une ligne \texttt{LISTENING} avec un PID apparaît $\rightarrow$ Gestionnaire des tâches (onglet Détails, colonne PID) $\rightarrow$ arrêter le processus ou changer le port Apache (Méthode 4).
\item \textbf{Test de validation} : navigateur $\rightarrow$ \texttt{http://localhost} (page d'accueil WampServer) ET \texttt{http://localhost/phpmyadmin} (connexion BDD). Icône doit devenir \textbf{verte}.
\item \textbf{Pourquoi éviter \texttt{C:\textbackslash Program Files}} : chemin avec \textbf{espace} (\texttt{Program Files}) + protection \textbf{UAC} (droits admin). Apache/PHP gèrent mal les espaces dans les chemins (modules, logs, fichiers temporaires). Installer à la racine : \texttt{C:\textbackslash wamp64}.
\end{enumerate}
\end{exoresolu}

\begin{methode}[Démarrer et arrêter un service web]
\begin{enumerate}
\item \textbf{Identifier le service} : Serveur web (Apache : \texttt{wampapache64} sous WampServer 64b, \texttt{Apache2.4} sous XAMPP) ou Serveur de données (\texttt{wampmysqld64}, \texttt{MySQL}).
\item \textbf{Voie graphique} : WampServer : clic gauche icône $\rightarrow$ Apache/MySQL $\rightarrow$ \emph{Administration du service} $\rightarrow$ \emph{Démarrer/Arrêter/Redémarrer}. XAMPP : Control Panel $\rightarrow$ boutons \emph{Start}/\emph{Stop}.
\item \textbf{Voie ligne de commandes (Windows Admin)} :
\begin{lstlisting}[language=bash]
net start wampapache64
net stop wampapache64
net start wampmysqld64
\end{lstlisting}
Sous Linux (LAMP) :
\begin{lstlisting}[language=bash]
sudo systemctl start apache2
sudo systemctl stop apache2
sudo systemctl status apache2
\end{lstlisting}
\item \textbf{Vérifier l'état} : couleur icône, \texttt{http://localhost}, \texttt{systemctl status}, \texttt{netstat -ano | findstr :80}.
\item \textbf{Interpréter un échec} : consulter \texttt{apache\_error.log} (\texttt{C:\textbackslash wamp64\textbackslash logs\textbackslash}) : cause quasi toujours écrite (port occupé, erreur syntaxe \texttt{httpd.conf}, module manquant).
\end{enumerate}
\textbf{Réflexe} : après \textbf{toute modification de \texttt{httpd.conf}}, il faut \textbf{redémarrer} le service (pas juste démarrer) pour recharger la configuration en mémoire.
\end{methode}

\begin{exoresolu}[Administration des services — type Bac]
\textbf{Énoncé.} Sur le serveur du CENADI simulé en salle informatique, un élève modifie le fichier de configuration d'Apache sous WampServer puis constate que ses modifications ne sont pas prises en compte. (1) Expliquer la cause. (2) Donner la manipulation graphique correcte. (3) Donner la commande Windows permettant d'arrêter le service Apache de WampServer 64 bits. (4) Le redémarrage échoue : indiquer le fichier à consulter pour diagnostiquer le problème.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
\item \textbf{Cause} : Apache lit \texttt{httpd.conf} \textbf{une seule fois au démarrage} et le garde en mémoire. Modifier le fichier à chaud ne change rien. Il faut \textbf{redémarrer le service}.
\item \textbf{Manipulation graphique} : Clic gauche icône WampServer $\rightarrow$ \emph{Apache} $\rightarrow$ \emph{Administration du service} $\rightarrow$ \textbf{Redémarrer le service} (ou \emph{Redémarrer tous les services}). Icône $\rightarrow$ verte.
\item \textbf{Commande d'arrêt} (Invite de commandes \textbf{Admin}) :
\begin{lstlisting}[language=bash]
net stop wampapache64
\end{lstlisting}
(Nom exact vérifiable dans \texttt{services.msc}).
\item \textbf{Diagnostic} : journal d'erreurs \texttt{apache\_error.log} dans \texttt{C:\textbackslash wamp64\textbackslash logs\textbackslash}. Indique la ligne fautive (syntaxe) ou le conflit (port).
\end{enumerate}
\textbf{Conclusion.} Toute modif de config $\rightarrow$ redémarrage service. Tout échec $\rightarrow$ lire les logs (\emph{logs}) en premier.
\end{exoresolu}

\begin{methode}[Accéder au fichier de configuration et modifier le port d'écoute]
\begin{enumerate}
\item \textbf{Localiser \texttt{httpd.conf}} :
\begin{itemize}
\item WampServer : \texttt{C:\textbackslash wamp64\textbackslash bin\textbackslash apache\textbackslash apache2.4.x\textbackslash conf\textbackslash httpd.conf} (accès rapide : icône $\rightarrow$ Apache $\rightarrow$ \texttt{httpd.conf}).
\item XAMPP : \texttt{C:\textbackslash xampp\textbackslash apache\textbackslash conf\textbackslash httpd.conf}.
\end{itemize}
\item \textbf{Sauvegarder} avant modif : copier en \texttt{httpd.conf.bak} (erreur syntaxe = Apache ne démarre plus).
\item \textbf{Repérer la directive \texttt{Listen}} : ligne \texttt{Listen 80} (ou \texttt{Listen 0.0.0.0:80} ou \texttt{Listen [::]:80} pour IPv6).
\item \textbf{Modifier le port} : choisir un port libre $\ge 1024$ (ex. \texttt{8080}, \texttt{8000}, \texttt{8888}).
\begin{lstlisting}[language=apacheconf]
# Écoute sur toutes les interfaces (IPv4) sur le port 8080
Listen 8080

# Nom du serveur cohérent avec le port
ServerName localhost:8080
\end{lstlisting}
\item \textbf{Enregistrer, redémarrer Apache}, tester : \texttt{http://localhost:8080}.
\item \textbf{Vérifier l'écoute} : \texttt{netstat -ano | findstr :8080} $\rightarrow$ doit afficher \texttt{LISTENING}.
\end{enumerate}
\textbf{À retenir} : Port 80 = standard HTTP (443 HTTPS). Si port changé, l'URL \textbf{doit} l'inclure (\texttt{:8080}), sinon navigateur interroge port 80 par défaut.
\end{methode}

\begin{exoresolu}[Conflit de port et reconfiguration — type Bac]
\textbf{Énoncé.} Sur le poste d'un cybercafé de Yaoundé, Apache (WampServer) refuse de démarrer : le journal indique \texttt{(OS 10048) Une seule utilisation de chaque adresse de socket est normalement autorisée : AH00072: make\_sock: could not bind to address 0.0.0.0:80}. (1) Expliquer la signification. (2) Commande pour identifier l'application occupante. (3) Modifications exactes de \texttt{httpd.conf} pour port 8080. (4) URL de test. (5) Justifier le choix 8080.
\tcblower
\textbf{Solution détaillée.}
\begin{enumerate}
\item \textbf{Signification} : \texttt{could not bind to address 0.0.0.0:80} = Apache ne peut pas s'attacher (\emph{bind}) au port 80 sur toutes les interfaces (\texttt{0.0.0.0}) car \textbf{ce port est déjà occupé} par un autre processus (Skype, IIS, VMware, autre Apache). Un port = un seul processus \texttt{LISTENING}.
\item \textbf{Commande d'identification} :
\begin{lstlisting}[language=bash]
netstat -ano | findstr :80
\end{lstlisting}
Dernière colonne = \textbf{PID} du coupable $\rightarrow$ Gestionnaire des tâches (Détails, colonne PID) pour nommer le processus.
\item \textbf{Modifications \texttt{httpd.conf}} (après backup) :
\begin{lstlisting}[language=apacheconf]
# Directive Listen (souvent 2 lignes : IPv4 et IPv6, modifier les deux ou commenter IPv6 si pas utilisé)
Listen 8080
# Listen [::]:8080  (optionnel pour IPv6)

# Directive ServerName (décommenter et adapter)
ServerName localhost:8080
\end{lstlisting}
Enregistrer $\rightarrow$ Redémarrer Apache (icône $\rightarrow$ Redémarrer tous les services).
\item \textbf{URL de test} : \texttt{http://localhost:8080}. Port obligatoire dans l'URL (défaut navigateur = 80).
\item \textbf{Justification 8080} : Ports $0\text{--}1023$ = privilégiés (services système : 80 HTTP, 443 HTTPS, 22 SSH, 25 SMTP). Ports $1024\text{--}49151$ = enregistrés (utilisateurs). 8080 = port « HTTP alternatif » standard, non privilégié ($\ge 1024$), rarement utilisé par un service système, respectant $1024 \le p \le 65535$.
\end{enumerate}
\textbf{Conclusion.} Après modif \texttt{Listen} + redémarrage, Apache écoute sur 8080, site accessible via \texttt{http://localhost:8080}.
\end{exoresolu}

\courssub{Répertoire racine et fichier de configuration}

\begin{definition}[DocumentRoot (Répertoire racine)]
Directive Apache (\texttt{DocumentRoot}) définissant le dossier physique dont le contenu est publié sur le web. Tout fichier \emph{hors} de cette arborescence est \textbf{inaccessible via HTTP}.
\begin{itemize}
\item WampServer : \texttt{C:\textbackslash wamp64\textbackslash www} (défini dans \texttt{httpd.conf} et \texttt{httpd-vhosts.conf}).
\item XAMPP : \texttt{C:\textbackslash xampp\textbackslash htdocs}.
\item Linux (LAMP) : \texttt{/var/www/html}.
\end{itemize}
\end{definition}

\begin{propriete}[Fichier de configuration principal \texttt{httpd.conf}]
\begin{itemize}
\item \textbf{Directives clés} : \texttt{Listen} (port/IP), \texttt{ServerName} (nom:port), \texttt{DocumentRoot} (chemin racine), \texttt{DirectoryIndex} (fichiers par défaut : \texttt{index.php index.html}), \texttt{LoadModule} (modules PHP, rewrite, ssl), \texttt{Include} (fichiers conf additionnels : vhosts, ssl, phpmyadmin).
\item \textbf{Syntaxe} : une directive par ligne, arguments séparés par espaces. Commentaire : \texttt{\#}.
\item \textbf{Prise en compte} : uniquement au \textbf{démarrage/redémarrage} du service Apache.
\end{itemize}
\end{propriete}

\begin{attention}[Pièges classiques \texttt{httpd.conf}]
\begin{enumerate}
\item Oublier de \textbf{redémarrer Apache} après modification.
\item Laisser un espace dans le chemin \texttt{DocumentRoot "C:/wamp64/www"} (Apache préfère slashs \texttt{/} ou antislashs doubles \texttt{\textbackslash\textbackslash} ; les guillemets sont obligatoires si espace dans le chemin, mais \textbf{on évite les espaces}).
\item Modifier \texttt{Listen 80} sans toucher à \texttt{ServerName localhost:80} $\rightarrow$ avertissement au démarrage, mais fonctionne.
\item Éditer le fichier avec le Bloc-notes Windows (encodage BOM, fins de ligne CRLF) $\rightarrow$ préférer \textbf{Notepad++}, \textbf{VS Code}, \textbf{Sublime Text} (encodage UTF-8 sans BOM, LF).
\end{enumerate}
\end{attention}

\courssub{Hébergement local et déploiement d'une application}

\begin{methode}[Démarrer une application hébergée et décrire la procédure d'hébergement local]
\begin{enumerate}
\item \textbf{Repérer le DocumentRoot} : \texttt{C:\textbackslash wamp64\textbackslash www} (WampServer) ou \texttt{C:\textbackslash xampp\textbackslash htdocs} (XAMPP). Seul ce dossier est servi.
\item \textbf{Copier le projet} dans un sous-dossier du DocumentRoot, ex. \texttt{www\textbackslash biblio}. Fichiers sur Bureau/Documents = \emph{inaccessibles via HTTP}.
\item \textbf{Importer la base de données} si nécessaire :
\begin{enumerate}
\item \texttt{http://localhost/phpmyadmin} $\rightarrow$ \emph{Nouvelle base} (ex. \texttt{bd\_biblio}, interclassement \texttt{utf8mb4\_general\_ci}).
\item Onglet \emph{Importer} $\rightarrow$ choisir \texttt{script.sql} $\rightarrow$ \emph{Exécuter}.
\end{enumerate}
\item \textbf{Configurer la connexion PHP} de l'application (fichier \texttt{config.php}, \texttt{db.php}, \texttt{.env}) :
\begin{lstlisting}[language=Php]
<?php
// Exemple PDO standard
$host = '127.0.0.1'; // ou 'localhost'
$dbname = 'bd_biblio';
$user = 'root';
$pass = 'mot_de_passe_defini_dans_phpmyadmin'; // '' (vide) par défaut WampServer non sécurisé
$charset = 'utf8mb4';

$dsn = "mysql:host=$host;dbname=$dbname;charset=$charset";
$options = [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,
];
try {
    $pdo = new PDO($dsn, $user, $pass, $options);
} catch (\PDOException $e) {
    throw new \PDOException($e->getMessage(), (int)$e->getCode());
}
\end{lstlisting}
\item \textbf{Démarrer services} (Apache + MySQL) $\rightarrow$ Lancer app : \texttt{http://localhost/biblio}. Apache cherche \texttt{index.php} puis \texttt{index.html} (directive \texttt{DirectoryIndex}).
\item \textbf{Accès réseau local (autres postes)} : Remplacer \texttt{localhost} par \textbf{IP locale du serveur} (ex. \texttt{http://192.168.1.10/biblio}). Conditions :
\begin{itemize}
\item Pare-feu Windows (Poste serveur) : Règle entrante \textbf{Autoriser} port TCP 80 (ou 8080) pour \emph{Domaine/Privé}.
\item Apache \texttt{httpd.conf} / \texttt{httpd-vhosts.conf} : directive \texttt{Require all granted} dans le bloc \texttt{<Directory "\${INSTALL\_DIR}/www">} (défaut WampServer 3.x : \texttt{Require local} seulement $\rightarrow$ bloquer l'extérieur). Modifier en \texttt{Require all granted} pour accès LAN.
\end{itemize}
\end{enumerate}
\textbf{Réflexe} : Erreur 404 = mauvais chemin / hors DocumentRoot. Code PHP affiché en clair = service PHP/Apache arrêté \textbf{OU} fichier ouvert via \texttt{file://} (double-clic) au lieu de \texttt{http://localhost}.
\end{methode}

\begin{experience}[TP Guidé : Déployer un mini-site PHP/MySQL en réseau local]
\textbf{Objectif} : Mettre en ligne une application de gestion de notes accessible depuis les postes élèves.
\textbf{Matériel/Logiciels} : Poste serveur (Windows 10, WampServer 3.3+ installé, IP fixe \texttt{192.168.10.5}), Postes clients (navigateur), Dossier projet \texttt{gestion\_notes} (\texttt{index.php}, \texttt{notes.sql}).
\textbf{Manipulation} :
\begin{enumerate}
\item \textbf{Serveur} : Copier \texttt{gestion\_notes} dans \texttt{C:\textbackslash wamp64\textbackslash www\textbackslash}.
\item \textbf{Base} : \texttt{http://localhost/phpmyadmin} $\rightarrow$ Créer \texttt{bd\_notes} $\rightarrow$ Importer \texttt{notes.sql} $\rightarrow$ Vérifier tables.
\item \textbf{Config PHP} : Éditer \texttt{www\textbackslash gestion\_notes\textbackslash config.php} $\rightarrow$ \texttt{\$host='127.0.0.1'; \$user='root'; \$pass=''; \$db='bd\_notes';}.
\item \textbf{Pare-feu} : \texttt{Panneau de config} $\rightarrow$ \texttt{Pare-feu Windows} $\rightarrow$ \texttt{Règles entrantes} $\rightarrow$ \texttt{Nouvelle règle} $\rightarrow$ \texttt{Port} $\rightarrow$ \texttt{TCP 80} $\rightarrow$ \texttt{Autoriser} $\rightarrow$ \texttt{Profil Privé} $\rightarrow$ Nommer « Apache HTTP ».
\item \textbf{Apache Distant} : Icône WampServer $\rightarrow$ Apache $\rightarrow$ \texttt{httpd-vhosts.conf} (ou \texttt{httpd.conf} bloc \texttt{<Directory>}) $\rightarrow$ Remplacer \texttt{Require local} par \texttt{Require all granted} $\rightarrow$ \textbf{Redémarrer tous les services}.
\item \textbf{Test Local} : \texttt{http://localhost/gestion\_notes} $\rightarrow$ OK.
\item \textbf{Test Client} : Sur poste élève, navigateur $\rightarrow$ \texttt{http://192.168.10.5/gestion\_notes} $\rightarrow$ Page d'accueil affichée.
\end{enumerate}
\textbf{Observations} : Si 403 Forbidden $\rightarrow$ vérifier \texttt{Require all granted} + redémarrage. Si timeout $\rightarrow$ Pare-feu / IP incorrecte / Apache pas démarré.
\textbf{Interprétation} : L'hébergement local transforme un poste de travail en serveur LAN. La sécurité (pare-feu, mots de passe BDD, HTTPS) devient critique si exposé au-delà du LAN.
\end{experience}

\courssub{Synthèse et pièges à éviter}

\begin{attention}[Les 5 erreurs qui coûtent des points au Bac]
\begin{enumerate}
\item \textbf{Confondre composants et environnement intégré.} Répondre « Apache, MySQL, PHP » à « citer des environnements intégrés » est \textbf{faux}. Réponses attendues : \textbf{WampServer, XAMPP, EasyPHP, LAMP}. Apache = serveur web, PHP = préprocesseur = \emph{éléments constitutifs}.
\item \textbf{Oublier le redémarrage après modification de \texttt{httpd.conf}.} La config est lue \textbf{au démarrage} uniquement. Sans redémarrage, aucune modif (port, DocumentRoot, modules) n'est active. Le mentionner explicitement rapporte des points.
\item \textbf{Changer le port sans changer l'URL.} Après \texttt{Listen 8080}, l'adresse devient \texttt{http://localhost:8080}. Écrire \texttt{localhost} interroge le port 80 (défaut). Choisir un port $< 1024$ sans justification = maladresse (ports privilégiés). Utiliser $1024 \le p \le 65535$ (ex. 8080, 8000).
\item \textbf{Placer le projet hors du DocumentRoot.} Site sur Bureau / Documents = non servi par Apache. Erreur classique aussi : double-clic sur \texttt{.php} (\texttt{file://}) au lieu de \texttt{http://localhost} $\rightarrow$ code source affiché.
\item \textbf{Confondre hébergeur, serveur web et service web.}
\begin{itemize}
\item \textbf{Hébergeur} = Entreprise (OVH, CAMTEL, startup locale).
\item \textbf{Serveur web} = Logiciel (Apache, Nginx) ou Machine.
\item \textbf{Service web} = Application exposant une API (ex. API MTN MoMo).
\end{itemize}
Employer le terme exact demandé par la question.
\end{enumerate}
\end{attention}

\courssub{Je vérifie mes connaissances}

\begin{corrige}[Exercice 1 — QCM : vocabulaire du web]
\begin{enumerate}
\item \textbf{Réponse b : un \cle{serveur web}.} C'est par définition le logiciel qui écoute les requêtes \cle{HTTP} (généralement sur le port 80) et renvoie des pages web. Le navigateur (a) est le \emph{client} qui envoie les requêtes ; l'\cle{hébergeur web} (c) est une entreprise qui loue des serveurs ; le \cle{préprocesseur} (d) exécute les scripts (PHP) avant l'envoi de la page.
\item \textbf{Réponse c : LWS (ou OVH).} Ce sont des entreprises qui mettent à disposition des serveurs connectés en permanence à Internet. \cle{Apache} (a) est un logiciel serveur web, \cle{PHP} (b) un préprocesseur, \cle{MySQL} (d) un serveur de données.
\item \textbf{Réponse b : \cle{PHP}.} Le \og P \fg{} de \cle{WAMP} désigne PHP, le préprocesseur qui exécute les scripts côté serveur. \cle{HTML} est un langage de balisage interprété par le navigateur, \cle{HTTP} un protocole, \cle{SQL} un langage d'interrogation de bases de données.
\item \textbf{Réponse c : 80.} Le port 80 est le port standard de HTTP. Le port 21 correspond à \cle{FTP}, 443 à \cle{HTTPS} et 3306 au serveur MySQL.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 2 — Vrai ou faux justifié]
\begin{enumerate}
\item \textbf{Faux.} \cle{XAMPP} est multiplateforme : la lettre \og X \fg{} signifie justement \emph{cross-platform}. Il existe des versions pour Windows, Linux et macOS.
\item \textbf{Vrai.} Le dossier \texttt{C:\textbackslash xampp\textbackslash htdocs} est le \cle{répertoire racine} (\cle{DocumentRoot}) du serveur Apache de XAMPP : c'est à partir de ce dossier que le serveur sert les fichiers demandés par les URL.
\item \textbf{Faux.} Apache lit son \cle{fichier de configuration} uniquement au démarrage. Après toute modification de \texttt{httpd.conf}, il faut \textbf{redémarrer le service Apache} pour que les changements soient pris en compte.
\item \textbf{Faux.} Le \cle{serveur web} est le \emph{logiciel} (ou la machine) qui traite les requêtes HTTP, tandis que le \cle{service web} est la \emph{fonctionnalité} offerte à travers le réseau (ensemble de programmes communiquant via des standards comme HTTP). Un serveur web peut héberger plusieurs services web.
\item \textbf{Vrai.} Le \og M \fg{} de \cle{WAMP} désigne \cle{MySQL}, le \cle{serveur de données} (SGBD) qui stocke et interroge les bases de données de l'application.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 3 — Décodage des sigles]
\begin{itemize}
\item \textbf{\cle{WAMP}} : \textbf{W}indows (système d'exploitation), \textbf{A}pache (serveur web), \textbf{M}ySQL (serveur de données), \textbf{P}HP (préprocesseur). C'est un \cle{environnement intégré} réservé à Windows.
\item \textbf{\cle{XAMPP}} : \textbf{X} = \emph{cross-platform} (fonctionne sous Windows, Linux et macOS), \textbf{A}pache (serveur web), \textbf{M}ariaDB/MySQL (serveur de données), \textbf{P}HP et \textbf{P}erl (préprocesseurs). En plus d'Apache, MySQL et PHP, XAMPP est livré par exemple avec \textbf{phpMyAdmin} (interface web d'administration des bases de données), \textbf{FileZilla Server} (serveur FTP), \textbf{Mercury} (serveur de messagerie) ou encore \textbf{Tomcat}.
\item \textbf{\cle{LAMP}} : \textbf{L}inux (système d'exploitation), \textbf{A}pache (serveur web), \textbf{M}ySQL (serveur de données), \textbf{P}HP (préprocesseur). C'est l'architecture classique des serveurs de production sous Linux.
\end{itemize}
\end{corrige}

\begin{corrige}[Exercice 4 — Correspondance URL / fichier]
La règle de correspondance est la suivante : on supprime le préfixe \texttt{http://localhost} (le \cle{port d'écoute} n'influence pas le chemin disque) et on remplace la racine de l'URL par le \cle{DocumentRoot}.
\begin{enumerate}
\item \texttt{http://localhost/ecole/eleves/liste.php} $\rightarrow$ \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash ecole\textbackslash eleves\textbackslash liste.php}
\item \texttt{http://localhost:8080/images/logo.png} $\rightarrow$ \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash images\textbackslash logo.png}. Le port 8080 indique seulement sur quel port contacter le serveur ; il ne change rien au chemin disque.
\item \texttt{http://localhost/index.html} $\rightarrow$ \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash index.html}
\end{enumerate}
Le nom \texttt{localhost} peut être utilisé car il désigne toujours la machine locale elle-même : il est résolu automatiquement vers l'adresse IP de bouclage \texttt{127.0.0.1}, sans passer par un serveur DNS.
\end{corrige}

\begin{corrige}[Exercice 5 — Panne de WampServer]
\begin{enumerate}
\item Signification des couleurs de l'icône :
\begin{itemize}
\item \textbf{Rouge} : aucun service n'est démarré (Apache et MySQL sont arrêtés) ;
\item \textbf{Orange} : seulement \emph{une partie} des services est démarrée (par exemple MySQL fonctionne mais Apache a échoué) ;
\item \textbf{Vert} : tous les services sont démarrés, l'environnement est opérationnel.
\end{itemize}
\item Trois causes possibles :
\begin{itemize}
\item le \textbf{port 80 est déjà occupé} par un autre logiciel (Skype, IIS, un autre Apache) ;
\item un \textbf{service n'a pas pu démarrer} à cause d'une erreur dans un fichier de configuration (\texttt{httpd.conf} ou \texttt{my.ini}) ;
\item des \textbf{droits insuffisants} (WampServer lancé sans les droits administrateur) ou un pare-feu/antivirus qui bloque le démarrage.
\end{itemize}
\item Résolution du conflit de port :
\begin{enumerate}
\item ouvrir le fichier \texttt{httpd.conf} (menu WampServer $\rightarrow$ Apache $\rightarrow$ \texttt{httpd.conf}) ;
\item repérer la directive \texttt{Listen 80} et la remplacer par \texttt{Listen 8080} (adapter aussi \texttt{ServerName localhost:80} en \texttt{ServerName localhost:8080}) ;
\item enregistrer le fichier puis \textbf{redémarrer tous les services} depuis l'icône WampServer ;
\item tester dans le navigateur l'URL \texttt{http://localhost:8080}.
\end{enumerate}
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 6 — Réécriture de directives Apache]
\begin{enumerate}
\item Nouvelles directives :
\begin{lstlisting}[language=apacheconf]
Listen 9090
DocumentRoot "D:/sites"
\end{lstlisting}
On remarque que même sous Windows, on utilise des barres obliques \texttt{/} dans \texttt{httpd.conf}, et le chemin est placé entre guillemets.

\end{center}
\item Action obligatoire : \textbf{redémarrer le service Apache} (par exemple via l'icône WampServer : \og Redémarrer tous les services \fg{}), car Apache ne relit son fichier de configuration qu'au démarrage.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 7 — Démarrage et arrêt des services]
\begin{enumerate}
\item Deux méthodes de démarrage :
\begin{itemize}
\item \textbf{Méthode graphique} : clic gauche sur l'icône WampServer dans la zone de notification $\rightarrow$ \og Démarrer tous les services \fg{} (ou démarrer Apache et MySQL séparément dans leurs sous-menus respectifs).
\item \textbf{Via les services Windows} : ouvrir \texttt{services.msc} (touche Windows + R), repérer les services \texttt{wampapache64} et \texttt{wampmysqld64}, clic droit $\rightarrow$ \og Démarrer \fg{}.
\end{itemize}
\item Vérification sans navigateur : ouvrir l'invite de commandes et saisir :
\begin{lstlisting}
netstat -ano | findstr :80
\end{lstlisting}
Si Apache écoute bien, une ligne apparaît avec l'état \texttt{LISTENING} sur l'adresse \texttt{0.0.0.0:80} (ou \texttt{127.0.0.1:80}). La colonne finale donne le PID du processus, identifiable dans le Gestionnaire des tâches.
\item Il faut arrêter proprement les services pour éviter la \textbf{corruption des données} (MySQL peut laisser des tables dans un état incohérent si on le coupe brutalement), libérer les \textbf{ports et fichiers verrouillés} (sinon la désinstallation ou la mise à jour échoue avec des erreurs \og fichier en cours d'utilisation \fg{}) et garantir une réinstallation propre.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 9 — Boutique en ligne à Douala]
\begin{enumerate}
\item Définitions :
\begin{itemize}
\item \textbf{\cle{Serveur web}} : logiciel (comme Apache ou Nginx) installé sur une machine, capable de recevoir des requêtes HTTP envoyées par des navigateurs et de renvoyer en réponse des pages web (HTML, images, etc.).
\item \textbf{\cle{Hébergeur web}} : entreprise qui loue de l'espace disque et de la bande passante sur ses serveurs connectés en permanence à Internet, afin de rendre des sites accessibles 24 h/24 (ex. : OVH, LWS).
\end{itemize}
\item Hébergeurs web : \textbf{OVH}, \textbf{LWS} (on accepte aussi Hostinger, o2switch, ou un hébergeur local). Logiciels serveurs web : \textbf{Apache}, \textbf{Nginx} (on accepte aussi Microsoft IIS).
\item Tableau comparatif :
\begin{center}
\begin{tabularx}{\linewidth}{|l|X|X|}
\hline
\rowcolor{popblueL} \textbf{Critère} & \textbf{Hébergement local} & \textbf{Hébergeur professionnel} \\
\hline
Coût & Faible au départ (matériel existant), mais coûts cachés : électricité, onduleur, connexion & Abonnement mensuel/annuel, coût prévisible \\

\hline
Compétences requises & Élevées : configuration réseau, IP fixe, sécurité, pare-feu, maintenance & Faibles : l'hébergeur gère l'infrastructure, interface d'administration simple \\
\hline
\end{tabularx}
\end{center}
\item \textbf{Recommandation : l'hébergement professionnel.} Deux arguments :
\begin{itemize}
\item la boutique doit être accessible \textbf{24 h/24}, or les coupures d'électricité fréquentes à Douala rendraient un serveur local régulièrement hors ligne, ce qui ferait perdre des ventes ;
\item un hébergeur professionnel garantit une \textbf{bande passante suffisante}, une adresse IP fixe, un nom de domaine et une \textbf{sécurité} (pare-feu, sauvegardes, certificat HTTPS) difficiles à mettre en œuvre localement par une PME.
\end{itemize}
\item Les trois éléments constitutifs de XAMPP :
\begin{itemize}
\item le \textbf{serveur web (Apache)} : reçoit les requêtes HTTP du navigateur et renvoie les pages ;
\item le \textbf{préprocesseur (PHP)} : exécute les scripts PHP côté serveur (calculs, traitement des formulaires) et génère le HTML envoyé au client ;
\item le \textbf{serveur de données (MySQL/MariaDB)} : stocke et interroge les données de la boutique (produits, clients, commandes) via le langage SQL.
\end{itemize}
\end{enumerate}
\textbf{Barème indicatif (10 pts)} : définitions $2\times1$ pt ; exemples $4\times0,5$ pt ; tableau 2 pts ; recommandation justifiée 2 pts ; éléments constitutifs $3\times0,67$ pt.\par

\end{corrige}

\begin{corrige}[Exercice 10 — Configuration d'un serveur de lycée]
\begin{enumerate}
\item Apache refuse de démarrer car la directive \texttt{Listen 80} lui ordonne d'écouter sur le port 80, or ce port est \textbf{déjà occupé par un autre logiciel} : deux processus ne peuvent pas écouter simultanément sur le même port d'une même machine. Le socket ne peut pas être créé, d'où l'échec du démarrage.
\item Directives modifiées :
\begin{lstlisting}[language=apacheconf]
Listen 8081
ServerName localhost:8081
DocumentRoot "C:/wamp64/www"
\end{lstlisting}
Il faut ensuite enregistrer le fichier et \textbf{redémarrer les services} WampServer.
\item Le dossier \texttt{biblio} est placé dans le DocumentRoot \texttt{C:\textbackslash wamp64\textbackslash www}, donc il correspond au chemin \texttt{/biblio} dans l'URL. Le port 8081 devant être précisé :
\begin{center}
\texttt{http://localhost:8081/biblio/login.php}
\end{center}
\item Depuis un autre poste, on remplace \texttt{localhost} par l'adresse IP du serveur :
\begin{center}
\texttt{http://192.168.1.10:8081/biblio/login.php}
\end{center}
\textbf{Condition réseau} : les deux postes doivent être sur le \textbf{même réseau local} (même sous-réseau, ici \texttt{192.168.1.0/24}) et le \textbf{pare-feu} du poste serveur doit autoriser les connexions entrantes sur le port 8081.
\item Procédure complète d'hébergement local d'un site dynamique :
\begin{enumerate}
\item télécharger et installer un environnement intégré (WampServer) sur le poste serveur ;
\item démarrer les services Apache et MySQL et vérifier que l'icône passe au vert ;
\item copier les fichiers du site dans un sous-dossier du DocumentRoot (\texttt{C:\textbackslash wamp64\textbackslash www\textbackslash biblio}) ;
\item créer la base de données via phpMyAdmin et y importer le script SQL de l'application ;
\item adapter le fichier de connexion du site (hôte \texttt{localhost}, nom de la base, identifiants MySQL) ;
\item tester dans le navigateur l'URL \texttt{http://localhost/biblio} et vérifier le bon fonctionnement des pages.
\end{enumerate}
\end{enumerate}
\textbf{Barème indicatif (10 pts)} : explication 1,5 pt ; directives 1,5 pt ; URL locale 1,5 pt ; URL réseau + condition 2 pts ; procédure 3,5 pts (cohérence des étapes).\par
\textbf{Points de vigilance} : penser à modifier \emph{à la fois} \texttt{Listen} et \texttt{ServerName} ; ne pas oublier le port dans l'URL dès qu'il diffère de 80 ; citer explicitement le redémarrage du service ; pour la question 4, la condition réseau (même sous-réseau, pare-feu) est attendue en plus de l'URL.
\end{corrige}

\begin{corrige}[Exercice 11 — Projet de fin d'année]
\begin{enumerate}
\item \textbf{WampServer} est le plus adapté à un poste Windows. Arguments : il est \textbf{conçu spécifiquement pour Windows} (le \og W \fg{} de WAMP), donc parfaitement intégré au système ; il offre une \textbf{interface graphique simple} (icône de notification) permettant de démarrer/arrêter les services et d'accéder aux configurations sans ligne de commande, idéal pour des élèves. (XAMPP est aussi accepté s'il est justifié.)
\item Architecture de l'environnement :
\begin{popfigure}
\begin{tikzpicture}[

\node[box, right=of apache, align=center] (php){Préprocesseur\\ PHP};
\node[box, below=of php, align=center] (sql){Serveur de Données\\ MySQL};
% Requêtes
\draw[flux] (nav) -- node[above, font=\scriptsize] {Requête HTTP} (apache);
\draw[flux] (apache) -- node[above, font=\scriptsize] {Script PHP à exécuter} (php);

\legende{Architecture d'un environnement intégré : le navigateur envoie une requête HTTP à Apache, qui transmet les scripts au préprocesseur PHP ; PHP interroge MySQL, reçoit les résultats, génère le HTML qu'il renvoie à Apache, qui enfin envoie la réponse HTTP au client.}
\end{popfigure}
\item Correspondances :
\begin{itemize}
\item \texttt{http://localhost/notes/v1/bulletin.php} $\rightarrow$ \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash notes\textbackslash v1\textbackslash bulletin.php} ;
\item \texttt{C:\textbackslash xampp\textbackslash htdocs\textbackslash notes\textbackslash style.css} $\rightarrow$ \texttt{http://localhost/notes/style.css} (on remplace le DocumentRoot \texttt{C:\textbackslash xampp\textbackslash htdocs} par \texttt{http://localhost}).
\end{itemize}
\item Cause : après modification de la directive \texttt{Listen 80} en \texttt{Listen 8000}, Apache n'écoute plus sur le port 80. Or une URL sans port indiqué utilise \emph{implicitement} le port 80 : le navigateur contacte donc un port où plus aucun service n'écoute, d'où l'erreur de connexion. Nouvelle URL correcte :
\begin{center}
\texttt{http://localhost:8000/notes/v1/bulletin.php}
\end{center}
\item L'hébergement local ne suffit plus car le poste des élèves n'est \textbf{pas accessible depuis Internet} : il possède une adresse IP privée (non routable), n'est pas allumé en permanence et le réseau du lycée n'est pas ouvert vers l'extérieur. Les parents, chez eux, ne pourraient donc jamais atteindre le site.\par
\textbf{Solution de déploiement chez un hébergeur} :
\begin{enumerate}
\item choisir un hébergeur web (OVH, LWS, etc.) et souscrire une offre mutualisée avec PHP et MySQL ;
\item enregistrer un nom de domaine (par exemple \texttt{notes-lycee.cm}) ;
\item transférer les fichiers du site sur le serveur de l'hébergeur via un client FTP (FileZilla) ;
\item créer la base MySQL chez l'hébergeur et y importer les données (export/import via phpMyAdmin) ;
\item adapter le fichier de connexion (hôte, identifiants de l'hébergeur) puis tester le site en ligne.
\end{enumerate}
\end{enumerate}
\textbf{Barème indicatif (10 pts)} : choix justifié 1,5 pt ; schéma (4 composants + flux) 2,5 pts ; correspondances 2 pts ; explication du port + URL 2 pts ; limites de l'hébergement local + étapes de déploiement 2 pts.\par
\textbf{Points de vigilance} : le schéma doit faire apparaître les \emph{quatre} composants et le sens des flux (requête HTTP vers le serveur, page HTML en retour) ; rappeler qu'une URL sans port vise le port 80 par défaut ; pour le déploiement, citer le transfert FTP \emph{et} la migration de la base de données, deux étapes souvent oubliées.
\end{corrige}

\begin{bilan}
\textbf{Définitions clés}
\begin{itemize}
  \item \cle{Serveur web} : logiciel (ou machine) qui reçoit les requêtes \cle{HTTP} d'un client (navigateur) et renvoie des pages web. Exemples : \textbf{Apache}, \textbf{Nginx}, \textbf{IIS}.
  \item \cle{Service web} : application accessible via le web qui fournit des données à d'autres programmes (échange machine à machine, souvent en XML ou JSON).
  \item \cle{Hébergeur web} : entreprise qui met à disposition des serveurs connectés en permanence à Internet pour publier des sites (ex. : OVH, ou hébergeurs locaux au Cameroun).
  \item \cle{Environnement intégré} : paquet logiciel réunissant en une seule installation tout le nécessaire au développement web.
  \item \cle{DocumentRoot} : répertoire racine du serveur, seul dossier dont le contenu est accessible via HTTP.
  \item \cle{Port d'écoute} : numéro identifiant le service sur la machine ; par défaut \textbf{80} pour HTTP et \textbf{443} pour HTTPS.
\end{itemize}

\textbf{Architecture d'un environnement intégré (3 éléments)}
\begin{enumerate}
  \item Le \cle{serveur web} (Apache) : traite les requêtes HTTP et sert les fichiers.
  \item Le \cle{serveur de données} (MySQL/MariaDB) : stocke et interroge les bases de données via SQL.
  \item Le \cle{préprocesseur} (PHP) : exécute les scripts côté serveur et génère le HTML dynamique.
\end{enumerate}

\textbf{Méthodes express}
\begin{itemize}
  \item \emph{Démarrer un service} : lancer WampServer/XAMPP, vérifier l'icône (verte = services actifs ; orange/rouge = problème, souvent un port occupé).
  \item \emph{Changer le port d'écoute} : ouvrir \texttt{httpd.conf}, modifier la directive \texttt{Listen 80} en \texttt{Listen 8080}, redémarrer Apache, puis accéder via \texttt{http://localhost:8080/}.
  \item \emph{Héberger localement un site} : copier les fichiers du projet dans le DocumentRoot (\texttt{C:\textbackslash wamp64\textbackslash www} ou \texttt{C:\textbackslash xampp\textbackslash htdocs}), importer la base via phpMyAdmin, ouvrir \texttt{http://localhost/monprojet/}.
  \item \emph{Tester une page PHP} : elle doit obligatoirement passer par le serveur (\texttt{http://localhost/...}) et jamais être ouverte directement en double-cliquant sur le fichier.
\end{itemize}
\end{bilan}

\end{itemize}
