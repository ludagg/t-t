\begin{exercice}[Gestion dynamique d'un catalogue de modules]
On souhaite développer une interface d'administration pour un établissement de formation. La page unique \texttt{admin.html} doit permettre de saisir des modules (code, intitulé, volume horaire, coefficient), de les afficher dans un tableau récapitulatif triable par colonne, et de calculer le total des volumes horaires et la moyenne des coefficients. Aucune base de données ni backend n'est utilisé ; la persistance se fait via \texttt{localStorage}.

\begin{enumerate}
    \item \textbf{Structure HTML (3 pts).} Écrire le squelette HTML5 complet. Le formulaire de saisie (identifié \texttt{form-module}) doit contenir : un \texttt{select} pour le semestre (S1, S2, S3, S4), des \texttt{input} adaptés pour les autres champs (types, contraintes \texttt{min}, \texttt{max}, \texttt{pattern}, \texttt{required}), et deux boutons : « Ajouter » (type \texttt{submit}) et « Réinitialiser » (type \texttt{reset}). Prévoir un \texttt{section} pour le tableau (identifié \texttt{vue-tableau}) avec \texttt{thead}, \texttt{tbody} (identifié \texttt{corps-tableau}), \texttt{tfoot} pour les totaux, et une zone d'alerte (identifiée \texttt{zone-message}) pour les retours utilisateur.
    \item \textbf{Modèle de données et stockage (3 pts).} Définir la structure d'un objet \texttt{Module} en JavaScript. Écrire la fonction \texttt{chargerCatalogue()} qui récupère le tableau d'objets depuis \texttt{localStorage} (clé \texttt{'catalogueModules'}), gère l'absence de donnée (retourne un tableau vide), et appelle \texttt{rendreTableau()}.
    \item \textbf{Rendu et tri (4 pts).} Implémenter \texttt{rendreTableau(liste)}. Cette fonction vide \texttt{corps-tableau}, génère les \texttt{tr}/\texttt{td} pour chaque module, ajoute une colonne d'action avec un bouton « Supprimer » (attribut \texttt{data-code} pour identifier le module), met à jour le \texttt{tfoot} (total volume horaire, moyenne coefficient arrondie à 2 décimales). Implémenter le tri dynamique : un clic sur un \texttt{th} (sauf colonne action) trie \texttt{liste} selon la colonne (ordre croissant/décroissant alterné, indicateur visuel ▼/▲ dans le \texttt{th}) et rafraîchit l'affichage.
    \item \textbf{Gestion des événements et validation (4 pts).} Au \texttt{submit} du formulaire : empêcher le rechargement, valider côté client (code unique non vide, volume horaire entier $>0$, coefficient nombre $>0$). En cas d'erreur, afficher le message dans \texttt{zone-message} (classe \texttt{erreur}) sans vider le formulaire. En cas de succès : ajouter l'objet au catalogue, sauvegarder dans \texttt{localStorage}, rafraîchir le tableau, vider le formulaire, afficher un message de succès (classe \texttt{succes}). Gérer la suppression via délégation d'événement sur \texttt{corps-tableau} (confirmation \texttt{confirm()} avant suppression effective).
    \item \textbf{Analyse critique (2 pts).} Expliquer pourquoi la validation côté client est insuffisante pour garantir l'intégrité des données dans une application réelle. Citer deux types d'attaques ou de contournements possibles. Proposer une architecture complémentaire.
\end{enumerate}
\end{exercice}

\begin{exercice}[Formulaire d'inscription multi-étapes avec validation contextuelle]
On conçoit un formulaire d'inscription en trois étapes (fieldsets) : 1. Identité (Nom, Prénom, Email, Date de naissance), 2. Coordonnées (Adresse, Ville, Code postal, Téléphone), 3. Sécurité (Mot de passe, Confirmation, Question secrète, Réponse). La navigation se fait par boutons « Suivant » / « Précédent » ; le bouton « Valider » n'apparaît qu'à l'étape 3. Un indicateur de progression (barre ou étapes numérotées) montre l'avancement.

\begin{enumerate}
    \item \textbf{Architecture HTML sémantique (3 pts).} Produire le code HTML du formulaire (\texttt{id="inscription"}). Utiliser \texttt{fieldset} pour chaque étape (attribut \texttt{hidden} géré en JS), \texttt{legend} pour les titres. Associer correctement chaque \texttt{label} à son \texttt{input} (\texttt{for}/\texttt{id}). Choisir les types d'\texttt{input} les plus pertinents (email, tel, date, password, number pour code postal). Ajouter les attributs de contrainte HTML5 (\texttt{required}, \texttt{minlength}, \texttt{pattern} pour le téléphone français, \texttt{min}/\texttt{max} pour la date de naissance : majeur, $<100$ ans). Prévoir un \texttt{output} ou \texttt{span} de classe \texttt{erreur-champ} après chaque champ pour les messages d'erreur JS.
    \item \textbf{Machine à états de navigation (3 pts).} En JavaScript, créer un objet \texttt{FormWizard} (ou module IIFE) encapsulant : l'index de l'étape courante, la liste des \texttt{fieldset}, les références aux boutons de navigation. Implémenter \texttt{afficherEtape(index)} qui gère l'attribut \texttt{hidden}, l'état \texttt{disabled} des boutons « Précédent » (étape 0) / « Suivant » (dernière étape), et met à jour l'indicateur de progression.
    \item \textbf{Validation différentielle par étape (4 pts).} Implémenter \texttt{validerEtapeActuelle()}. Cette fonction ne valide \textbf{que} les champs visibles de l'étape courante. Elle utilise l'API \texttt{Constraint Validation} (\texttt{checkValidity()}, \texttt{validity}) pour la validation native, mais ajoute des règles personnalisées : unicité de l'email (simulée via un \texttt{Set} d'emails « déjà pris » fourni), cohérence « Mot de passe / Confirmation » (étape 3), force du mot de passe (regex : 8 car., 1 maj, 1 min, 1 chiffre, 1 spécial). Afficher les messages d'erreur dans les \texttt{span.erreur-champ} correspondants et ajouter la classe \texttt{invalide} sur l'\texttt{input}. Retourner \texttt{true} si l'étape est valide. Le bouton « Suivant » ne passe à l'étape suivante que si cette fonction retourne \texttt{true}.
    \item \textbf{Soumission finale et agrégation (2 pts).} Au \texttt{submit} final (étape 3 valide), construire un objet \texttt{FormData} ou un objet littéral contenant toutes les données des 3 étapes (exclure la confirmation de mot de passe). Simuler l'envoi \texttt{fetch('/api/inscription', ...)} avec \texttt{JSON.stringify}. Gérer la réponse (succès/erreur réseau) et afficher un message global.
    \item \textbf{Accessibilité et UX (2 pts).} Citer 3 attributs ARIA ou rôles HTML à ajouter pour rendre ce formulaire multi-étapes accessible aux lecteurs d'écran (navigation, région live pour erreurs, indication d'étape courante). Justifier l'intérêt de la validation \textbf{au fur et à mesure} (sur événement \texttt{input} ou \texttt{blur}) en plus de la validation à la navigation.
\end{enumerate}
\end{exercice}

\begin{exercice}[Tableau de bord interactif : filtrage, pagination et export]
Une page \texttt{dashboard.html} affiche une liste d'étudiants (Matricule, Nom, Prénom, Filière, Niveau, Moyenne) dans un tableau paginé (10 lignes/page). Les données initiales (50 entrées) sont fournies dans un fichier \texttt{data/etudiants.json} chargé via \texttt{fetch} au chargement de la page. L'interface propose : un champ de recherche global (filtre sur toutes les colonnes textuelles), un sélecteur de filtre par Filière, un tri par colonne (clic sur en-tête), et un bouton « Exporter CSV » (uniquement les lignes filtrées et triées courantes).

\begin{enumerate}
    \item \textbf{Chargement asynchrone et état initial (2 pts).} Écrire la fonction asynchrone \texttt{initDashboard()}. Elle doit : afficher un état « Chargement... » dans \texttt{tbody}, récupérer le JSON via \texttt{fetch}, gérer les erreurs HTTP/réseau (affichage message d'erreur dans le tableau), stocker les données brutes dans une variable module \texttt{let donneesBrutes = []}, et appeler \texttt{appliquerFiltresEtRendu()}.
    \item \textbf{Pipeline de transformation des données (4 pts).} Implémenter \texttt{appliquerFiltresEtRendu()}. Cette fonction chaîne les opérations pures (sans effet de bord sur le DOM) sur \texttt{donneesBrutes} :
    \begin{enumerate}
        \item Filtre texte (insensible à la casse, recherche partielle sur Nom, Prénom, Matricule).
        \item Filtre Filière (valeur « Toutes » = pas de filtre).
        \item Tri (selon \texttt{colonneTri} et \texttt{ordreTri} stockés en état).
    \end{enumerate}
    Elle met à jour \texttt{donneesFiltrees} (résultat final), réinitialise la page courante à 1, et appelle \texttt{rendrePage()} et \texttt{rendrePagination()}.
    \item \textbf{Rendu paginé et performances (3 pts).} Implémenter \texttt{rendrePage()}. Calculer les indices de début/fin selon \texttt{pageCourante} et \texttt{TAILLE\_PAGE=10}. Utiliser un \texttt{DocumentFragment} pour construire les \texttt{tr} (création via \texttt{document.createElement} ou \texttt{template} \texttt{content.cloneNode(true)}) et les ajouter au fragment, puis vider \texttt{tbody} (\texttt{innerHTML=''}) et y ajouter le fragment en une seule opération. Mettre à jour l'affichage « Page X sur Y / N résultats totaux ».
    \item \textbf{Génération CSV côté client (3 pts).} Implémenter \texttt{exporterCSV()}. Construire la chaîne CSV (en-têtes + lignes de \texttt{donneesFiltrees}) en échappant correctement les guillemets doubles et les retours à la ligne dans les cellules (RFC 4180). Créer un \texttt{Blob} de type \texttt{text/csv;charset=utf-8;}, générer une URL objet (\texttt{URL.createObjectURL}), déclencher le téléchargement via un lien \texttt{<a download="etudiants\_export.csv">} simulé, puis révoquer l'URL. Gérer le BOM UTF-8 (\texttt{\textbackslash uFEFF}) pour Excel.
    \item \textbf{Architecture et maintenabilité (2 pts).} Le code actuel mélange logique métier (filtres, tri, CSV) et manipulation DOM dans les mêmes fonctions. Proposer une refactorisation selon le pattern \textbf{MVC} ou \textbf{Modèle-Vue-Contrôleur} (ou MVVM) adaptée au Vanilla JS. Décrire succinctement les responsabilités de chaque couche (Modèle : état + données + persistance ; Vue : rendu + écouteurs UI ; Contrôleur : orchestration). Quel avantage pour les tests unitaires ?
\end{enumerate}
\end{exercice}

\begin{exercice}[Sécurité et limites de la validation côté client]
On considère l'exercice 1 (Catalogue de modules). Un étudiant malveillant ouvre les outils de développement (F12), modifie le HTML pour supprimer l'attribut \texttt{required} sur le champ « Code », change le \texttt{type="number"} du volume horaire en \texttt{type="text"}, et injecte un \texttt{<script>alert(1)</script>} dans l'intitulé via la console : \texttt{document.querySelector('\#intitule').value = '<script>alert(1)</script>'}.

\begin{enumerate}
    \item \textbf{Contournement des contraintes HTML5 (2 pts).} Expliquer pourquoi la suppression des attributs \texttt{required}, \texttt{min}, \texttt{max}, \texttt{pattern} dans l'inspecteur permet de soumettre des données invalides malgré le code JavaScript de validation écrit dans l'exercice 1 (question 4). Quel événement JavaScript est déclenché par le \texttt{submit} natif du formulaire même si les contraintes HTML sont violées après modification du DOM ?
    \item \textbf{Injection XSS stockée via localStorage (3 pts).} Si la fonction \texttt{rendreTableau()} insère l'intitulé via \texttt{cellule.textContent = module.intitule}, l'injection est-elle neutralisée ? Et si elle utilise \texttt{cellule.innerHTML += module.intitule} ? Démontrer par l'exemple. Comment l'attaque devient-elle « stockée » et persistante pour les autres utilisateurs (si partie partagée) ou pour la même session ? Proposer la fonction d'échappement HTML minimale à appliquer systématiquement avant tout \texttt{innerHTML}.
    \item \textbf{Validation du code unique : faille de course (TOCTOU) (2 pts).} La vérification « code unique » se fait en JS en parcourant \texttt{catalogueModules} avant \texttt{push}. Imaginer un scénario (même utilisateur, onglets multiples, ou manipulation console rapide) où deux modules avec le même code sont ajoutés. Expliquer le principe \textit{Time-Of-Check to Time-Of-Use}. Pourquoi \texttt{localStorage} n'offre-t-il pas de transactions atomiques ?
    \item \textbf{Principes de défense en profondeur (3 pts).} Citer et expliquer 3 mesures complémentaires \textbf{côté serveur} (backend) indispensables pour sécuriser réellement cette fonctionnalité d'ajout de module, même si le frontend est parfaitement codé. (Indices : validation schéma, authentification/autorisation, en-têtes HTTP, sanitization sortie).
    \item \textbf{Content Security Policy (2 pts).} Écrire l'en-tête HTTP \texttt{Content-Security-Policy} le plus restrictif possible pour cette page (scripts inline interdits, styles inline interdits, fontes/images self, pas de frames, pas d'objets), qui aurait empêché l'exécution du \texttt{<script>alert(1)</script>} même s'il avait été injecté via \texttt{innerHTML}.
\end{enumerate}
\end{exercice}
