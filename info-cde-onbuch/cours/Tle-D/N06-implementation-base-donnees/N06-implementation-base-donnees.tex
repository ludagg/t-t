\coursec{Bases de données, SGBD et langage SQL}

Au lycée bilingue de Yaoundé, le censeur gère encore les \num{2400} élèves dans de gros cahiers cartonnés : un cahier pour les inscriptions, un autre pour les notes, un troisième pour les paiements de la scolarité. À chaque conseil de classe, il passe trois jours entiers à rechercher, recopier et recouper des informations, au risque d'oublier un élève ou de mélanger deux homonymes. Excédé, le proviseur prend une décision : le lycée se dotera d'une \cle{base de données}, et ce sont les élèves de Terminale scientifique qui auront la mission de la construire et de l'interroger.

Comment créer les tables ? Comment y insérer les \num{2400} élèves ? Comment corriger une erreur de saisie sans tout recopier ? Comment retrouver \emph{en une seconde} tous les élèves de Tle C nés après 2006 ? Toutes ces opérations reposent sur trois piliers : la \cle{base de données} (les informations organisées), le \cle{SGBD} (le logiciel qui les gère) et le langage \cle{SQL} (le langage qui permet de dialoguer avec ce logiciel). C'est toute la puissance de ce trio que cette leçon va dévoiler, étape par étape.

\courssub{Notion de base de données}

\textbf{Intuition : à quel problème répond une base de données ?}\par
Imagine le cahier des inscriptions du lycée. Pour retrouver un élève, on feuillette page par page ; pour corriger une date de naissance, on rature ; pour connaître les élèves de Tle C, on relit tout le cahier. Les informations sont dupliquées (le nom d'un élève figure dans le cahier des notes \emph{et} dans celui des paiements), incohérentes (une date corrigée ici, oubliée là) et fragiles (un cahier mouillé, et tout est perdu). Une base de données résout exactement ces trois maux : elle \emph{centralise} les données, les \emph{structure} de façon rigoureuse et les conserve de manière \emph{permanente} sur un support numérique, où des milliers de recherches par seconde deviennent possibles.

\begin{definition}[Base de données]
Une \cle{base de données} (en abrégé \textbf{BD}) est un ensemble \textbf{structuré et organisé} de données relatives à un \textbf{même domaine}, stockées de façon \textbf{permanente} sur un support numérique, et accessibles à plusieurs utilisateurs.
\end{definition}

Décortiquons les quatre caractéristiques de cette définition :

\begin{itemize}
\item \textbf{Structurée} : les données ne sont pas jetées en vrac ; elles sont rangées dans des \emph{tables} (tableaux à deux dimensions), elles-mêmes décrites par des règles précises (chaque colonne a un nom et un type).
\item \textbf{Organisée autour d'un même domaine} : la base du lycée ne contient que ce qui concerne la vie scolaire (élèves, classes, notes, paiements), pas les stocks d'une boutique.
\item \textbf{Permanente} : les données survivent à l'extinction de l'ordinateur, car elles sont enregistrées sur le disque dur, contrairement aux variables d'un programme qui vivent en mémoire vive.
\item \textbf{Partageable} : le censeur, le comptable et le proviseur peuvent consulter la même base, chacun selon ses droits.
\end{itemize}

\begin{exemplebox}[La base fil conducteur : GESTION\_LYCEE]
Toute cette leçon s'appuiera sur une même base de données, nommée \texttt{GESTION\_LYCEE}, qui contient (entre autres) deux tables :
\begin{itemize}
\item la table \texttt{ELEVE} : matricule, nom, prénom, date de naissance, sexe, code de la classe ;
\item la table \texttt{CLASSE} : code de la classe, libellé (par exemple « Tle C 1 »), effectif, salle.
\end{itemize}
Chaque élève appartient à une classe : on dit que les deux tables sont \emph{reliées}. Ce lien sera exploité à la fin de la leçon grâce aux jointures.
\end{exemplebox}

\courssub{Le SGBD : le logiciel qui gère la base}

\textbf{Intuition.}\par
Une base de données n'est qu'un ensemble de fichiers sur un disque : elle ne fait rien toute seule. Il faut un logiciel « chef d'orchestre » qui reçoive les demandes des utilisateurs, vérifie les droits d'accès, garantit la cohérence des données et range physiquement les informations sur le disque. Ce logiciel, c'est le SGBD.

\begin{definition}[SGBD]
Un \cle{SGBD} (Système de Gestion de Bases de Données) est un \textbf{logiciel} qui permet de \textbf{créer}, \textbf{manipuler} et \textbf{administrer} une base de données : il assure le stockage, la recherche, la mise à jour, la sécurité et la cohérence des données.
\end{definition}

Les quatre \cle{fonctions de manipulation des données} offertes par tout SGBD sont à connaître par cœur :

\begin{center}

\begin{attention}[SGBD $\neq$ base de données]
L'erreur la plus fréquente au Baccalauréat est de confondre les deux notions. La \textbf{base de données} est l'ensemble des \emph{données organisées} (les fichiers contenant les élèves, les classes...) ; le \textbf{SGBD} est le \emph{logiciel} qui les gère (MySQL, Access...). Dire « MySQL est une base de données » est faux : MySQL est un SGBD, qui permet de créer et d'exploiter des bases de données.
\end{attention}

\item \textbf{MySQL} : SGBD libre et gratuit, très répandu dans le monde professionnel, manipulé en \emph{mode console} (on tape des instructions SQL dans une fenêtre de commandes) ou via des outils graphiques. C'est lui qui équipe la majorité des sites web et des serveurs d'entreprise.
\end{itemize}

\courssub{Le langage SQL : parler au SGBD}

\textbf{Intuition.}\par
Le SGBD est puissant, mais il ne comprend ni le français ni l'anglais courant. Pour lui demander « donne-moi les élèves de Tle C nés après 2006 », il faut un langage rigoureux, sans ambiguïté, avec une grammaire stricte. Ce langage existe, il est international, et il s'appelle SQL.

\begin{definition}[SQL]
Le langage \cle{SQL} (\emph{Structured Query Language}, « langage structuré d'interrogation ») est le langage \textbf{normalisé} de définition, de manipulation et d'interrogation des \textbf{bases de données relationnelles}.
\end{definition}

\begin{definition}[Requête]
Une \cle{requête} est une \textbf{instruction SQL} envoyée au SGBD pour obtenir une \textbf{action} (créer une table, insérer un élève, modifier une donnée) ou un \textbf{résultat} (la liste des élèves d'une classe).
\end{definition}

\begin{propriete}[Portabilité du SQL (admise)]
Tout SGBD relationnel comprend le langage SQL, qui est une \textbf{norme internationale}. Par conséquent, une requête écrite pour MySQL fonctionne, à quelques détails près, sous Access, PostgreSQL ou SQLite : les requêtes sont \textbf{portables} d'un SGBD à l'autre. Apprendre SQL, c'est apprendre à dialoguer avec \emph{tous} les SGBD relationnels à la fois.
\end{propriete}

\begin{savaistu}[SQL, un demi-siècle de bons et loyaux services]
SQL est né dans les laboratoires d'\textbf{IBM} au début des années 1970, sous le nom de SEQUEL, à partir des travaux du mathématicien Edgar Frank Codd sur le modèle relationnel. Normalisé dès 1986, il est devenu un \textbf{standard international} (ISO) régulièrement enrichi. Aujourd'hui, il est partout : les banques l'utilisent pour gérer les comptes, la CAMTEL pour gérer ses abonnés à la fibre optique, et MTN Cameroun pour suivre des millions de clients et leurs forfaits. Chaque rechargement de crédit déclenche des requêtes SQL !
\end{savaistu}

\textbf{Les deux grandes familles de requêtes.}\par
Il est essentiel de distinguer, dès maintenant, deux catégories d'instructions SQL :

\begin{itemize}
\item Les \textbf{requêtes de définition des données} (LDD) agissent sur la \emph{structure} de la base : créer une table (\texttt{CREATE TABLE}), modifier sa structure (\texttt{ALTER TABLE}), la détruire (\texttt{DROP TABLE}). Elles fabriquent les « tiroirs ».
\item Les \textbf{requêtes de manipulation des données} (LMD) agissent sur le \emph{contenu} des tables : insérer (\texttt{INSERT INTO}), modifier (\texttt{UPDATE}), supprimer (\texttt{DELETE}) et sélectionner (\texttt{SELECT}) des données. Elles remplissent et vident les tiroirs.
\end{itemize}

\begin{aretenir}[Convention d'écriture du SQL]
\begin{itemize}
\item Les \textbf{mots-clés} du langage s'écrivent en \textbf{MAJUSCULES} : \texttt{SELECT}, \texttt{FROM}, \texttt{WHERE}, \texttt{INSERT INTO}...
\item Les noms des tables et des colonnes s'écrivent en minuscules ou en majuscules, selon le choix du concepteur (nous écrirons les tables en majuscules : \texttt{ELEVE}, \texttt{CLASSE}).
\item Chaque instruction se termine par un \textbf{point-virgule} \texttt{;} : c'est lui qui signale au SGBD la fin de l'ordre.
\end{itemize}
\end{aretenir}

\begin{attention}[Le point-virgule oublié]
En mode console MySQL, si tu valides une instruction sans le \texttt{;} final, le SGBD \emph{attend la suite} et affiche une flèche \texttt{->} : il ne s'agit pas d'une erreur, tape simplement \texttt{;} puis Entrée. Autre piège : SQL n'est pas sensible à la casse pour les mots-clés (\texttt{select} fonctionne), mais respecter la convention des majuscules rend tes requêtes lisibles — et c'est ce qu'attend le correcteur au Baccalauréat.
\end{attention}

\courssub{Premier contact avec SQL}

Pour fixer les idées, voici un premier aperçu des quatre fonctions de manipulation appliquées à la table \texttt{ELEVE} de notre base \texttt{GESTION\_LYCEE}. Chaque instruction sera étudiée en détail dans les sections suivantes ; observe pour l'instant la logique générale : un verbe d'action, une table, des précisions.

\begin{lstlisting}[language=SQL]
-- Insertion : inscrire un nouvel eleve dans la table ELEVE
INSERT INTO ELEVE (matricule, nom, prenom, date_naiss, sexe, code_classe)
VALUES ('LB2401', 'NGONO', 'Ariane', '2006-03-15', 'F', 'TC1');

-- Selection : retrouver les eleves de Tle C 1 nes apres 2006
SELECT nom, prenom
FROM ELEVE
WHERE code_classe = 'TC1' AND date_naiss > '2006-12-31';

-- Modification : corriger la date de naissance d'un eleve
UPDATE ELEVE
SET date_naiss = '2006-03-25'
WHERE matricule = 'LB2401';

-- Suppression : radier un eleve qui a quitte le lycee
DELETE FROM ELEVE
WHERE matricule = 'LB2401';
\end{lstlisting}

Remarque la structure commune : un \textbf{mot-clé d'action} en majuscules ouvre l'instruction, le nom de la \textbf{table} suit, puis viennent les \textbf{conditions} ou les \textbf{valeurs}, et le tout se termine par un \texttt{;}.

\begin{exoresolu}[Identifier les notions dans un scénario]
Le comptable du lycée ouvre le logiciel MySQL, se connecte à la base \texttt{GESTION\_LYCEE} et tape une instruction pour obtenir la liste des élèves n'ayant pas encore payé la scolarité. Pour chaque élément souligné de cette phrase, dire s'il s'agit de la base de données, du SGBD, du langage SQL ou d'une requête.
\tcblower
Analysons chaque élément :
\begin{enumerate}
\item \textbf{MySQL} : c'est le \textbf{SGBD}, c'est-à-dire le logiciel qui gère la base ;
\item \textbf{GESTION\_LYCEE} : c'est la \textbf{base de données}, l'ensemble structuré des données du lycée ;
\item \textbf{l'instruction tapée} (par exemple \texttt{SELECT nom FROM ELEVE WHERE scolarite = 'non paye' ;}) : c'est une \textbf{requête}, écrite en \textbf{SQL}, le langage normalisé compris par le SGBD.
\end{enumerate}
Ce scénario illustre la chaîne complète : l'utilisateur formule une \emph{requête} en \emph{SQL}, que le \emph{SGBD} exécute sur la \emph{base de données} pour renvoyer le résultat.
\end{exoresolu}

\item On distingue les requêtes de \textbf{définition} (structure : \texttt{CREATE}, \texttt{ALTER}, \texttt{DROP}) et les requêtes de \textbf{manipulation} (contenu : \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}, \texttt{SELECT}).

\end{itemize}

Maintenant que le décor est planté — la base, le logiciel, le langage —, la prochaine étape consiste à apprendre à \emph{construire} les tables : types de données et contraintes d'intégrité nous attendent.

\coursec{Types de données et contraintes d'intégrité}

Dans la section précédente, nous avons découvert ce qu'est une \cle{base de données}, le rôle du \cle{SGBD} et le langage \cle{SQL} qui permet de dialoguer avec lui. Nous savons donc désormais \emph{à qui} nous adresser pour stocker les informations du lycée. Reste une question essentielle : \emph{comment} décrire précisément chaque information à enregistrer ?

Imagine la secrétaire du lycée bilingue de Bafoussam qui reçoit une fiche d'inscription vierge. Sur cette fiche, chaque case a une nature bien précise : la case « matricule » attend un code court, la case « nom » attend du texte, la case « date de naissance » attend une date, la case « effectif de la classe » attend un nombre entier. Si un élève écrit « bonjour » dans la case date de naissance, la secrétaire refuse la fiche. Le SGBD fonctionne exactement pareil : avant de créer une table, on doit déclarer le \cle{type} de chaque colonne (ce qu'elle peut contenir) et ses \cle{contraintes} (les règles qu'elle doit respecter). C'est l'objet de cette section.

\courssub{Notion de type de donnée}

\begin{definition}[Type de donnée]
Un \cle{type de donnée} est la nature des valeurs qu'une colonne (attribut) d'une table est autorisée à contenir. Il est déclaré à la création de la table, juste après le nom de la colonne. Le SGBD rejette toute valeur qui ne respecte pas le type déclaré.
\end{definition}

Pourquoi est-ce si important ? Trois raisons concrètes :

\begin{itemize}
\item \textbf{La cohérence} : impossible d'enregistrer le texte \texttt{'abc'} dans une colonne déclarée entière ; le SGBD bloque l'erreur dès la saisie.
\item \textbf{L'économie de mémoire} : un entier occupe quelques octets, un long texte beaucoup plus ; choisir le bon type évite de gaspiller l'espace disque du serveur.
\item \textbf{Des calculs corrects} : on peut additionner deux colonnes de type \texttt{INT}, trier des dates chronologiquement, ce qui serait impossible si tout était stocké comme du texte.
\end{itemize}

Le programme officiel retient quatre types, que l'on retrouve dans Access et MySQL. Étudions-les un par un.

\textbf{Le type CHAR(n) : chaîne de longueur fixe}\par
\texttt{CHAR(n)} désigne une chaîne de caractères de \emph{longueur exactement égale à} $n$. Si la valeur saisie est plus courte, le SGBD la \emph{complète automatiquement par des espaces} à droite jusqu'à atteindre $n$ caractères. Ce type convient aux codes normalisés dont la longueur est toujours la même : un code de classe \texttt{'TC1'} dans un \texttt{CHAR(4)} sera stocké \texttt{'TC1 '} (avec un espace), un indicatif téléphonique, un code postal, etc.

\textbf{Le type VARCHAR(n) : chaîne de longueur variable}\par
\texttt{VARCHAR(n)} désigne une chaîne de caractères de \emph{longueur variable, limitée à au plus} $n$ caractères. Ici, aucun espace n'est ajouté : la valeur occupe exactement la place nécessaire. C'est le type idéal pour les informations textuelles dont la longueur varie d'une ligne à l'autre : un nom d'élève (\texttt{VARCHAR(30)}), une adresse, une ville.

\begin{methode}[Choisir entre CHAR et VARCHAR]
Pour décider du type d'une colonne textuelle, pose-toi une seule question : la longueur de la valeur est-elle \emph{fixe et connue à l'avance} ?
\begin{enumerate}
\item Si la valeur a \textbf{toujours la même longueur} (code, matricule normalisé, indicatif), choisis \texttt{CHAR(n)} avec $n$ égal à cette longueur exacte.
\item Si la longueur \textbf{varie d'une ligne à l'autre} (nom, prénom, adresse), choisis \texttt{VARCHAR(n)} avec $n$ légèrement supérieur à la plus longue valeur prévisible.
\item En cas de doute, choisis \texttt{VARCHAR} : il est plus souple et n'ajoute jamais d'espaces parasites.
\end{enumerate}
\end{methode}

\textbf{Le type INT : nombre entier}\par
\texttt{INT} (abréviation de \emph{integer}, entier) désigne un nombre entier relatif, sans partie décimale. On l'utilise pour tout ce qui se compte ou se numérote : un effectif de classe, une année de naissance, un numéro d'ordre, une quantité en stock dans la boutique du lycée.

\textbf{Le type DATE : les dates}\par
\texttt{DATE} désigne une date calendaire. En SQL, une date s'écrit \emph{entre apostrophes} et au format international \texttt{'AAAA-MM-JJ'} : année sur quatre chiffres, puis le mois sur deux chiffres, puis le jour sur deux chiffres, séparés par des tirets. Par exemple, le 15 mars 2007 s'écrit \texttt{'2007-03-15'}.

\begin{attention}[Le format des dates : l'erreur classique]
L'erreur la plus fréquente des débutants est d'écrire une date « à la française » : \texttt{'15/03/2007'}. \textbf{SQL refuse ce format.} La date doit être écrite au format \texttt{'AAAA-MM-JJ'}, entre apostrophes, avec des tirets : \texttt{'2007-03-15'}. Retiens l'ordre : \textbf{année, mois, jour}, du plus grand au plus petit. Une date mal formatée provoque soit une erreur, soit pire : une date incorrecte silencieusement enregistrée.
\end{attention}

\courssub{Les contraintes d'intégrité}

Déclarer un type ne suffit pas. Reprenons notre fiche d'inscription : la secrétaire exige aussi que la case « nom » ne soit \emph{jamais vide}, que deux élèves n'aient \emph{jamais le même matricule}, et que la classe indiquée \emph{existe réellement} dans l'établissement. Ces règles, en SQL, s'appellent des contraintes d'intégrité.

\begin{definition}[Contrainte d'intégrité]
Une \cle{contrainte d'intégrité} est une règle déclarée sur une colonne (ou une table) que le SGBD fait respecter en permanence. Toute insertion ou modification qui violerait la contrainte est \emph{rejetée} avec un message d'erreur. Les contraintes garantissent l'exactitude et la cohérence des données.
\end{definition}

\textbf{La contrainte PRIMARY KEY : l'identifiant unique}\par

Dans un lycée de $1\,500$ élèves, deux élèves peuvent s'appeler « Ngo Bell Marie ». Comment distinguer leurs dossiers sans ambiguïté ? Grâce au matricule : un code attribué à un élève et à lui seul. C'est exactement le rôle de la clé primaire.

\begin{definition}[Clé primaire]
La \cle{clé primaire} (\texttt{PRIMARY KEY}) d'une table est une colonne (ou un ensemble de colonnes) qui \emph{identifie de façon unique chaque ligne} de la table. Une valeur de clé primaire doit être :
\begin{itemize}
\item \textbf{unique} : deux lignes ne peuvent jamais avoir la même valeur ;
\item \textbf{non nulle} : la valeur est obligatoirement renseignée.
\end{itemize}
\end{definition}

\begin{propriete}[Unicité de la clé primaire]
Une table ne peut avoir qu'\textbf{une seule clé primaire}. En revanche, elle peut posséder \emph{plusieurs} contraintes \texttt{NOT NULL} et \emph{plusieurs} contraintes \texttt{REFERENCES} sur des colonnes différentes.
\end{propriete}

\textbf{La contrainte NOT NULL : la valeur obligatoire}\par

\begin{definition}[NOT NULL]
La contrainte \cle{NOT NULL} appliquée à une colonne interdit l'absence de valeur (la valeur \texttt{NULL}, c'est-à-dire « vide » ou « inconnue ») pour cette colonne. Toute ligne insérée doit obligatoirement fournir une valeur.
\end{definition}

Exemple : le nom d'un élève doit être \texttt{NOT NULL} (un élève sans nom n'a pas de sens dans le fichier), alors que son numéro de téléphone peut rester vide si sa famille n'en a pas.

\textbf{La contrainte REFERENCES : la clé étrangère}\par

Venons-en à la règle la plus subtile. Le lycée gère deux tables : \texttt{CLASSE} (les classes existantes) et \texttt{ELEVE} (les élèves inscrits). Chaque élève appartient à une classe : on stocke donc dans \texttt{ELEVE} une colonne \texttt{codeClasse}. Mais comment empêcher qu'on inscrive un élève dans la classe \texttt{'ZZ9'} qui n'existe pas ? En déclarant que \texttt{codeClasse} de \texttt{ELEVE} \emph{référence} la clé primaire de \texttt{CLASSE}.

\begin{definition}[Clé étrangère]
Une \cle{clé étrangère} est une colonne d'une table qui fait référence à la clé primaire d'une autre table. Elle se déclare avec la contrainte \texttt{REFERENCES} suivie du nom de la table et de la colonne référencées :
\begin{center}
\texttt{codeClasse CHAR(4) REFERENCES CLASSE(codeClasse)}
\end{center}
Elle garantit l'\emph{intégrité référentielle} : toute valeur saisie dans la clé étrangère doit exister comme clé primaire dans la table référencée (ou être \texttt{NULL} si la colonne l'autorise).
\end{definition}

\courssub{Choix raisonné des types et des contraintes}

Concevoir une table, c'est raisonner colonne par colonne. Pour chaque information, on se pose trois questions, dans l'ordre :

\begin{enumerate}
\item \textbf{Quelle est la nature de l'information ?} Texte de longueur fixe (\texttt{CHAR}), texte variable (\texttt{VARCHAR}), nombre entier (\texttt{INT}) ou date (\texttt{DATE}) ?
\item \textbf{Cette information identifie-t-elle la ligne ?} Si oui, c'est la clé primaire (\texttt{PRIMARY KEY}).
\item \textbf{Cette information est-elle obligatoire ?} Si oui, on ajoute \texttt{NOT NULL}. \textbf{Renvoie-t-elle vers une autre table ?} Si oui, on ajoute \texttt{REFERENCES}.
\end{enumerate}

\begin{exemplebox}[La table ELEVE du lycée, entièrement justifiée]
Appliquons la démarche à la table des élèves :
\begin{lstlisting}[language=SQL]
-- Table des classes (référencée par ELEVE)
CREATE TABLE CLASSE (
    codeClasse CHAR(4) PRIMARY KEY,      -- code fixe : 'TC1 ', 'TD2 '
    nomClasse  VARCHAR(30) NOT NULL,     -- libellé variable, obligatoire
    effectif   INT                       -- nombre d'élèves (peut être vide au départ)
);

-- Table des élèves
CREATE TABLE ELEVE (
    matricule  CHAR(6) PRIMARY KEY,                  -- code fixe, unique et non nul
    nom        VARCHAR(30) NOT NULL,                 -- longueur variable, obligatoire
    dateNaiss  DATE,                                 -- ex. '2007-03-15', peut être inconnue
    codeClasse CHAR(4) REFERENCES CLASSE(codeClasse) -- clé étrangère vers CLASSE
);
\end{lstlisting}
Chaque choix est motivé : le matricule est un code normalisé de 6 caractères (\texttt{CHAR(6)}) et sert d'identifiant (\texttt{PRIMARY KEY}) ; le nom varie en longueur (\texttt{VARCHAR(30)}) mais ne peut être vide (\texttt{NOT NULL}) ; la date de naissance est une \texttt{DATE} ; la classe de l'élève doit exister dans \texttt{CLASSE} (\texttt{REFERENCES}).
\end{exemplebox}

\begin{attention}[Pièges fréquents sur les contraintes]
\begin{itemize}
\item Une table ne peut avoir qu'\textbf{une seule} clé primaire : écrire deux fois \texttt{PRIMARY KEY} dans le même \texttt{CREATE TABLE} provoque une erreur.
\item On peut en revanche multiplier les \texttt{NOT NULL} et les \texttt{REFERENCES} sur autant de colonnes que nécessaire.
\item La clé étrangère et la clé primaire référencée doivent avoir des \textbf{types compatibles} : un \texttt{CHAR(4)} ne peut pas référencer un \texttt{INT}.
\item Il faut créer la table référencée (\texttt{CLASSE}) \emph{avant} la table qui la référence (\texttt{ELEVE}).
\end{itemize}
\end{attention}

\begin{exoresolu}[Concevoir la table LIVRE d'une bibliothèque scolaire]
Énoncé : la bibliothèque du lycée veut enregistrer ses livres. Chaque livre possède un code fixe de 5 caractères (identifiant unique), un titre obligatoire d'au plus 40 caractères, une année d'édition (entier, facultative) et le code de la classe à laquelle il est affecté (code fixe de 4 caractères, devant exister dans la table \texttt{CLASSE}). Écris l'instruction SQL de création de la table \texttt{LIVRE} en justifiant chaque choix.
\tcblower
Solution détaillée. On raisonne colonne par colonne :
\begin{itemize}
\item \textbf{code du livre} : longueur fixe de 5 caractères $\Rightarrow$ \texttt{CHAR(5)} ; il identifie chaque livre $\Rightarrow$ \texttt{PRIMARY KEY}.
\item \textbf{titre} : texte de longueur variable, au plus 40 caractères $\Rightarrow$ \texttt{VARCHAR(40)} ; obligatoire $\Rightarrow$ \texttt{NOT NULL}.
\item \textbf{année d'édition} : nombre entier $\Rightarrow$ \texttt{INT} ; facultative $\Rightarrow$ pas de \texttt{NOT NULL}.
\item \textbf{code de la classe} : longueur fixe $\Rightarrow$ \texttt{CHAR(4)} ; doit exister dans \texttt{CLASSE} $\Rightarrow$ \texttt{REFERENCES CLASSE(codeClasse)}.
\end{itemize}
\begin{lstlisting}[language=SQL]
CREATE TABLE LIVRE (
    codeLivre  CHAR(5) PRIMARY KEY,                  -- identifiant unique du livre
    titre      VARCHAR(40) NOT NULL,                 -- titre obligatoire, longueur variable
    anneeEdit  INT,                                  -- année d'édition (facultative)
    codeClasse CHAR(4) REFERENCES CLASSE(codeClasse) -- classe d'affectation existante
);
\end{lstlisting}
Vérification mentale : une seule clé primaire, les types de \texttt{codeClasse} sont identiques dans les deux tables (\texttt{CHAR(4)}), et la table \texttt{CLASSE} est supposée déjà créée. La requête est correcte.
\end{exoresolu}

\begin{aretenir}[L'essentiel de la section]
\begin{itemize}
\item Le \cle{type} d'une colonne définit la nature de ses valeurs : \texttt{CHAR(n)} (texte de longueur fixe, complété par des espaces), \texttt{VARCHAR(n)} (texte de longueur variable, au plus $n$ caractères), \texttt{INT} (entier), \texttt{DATE} (date au format \texttt{'AAAA-MM-JJ'}).
\item Les \cle{contraintes d'intégrité} font respecter des règles : \texttt{PRIMARY KEY} (identifiant unique et non nul, une seule par table), \texttt{NOT NULL} (valeur obligatoire), \texttt{REFERENCES} (clé étrangère pointant vers la clé primaire d'une autre table).
\item Le choix du type et des contraintes se fait colonne par colonne, selon la nature de l'information, son caractère obligatoire et ses liens avec les autres tables.
\end{itemize}
\end{aretenir}

Le proviseur veut créer la table \texttt{ENSEIGNANT} : matricule (code fixe de 6 caractères, identifiant), nom (obligatoire, au plus 30 caractères), date de naissance, et code de la matière enseignée (code fixe de 3 caractères référençant la clé primaire \texttt{codeMat} de la table \texttt{MATIERE}). Écris l'instruction \texttt{CREATE TABLE} complète, puis explique pourquoi on a choisi \texttt{CHAR} plutôt que \texttt{VARCHAR} pour le matricule.
\end{exercice}

\begin{corrige}[Exercice 1]
\begin{lstlisting}[language=SQL]
CREATE TABLE ENSEIGNANT (
    matricule CHAR(6) PRIMARY KEY,
    nom       VARCHAR(30) NOT NULL,
    dateNaiss DATE,
    codeMat   CHAR(3) REFERENCES MATIERE(codeMat)

\end{lstlisting}
Le matricule est déclaré \texttt{CHAR(6)} car sa longueur est \emph{fixe et connue} : tous les matricules ont exactement 6 caractères. \texttt{VARCHAR} serait inutile ici, puisqu'il est conçu pour les longueurs variables ; de plus, \texttt{CHAR} garantit qu'aucun matricule plus court ou plus long ne sera accepté.
\end{corrige}

\coursec{Requêtes de définition des données : CREATE, ALTER, DROP}

Dans la section précédente, tu as appris à choisir un \cle{type de données} pour chaque attribut (\texttt{CHAR}, \texttt{VARCHAR}, \texttt{INT}, \texttt{DATE}) et à poser les \cle{contraintes d'intégrité} qui garantissent la qualité des données (\texttt{PRIMARY KEY}, \texttt{REFERENCES}, \texttt{NOT NULL}). Mais tout cela restait de la théorie : nous avions dessiné des tableaux de structure sur le papier. Il est temps maintenant de \emph{fabriquer réellement} les tables dans la machine. C'est le rôle des \cle{requêtes de définition des données} (LDD, Langage de Définition de Données) : \texttt{CREATE}, \texttt{ALTER} et \texttt{DROP}.

Reprenons notre fil conducteur : la direction du Lycée de Nkol-Eton veut informatiser la gestion des élèves. Le MCD a été validé, le MLD a produit le schéma relationnel suivant :

\begin{center}
\texttt{CLASSE(\cle{codeClasse}, libelle, effectifMax)}\\
\texttt{ELEVE(\cle{matricule}, nom, dateNaiss, \#codeClasse)}
\end{center}

Comment transformer ces deux lignes de texte en véritables tables dans MySQL ou Access ? C'est toute la question de cette section.

\courssub{Création et sélection d'une base de données}

\textbf{Intuition.} Avant de ranger des dossiers dans des tiroirs, il faut d'abord disposer d'une armoire. La \cle{base de données} est cette armoire : c'est le conteneur qui regroupera toutes les tables du lycée (CLASSE, ELEVE, et plus tard PROFESSEUR, NOTE, etc.).

\begin{propriete}[Création d'une base de données]
La requête de création d'une base de données s'écrit :
\begin{lstlisting}[language=SQL]
CREATE DATABASE nomBase;
\end{lstlisting}
Sous MySQL, la base créée n'est pas automatiquement active : il faut la \emph{sélectionner} pour que les requêtes suivantes s'y appliquent :
\begin{lstlisting}[language=SQL]
USE nomBase;
\end{lstlisting}
\end{propriete}

\begin{exemplebox}[Création de la base du lycée]
\begin{lstlisting}[language=SQL]
-- Creation de la base de donnees du Lycee de Nkol-Eton
CREATE DATABASE lycee_nkoleton;

-- Selection de la base : toutes les requetes suivantes
-- porteront sur cette base
USE lycee_nkoleton;
\end{lstlisting}
Sans le \texttt{USE}, MySQL répondrait par l'erreur \emph{« No database selected »} dès que l'on tenterait de créer une table.
\end{exemplebox}

\begin{attention}[N'oublie pas le point-virgule]
En mode console MySQL, chaque requête se termine par un \texttt{;} : c'est lui qui ordonne l'exécution. Si tu valides sans point-virgule, MySQL attend patiemment la suite de la requête sur la ligne suivante (le prompt affiche \texttt{->}).
\end{attention}

\courssub{Création d'une table : CREATE TABLE}

\textbf{Intuition.} Créer une table, c'est construire un \emph{casier vide} avec des colonnes étiquetées et des règles de contrôle à l'entrée. On ne met encore aucune donnée dedans : on définit uniquement la \cle{structure} — le nom de chaque colonne (attribut), son type, et les contraintes qu'elle doit respecter.

\begin{propriete}[Syntaxe générale de CREATE TABLE]
\begin{lstlisting}[language=SQL]
CREATE TABLE nomTable (
    attribut1 TYPE [contraintes],
    attribut2 TYPE [contraintes],
    ...
    [contraintes de table]
);
\end{lstlisting}
\begin{itemize}
\item \texttt{nomTable} : le nom de la table, sans espace ni accent (par convention en majuscules) ;
\item chaque attribut est déclaré avec son \cle{type} (\texttt{CHAR(n)}, \texttt{VARCHAR(n)}, \texttt{INT}, \texttt{DATE}, ...) ;
\item les contraintes possibles sont \texttt{PRIMARY KEY} (clé primaire), \texttt{NOT NULL} (valeur obligatoire), \texttt{REFERENCES table(attribut)} (clé étrangère) ;
\item les déclarations d'attributs sont séparées par des virgules ; la dernière ligne avant la parenthèse fermante ne porte \emph{pas} de virgule.
\end{itemize}
\end{propriete}

\begin{methode}[Écrire un CREATE TABLE en quatre étapes]
Face à un tableau de structure (ou à un schéma relationnel), procède toujours dans cet ordre :
\begin{enumerate}
\item \textbf{Lister les attributs} de la table, en recopiant fidèlement leurs noms depuis le MLD ;
\item \textbf{Choisir le type} de chaque attribut : \texttt{CHAR(n)} pour un code de longueur fixe (matricule), \texttt{VARCHAR(n)} pour un texte de longueur variable (nom), \texttt{INT} pour un nombre entier (effectif), \texttt{DATE} pour une date ;
\item \textbf{Poser la clé primaire} : ajouter \texttt{PRIMARY KEY} sur l'attribut souligné dans le schéma relationnel ;
\item \textbf{Poser les contraintes restantes} : \texttt{NOT NULL} sur les attributs obligatoires, et \texttt{REFERENCES} sur chaque clé étrangère (attribut précédé de \# dans le MLD).
\end{enumerate}
\end{methode}

\begin{exemplebox}[Création des tables CLASSE et ELEVE]
\begin{lstlisting}[language=SQL]
-- Etape 1 : la table referencee d'abord
CREATE TABLE CLASSE (
    codeClasse  CHAR(4) PRIMARY KEY,   -- ex : 'TLEC'
    libelle     VARCHAR(30) NOT NULL,  -- ex : 'Terminale C'
    effectifMax INT                    -- ex : 60
);

-- Etape 2 : la table qui reference CLASSE
CREATE TABLE ELEVE (
    matricule  CHAR(6) PRIMARY KEY,    -- ex : '24A001'
    nom        VARCHAR(30) NOT NULL,
    dateNaiss  DATE,                   -- format 'AAAA-MM-JJ'
    codeClasse CHAR(4) REFERENCES CLASSE(codeClasse)
);
\end{lstlisting}
La contrainte \texttt{REFERENCES CLASSE(codeClasse)} signifie : « la valeur de \texttt{codeClasse} dans ELEVE doit exister comme valeur de \texttt{codeClasse} dans CLASSE ». Impossible donc d'inscrire un élève dans une classe qui n'existe pas : c'est l'\cle{intégrité référentielle}.
\end{exemplebox}

\begin{attention}[Crée toujours la table référencée en premier]
Erreur classique du débutant : écrire \texttt{CREATE TABLE ELEVE} avant \texttt{CREATE TABLE CLASSE}. La contrainte \texttt{REFERENCES CLASSE(codeClasse)} échoue alors, car la table référencée \emph{n'existe pas encore} au moment de la création. Règle d'or : on crée d'abord la table qui contient la clé primaire référencée (CLASSE), ensuite la table qui porte la clé étrangère (ELEVE).
\end{attention}

\begin{popfigure}
\begin{lstlisting}[language=SQL]
-- ============================================
-- Script complet de creation de la base
-- Lycee de Nkol-Eton (MySQL)
-- ============================================
CREATE DATABASE lycee_nkoleton;   -- l'armoire
USE lycee_nkoleton;               -- on ouvre l'armoire

-- Table referencee : creee EN PREMIER

    codeClasse  CHAR(4) PRIMARY KEY,
    libelle     VARCHAR(30) NOT NULL,
    effectifMax INT
);

-- Table referencante : creee ENSUITE

    matricule  CHAR(6) PRIMARY KEY,
    nom        VARCHAR(30) NOT NULL,
    dateNaiss  DATE,
    codeClasse CHAR(4) REFERENCES CLASSE(codeClasse)
);
\end{lstlisting}

\end{popfigure}

\courssub{Modification de la structure : ALTER TABLE}

\textbf{Intuition.} Quelques semaines après la mise en service, la direction s'aperçoit qu'elle a besoin du \emph{sexe} des élèves pour les statistiques MINEDUB, que le nom de 30 caractères est trop court pour certains élèves, et que la colonne \texttt{effectifMax} n'est finalement jamais utilisée. Faut-il tout détruire et recommencer ? Non : la requête \texttt{ALTER TABLE} permet de \emph{modifier la structure d'une table existante} sans la supprimer.

\begin{propriete}[Les trois variantes de ALTER TABLE]
\begin{itemize}
\item \textbf{Ajouter une colonne} : \texttt{ALTER TABLE nomTable ADD colonne TYPE ;}
\item \textbf{Modifier le type d'une colonne} : \texttt{ALTER TABLE nomTable MODIFY colonne NOUVEAU\_TYPE ;}
\item \textbf{Supprimer une colonne} : \texttt{ALTER TABLE nomTable DROP COLUMN colonne ;}
\end{itemize}
\end{propriete}

\begin{exemplebox}[Faire évoluer la table ELEVE]
\begin{lstlisting}[language=SQL]
-- Ajouter la colonne sexe ('M' ou 'F')
ALTER TABLE ELEVE ADD sexe CHAR(1);

-- Elargir le nom de 30 a 50 caracteres
ALTER TABLE ELEVE MODIFY nom VARCHAR(50) NOT NULL;

-- Supprimer la colonne effectifMax devenue inutile
ALTER TABLE CLASSE DROP COLUMN effectifMax;
\end{lstlisting}
\end{exemplebox}

\begin{attention}[Réduire un type peut détruire des données]
Si tu modifies \texttt{VARCHAR(50)} en \texttt{VARCHAR(10)} alors que certains noms stockés dépassent 10 caractères, ils seront \emph{tronqués}. Avant un \texttt{MODIFY} qui réduit une taille, vérifie toujours le contenu existant.
\end{attention}

\courssub{Suppression d'une table : DROP TABLE}

\textbf{Intuition.} \texttt{DROP TABLE} est le bulldozer du SQL : il rase la table entière — la structure \emph{et} toutes les données qu'elle contient. Il n'y a pas de corbeille, pas de message « êtes-vous sûr ? » en mode console : la suppression est immédiate et définitive.

\begin{propriete}[Suppression d'une table]
\begin{lstlisting}[language=SQL]
DROP TABLE nomTable;
\end{lstlisting}
Cette requête supprime définitivement la table : sa structure, ses données et ses contraintes disparaissent ensemble.
\end{propriete}

\textbf{Ordre de suppression.} C'est l'inverse de l'ordre de création. Si tu tentes de supprimer CLASSE alors que ELEVE contient encore une clé étrangère qui la référence, MySQL refuse (pour protéger l'intégrité référentielle). Il faut donc :

\begin{enumerate}
\item supprimer d'abord la table qui \emph{contient la clé étrangère} : \texttt{DROP TABLE ELEVE ;}
\item supprimer ensuite la table référencée : \texttt{DROP TABLE CLASSE ;}
\end{enumerate}

\begin{attention}[DROP TABLE n'est pas DELETE]
Ne confonds jamais ces deux requêtes :
\begin{itemize}
\item \texttt{DELETE FROM ELEVE ;} vide la table de ses \emph{lignes}, mais la table (sa structure) continue d'exister — on pourra y insérer de nouveaux élèves ;
\item \texttt{DROP TABLE ELEVE ;} supprime la table \emph{elle-même} : structure et données. Après cette requête, la table n'existe plus du tout.
\end{itemize}
Et rappelle-toi : \texttt{DROP TABLE} est \textbf{irréversible}. En entreprise, on fait une sauvegarde avant toute suppression.
\end{attention}

\coursec{Insertion, modification et suppression des données}

Après avoir défini la structure de nos tables avec les commandes \texttt{CREATE TABLE}, \texttt{ALTER TABLE} et \texttt{DROP TABLE} (section précédente), notre base de données est prête, mais elle est vide. Une base de données sans données est comme une bibliothèque sans livres : l'armature existe, mais l'utilité est nulle. Cette section aborde le cœur du métier : \textbf{peupler les tables}, \textbf{corriger les erreurs} et \textbf{nettoyer les informations obsolètes}. Nous allons manipuler le langage \textbf{DML} (Data Manipulation Language) avec les trois ordres fondamentaux : \texttt{INSERT}, \texttt{UPDATE} et \texttt{DELETE}.

\courssub{Insertion de données : la commande INSERT INTO}

\textbf{Intuition et besoin concret.}\par
Imaginez la secrétaire du Lycée Bilingue de Nkolbisson qui enregistre un nouvel élève, \emph{NGONO Aline}, en Terminale C1. Elle remplit une fiche papier : matricule, nom, date de naissance, classe. En SQL, cette action correspond à l'ajout d'une \textbf{ligne} (un tuple) dans la table \texttt{ELEVE}. La commande \texttt{INSERT INTO} est l'équivalent numérique de ce geste.

\begin{definition}[Commande INSERT INTO]
L'instruction \texttt{INSERT INTO} permet d'ajouter une ou plusieurs nouvelles lignes dans une table existante. Elle existe sous deux formes principales :
\begin{enumerate}
    \item \textbf{Insertion explicite (recommandée) :} on précise la liste des colonnes ciblées. Cela protège contre les erreurs si la structure de la table évolue (ajout d'une colonne avec valeur par défaut).
    \item \textbf{Insertion implicite :} on omet la liste des colonnes ; il faut alors fournir une valeur pour \textbf{chaque} colonne de la table, dans l'ordre exact de leur définition (\texttt{CREATE TABLE}).
\end{enumerate}
\end{definition}

\begin{propriete}[Syntaxe générale de INSERT INTO]
\begin{lstlisting}[language=SQL]
-- Forme explicite (PRÉFÉRÉE)
INSERT INTO nom_table (colonne1, colonne2, colonne3, ...)
VALUES (valeur1, valeur2, valeur3, ...);

-- Forme implicite (RISQUÉE si structure change)
INSERT INTO nom_table
VALUES (valeur1, valeur2, valeur3, ...);
\end{lstlisting}
\end{propriete}

\begin{aretenir}[Règles de correspondance et formatage des valeurs]
\begin{itemize}
    \item \textbf{Ordre strict :} La liste des valeurs dans \texttt{VALUES} doit correspondre \textbf{exactement} (ordre, nombre, type) à la liste des colonnes (explicite ou implicite).
    \item \textbf{Chaînes de caractères (\texttt{VARCHAR}, \texttt{CHAR}) et dates (\texttt{DATE}) :} \textbf{Obligatoirement} encadrées par des \textbf{apostrophes simples} (\texttt{'...'}). Exemple : \texttt{'NGONO Aline'}, \texttt{'2007-05-12'} (format ISO \texttt{AAAA-MM-JJ}).
    \item \textbf{Nombres (\texttt{INT}, \texttt{DECIMAL}, \texttt{FLOAT}) :} \textbf{Sans apostrophes}. Exemple : \texttt{15000}, \texttt{12.50}.
    \item \textbf{Valeur \texttt{NULL} :} Saisir le mot-clé \texttt{NULL} (sans guillemets) pour une colonne autorisant l'absence de valeur.
\end{itemize}
\end{aretenir}

\begin{methode}[Écrire un INSERT INTO sans erreur]
\begin{enumerate}
    \item \textbf{Identifier la table cible} (ex: \texttt{ELEVE}).
    \item \textbf{Lister les colonnes} à renseigner (toutes sauf celles avec \texttt{AUTO\_INCREMENT} ou valeur par défaut gérée par le SGBD). Écrire : \texttt{INSERT INTO ELEVE (matricule, nom, dateNaiss, codeClasse)}.
    \item \textbf{Préparer les valeurs} dans le \textbf{même ordre} : chaînes/dates entre \texttt{' '}, nombres nus, \texttt{NULL} si besoin.
    \item \textbf{Vérifier les contraintes :} La clé primaire (ex: \texttt{matricule}) est-elle unique ? La clé étrangère (ex: \texttt{codeClasse}) existe-t-elle dans la table \texttt{CLASSE} ?
    \item \textbf{Exécuter} et vérifier le message \texttt{1 row(s) affected} (MySQL) ou \texttt{Query OK}.
\end{enumerate}
\end{methode}

\begin{exemplebox}[Insertion d'un élève complet]
Supposons la table \texttt{ELEVE} créée précédemment :
\texttt{CREATE TABLE ELEVE (matricule CHAR(6) PRIMARY KEY, nom VARCHAR(50) NOT NULL, dateNaiss DATE, codeClasse CHAR(4) REFERENCES CLASSE(codeClasse));}

On insère \emph{NGONO Aline}, née le 12 mai 2007, en classe \texttt{TC1} (qui existe dans \texttt{CLASSE}).
\begin{lstlisting}[language=SQL]
INSERT INTO ELEVE (matricule, nom, dateNaiss, codeClasse)
VALUES ('E0012', 'NGONO Aline', '2007-05-12', 'TC1');
\end{lstlisting}
\emph{Analyse :} \texttt{'E0012'} (CHAR), \texttt{'NGONO Aline'} (VARCHAR), \texttt{'2007-05-12'} (DATE) sont entre apostrophes. L'ordre respecte la liste des colonnes. Si \texttt{TC1} n'existe pas dans \texttt{CLASSE}, le SGBD rejette l'insertion (erreur de clé étrangère).
\end{exemplebox}

\begin{attention}[Pièges fréquents sur INSERT]
\begin{itemize}
    \item \textbf{Oublier les apostrophes sur une date ou une chaîne :} \texttt{VALUES (E0012, NGONO Aline, 2007-05-12, TC1)} $\rightarrow$ Erreur de syntaxe (le SGBD croit que ce sont des noms de colonnes ou des calculs : 2007 moins 5 moins 12).
    \item \textbf{Mettre des apostrophes sur un entier :} \texttt{VALUES ('E0012', 'NGONO', '2007-05-12', '15')} pour un \texttt{INT} $\rightarrow$ Fonctionne souvent par conversion implicite, mais c'est une \textbf{mauvaise pratique} source de bugs (comparaison chaîne vs nombre).
    \item \textbf{Ordre inversé :} \texttt{INSERT INTO ELEVE (nom, matricule) VALUES ('E0012', 'NGONO')} $\rightarrow$ Le matricule reçoit le nom et vice-versa. Données corrompues silencieusement !
    \item \textbf{Violation de contrainte :} Clé primaire dupliquée (\texttt{Duplicate entry 'E0012' for key 'PRIMARY'}) ou clé étrangère inexistante (\texttt{Cannot add or update a child row: a foreign key constraint fails}).
\end{itemize}
\end{attention}

\courssub{Modification de données : la commande UPDATE}

\textbf{Intuition et besoin concret.}\par
L'élève \emph{NGONO Aline} change de classe : elle passe de \texttt{TC1} à \texttt{TC2} (redoublement ou réorientation). On ne supprime pas sa fiche pour en recréer une (on perdrait son historique, son matricule). On \textbf{modifie} la valeur de la colonne \texttt{codeClasse} pour \textbf{sa} ligne uniquement.

\begin{definition}[Commande UPDATE]
L'instruction \texttt{UPDATE} modifie la valeur d'un ou plusieurs attributs pour \textbf{un ensemble de lignes} sélectionnées par une condition. C'est une opération \textbf{irréversible} (sauf transaction \texttt{ROLLBACK} non vue au programme).
\end{definition}

\begin{propriete}[Syntaxe générale de UPDATE]
\begin{lstlisting}[language=SQL]
UPDATE nom_table
SET colonne1 = nouvelleValeur1,
    colonne2 = nouvelleValeur2,
    ...
WHERE condition_de_selection;
\end{lstlisting}
\end{propriete}

\begin{aretenir}[La clause WHERE : garde-fou vital]
\begin{itemize}
    \item \textbf{Avec \texttt{WHERE} :} Seules les lignes satisfaisant la condition sont modifiées. C'est le cas normal (ex: \texttt{WHERE matricule = 'E0012'}).
    \item \textbf{Sans \texttt{WHERE} :} \textbf{TOUTES} les lignes de la table sont modifiées. \texttt{UPDATE ELEVE SET codeClasse = 'TC2';} $\rightarrow$ \textbf{Tous les élèves du lycée passent en TC2}. Catastrophe administrative garantie.
\end{itemize}
\end{aretenir}

\begin{exemplebox}[Changement de classe pour un élève]
\begin{lstlisting}[language=SQL]
-- 1. Vérification préalable (BONNE PRATIQUE)
SELECT matricule, nom, codeClasse FROM ELEVE WHERE matricule = 'E0012';
-- Résultat : E0012 | NGONO Aline | TC1

-- 2. Modification ciblée
UPDATE ELEVE
SET codeClasse = 'TC2'
WHERE matricule = 'E0012';

-- 3. Contrôle post-modification
SELECT matricule, nom, codeClasse FROM ELEVE WHERE matricule = 'E0012';
-- Résultat : E0012 | NGONO Aline | TC2
\end{lstlisting}
\end{exemplebox}

\begin{lstlisting}[language=SQL]

\end{lstlisting}
\textbf{Règle d'or :} Avant tout \texttt{UPDATE}, écrivez et testez le \texttt{SELECT} correspondant avec le même \texttt{WHERE}. Si le \texttt{SELECT} retourne les bonnes lignes, le \texttt{UPDATE} les modifiera.
\end{attention}

\courssub{Suppression de données : la commande DELETE}

\textbf{Intuition et besoin concret.}\par
Un élève quitte définitivement l'établissement (déménagement, exclusion définitive). Sa fiche doit disparaître de la table \texttt{ELEVE} pour ne plus apparaître dans les listes de classe, les bulletins, les effectifs. C'est le rôle de \texttt{DELETE}.

\begin{definition}[Commande DELETE]
L'instruction \texttt{DELETE FROM} supprime \textbf{définitivement} un ensemble de lignes d'une table. Comme \texttt{UPDATE}, elle opère sur les lignes sélectionnées par une clause \texttt{WHERE}.
\end{definition}

\begin{propriete}[Syntaxe générale de DELETE]
\begin{lstlisting}[language=SQL]
DELETE FROM nom_table
WHERE condition_de_selection;
\end{lstlisting}
\end{propriete}

\begin{aretenir}[DELETE sans WHERE = Table vide]
\begin{itemize}
    \item \texttt{DELETE FROM ELEVE WHERE matricule = 'E0013';} $\rightarrow$ Supprime \textbf{une} ligne (celle d'Aline).
    \item \texttt{DELETE FROM ELEVE;} $\rightarrow$ Supprime \textbf{toutes} les lignes. La table existe toujours (structure intacte), mais elle est vide. \textbf{Irréversible}.
\end{itemize}
\end{aretenir}

\begin{attention}[Contraintes d'intégrité et suppression]
\begin{itemize}
    \item \textbf{Clé étrangère (FK) :} Si \texttt{ELEVE.codeClasse} référence \texttt{CLASSE.codeClasse}, on ne peut pas supprimer la classe \texttt{TC1} tant qu'un élève y est inscrit (\texttt{ERROR 1451: Cannot delete or update a parent row}).
    \item \textbf{Solutions :} Supprimer d'abord les élèves de cette classe, ou modifier leur classe, ou définir \texttt{ON DELETE CASCADE} / \texttt{ON DELETE SET NULL} à la création de la FK (niveau avancé).
    \item \textbf{Clé primaire (PK) :} On ne peut pas insérer deux fois le même matricule. \texttt{INSERT} échouera sur \texttt{Duplicate entry}.
\end{itemize}
\end{attention}

\courssub{Exemple résolu complet : Gestion d'une mini-bibliothèque scolaire}

\begin{exoresolu}[Cycle de vie d'un ouvrage : Insert, Update, Delete]
\textbf{Contexte :} La bibliothèque du Lycée de Nkongsamba gère les ouvrages. Table \texttt{OUVRAGE} :
\texttt{CREATE TABLE OUVRAGE (code CHAR(5) PRIMARY KEY, titre VARCHAR(100) NOT NULL, auteur VARCHAR(50), anneeEdition INT, statut VARCHAR(20) DEFAULT 'DISPONIBLE');}

\textbf{Étape 1 : Acquisition de 3 nouveaux livres (INSERT).}
\begin{lstlisting}[language=SQL]
INSERT INTO OUVRAGE (code, titre, auteur, anneeEdition) VALUES
('L001', 'Algorithmique en C', 'KAMGA Jean', 2020),
('L002', 'Physique Terminale', 'FOUDA Marie', 2022),
('L003', 'Chimie Organique', 'NGUEMA Paul', 2019);
-- Note : 'statut' prend la valeur par défaut 'DISPONIBLE'.
\end{lstlisting}

\textbf{Étape 2 : Le livre L002 est emprunté (UPDATE).}
\begin{lstlisting}[language=SQL]
UPDATE OUVRAGE SET statut = 'EMPRUNTE' WHERE code = 'L002';
\end{lstlisting}

\textbf{Étape 3 : Le livre L001 est perdu (dégât des eaux), on le retire du catalogue (DELETE).}
\begin{lstlisting}[language=SQL]
DELETE FROM OUVRAGE WHERE code = 'L001';
\end{lstlisting}

\textbf{Étape 4 : État final de la table.}
\begin{lstlisting}[language=SQL]
SELECT * FROM OUVRAGE;
\end{lstlisting}
\begin{center}
\begin{tabular}{|c|l|l|c|l|}
\hline
\textbf{code} & \textbf{titre} & \textbf{auteur} & \textbf{anneeEdition} & \textbf{statut} \\
\hline
L002 & Physique Terminale & FOUDA Marie & 2022 & EMPRUNTE \\
L003 & Chimie Organique & NGUEMA Paul & 2019 & DISPONIBLE \\
\hline
\end{tabular}
\end{center}
\tcblower
\textbf{Analyse pédagogique :}
\begin{enumerate}
    \item L'\texttt{INSERT} multiple (séparé par des virgules) est plus performant que 3 instructions séparées.
    \item L'\texttt{UPDATE} cible \textbf{uniquement} \texttt{L002} grâce à la PK. Sans \texttt{WHERE}, les 3 livres seraient passés en \texttt{EMPRUNTE}.
    \item Le \texttt{DELETE} retire \texttt{L001} définitivement. La PK \texttt{L001} devient réutilisable (sauf contrainte métier).
    \item Le \texttt{DEFAULT} sur \texttt{statut} évite de le répéter à l'insertion.
\end{enumerate}
\end{exoresolu}

\courssub{Mise en œuvre pratique : MySQL Console vs Access Mode Graphique}

Le programme exige de savoir créer une base et une table \textbf{en mode console (MySQL)} et \textbf{en mode graphique (Access)}. Pour la manipulation de données (DML), la console MySQL reste l'outil de référence pour l'apprentissage du SQL standard.

\begin{experience}[TP Guidé : Manipulation DML sur MySQL Console]
\textbf{Objectif :} Créer une base \texttt{LYCEE\_DB}, la table \texttt{ELEVE}, et exécuter le cycle Insert/Update/Delete.
\textbf{Matériel :} Poste de travail avec MySQL Server installé (XAMPP, WAMP, ou MySQL Community Server).
\textbf{Manipulation :}
\begin{enumerate}
    \item Ouvrir l'invite de commande (Windows : \texttt{Win+R} $\rightarrow$ \texttt{cmd}).
    \item Se connecter : \texttt{mysql -u root -p} (Entrer le mot de passe, souvent vide en local).
    \item Créer et sélectionner la base :
\begin{lstlisting}[language=SQL]
CREATE DATABASE LYCEE_DB CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
USE LYCEE_DB;
\end{lstlisting}
    \item Créer la table \texttt{CLASSE} (référencée par FK) puis \texttt{ELEVE} :
\begin{lstlisting}[language=SQL]
CREATE TABLE CLASSE (
    codeClasse CHAR(4) PRIMARY KEY,
    libelle VARCHAR(30) NOT NULL,
    niveau VARCHAR(10)
);

CREATE TABLE ELEVE (
    matricule CHAR(6) PRIMARY KEY,
    nom VARCHAR(50) NOT NULL,
    dateNaiss DATE,
    codeClasse CHAR(4),
    CONSTRAINT fk_eleve_classe FOREIGN KEY (codeClasse) REFERENCES CLASSE(codeClasse)
);
\end{lstlisting}
    \item Insérer des classes (prérequis pour la FK) :
\begin{lstlisting}[language=SQL]
INSERT INTO CLASSE VALUES ('TC1', 'Terminale C1', 'Terminale'), ('TC2', 'Terminale C2', 'Terminale');
\end{lstlisting}
    \item \textbf{Tester l'INSERT élève} (réussi) :
\begin{lstlisting}[language=SQL]
INSERT INTO ELEVE VALUES ('E001', 'ABENA Marc', '2006-03-15', 'TC1');
\end{lstlisting}
    \item \textbf{Tester l'INSERT élève en erreur (FK)} :
\begin{lstlisting}[language=SQL]
INSERT INTO ELEVE VALUES ('E002', 'BELA Claire', '2007-01-10', 'TD1');
-- ERREUR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails...
\end{lstlisting}
    \item \textbf{Tester UPDATE avec WHERE} :
\begin{lstlisting}[language=SQL]
UPDATE ELEVE SET codeClasse = 'TC2' WHERE matricule = 'E001';
SELECT * FROM ELEVE; -- Vérifier : Marc est maintenant en TC2
\end{lstlisting}
    \item \textbf{Tester DELETE avec WHERE} :
\begin{lstlisting}[language=SQL]
DELETE FROM ELEVE WHERE matricule = 'E001';
SELECT * FROM ELEVE; -- Table vide
\end{lstlisting}
    \item Quitter : \texttt{EXIT;}
\end{enumerate}
\textbf{Observations attendues :} Les messages \texttt{Query OK, 1 row affected} confirment le succès. Les messages d'erreur \texttt{ERROR 1452} (FK) ou \texttt{ERROR 1062} (PK dupliquée) montrent l'application des contraintes d'intégrité.
\textbf{Interprétation :} Le SGBD garantit la cohérence des données (intégrité référentielle) en bloquant les opérations invalides. La clause \texttt{WHERE} est le scalpel du chirurgien : sans elle, c'est la tronçonneuse.
\end{experience}

\begin{savaistu}[Le saviez-vous ? : Le coût d'un DELETE sans WHERE]
Selon une étude de \emph{Verizon Data Breach Investigations Report}, près de \textbf{20\% des incidents de perte de données critiques en entreprise} sont dus à des erreurs humaines, dont la majorité sont des \texttt{UPDATE} ou \texttt{DELETE} exécutés sans clause \texttt{WHERE} en environnement de production. Les administrateurs de bases de données (DBA) expérimentés appliquent la règle du \textbf{"Select d'abord"} : \textit{« Je ne lance jamais un UPDATE ou DELETE sans avoir copié-collé son WHERE dans un SELECT pour vérifier les lignes ciblées »}. Dans les grands systèmes (banques, télécoms comme CAMTEL), on utilise des \textbf{transactions} (\texttt{BEGIN; ... COMMIT;/ROLLBACK;}) pour pouvoir annuler une erreur, mais au Bac, on apprend la rigueur \textbf{avant} d'exécuter !
\end{savaistu}

\begin{exercice}[Entraînement au Baccalauréat]
Soit la table \texttt{PRODUIT} (\texttt{ref} CHAR(5) PK, \texttt{libelle} VARCHAR(30), \texttt{prixU} DECIMAL(10,2), \texttt{stock} INT, \texttt{cat} CHAR(3)).
\begin{enumerate}
    \item Écrire l'instruction \texttt{INSERT} pour ajouter le produit \texttt{('P001', 'Clavier USB', 12500.00, 50, 'INF')}.
    \item Écrire l'\texttt{UPDATE} pour augmenter de 10\% le prix de tous les produits de la catégorie \texttt{'INF'}.
    \item Écrire le \texttt{DELETE} pour supprimer les produits dont le stock est à 0.
    \item Quel serait l'effet de \texttt{UPDATE PRODUIT SET prixU = 0;} (sans WHERE) ?
\end{enumerate}
\end{exercice}

\begin{corrige}[Exercice n°1]
\begin{enumerate}
    \item \texttt{INSERT INTO PRODUIT (ref, libelle, prixU, stock, cat) VALUES ('P001', 'Clavier USB', 12500.00, 50, 'INF');} (Nombres sans guillemets, chaînes/date avec).
    \item \texttt{UPDATE PRODUIT SET prixU = prixU * 1.10 WHERE cat = 'INF';} (Calcul sur la colonne existante, condition sur catégorie).
    \item \texttt{DELETE FROM PRODUIT WHERE stock = 0;} (Suppression conditionnelle).
    \item \textbf{Catastrophe :} Le prix de \textbf{tous} les produits (toutes catégories confondues) devient 0 FCFA. La base de données est corrompue logiquement. Restauration depuis sauvegarde nécessaire.
\end{enumerate}

\coursec{Interrogation d'une table : SELECT}

Après avoir appris à créer la structure de nos tables (\texttt{CREATE TABLE}), à la modifier (\texttt{ALTER TABLE}) et à y insérer, modifier ou supprimer des lignes (\texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}), nous arrivons à l'opération la plus fréquente et la plus puissante : \textbf{interroger la base de données pour en extraire de l'information}. C'est le cœur du métier de développeur ou d'administrateur de bases de données : transformer des données brutes stockées sur disque en réponses exploitables pour un tableau de bord, un bulletin de notes, un état de stock ou une facture.

\courssub{Projection et restriction : les deux piliers du SELECT}

Toute requête \texttt{SELECT} répond à deux questions fondamentales : \emph{quelles colonnes} veux-je voir ? (projection) et \emph{quelles lignes} m'intéressent ? (restriction). Comprendre cette distinction est la clé pour écrire des requêtes justes et efficaces.

\begin{definition}[Projection (choix des colonnes)]
La \cle{projection} consiste à sélectionner un sous-ensemble des attributs (colonnes) d'une relation (table). En SQL, elle se réalise en listant les noms des colonnes souhaitées après le mot-clé \texttt{SELECT}. Le résultat est une table qui ne contient que ces colonnes, dans l'ordre indiqué.
\end{definition}

\begin{definition}[Restriction (choix des lignes)]
La \cle{restriction} consiste à ne conserver que les tuples (lignes) qui satisfont un prédicat (une condition booléenne). En SQL, elle s'exprime dans la clause \texttt{WHERE}. Le résultat est une table qui a les mêmes colonnes que la table source, mais moins de lignes (ou autant, ou zéro).
\end{definition}

\begin{aretenir}[Ordre logique d'exécution mental]
Même si on l'écrit \texttt{SELECT ... FROM ... WHERE ...}, le SGBD traite logiquement la requête dans cet ordre :
\begin{enumerate}
    \item \texttt{FROM} : identifier la table source.
    \item \texttt{WHERE} : filtrer les lignes (restriction).
    \item \texttt{SELECT} : projeter les colonnes (projection).
\end{enumerate}
C'est pourquoi on ne peut pas utiliser un alias de colonne défini dans le \texttt{SELECT} à l'intérieur du \texttt{WHERE} de la même requête.
\end{aretenir}

\courssub{Syntaxe générale et l'étoile (*)}

La syntaxe canonique d'une requête de sélection sur une seule table est :

\begin{lstlisting}[language=SQL]
SELECT [DISTINCT] liste_attributs
FROM nom_table
[WHERE condition];
\end{lstlisting}

\begin{itemize}
    \item \texttt{SELECT} : mot-clé obligatoire qui ouvre la requête.
    \item \texttt{DISTINCT} : optionnel, élimine les lignes dupliquées dans le résultat (voir plus loin).
    \item \texttt{liste\_attributs} : noms des colonnes séparés par des virgules, ou l'étoile \texttt{*}.
    \item \texttt{FROM nom\_table} : obligatoire, indique la table source.
    \item \texttt{WHERE condition} : optionnel, filtre les lignes.
\end{itemize}

\begin{propriete}[L'étoile \texttt{*} : toutes les colonnes]
L'astérisque \texttt{*} est un raccourci qui signifie « tous les attributs de la table dans l'ordre de leur définition ».
\begin{lstlisting}[language=SQL]
SELECT * FROM ELEVE;
\end{lstlisting}
\emph{Attention :} En production (application réelle), on évite \texttt{SELECT *} car :
\begin{enumerate}
    \item Cela transfère plus de données que nécessaire (réseau, mémoire).
    \item Si la structure de la table change (ajout/suppression de colonne), l'application peut planter ou afficher des données inattendues.
    \item Cela rend le code moins lisible (on ne sait pas quelles colonnes sont utilisées).
\end{enumerate}
\emph{Au Bac et en TP :} \texttt{SELECT *} est parfaitement acceptable pour explorer une table ou pour des exercices simples.
\end{propriete}

\courssub{La restriction avec WHERE : filtrer les lignes}

La clause \texttt{WHERE} ne garde que les lignes pour lesquelles la condition est \texttt{VRAI} (TRUE). Les opérateurs de comparaison autorisés au programme sont : \texttt{=}, \texttt{<>} (différent), \texttt{<}, \texttt{>}, \texttt{<=}, \texttt{>=}.

\begin{propriete}[Opérateurs de comparaison en SQL]
\begin{itemize}
    \item \texttt{=} : égalité (fonctionne sur nombres, chaînes, dates).
    \item \texttt{<>} : différence (standard SQL ; \texttt{!=} existe souvent mais n'est pas au programme).
    \item \texttt{<, >, <=, >=} : ordre strict ou large (numérique, alphabétique, chronologique).
\end{itemize}
\emph{Règles sur les chaînes :} En SQL standard, la comparaison de chaînes \emph{peut} être sensible à la casse selon le \emph{collation} de la base. Au programme, on considère généralement une correspondance exacte. On écrit les littéraux chaînes entre \textbf{guillemets simples} : \texttt{'TC1'}. Les dates s'écrivent aussi entre guillemets simples au format ISO : \texttt{'2007-01-01'}.
\end{propriete}

\begin{exemplebox}[Restriction simple sur une chaîne]
\textbf{Consigne :} Lister les élèves de la classe \texttt{TC1}.
\begin{lstlisting}[language=SQL]
SELECT matricule, nom, prenom

\courssub{Combinaison de conditions : AND, OR et priorités}

Pour exprimer des critères complexes, on combine des conditions simples avec les opérateurs logiques \texttt{AND} (ET logique) et \texttt{OR} (OU logique).

\begin{propriete}[Priorité des opérateurs logiques]
En SQL, comme en algorithmique et en mathématiques : \textbf{\texttt{AND} est prioritaire sur \texttt{OR}}.
\begin{itemize}
    \item \texttt{A AND B OR C} s'interprète \texttt{(A AND B) OR C}.
    \item \texttt{A OR B AND C} s'interprète \texttt{A OR (B AND C)}.
\end{itemize}
\textbf{Règle d'or :} Utilisez \textbf{toujours des parenthèses} pour lever toute ambiguïté et rendre votre intention explicite. Cela évite des bugs subtils et facilite la relecture.
\end{propriete}

\begin{attention}[Piège classique : AND vs OR sur le même attribut]
\begin{itemize}
    \item \texttt{WHERE codeClasse = 'TC1' AND codeClasse = 'TD2'} $\rightarrow$ \textbf{JAMAIS VRAI}. Une même ligne ne peut pas avoir deux valeurs différentes pour la même colonne en même temps. Résultat : 0 lignes.
    \item \texttt{WHERE codeClasse = 'TC1' OR codeClasse = 'TD2'} $\rightarrow$ \textbf{VRAI} pour les lignes qui valent 'TC1' \textbf{OU} 'TD2'. C'est la bonne écriture pour « élèves de TC1 ou TD2 ».
\end{itemize}
\end{attention}

\begin{exemplebox}[Combinaison AND : restriction multiple]
\textbf{Consigne :} Élèves de la classe \texttt{TC1} \textbf{ET} nés \textbf{après} le 1er janvier 2007.
\begin{lstlisting}[language=SQL]
SELECT nom, prenom, dateNaiss, codeClasse
FROM ELEVE
WHERE codeClasse = 'TC1' 
  AND dateNaiss > '2007-01-01';

\end{tabularx}
\end{center}
\legende{Jean (E001) est en TC1 mais né en 2006 $\rightarrow$ exclu.}
\end{exemplebox}

\courssub{Élimination des doublons : DISTINCT}

Par défaut, \texttt{SELECT} renvoie \textbf{toutes} les lignes qui satisfont la condition, même si plusieurs lignes sont identiques sur les colonnes projetées. Le mot-clé \texttt{DISTINCT} (placé \textbf{immédiatement après SELECT}) demande au SGBD d'éliminer les lignes dupliquées dans le \textbf{résultat final}.

\begin{propriete}[Syntaxe et portée de DISTINCT]
\begin{lstlisting}[language=SQL]
SELECT DISTINCT liste_attributs
FROM table
WHERE condition;
\end{lstlisting}
\begin{itemize}
    \item \texttt{DISTINCT} s'applique à \textbf{l'ensemble de la ligne de résultat} (la combinaison de toutes les colonnes listées).
    \item \texttt{SELECT DISTINCT codeClasse, sexe FROM ELEVE} : élimine les doublons sur le couple (classe, sexe).
    \item \texttt{SELECT DISTINCT codeClasse FROM ELEVE} : élimine les doublons sur la seule colonne classe.
\end{itemize}
\end{propriete}

\begin{attention}[Position de DISTINCT]
\texttt{DISTINCT} s'écrit \textbf{une seule fois}, juste après \texttt{SELECT}.
\begin{itemize}
    \item \texttt{SELECT DISTINCT nom, prenom FROM ...} \checkmark Correct.
    \item \texttt{SELECT nom, DISTINCT prenom FROM ...} \textcolor{red}{Erreur de syntaxe}.
    \item \texttt{SELECT DISTINCT nom, DISTINCT prenom FROM ...} \textcolor{red}{Erreur de syntaxe}.
\end{itemize}
\end{attention}

\begin{exemplebox}[DISTINCT sur une colonne]
\textbf{Consigne :} Quelles sont les classes représentées dans la table ? (Liste sans doublons).
\begin{lstlisting}[language=SQL]
SELECT DISTINCT codeClasse
FROM ELEVE;
\end{lstlisting}

\textbf{Résultat :}

\begin{center}
\begin{tabular}{|c|}\hline
\textbf{codeClasse} \\\hline
TC1 \\\hline
TD2 \\\hline
TE3 \\\hline
\end{tabular}
\end{center}
\legende{3 lignes au lieu de 6. L'ordre n'est pas garanti sans ORDER BY (non au programme).}
\end{exemplebox}

\begin{exemplebox}[DISTINCT sur plusieurs colonnes]
\textbf{Consigne :} Liste des couples (classe, sexe) existants.
\begin{lstlisting}[language=SQL]
SELECT DISTINCT codeClasse, sexe
FROM ELEVE;
\end{lstlisting}

\textbf{Résultat :}

\begin{center}
\begin{tabular}{|c|c|}\hline
\textbf{codeClasse} & \textbf{sexe} \\\hline
TC1 & M \\\hline
TC1 & F \\\hline
TD2 & M \\\hline
TD2 & F \\\hline
TE3 & F \\\hline
\end{tabular}
\end{center}
\legende{5 couples distincts. Le couple (TD2, F) n'existe pas dans nos données.}
\end{exemplebox}

\courssub{Méthode pas à pas pour construire un SELECT}

\begin{methode}[Construire une requête SELECT correcte]
Suivez ces 4 étapes dans l'ordre :
\begin{enumerate}
    \item \textbf{Identifier la table source} $\rightarrow$ Écrire \texttt{FROM nom\_table}. (C'est la base, on ne peut pas sélectionner sans savoir où regarder).
    \item \textbf{Définir le filtre sur les lignes} $\rightarrow$ Écrire la clause \texttt{WHERE condition}. Traduire l'énoncé français en booléen (attention aux \texttt{AND}/\texttt{OR}, aux parenthèses, aux guillemets simples pour chaînes/dates). Testez mentalement : « Cette ligne passe-t-elle ? ».
    \item \textbf{Choisir les colonnes à afficher} $\rightarrow$ Écrire la liste après \texttt{SELECT} (noms exacts, séparés par des virgules, ou \texttt{*}). Pensez à \texttt{DISTINCT} si l'énoncé demande « la liste des... » ou « les différentes valeurs de... ».
    \item \textbf{Relire et valider} : Vérifier l'orthographe des noms de table/colonnes, la cohérence des types (comparer date avec date, nombre avec nombre), la priorité \texttt{AND}/\texttt{OR}.
\end{enumerate}
\end{methode}

\begin{exoresolu}[Requête complète combinée]
\textbf{Énoncé :} Écrire la requête SQL qui affiche le \texttt{nom}, \texttt{prenom} et \texttt{dateNaiss} des élèves \textbf{filles} de la classe \texttt{TC1} nées \textbf{en 2007 ou 2008}.

\textbf{Solution détaillée :}
\begin{enumerate}
    \item \texttt{FROM ELEVE}
    \item Condition : \texttt{sexe = 'F'} \textbf{ET} \texttt{codeClasse = 'TC1'} \textbf{ET} (\texttt{dateNaiss >= '2007-01-01'} \textbf{ET} \texttt{dateNaiss <= '2008-12-31'}). 
    On peut simplifier la condition sur l'année avec \texttt{YEAR(dateNaiss) IN (2007, 2008)} mais \texttt{YEAR()} n'est pas au programme. On utilise les comparaisons de dates.
    \item Colonnes : \texttt{nom, prenom, dateNaiss}.
    \item Pas de doublons demandés $\rightarrow$ pas de \texttt{DISTINCT}.
\end{enumerate}

\begin{lstlisting}[language=SQL]
SELECT nom, prenom, dateNaiss
FROM ELEVE
WHERE sexe = 'F'
  AND codeClasse = 'TC1'
  AND dateNaiss >= '2007-01-01'
  AND dateNaiss <= '2008-12-31';
\end{lstlisting}

\textbf{Vérification sur nos données :}
\begin{itemize}
    \item E002 ETOUNDI Marie F 2007-11-23 TC1 $\rightarrow$ \textcolor{green}{OUI}
    \item E004 KAMGA Grace F 2008-01-30 TC1 $\rightarrow$ \textcolor{green}{OUI}
    \item E001 MBARGA Jean M $\rightarrow$ Non (sexe)
    \item E006 BELLA Anne F 2006-12-01 TE3 $\rightarrow$ Non (classe, date)
\end{itemize}
\textbf{Résultat attendu :} 2 lignes (ETOUNDI, KAMGA).
\end{exoresolu}

\courssub{Mise en œuvre graphique sous Access (Grille QBE)}

Le programme exige de savoir créer une requête en mode graphique sous Access (Query By Example). C'est un complément très utile pour le Bac pratique.

\begin{experience}[Créer une requête SELECT sous Access (Mode Création)]
\textbf{Objectif :} Obtenir la liste des élèves de TC1 nés après 2007-01-01 (nom, prénom, date de naissance).

\textbf{Matériel :} MS Access (ou LibreOffice Base), base \texttt{Ecole.accdb} contenant la table \texttt{ELEVE}.

\textbf{Manipulation pas à pas :}
\begin{enumerate}
    \item Onglet \textbf{Créer} $\rightarrow$ groupe \textbf{Requêtes} $\rightarrow$ cliquer \textbf{Conception de requête}.
    \item Dans la boîte \emph{Afficher la table}, double-cliquer sur \texttt{ELEVE} $\rightarrow$ \textbf{Fermer}.
    \item Dans la grille QBE (bas de la fenêtre) :
    \begin{itemize}
        \item Colonne 1 : Ligne \textbf{Champ} $\rightarrow$ choisir \texttt{nom} (liste déroulante). Ligne \textbf{Visible} $\rightarrow$ cochée.
        \item Colonne 2 : \textbf{Champ} $\rightarrow$ \texttt{prenom}. \textbf{Visible} $\rightarrow$ cochée.
        \item Colonne 3 : \textbf{Champ} $\rightarrow$ \texttt{dateNaiss}. \textbf{Visible} $\rightarrow$ cochée.
        \item Colonne 4 : \textbf{Champ} $\rightarrow$ \texttt{codeClasse}. \textbf{Visible} $\rightarrow$ \textbf{décochée} (critère seulement). Ligne \textbf{Critère} $\rightarrow$ taper \texttt{"TC1"} (Access ajoute les guillemets doubles automatiquement pour le texte).
        \item Colonne 5 : \textbf{Champ} $\rightarrow$ \texttt{dateNaiss} (ou une colonne vide si on réutilise la 3). Ligne \textbf{Critère} $\rightarrow$ taper \texttt{>\#2007-01-01\#} (Access utilise \# pour les dates).
    \end{itemize}
    \item Pour \texttt{DISTINCT} : Menu \textbf{Conception} $\rightarrow$ groupe \textbf{Résultats} $\rightarrow$ cocher \textbf{Valeurs distinctes} (icône sigma $\Sigma$ avec lignes distinctes).
    \item Exécuter : Onglet \textbf{Conception} $\rightarrow$ \textbf{Exécuter} (icône ! point d'exclamation rouge) ou basculer en \textbf{Mode Feuille de données}.
    \item Basculer en \textbf{Mode SQL} (Vue $\rightarrow$ Mode SQL) pour voir le code généré :
\end{enumerate}

\begin{lstlisting}[language=SQL]
SELECT ELEVE.nom, ELEVE.prenom, ELEVE.dateNaiss
FROM ELEVE
WHERE (((ELEVE.codeClasse)="TC1") AND ((ELEVE.dateNaiss)>#2007-01-01#));
\end{lstlisting}

\textbf{Observations :}
\begin{itemize}
    \item Access préfixe les colonnes par le nom de table (\texttt{ELEVE.nom}) : bonne pratique pour éviter l'ambiguïté (indispensable en jointure).
    \item Les parenthèses sont abondantes : Access sécurise la priorité.
    \item Les chaînes sont entre \texttt{" "}, les dates entre \texttt{\# \#}. En SQL standard (MySQL), ce sont des guillemets simples \texttt{' '} pour les deux.
\end{itemize}
\end{experience}

\courssub{Synthèse et points de vigilance pour le Bac}

\begin{aretenir}[Check-list SELECT pour l'examen]
\begin{itemize}
    \item \textbf{Syntaxe de base :} \texttt{SELECT ... FROM ... WHERE ... ;} (point-virgule final).
    \item \textbf{Guillemets :} \textbf{Simples} \texttt{'valeur'} pour chaînes et dates en SQL standard (MySQL). Doubles \texttt{"valeur"} en Access.
    \item \textbf{Format date :} \texttt{'AAAA-MM-JJ'} (ISO 8601) en SQL standard.
    \item \textbf{AND / OR :} \texttt{AND} prioritaire. \textbf{Toujours parenthéser} les \texttt{OR} mélangés à des \texttt{AND}.
    \item \textbf{DISTINCT :} Juste après \texttt{SELECT}. Porte sur \textbf{toute la ligne résultat}.
    \item \textbf{* vs Liste :} Préférer la liste explicite (projection), sauf exploration rapide.
    \item \textbf{Alias :} Non au programme pour le \texttt{SELECT} simple (utile pour jointure, voir section 6).
\end{itemize}
\end{aretenir}

\begin{exercice}[Entraînement SELECT]
Soit la table \texttt{PRODUIT} (codeP, libelle, prixU, stock, codeCat) avec données :
\begin{center}
\begin{tabular}{|c|l|c|c|c|}\hline
\textbf{codeP} & \textbf{libelle} & \textbf{prixU} & \textbf{stock} & \textbf{codeCat} \\\hline
P1 & Stylo Bille & 100 & 500 & PAP \\\hline
P2 & Cahier 100p & 500 & 200 & PAP \\\hline
P3 & Clé USB 16Go & 3500 & 50 & INF \\\hline
P4 & Souris Optique & 4500 & 30 & INF \\\hline
P5 & Ramette A4 & 2500 & 100 & PAP \\\hline
P6 & Disque Dur 1To & 35000 & 10 & INF \\\hline
\end{tabular}
\end{center}
Écrire les requêtes SQL pour :
\begin{enumerate}
    \item Afficher tous les produits de la catégorie \texttt{'PAP'}.
    \item Afficher le libellé et le prix des produits dont le stock est \textbf{inférieur à 100}.
    \item Afficher les \textbf{différentes} catégories présentes.
    \item Afficher les produits \texttt{'INF'} \textbf{OU} dont le prix est \textbf{supérieur à 3000}.
    \item Afficher le libellé et le stock des produits \texttt{'PAP'} \textbf{ET} (stock $>$ 150 \textbf{OU} prix $<$ 300).
\end{enumerate}
\end{exercice}

\begin{corrige}[Exercice Entraînement SELECT]
\begin{enumerate}
    \item \texttt{SELECT * FROM PRODUIT WHERE codeCat = 'PAP';}
    \item \texttt{SELECT libelle, prixU FROM PRODUIT WHERE stock < 100;}
    \item \texttt{SELECT DISTINCT codeCat FROM PRODUIT;} (Résultat : PAP, INF)
    \item \texttt{SELECT * FROM PRODUIT WHERE codeCat = 'INF' OR prixU > 3000;} (P3, P4, P6)
    \item \texttt{SELECT libelle, stock FROM PRODUIT WHERE codeCat = 'PAP' AND (stock > 150 OR prixU < 300);} 
    \emph{Analyse :} P1 (stock 500 > 150) $\rightarrow$ Oui. P2 (stock 200 > 150) $\rightarrow$ Oui. P5 (stock 100 $\ngtr$ 150 ET prix 2500 $\nless$ 300) $\rightarrow$ Non. Résultat : P1, P2.
\end{enumerate}
\end{corrige}

\begin{savaistu}[SQL : Un standard qui a 50 ans]
Le langage SQL (Structured Query Language) est né en 1974 chez IBM (projet System R) sous le nom SEQUEL. Il a été standardisé par l'ANSI en 1986 (SQL-86) puis l'ISO en 1987. Ce qui est remarquable, c'est sa longévité : les requêtes \texttt{SELECT}, \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE} que vous apprenez aujourd'hui en Terminale au Cameroun sont \textbf{identiques} à celles qu'écrivent les ingénieurs de Google, Facebook, ou les administrateurs de la base de données du Ministère de l'Éducation de Base (MINEDUB) pour gérer les millions d'élèves du pays. La puissance du déclaratif : vous dites \emph{quoi} faire, le SGBD décide \emph{comment} le faire (optimiseur de requêtes).
\end{savaistu}

\coursec{Jointure entre deux tables et mise en œuvre pratique}

Après avoir maîtrisé l'interrogation d'une \emph{seule} table avec \texttt{SELECT}, nous abordons maintenant une situation bien plus fréquente dans la vie réelle : l'information que l'on cherche est \emph{éclatée} sur plusieurs tables. Rappelons-nous notre modélisation (MCD/MLD) : pour éviter la redondance, nous avons séparé les élèves de leurs classes, les commandes de leurs clients, les livres de leurs auteurs. Pour retrouver une information complète — « le nom de l'élève \textbf{et} le libellé de sa classe » —, il faut \emph{reconnecter} ces tables au moment de la requête. C'est précisément le rôle de la \textbf{jointure}.

\courssub{Principe de la jointure : réconcilier les tables par la clé étrangère}

Dans un modèle relationnel normalisé, une relation (table) \texttt{ELEVE} possède une \cle{clé étrangère} \texttt{codeClasse} qui référence la \cle{clé primaire} \texttt{codeClasse} de la table \texttt{CLASSE}. Physiquement, les deux tables sont stockées séparément. Logiquement, une ligne d'\texttt{ELEVE} « appartient » à une et une seule ligne de \texttt{CLASSE} grâce à l'égalité de ces deux colonnes.

\begin{definition}[Jointure (équi-jointure naturelle sur clé étrangère / clé primaire)]
Une \textbf{jointure} entre deux tables \texttt{T1} et \texttt{T2} consiste à construire un ensemble de lignes résultat en associant chaque ligne de \texttt{T1} aux lignes de \texttt{T2} qui satisfont une \textbf{condition de jointure}, le plus souvent l'égalité entre la clé étrangère de l'une et la clé primaire de l'autre :
\[
\texttt{T1.cleEtrangere = T2.clePrimaire}
\]
On ne conserve dans le résultat que les attributs utiles (projection) et éventuellement on filtre davantage (restriction).
\end{definition}

\courssub{Syntaxe SQL au programme : jointure dans la clause WHERE}

Le programme officiel de Terminale C/D/E impose la syntaxe « ancienne » (SQL-89), encore très utilisée pour sa simplicité pédagogique, où la jointure s'écrit dans la clause \texttt{WHERE} aux côtés des éventuelles restrictions.

\begin{propriete}[Syntaxe de la jointure à deux tables (programme officiel)]
\begin{lstlisting}[language=SQL]
SELECT t1.attribut1, t2.attribut2, ...
FROM table1 t1, table2 t2
WHERE t1.colonneCommune = t2.colonneCommune
  [AND conditionDeRestriction];
\end{lstlisting}
\begin{itemize}
\item \texttt{table1 t1}, \texttt{table2 t2} : les \textbf{alias} (noms courts) donnés aux tables. Ils sont \emph{obligatoires} dès qu'un nom d'attribut existe dans les deux tables (ex. \texttt{codeClasse}) pour lever l'ambiguïté.
\item \texttt{t1.colonneCommune = t2.colonneCommune} : la \textbf{condition de jointure} (égalité FK = PK).
\item \texttt{AND conditionDeRestriction} : filtre supplémentaire (ex. ne garder que la classe 'TC1').
\end{itemize}
\end{propriete}

\begin{aretenir}[Rôle des alias]
Les alias (\texttt{e} pour \texttt{ELEVE}, \texttt{c} pour \texttt{CLASSE}) servent à deux fins :
\begin{enumerate}
\item \textbf{Raccourcir} l'écriture : \texttt{e.nom} au lieu de \texttt{ELEVE.nom}.
\item \textbf{Lever l'ambiguïté} : si les deux tables ont une colonne \texttt{codeClasse}, écrire seulement \texttt{codeClasse} dans le \texttt{SELECT} ou le \texttt{WHERE} provoquerait une erreur « Column 'codeClasse' in field list is ambiguous ». Il faut \emph{toujours} préfixer : \texttt{e.codeClasse} ou \texttt{c.codeClasse}.
\end{enumerate}
\end{aretenir}

\courssub{Méthode pas à pas pour écrire une jointure correcte}

\begin{methode}[Écrire une requête de jointure entre deux tables]
\begin{enumerate}
\item \textbf{Identifier les deux tables} concernées par la question (ex. \texttt{ELEVE} et \texttt{CLASSE}).
\item \textbf{Trouver la colonne commune} : la clé étrangère dans la table « faible » (\texttt{ELEVE.codeClasse}) et la clé primaire dans la table « forte » (\texttt{CLASSE.codeClasse}).
\item \textbf{Poser des alias courts et mnémotechniques} : \texttt{ELEVE e}, \texttt{CLASSE c}.
\item \textbf{Écrire la condition de jointure} dans le \texttt{WHERE} : \texttt{e.codeClasse = c.codeClasse}.
\item \textbf{Préfixer \emph{tous} les attributs} du \texttt{SELECT} et du \texttt{WHERE} par leur alias (\texttt{e.nom}, \texttt{c.libelle}, \texttt{c.libelle = 'TC1'}).
\item \textbf{Ajouter les restrictions métier} avec \texttt{AND} si nécessaire.
\end{enumerate}
\end{methode}

\courssub{Exemple complet : afficher l'élève et sa classe}

Reprenons notre base \texttt{ETABLISSEMENT} avec les tables :
\begin{itemize}
\item \texttt{CLASSE(codeClasse PK, libelle, effectifMax)}
\item \texttt{ELEVE(matricule PK, nom, prenom, dateNaiss, codeClasse FK $\rightarrow$ CLASSE)}
\end{itemize}

\begin{exemplebox}[Jointure simple : liste des élèves avec le libellé de leur classe]
\textbf{Question :} Afficher le nom, le prénom de chaque élève et le libellé de sa classe.

\textbf{Analyse :} Deux tables (\texttt{ELEVE}, \texttt{CLASSE}), colonne commune \texttt{codeClasse}. On veut \texttt{nom}, \texttt{prenom} (dans \texttt{ELEVE}) et \texttt{libelle} (dans \texttt{CLASSE}).

\textbf{Requête SQL :}
\begin{lstlisting}[language=SQL]
SELECT e.nom, e.prenom, c.libelle
FROM ELEVE e, CLASSE c
WHERE e.codeClasse = c.codeClasse;
\end{lstlisting}

\textbf{Explication ligne par ligne :}
\begin{itemize}
\item \texttt{SELECT e.nom, e.prenom, c.libelle} : on projette trois colonnes, chacune préfixée par son alias.
\item \texttt{FROM ELEVE e, CLASSE c} : on déclare les deux sources avec leurs alias.
\item \texttt{WHERE e.codeClasse = c.codeClasse} : c'est le \emph{filtre de jointure}. Pour chaque élève \texttt{e}, le SGBD cherche la (unique) classe \texttt{c} dont le \texttt{codeClasse} est égal. Les lignes qui ne trouvent pas de correspondance (élève sans classe ou classe sans élève) sont exclues (jointure \emph{interne}).
\end{itemize}

\textbf{Résultat attendu (extrait) :}
\begin{center}
\begin{tabularx}{\linewidth}{|l|l|X|}
\hline
\textbf{nom} & \textbf{prenom} & \textbf{libelle} \\
\hline
MBARGA & Jean & Terminale C1 \\
\hline
ESSOMBA & Marie & Terminale C1 \\
\hline
FOUDA & Paul & Terminale D2 \\
\hline
\end{tabularx}
\end{center}
\end{exemplebox}

\courssub{Jointure combinée à une restriction (AND)}

Très souvent, on ne veut pas \emph{toutes} les lignes jointes, mais un sous-ensemble.

\begin{exemplebox}[Jointure + restriction : élèves d'une classe donnée]
\textbf{Question :} Afficher le nom et le prénom des élèves de la classe dont le libellé est 'Terminale C1', avec le libellé de la classe.

\textbf{Requête SQL :}
\begin{lstlisting}[language=SQL]
SELECT e.nom, e.prenom, c.libelle
FROM ELEVE e, CLASSE c
WHERE e.codeClasse = c.codeClasse
  AND c.libelle = 'Terminale C1';
\end{lstlisting}

\textbf{Observation :} La condition de jointure (\texttt{e.codeClasse = c.codeClasse}) et la condition de restriction (\texttt{c.libelle = 'Terminale C1'}) sont simplement combinées par \texttt{AND} dans le même \texttt{WHERE}. L'ordre n'a pas d'importance pour le résultat, mais placer la jointure en premier est une bonne habitude de lisibilité.
\end{exemplebox}

\courssub{Le piège majeur : l'oubli de la condition de jointure → produit cartésien}

Si vous oubliez la ligne \texttt{WHERE e.codeClasse = c.codeClasse}, le SGBD n'a plus aucune instruction pour associer les lignes. Il effectue alors le \textbf{produit cartésien} (ou \emph{jointure cartésienne}) : \emph{chaque} ligne de la première table est combinée avec \emph{chaque} ligne de la seconde.

\begin{attention}[Erreur fatale : produit cartésien involontaire]
\begin{lstlisting}[language=SQL]
-- ERREUR : condition de jointure oubliée !
SELECT e.nom, c.libelle
FROM ELEVE e, CLASSE c;
-- (pas de WHERE, ou WHERE sans égalité sur les clés)
\end{lstlisting}
\textbf{Conséquences :}
\begin{itemize}
\item Si \texttt{ELEVE} a 500 lignes et \texttt{CLASSE} 20 lignes $\rightarrow$ \textbf{10 000 lignes} dans le résultat.
\item Le résultat est \emph{sémantiquement faux} : un même élève apparaît 20 fois, associé à des classes qui ne sont pas la sienne.
\item Temps d'exécution explosif, saturation mémoire possible sur de grosses tables.
\end{itemize}
\textbf{Règle d'or :} Pour $n$ tables jointes, il faut \textbf{au minimum $n-1$ conditions d'égalité} dans le \texttt{WHERE} (une par lien FK-PK du graphe de jointure).
\end{attention}

\courssub{Mise en œuvre pratique : création et exploitation en console MySQL}

Le programme exige de savoir créer la base et les tables en \textbf{mode console} (ligne de commande MySQL) puis d'y insérer et sélectionner des données. Voici la séquence complète, testée sur un serveur MySQL/MariaDB standard (ex. XAMPP, WAMP, ou serveur Linux du lycée).

\begin{experience}[TP guidé : Base ETABLISSEMENT en console MySQL]
\textbf{Objectif :} Créer la base, les deux tables liées par une clé étrangère, insérer des données, faire une jointure.
\textbf{Matériel :} Accès à un terminal (Invite de commandes Windows / Terminal Linux) avec \texttt{mysql} client installé.

\textbf{Étapes :}
\begin{enumerate}
\item \textbf{Ouvrir le client MySQL} : \texttt{mysql -u root -p} (Entrer le mot de passe, souvent vide en local XAMPP).
\item \textbf{Créer la base} :
\begin{lstlisting}[language=SQL]
CREATE DATABASE ETABLISSEMENT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
\end{lstlisting}
\item \textbf{Sélectionner la base} :
\begin{lstlisting}[language=SQL]
USE ETABLISSEMENT;
\end{lstlisting}
\item \textbf{Créer la table parente (CLASSE) d'abord} (pas de FK sortante) :
\begin{lstlisting}[language=SQL]
CREATE TABLE CLASSE (
    codeClasse VARCHAR(10) PRIMARY KEY,
    libelle VARCHAR(50) NOT NULL,
    effectifMax INT UNSIGNED DEFAULT 60
) ENGINE=InnoDB;
\end{lstlisting}
\item \textbf{Créer la table fille (ELEVE) avec la FK} :
\begin{lstlisting}[language=SQL]
CREATE TABLE ELEVE (
    matricule INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    nom VARCHAR(50) NOT NULL,
    prenom VARCHAR(50) NOT NULL,
    dateNaiss DATE,
    codeClasse VARCHAR(10) NOT NULL,
    CONSTRAINT fk_eleve_classe
        FOREIGN KEY (codeClasse) REFERENCES CLASSE(codeClasse)
        ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE=InnoDB;
\end{lstlisting}
\item \textbf{Insérer des classes} :
\begin{lstlisting}[language=SQL]
INSERT INTO CLASSE (codeClasse, libelle, effectifMax) VALUES
('TC1', 'Terminale C1', 55),
('TD2', 'Terminale D2', 50),
('TE1', 'Terminale E1', 45);
\end{lstlisting}
\item \textbf{Insérer des élèves} (la FK doit exister dans CLASSE) :
\begin{lstlisting}[language=SQL]
INSERT INTO ELEVE (nom, prenom, dateNaiss, codeClasse) VALUES
('MBARGA', 'Jean', '2006-03-12', 'TC1'),
('ESSOMBA', 'Marie', '2005-11-25', 'TC1'),
('FOUDA', 'Paul', '2006-07-01', 'TD2'),
('ATANGANA', 'Grace', '2005-09-18', 'TE1');
\end{lstlisting}
\item \textbf{Tester la jointure} :
\begin{lstlisting}[language=SQL]
SELECT e.nom, e.prenom, c.libelle
FROM ELEVE e, CLASSE c
WHERE e.codeClasse = c.codeClasse
  AND c.libelle = 'Terminale C1';
\end{lstlisting}
\item \textbf{Quitter} : \texttt{EXIT;}
\end{enumerate}

\textbf{Observations attendues :}
\begin{itemize}
\item L'étape 5 réussit car \texttt{ENGINE=InnoDB} (moteur par défaut récent) supporte les FK. \texttt{MyISAM} les ignorerait.
\item L'étape 7 échouerait si on mettait \texttt{codeClasse = 'TX9'} (erreur 1452 : Cannot add or update a child row).
\item L'étape 8 affiche exactement les deux élèves de TC1.
\end{itemize}
\end{experience}

\courssub{Équivalent sous Microsoft Access (mode graphique)}

Le programme mentionne aussi l'interface graphique d'Access. La logique relationnelle est identique, mais les manipulations se font à la souris.

\begin{methode}[Créer la base ETABLISSEMENT sous Access]
\begin{enumerate}
\item \textbf{Nouvelle base} : Fichier $\rightarrow$ Nouveau $\rightarrow$ Base de données vide $\rightarrow$ Nommer \texttt{ETABLISSEMENT.accdb}.
\item \textbf{Créer la table CLASSE (mode Création)} :
  \begin{itemize}
  \item Onglet \textbf{Création} $\rightarrow$ \textbf{Table} (mode Création).
  \item Champs : \texttt{codeClasse} (Texte, Taille 10) $\rightarrow$ Clic droit $\rightarrow$ \textbf{Clé primaire} ; \texttt{libelle} (Texte, 50, Requis=Oui) ; \texttt{effectifMax} (Entier long).
  \item Enregistrer sous \texttt{CLASSE}.
  \end{itemize}
\item \textbf{Créer la table ELEVE (mode Création)} :
  \item Champs : \texttt{matricule} (Numérique, Type Entier long, Index=Oui (Sans doublons) $\rightarrow$ Clé primaire) ; \texttt{nom}, \texttt{prenom} (Texte, Requis=Oui) ; \texttt{dateNaiss} (Date/Heure) ; \texttt{codeClasse} (Texte, Taille 10, Requis=Oui).
  \item Enregistrer sous \texttt{ELEVE}.
\item \textbf{Définir la relation (Fenêtre Relations)} :
  \begin{itemize}
  \item Onglet \textbf{Outils de base de données} $\rightarrow$ \textbf{Relations}.
  \item Ajouter \texttt{CLASSE} et \texttt{ELEVE} $\rightarrow$ Fermer.
  \item Glisser \texttt{codeClasse} de \texttt{CLASSE} sur \texttt{codeClasse} de \texttt{ELEVE}.
  \item Cocher \textbf{Intégrité référentielle}, \textbf{Cascade mise à jour} ; laisser \textbf{Cascade suppression} décoché (suppression restreinte).
  \item Créer. Le trait « 1 » vers « $\infty$ » apparaît.
  \end{itemize}
\item \textbf{Saisir des données} : Ouvrir chaque table en mode Feuille de données, remplir.
\item \textbf{Faire la jointure (Requête en mode SQL)} :
  \begin{itemize}
  \item Onglet \textbf{Création} $\rightarrow$ \textbf{Requête} (mode SQL).
  \item Coller la requête SQL identique à MySQL (Access comprend cette syntaxe).
  \item Exécuter (!) $\rightarrow$ Résultat en grille.
  \end{itemize}
\item \textbf{Alternative : Requête en mode Grille (QBE - Query By Example)} :
  \begin{itemize}
  \item Créer $\rightarrow$ Requête (mode Création) $\rightarrow$ Ajouter \texttt{ELEVE}, \texttt{CLASSE}.
  \item La ligne de liaison (jointure) existe déjà grâce à la fenêtre Relations.
  \item Double-cliquer \texttt{nom}, \texttt{prenom} (ELEVE) et \texttt{libelle} (CLASSE) dans la grille.
  \item Critère sur \texttt{libelle} : \texttt{"Terminale C1"}.
  \item Exécuter.
  \end{itemize}
\end{enumerate}
\end{methode}

\begin{propriete}[Lien entre contrainte REFERENCES et condition de jointure (admise)]
La contrainte \texttt{FOREIGN KEY ... REFERENCES} posée lors du \texttt{CREATE TABLE} (ou via la fenêtre Relations d'Access) \textbf{garantit l'intégrité référentielle à l'insertion/modification} : on ne peut pas mettre un \texttt{codeClasse} inexistant dans \texttt{ELEVE}.
La condition de jointure \texttt{WHERE e.codeClasse = c.codeClasse} dans le \texttt{SELECT} \textbf{exploite cette intégrité} pour reconstruire l'information complète à la lecture. Si l'intégrité n'est pas garantie au niveau du SGBD (ex. tables MyISAM, ou FK désactivée), la jointure fonctionne quand même mais peut retourner des lignes « orphelines » (élève sans classe correspondante) si on utilise une \emph{jointure externe} (LEFT JOIN), hors programme. Au programme, la jointure interne suppose l'intégrité.
\end{propriete}

\courssub{Exercice résolu type Bac}

\begin{exoresolu}[Jointure sur base GESTION\_COMMANDES]
\textbf{Énoncé :} On considère la base de données d'un cybercafé \texttt{CYBER\_DOUALA} avec deux tables :
\begin{itemize}
\item \texttt{CLIENT(idClient PK, nom, prenom, quartier)}
\item \texttt{COMMANDE(numCmd PK, dateCmd, montant, idClient FK $\rightarrow$ CLIENT)}
\end{itemize}
Écrire la requête SQL qui affiche, pour chaque commande de plus de 5000 FCFA, le numéro de commande, la date, le montant, le nom et le prénom du client concerné. Trier par montant décroissant.

\textbf{Solution détaillée :}
\begin{enumerate}
\item \textbf{Tables :} \texttt{COMMANDE} (c) et \texttt{CLIENT} (cl). Colonne commune : \texttt{idClient}.
\item \textbf{Alias :} \texttt{c} pour COMMANDE, \texttt{cl} pour CLIENT.
\item \textbf{Jointure :} \texttt{c.idClient = cl.idClient}.
\item \textbf{Restriction :} \texttt{c.montant > 5000}.
\item \textbf{Projection :} \texttt{c.numCmd, c.dateCmd, c.montant, cl.nom, cl.prenom}.
\item \textbf{Tri :} \texttt{ORDER BY c.montant DESC}.
\end{enumerate}
\begin{lstlisting}[language=SQL]
SELECT c.numCmd, c.dateCmd, c.montant, cl.nom, cl.prenom
FROM COMMANDE c, CLIENT cl
WHERE c.idClient = cl.idClient
  AND c.montant > 5000
ORDER BY c.montant DESC;
\end{lstlisting}
\textbf{Vérification :} Tous les attributs sont préfixés. La jointure est présente. La restriction métier est ajoutée par \texttt{AND}. Le tri est explicite.
\end{exoresolu}

\begin{exercice}[Jointure bibliothèque scolaire]
La base \texttt{BIBLIO\_LYCEE} contient :
\texttt{AUTEUR(idAuteur PK, nomAuteur, pays)} et \texttt{LIVRE(isbn PK, titre, annee, idAuteur FK $\rightarrow$ AUTEUR)}.

\item Que se passe-t-il si un livre a un \texttt{idAuteur} qui n'existe pas dans \texttt{AUTEUR} (base corrompue) et qu'on fait la jointure interne ci-dessus ?
\end{enumerate}
\end{exercice}

\begin{exercice}[Jointure + agrégat (révision)]
Sur la base \texttt{ETABLISSEMENT} (\texttt{ELEVE}, \texttt{CLASSE}), écrire la requête qui affiche, pour chaque classe, son libellé et le nombre d'élèves qu'elle contient. Ordonner par effectif décroissant.
\textit{Indication :} \texttt{GROUP BY c.libelle} et \texttt{COUNT(e.matricule)}.
\end{exercice}

\begin{corrige}[Exercice 1]
\begin{enumerate}
\item \texttt{SELECT l.titre, a.nomAuteur FROM LIVRE l, AUTEUR a WHERE l.idAuteur = a.idAuteur;}
\item \texttt{SELECT l.titre, a.nomAuteur, a.pays FROM LIVRE l, AUTEUR a WHERE l.idAuteur = a.idAuteur AND l.annee > 2010;}
\item Le livre « orphelin » \textbf{disparaît} du résultat. La jointure interne ne conserve que les paires qui satisfont l'égalité. C'est pourquoi l'intégrité référentielle (FK) est cruciale : elle empêche l'existence de tels orphelins.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 2]
\begin{lstlisting}[language=SQL]
SELECT c.libelle, COUNT(e.matricule) AS effectif
FROM ELEVE e, CLASSE c
WHERE e.codeClasse = c.codeClasse
GROUP BY c.libelle
ORDER BY effectif DESC;
\end{lstlisting}
\textit{Note :} \texttt{COUNT(e.matricule)} compte les lignes par groupe. \texttt{GROUP BY c.libelle} suppose que \texttt{libelle} est unique (clé candidate), sinon grouper par \texttt{c.codeClasse} et sélectionner \texttt{c.libelle} (MySQL autorise cela si ONLY\_FULL\_GROUP\_BY est désactivé, mais le standard SQL exige de grouper par tous les attributs non agrégés du SELECT).
\end{corrige}

\begin{savaistu}[Le savais-tu ? : La jointure, star du Baccalauréat]
Depuis la réforme 2018 du programme MINESEC, \textbf{la question sur la jointure à deux tables avec alias est systématiquement présente} à l'épreuve pratique (TP) ou écrite de l'Informatique en Terminale C, D, E. Elle tombe sous l'une de ces formes :
\begin{itemize}
\item « Écrire la requête qui affiche \dots » (code SQL à produire).
\item « Compléter la requête suivante : \texttt{SELECT \dots FROM \dots WHERE \_\_\_\_\_\_} » (trouver la condition de jointure).
\item « Expliquer l'erreur dans cette requête : \texttt{SELECT nom, libelle FROM ELEVE, CLASSE;} » (produit cartésien).
\end{itemize}
\textbf{Astuce de champion :} Sur votre brouillon, dessinez toujours les deux tables avec leurs colonnes, entourez la clé étrangère et la clé primaire, tracez une flèche, écrivez l'alias au-dessus de chaque table. La requête s'écrit alors toute seule. Ne sautez jamais cette étape, même si l'exercice vous semble simple. C'est la garantie de ne pas oublier le \texttt{WHERE} ou de mélanger les alias.
\end{savaistu}

\begin{itemize}
    \item \textbf{Syntaxe \cle{CREATE TABLE}} :
    \texttt{CREATE TABLE NomTable (Col1 Type Contraintes, Col2 Type Contraintes, ..., CONSTRAINT NomFK FOREIGN KEY (ColLocale) REFERENCES TableRef(ColRef));}
    \item \textbf{Syntaxe \cle{ALTER TABLE}} (ajout/suppression colonne, modification type, ajout contrainte) :
    \texttt{ALTER TABLE NomTable ADD Colonne Type Contraintes;} \\
    \texttt{ALTER TABLE NomTable DROP COLUMN Colonne;} \\
    \texttt{ALTER TABLE NomTable MODIFY Colonne NouveauType;} \\
    \texttt{ALTER TABLE NomTable ADD CONSTRAINT NomFK FOREIGN KEY (ColLocale) REFERENCES TableRef(ColRef);}
    \item \textbf{Types courants} : \cle{VARCHAR(n)} (chaîne variable), \cle{CHAR(n)} (chaîne fixe), \cle{INT} (entier), \cle{DATE} (format \texttt{YYYY-MM-DD}).

    \item \textbf{\cle{SELECT} simple} : \texttt{SELECT Col1, Col2 FROM Table WHERE Condition ORDER BY Col1;}
    \item \textbf{Jointure équi-naturelle (syntaxe classique)} : \texttt{SELECT t1.ColA, t2.ColB FROM Table1 t1, Table2 t2 WHERE t1.ColCleEtr = t2.ColClePrim;}
    \item \textbf{Opérateurs de comparaison} : \texttt{=, <>, <, >, <=, >=} ; \textbf{Logiques} : \texttt{AND, OR, NOT}.
    \item \textbf{\cle{DISTINCT}} : élimine les doublons ; \texttt{*} : toutes les colonnes.
\end{itemize}

\textbf{Commentaires pédagogiques du corrigé}
\begin{itemize}
    \item \textbf{Ordre des opérations DDL} : La table référencée (\cle{CLASSE}) \textbf{doit} exister avant la table qui la référence (\cle{ELEVE}). Inverser l'ordre provoque une erreur \texttt{ERROR 1215 (HY000): Cannot add foreign key constraint}.
    \item \textbf{Format de date} : MySQL attend \texttt{YYYY-MM-DD} (norme ISO 8601). Écrire \texttt{'12/05/2006'} (format FR) entraîne une erreur ou une insertion \texttt{0000-00-00} selon le mode \cle{SQL\_MODE}.
    \item \textbf{Clé étrangère} : La contrainte \texttt{FK\_Eleve\_Classe} empêche d'insérer un élève avec un \cle{CodeClasse} inexistant (ex. \texttt{'TX1'}) et empêche de supprimer une classe tant qu'elle a des élèves (sauf \cle{ON DELETE CASCADE} non vu au programme).
    \item \textbf{\cle{UPDATE}/\cle{DELETE} sans \cle{WHERE}} : Rappelons que c'est la \textbf{première cause de perte de données} en production. Toujours tester la condition avec un \cle{SELECT} avant d'exécuter la modification.
    \item \textbf{Alias dans la jointure} : L'écriture \texttt{e.NomComplet} est obligatoire si le nom de colonne existe dans les deux tables (ici \cle{CodeClasse} est commun, d'où \texttt{e.CodeClasse} et \texttt{c.CodeClasse}). L'alias de colonne (\texttt{AS Eleve}) améliore la lisibilité de l'affichage final.
    \item \textbf{Jointure vs Produit cartésien} : Oublier la condition \texttt{WHERE e.CodeClasse = c.CodeClasse} produit un produit cartésien (7 $\times$ 3 = 21 lignes), résultat sans sens.
\end{itemize}
\end{exoresolu}

\begin{aretenir}[Bilan de l'activité]
Cette activité a permis de mettre en évidence, par la pratique, le cycle de vie complet d'une base de données relationnelle dans un contexte administratif camerounais concret :
\begin{itemize}
    \item La \textbf{modélisation physique} (choix des types, définition des clés primaires et étrangères) conditionne la qualité et la fiabilité des données stockées. L'omission d'une contrainte \cle{NOT NULL} ou \cle{REFERENCES} ouvre la porte à des anomalies (élèves sans classe, classes fantômes).
    \item Le \textbf{langage SQL} se révèle être un standard puissant : les mêmes instructions s'exécutent indifféremment en console \cle{MySQL} (serveur, multi-utilisateurs, réseau) ou en mode graphique \cle{Access} (monoposte, fichier local \texttt{.accdb}), ce qui illustre la portabilité du standard.
    \item La \textbf{manipulation de données} (\cle{INSERT}, \cle{UPDATE}, \cle{DELETE}) exige une rigueur absolue sur les clauses \cle{WHERE} : une requête mal ciblée modifie ou efface bien plus que prévu.
    \item L'\textbf{interrogation} (\cle{SELECT}) montre tout l'intérêt du relationnel : la jointure permet de restituer une information « métier » (Nom + Libellé classe) qui n'existe pas physiquement dans une seule table, évitant ainsi la redondance et les incohérences.
    \item Enfin, le travail en groupe et la confrontation papier/console ont renforcé la compétence « \textbf{Communiquer sur une solution technique} » : expliquer son script, justifier un type \cle{CHAR} vs \cle{VARCHAR}, ou déboguer une erreur de syntaxe \texttt{ERROR 1064} sont des gestes professionnels essentiels pour le Baccalauréat et au-delà.
\end{itemize}
\end{aretenir}

\coursec{Méthodes et exercices résolus}

\coursec{Leçon 6 : Implémentation d'une base de données}

\courssub{Bases de données, SGBD et langage SQL}

\begin{definition}[Notions fondamentales]
\begin{itemize}
    \item \textbf{Base de données (BD) :} Ensemble structuré de données persistantes, organisées pour un accès, une gestion et une mise à jour faciles. Elle modélise une partie du monde réel (ex: gestion d'un lycée, d'un cybercafé, d'une boutique).
    \item \textbf{SGBD (Système de Gestion de Base de Données) :} Logiciel serveur permettant de créer, manipuler, sécuriser et partager des bases de données. Exemples au programme : \texttt{Microsoft Access} (monoposte, fichier \texttt{.accdb}), \texttt{MySQL} / \texttt{MariaDB} (client-serveur, standard web/entreprise).
    \item \textbf{SQL (Structured Query Language) :} Langage standardisé (ISO/ANSI) pour dialoguer avec un SGBD relationnel. Deux sous-langages principaux :
    \begin{itemize}
        \item \textbf{DDL (Data Definition Language) :} \texttt{CREATE}, \texttt{ALTER}, \texttt{DROP} (structure).
        \item \textbf{DML (Data Manipulation Language) :} \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}, \texttt{SELECT} (données).
    \end{itemize}
    \item \textbf{Requête :} Instruction SQL envoyée au SGBD pour obtenir un résultat (création d'objet, modification de données, affichage de résultats).
\end{itemize}
\end{definition}

\begin{aretenir}[Architecture trois niveaux (rappel)]
Le SGBD sépare : \textbf{Niveau externe} (vues utilisateurs), \textbf{Niveau conceptuel} (schéma global, MCD/MLD), \textbf{Niveau interne} (stockage physique, index). L'indépendance des données permet de changer le stockage sans casser les applications.
\end{aretenir}

\courssub{Types de données et contraintes d'intégrité}

\begin{propriete}[Types de données SQL au programme (Terminale C/D/E)]
\begin{center}
\begin{tabularx}{\linewidth}{|l|X|l|}
\hline
\textbf{Type SQL} & \textbf{Usage / Description} & \textbf{Exemple littéral} \\ \hline
\texttt{INT} & Entier signé (4 octets), identifiants, compteurs, âges. & \texttt{123}, \texttt{-5} \\ \hline
\texttt{VARCHAR(n)} & Chaîne de longueur variable ($0$ à $n$ caractères). Efficace pour noms, adresses, emails. $n \le 65535$. & \texttt{'MBARGA'}, \texttt{'jean@email.cm'} \\ \hline
\texttt{CHAR(n)} & Chaîne de longueur \textbf{fixe} $n$ (complétée par des espaces). Codes fixes : sexe, code postal, matricule. & \texttt{'M'}, \texttt{'E20240001'} \\ \hline
\texttt{DATE} & Date calendaire (année, mois, jour). Format standard ISO : \texttt{AAAA-MM-JJ}. & \texttt{'2006-05-12'} \\ \hline
\end{tabularx}
\end{center}
\emph{Note :} \texttt{TEXT}, \texttt{BLOB}, \texttt{DECIMAL}, \texttt{DATETIME} existent mais ne sont pas au programme officiel.
\end{propriete}

\begin{propriete}[Contraintes d'intégrité (garantissent la qualité des données)]
\begin{itemize}
    \item \texttt{PRIMARY KEY (PK)} : Identifiant unique de la ligne. \textbf{Non nul} + \textbf{Unique}. Une seule PK par table (simple ou composée).
    \item \texttt{NOT NULL} : La colonne ne peut pas recevoir la valeur \texttt{NULL} (absence de valeur). Obligatoire pour les attributs identifiants ou métier indispensables.
    \item \texttt{UNIQUE} : Toutes les valeurs de la colonne (ou groupe de colonnes) sont distinctes. Accepte \texttt{NULL} (sauf MySQL où \texttt{NULL} $\neq$ \texttt{NULL} pour l'unicité). Ex: \texttt{Email}, \texttt{Matricule} (si pas PK).
    \item \texttt{FOREIGN KEY (FK) REFERENCES} : \textbf{Intégrité référentielle}. La valeur de la colonne enfant doit exister comme clé primaire dans la table parente (ou être \texttt{NULL} si autorisé). Empêche les orphelins.
    \item \texttt{DEFAULT valeur} : Valeur insérée automatiquement si omise dans \texttt{INSERT}. (Non explicitement au programme mais utile).
\end{itemize}
\end{propriete}

\courssub{Requêtes de définition des données : CREATE, ALTER, DROP}

\begin{methode}[Créer une table avec types et contraintes (CREATE TABLE)]
\textbf{Objectif :} Écrire une requête DDL pour créer une table structurée respectant l'intégrité.
\begin{enumerate}
    \item \textbf{Analyser le besoin :} Nom table, liste colonnes, types, contraintes (PK, NN, UQ, FK).
    \item \textbf{Choisir les types :} \texttt{INT} (id), \texttt{VARCHAR(n)} (texte variable), \texttt{CHAR(n)} (code fixe), \texttt{DATE} (date ISO).
    \item \textbf{Poser les contraintes :} \texttt{PRIMARY KEY}, \texttt{NOT NULL}, \texttt{UNIQUE}, \texttt{FOREIGN KEY ... REFERENCES ...}.
    \item \textbf{Rédiger la requête :} Syntaxe canonique.
    \item \textbf{Vérifier :} Parenthèses, virgules (pas après dernière colonne), noms sans espaces/accents (ou backticks \texttt{`}).
\end{enumerate}
\end{methode}

\begin{exoresolu}[Création de la table \texttt{ETUDIANT} d'un lycée]
\textbf{Énoncé :} Créer la table \texttt{ETUDIANT} :
\begin{itemize}
    \item \texttt{Matricule} : \texttt{CHAR(10)}, identifiant unique.
    \item \texttt{Nom}, \texttt{Prenom} : \texttt{VARCHAR(50)}, obligatoires.
    \item \texttt{DateNaiss} : \texttt{DATE}, obligatoire.
    \item \texttt{Sexe} : \texttt{CHAR(1)} ('M'/'F'), obligatoire.
    \item \texttt{Email} : \texttt{VARCHAR(100)}, unique.
    \item \texttt{IdClasse} : \texttt{INT}, référence \texttt{CLASSE(IdClasse)}.
\end{itemize}

\tcblower
\textbf{Solution détaillée :}
\begin{enumerate}
    \item \textbf{Colonnes \& Types :} \texttt{Matricule CHAR(10)}, \texttt{Nom/Prenom VARCHAR(50)}, \texttt{DateNaiss DATE}, \texttt{Sexe CHAR(1)}, \texttt{Email VARCHAR(100)}, \texttt{IdClasse INT}.
    \item \textbf{Contraintes :} PK sur \texttt{Matricule}, NN sur \texttt{Nom, Prenom, DateNaiss, Sexe, IdClasse}, UQ sur \texttt{Email}, FK \texttt{IdClasse $\rightarrow$ CLASSE(IdClasse)}.
    \item \textbf{Requête :}
\begin{lstlisting}[language=SQL]
CREATE TABLE ETUDIANT (
    Matricule CHAR(10) PRIMARY KEY,
    Nom VARCHAR(50) NOT NULL,
    Prenom VARCHAR(50) NOT NULL,
    DateNaiss DATE NOT NULL,
    Sexe CHAR(1) NOT NULL,
    Email VARCHAR(100) UNIQUE,
    IdClasse INT NOT NULL,
    CONSTRAINT FK_Etudiant_Classe 
        FOREIGN KEY (IdClasse) REFERENCES CLASSE(IdClasse)
);
\end{lstlisting}
\end{enumerate}
\textbf{Conclusion :} Table créée avec PK, unicité email, FK vers \texttt{CLASSE}.
\end{exoresolu}

\begin{methode}[Modifier et supprimer la structure d'une table (ALTER TABLE, DROP TABLE)]
\textbf{Objectif :} Adapter le schéma (ajouter/supprimer colonne, modifier type/contrainte) ou supprimer la table.
\begin{enumerate}
    \item \textbf{Ajouter une colonne :} \texttt{ALTER TABLE NomTable ADD NomColonne Type [Contraintes];}
    \item \textbf{Supprimer une colonne :} \texttt{ALTER TABLE NomTable DROP COLUMN NomColonne;} (\emph{Perte de données irréversible}).
    \item \textbf{Modifier une colonne (type/contraintes) :}
    \begin{itemize}
        \item MySQL : \texttt{ALTER TABLE NomTable MODIFY NomColonne NouveauType NouvellesContraintes;}
        \item Standard SQL / Access : \texttt{ALTER TABLE NomTable ALTER COLUMN NomColonne NouveauType [Contraintes];}
    \end{itemize}
    \item \textbf{Ajouter une contrainte (FK) :} \texttt{ALTER TABLE NomTable ADD CONSTRAINT NomContrainte FOREIGN KEY (ColFK) REFERENCES TableParente(ColPK);}
    \item \textbf{Supprimer une contrainte :} \texttt{ALTER TABLE NomTable DROP CONSTRAINT NomContrainte;} (MySQL : \texttt{DROP FOREIGN KEY NomContrainte;}).
    \item \textbf{Supprimer la table :} \texttt{DROP TABLE NomTable;} (structure + données + index + contraintes). \texttt{DROP TABLE IF EXISTS NomTable;} évite l'erreur si absente.
\end{enumerate}
\emph{Attention :} Toute commande DDL valide une transaction implicite (\texttt{COMMIT}) dans la plupart des SGBD.
\end{methode}

\begin{exoresolu}[Évolution du schéma : ajout colonne et FK]
\textbf{Énoncé :} Table \texttt{ETUDIANT} existante. Opérations :
\begin{enumerate}
    \item Ajouter \texttt{Telephone VARCHAR(15)} (optionnel).
    \item Rendre \texttt{Email} obligatoire (\texttt{NOT NULL}).
    \item Ajouter \texttt{IdTuteur INT} + FK \texttt{FK\_Etudiant\_Tuteur} vers \texttt{TUTEUR(IdTuteur)}.
    \item Supprimer table \texttt{ANCIENS\_NOTES}.
\end{enumerate}

\tcblower
\textbf{Solution détaillée :}
\begin{enumerate}
    \item \texttt{ALTER TABLE ETUDIANT ADD Telephone VARCHAR(15);}
    \item \textbf{MySQL :} \texttt{ALTER TABLE ETUDIANT MODIFY Email VARCHAR(100) NOT NULL;} \\
          \textbf{Standard/Access :} \texttt{ALTER TABLE ETUDIANT ALTER COLUMN Email SET NOT NULL;}
    \item \textbf{MySQL (une commande) :}
\begin{lstlisting}[language=SQL]
ALTER TABLE ETUDIANT 
    ADD IdTuteur INT,
    ADD CONSTRAINT FK_Etudiant_Tuteur FOREIGN KEY (IdTuteur) REFERENCES TUTEUR(IdTuteur);
\end{lstlisting}
          \textbf{Séparément (portable) :}
\begin{lstlisting}[language=SQL]
ALTER TABLE ETUDIANT ADD IdTuteur INT;
ALTER TABLE ETUDIANT ADD CONSTRAINT FK_Etudiant_Tuteur FOREIGN KEY (IdTuteur) REFERENCES TUTEUR(IdTuteur);
\end{lstlisting}
    \item \texttt{DROP TABLE IF EXISTS ANCIENS\_NOTES;}
\end{enumerate}
\textbf{Conclusion :} \texttt{ALTER TABLE} fait évoluer sans perte (sauf \texttt{DROP COLUMN}), \texttt{DROP TABLE} supprime définitivement.
\end{exoresolu}

\courssub{Insertion, modification et suppression des données}

\begin{methode}[Insérer des données (INSERT INTO)]
\textbf{Objectif :} Ajouter une ou plusieurs lignes.
\begin{enumerate}
    \item \textbf{Syntaxe explicite (recommandée) :} \texttt{INSERT INTO NomTable (Col1, Col2, ...) VALUES (Val1, Val2, ...);} Ordre colonnes = ordre valeurs. Colonnes omises = \texttt{DEFAULT} ou \texttt{NULL}.
    \item \textbf{Syntaxe implicite (risquée) :} \texttt{INSERT INTO NomTable VALUES (Val1, Val2, ...);} Doit fournir \textbf{toutes} les colonnes dans l'ordre exact de la définition.
    \item \textbf{Insertion multiple (MySQL, PG, SQL Server) :} \texttt{INSERT INTO NomTable (Col1, Col2) VALUES (V1, V2), (V3, V4), ...;} Performant.
    \item \textbf{Littéraux :} Chaînes/Date $\rightarrow$ \texttt{'valeur'} (guillemets simples). Nombres $\rightarrow$ \texttt{123}. \texttt{NULL} $\rightarrow$ mot-clé sans quotes. Date $\rightarrow$ \texttt{'AAAA-MM-JJ'}.
    \item \textbf{Respect contraintes :} Échec si violation PK (doublon), NN (manquant), UQ (doublon), FK (parent inexistant).
\end{enumerate}
\end{methode}

\begin{exoresolu}[Insertion d'élèves dans ETUDIANT]
\textbf{Énoncé :} Insérer 3 élèves (structure exercices 1+2 : \texttt{Telephone}, \texttt{IdTuteur} ajoutés). Classes (1,2) et Tuteurs (10,20) existent.

\begin{center}
\begin{tabular}{|l|l|l|l|l|l|l|l|}
\hline
Matricule & Nom & Prénom & DateNaiss & Sexe & Email & IdClasse & IdTuteur \\ \hline
E20240001 & MBARGA & Jean & 2006-05-12 & M & jean.mbarga@email.cm & 1 & 10 \\ \hline
E20240002 & ETOUNDI & Marie & 2007-11-23 & F & marie.etoundi@email.cm & 1 & 10 \\ \hline
E20240003 & FOUDA & Paul & 2005-02-28 & M & paul.fouda@email.cm & 2 & 20 \\ \hline
\end{tabular}
\end{center}

\tcblower
\textbf{Solution :} Syntaxe explicite multi-lignes. \texttt{Telephone} omis ($\rightarrow$ \texttt{NULL}).
\begin{lstlisting}[language=SQL]
INSERT INTO ETUDIANT (Matricule, Nom, Prenom, DateNaiss, Sexe, Email, IdClasse, IdTuteur)
VALUES
    ('E20240001', 'MBARGA', 'Jean', '2006-05-12', 'M', 'jean.mbarga@email.cm', 1, 10),
    ('E20240002', 'ETOUNDI', 'Marie', '2007-11-23', 'F', 'marie.etoundi@email.cm', 1, 10),
    ('E20240003', 'FOUDA', 'Paul', '2005-02-28', 'M', 'paul.fouda@email.cm', 2, 20);
\end{lstlisting}

\end{exoresolu}

\begin{methode}[Modifier et supprimer des données (UPDATE, DELETE)]
\textbf{Objectif :} Changer valeurs (\texttt{UPDATE}) ou retirer lignes (\texttt{DELETE}).
\begin{enumerate}
    \item \textbf{UPDATE :}
\begin{lstlisting}[language=SQL]
UPDATE NomTable
SET Col1 = NouvVal1, Col2 = NouvVal2, ...
WHERE Condition;  -- INDISPENSABLE ! Sans WHERE : TOUTES lignes modifiées.
\end{lstlisting}
    \item \textbf{DELETE :}
\begin{lstlisting}[language=SQL]
DELETE FROM NomTable
WHERE Condition;  -- INDISPENSABLE ! Sans WHERE : TOUTES lignes supprimées.
\end{lstlisting}
    \item \textbf{Clause WHERE :} Opérateurs \texttt{=}, \texttt{<>} (\texttt{!=}), \texttt{<}, \texttt{>}, \texttt{<=}, \texttt{>=}, \texttt{AND}, \texttt{OR}, \texttt{NOT}, \texttt{IN}, \texttt{BETWEEN}, \texttt{LIKE}, \texttt{IS NULL}. Parenthèses pour priorité.
    \item \textbf{Sous-requêtes dans WHERE :} Ex: \texttt{WHERE IdClasse IN (SELECT IdClasse FROM CLASSE WHERE Niveau = 'Terminale')}.
    \item \textbf{Contraintes :} \texttt{UPDATE} échoue si violation PK, UQ, FK, NN. \texttt{DELETE} échoue si lignes filles référencent (sauf \texttt{ON DELETE CASCADE}).
\end{enumerate}
\emph{Règle d'or :} Tester condition avec \texttt{SELECT * FROM NomTable WHERE Condition;} avant \texttt{UPDATE}/\texttt{DELETE}.
\end{methode}

\begin{exoresolu}[Mise à jour et suppression ciblées]
\textbf{Énoncé :} Table \texttt{ETUDIANT} peuplée.
\begin{enumerate}
    \item Élève \texttt{E20240001} : téléphone \texttt{'6XXYYZZWW'}.
    \item Élèves classe \texttt{IdClasse=1} $\rightarrow$ classe \texttt{IdClasse=3}.
    \item Supprimer élève \texttt{E20240003}.
\end{enumerate}

\tcblower
\textbf{Solution :}
\begin{enumerate}
    \item \textbf{Ciblage PK (sûr) :}
\begin{lstlisting}[language=SQL]
UPDATE ETUDIANT
SET Telephone = '6XXYYZZWW'
WHERE Matricule = 'E20240001';
\end{lstlisting}
    \item \textbf{Ciblage groupe (FK) :}
\begin{lstlisting}[language=SQL]
UPDATE ETUDIANT
SET IdClasse = 3
WHERE IdClasse = 1;
\end{lstlisting}
          \emph{Test préalable :} \texttt{SELECT * FROM ETUDIANT WHERE IdClasse = 1;} (retourne Jean, Marie $\rightarrow$ 2 lignes modifiées).
    \item \textbf{Suppression PK :}
\begin{lstlisting}[language=SQL]
DELETE FROM ETUDIANT
WHERE Matricule = 'E20240003';
\end{lstlisting}
          \emph{Note :} Échec si FK référençant cet élève avec \texttt{ON DELETE RESTRICT} (défaut). On suppose pas de table fille ou \texttt{CASCADE/SET NULL}.
\end{enumerate}
\textbf{Conclusion :} PK dans \texttt{WHERE} pour précision unitaire ; FK ou critère métier pour groupe.
\end{exoresolu}

\courssub{Interrogation d'une table : SELECT}

\begin{methode}[SELECT simple : filtres, tri, distinct, calculs, alias]
\textbf{Objectif :} Extraire données d'une table (projection, sélection, tri).
\begin{enumerate}
    \item \textbf{Syntaxe :}
\begin{lstlisting}[language=SQL]
SELECT [DISTINCT] Col1, Col2, ... | *
FROM NomTable
[WHERE Condition]
[ORDER BY Col1 [ASC|DESC], Col2 ...];
\end{lstlisting}
    \item \textbf{Colonnes :} Lister explicitement (\texttt{SELECT Nom, Prenom}) $>$ \texttt{SELECT *} (perf, clarté).
    \item \textbf{DISTINCT :} Élimine doublons sur \textbf{résultat final} (après projection). \texttt{SELECT DISTINCT IdClasse FROM ETUDIANT;}.
    \item \textbf{WHERE :} Filtre lignes \textbf{avant} projection. Opérateurs : comparaisons, \texttt{AND/OR/NOT}, \texttt{IN (liste)}, \texttt{BETWEEN v1 AND v2}, \texttt{LIKE 'motif'} (\texttt{\%} = chaîne quelconque, \texttt{\_} = 1 car), \texttt{IS NULL / IS NOT NULL}.
    \item \textbf{Expressions \& Alias :} \texttt{SELECT Nom, (YEAR(CURDATE())-YEAR(DateNaiss)) AS Age FROM ETUDIANT;} (Fonctions MySQL). \texttt{AS} optionnel mais clair. Permet \texttt{ORDER BY Age DESC}.
    \item \textbf{ORDER BY :} Tri résultat final. \texttt{ASC} (défaut) / \texttt{DESC}. Accepte alias ou n° colonne (\texttt{ORDER BY 3 DESC}).
\end{enumerate}
\end{methode}

\begin{exoresolu}[Requêtes de sélection variées sur ETUDIANT]
\textbf{Énoncé :} Écrire les requêtes pour :
\begin{enumerate}
    \item Nom, Prénom, Email de tous élèves, triés Nom puis Prénom.
    \item Matricule, Nom des élèves nés \textbf{après} 2006-01-01 (strict).
    \item Noms distincts des classes ayant au moins un élève (via \texttt{IdClasse}).
    \item Nom, Prénom, Âge approx (année courante - année naissance), tri âge décroissant.
\end{enumerate}

\tcblower
\textbf{Solution :}
\begin{enumerate}
    \item \begin{lstlisting}[language=SQL]
SELECT Nom, Prenom, Email
FROM ETUDIANT
ORDER BY Nom ASC, Prenom ASC;
\end{lstlisting}
    \item \begin{lstlisting}[language=SQL]
SELECT Matricule, Nom
FROM ETUDIANT
WHERE DateNaiss > '2006-01-01';
\end{lstlisting}
          \emph{Note :} \texttt{'>'} exclut le 2006-01-01. Inclusif : \texttt{>=}.
    \item \begin{lstlisting}[language=SQL]
SELECT DISTINCT IdClasse
FROM ETUDIANT;
\end{lstlisting}
          (Pour libellé classe : jointure nécessaire, voir §6).
    \item \begin{lstlisting}[language=SQL]
SELECT Nom, Prenom, 
       (YEAR(CURDATE()) - YEAR(DateNaiss)) AS Age
FROM ETUDIANT
ORDER BY Age DESC;
\end{lstlisting}
          \emph{Précision :} Âge "année civile". Âge exact MySQL : \texttt{TIMESTAMPDIFF(YEAR, DateNaiss, CURDATE())}.
\end{enumerate}
\textbf{Conclusion :} \texttt{SELECT} ne modifie pas. \texttt{DISTINCT} sur combinaison colonnes sélectionnées. Alias lisibilité + tri sur calculé.
\end{exoresolu}

\courssub{Jointure entre deux tables et mise en œuvre pratique}

\begin{methode}[Jointure interne (équi-jointure) : syntaxe programme officiel]
\textbf{Objectif :} Combiner lignes de deux tables liées par FK (table Enfant $\rightarrow$ table Parente).
\begin{enumerate}
    \item \textbf{Identifier relation :} \texttt{ETUDIANT.IdClasse} (FK) $\rightarrow$ \texttt{CLASSE.IdClasse} (PK).
    \item \textbf{Syntaxe "ancienne" (exigible au Bac) :}
\begin{lstlisting}[language=SQL]
SELECT t1.ColA, t2.ColB, ...
FROM Table1 t1, Table2 t2
WHERE t1.ColFK = t2.ColPK
  [AND AutresConditions];
\end{lstlisting}
    \item \textbf{Alias (t1, t2) :} \textbf{Obligatoires} si noms colonnes identiques (\texttt{IdClasse}). Préfixer \textbf{toutes} colonnes (\texttt{t1.Nom}, \texttt{t2.Libelle}) pour lever ambiguïté. Recommandés toujours.
    \item \textbf{Condition jointure :} \texttt{t1.FK = t2.PK}. \texttt{AND} implicite avec autres filtres \texttt{WHERE}.
    \item \textbf{Jointure externe (LEFT/RIGHT JOIN) :} Non au programme. Sert à afficher "parents sans enfants" (ex: classes vides).
\end{enumerate}
\end{methode}

\begin{exoresolu}[Jointure ETUDIANT - CLASSE pour bulletin]
\textbf{Énoncé :} Tables :
\begin{itemize}
    \item \texttt{ETUDIANT(Matricule, Nom, Prenom, IdClasse, ...)}
    \item \texttt{CLASSE(IdClasse, Libelle, Niveau, Salle)}
\end{itemize}
Afficher pour chaque élève : \texttt{Matricule, Nom, Prenom, Libelle, Niveau}, triés \texttt{Niveau, Libelle, Nom}.

\tcblower
\textbf{Solution :}
\begin{enumerate}
    \item \textbf{Analyse :} Lien \texttt{e.IdClasse = c.IdClasse}. Colonne commune $\rightarrow$ alias \textbf{indispensables}.
    \item \textbf{Alias :} \texttt{e} (ETUDIANT), \texttt{c} (CLASSE).
    \item \textbf{Requête :}
\begin{lstlisting}[language=SQL]
SELECT e.Matricule, e.Nom, e.Prenom, c.Libelle, c.Niveau
FROM ETUDIANT e, CLASSE c
WHERE e.IdClasse = c.IdClasse
ORDER BY c.Niveau, c.Libelle, e.Nom;
\end{lstlisting}
    \item \textbf{Explication :}
    \begin{enumerate}
        \item \texttt{FROM ETUDIANT e, CLASSE c} : Produit cartésien.
        \item \texttt{WHERE e.IdClasse = c.IdClasse} : Filtre équi-jointure interne. Exclut élèves sans classe (\texttt{NULL}) et classes vides.
        \item \texttt{SELECT ...} : Projection préfixée.
        \item \texttt{ORDER BY ...} : Tri classes puis élèves.
    \end{enumerate}
\end{enumerate}
\textbf{Conclusion :} Jointure interne = correspondances exactes. Alias courts évitent erreur "Column 'IdClasse' in where clause is ambiguous".
\end{exoresolu}

\begin{methode}[Création concrète : Console MySQL / Interface Access]
\textbf{Objectif :} Réaliser la création physiquement.
\begin{enumerate}
    \item \textbf{MySQL (Terminal) :}
    \begin{enumerate}
        \item Connexion : \texttt{mysql -u root -p} (mot de passe).
        \item Créer base : \texttt{CREATE DATABASE NomBase CHARACTER SET utf8mb4 COLLATE utf8mb4\_general\_ci;} (UTF-8 complet).
        \item Sélectionner : \texttt{USE NomBase;}.
        \item Exécuter \texttt{CREATE TABLE ... ;} (copier-coller ou \texttt{SOURCE fichier.sql;}).
        \item Vérifier : \texttt{SHOW TABLES;}, \texttt{DESCRIBE NomTable;}.
    \end{enumerate}
    \item \textbf{Access (Graphique) :}
    \begin{enumerate}
        \item Fichier $\rightarrow$ Nouveau $\rightarrow$ Base vide $\rightarrow$ Nommer (\texttt{GestionLycee.accdb}) $\rightarrow$ Créer.
        \item Onglet \textbf{Créer} $\rightarrow$ \textbf{Conception Table}.
        \item Saisir : Nom champ, Type (Texte Court $\approx$ VARCHAR, Numérique $\approx$ INT, Date/Heure $\approx$ DATE). Sélectionner PK $\rightarrow$ bouton \textbf{Clé primaire}.
        \item Propriétés (bas) : \texttt{Requis = Oui} (NOT NULL), \texttt{Indexé = Oui (Sans doublons)} (UNIQUE/PK).
        \item Enregistrer (Ctrl+S) $\rightarrow$ Nom table (\texttt{T\_Etudiant}).
        \item Relations : Outils $\rightarrow$ Relations $\rightarrow$ Ajouter tables $\rightarrow$ Glisser PK vers FK $\rightarrow$ Cocher \textbf{Intégrité référentielle}.
    \end{enumerate}
\end{enumerate}
\end{methode}

\begin{exoresolu}[Script complet MySQL pour base "LyceeDB"]
\textbf{Énoncé :} Script \texttt{creation.sql} pour :
\begin{enumerate}
    \item Base \texttt{LyceeDB} UTF-8.
    \item Table \texttt{CLASSE(IdClasse INT PK, Libelle VARCHAR(30) NN, Niveau VARCHAR(20))}.
    \item Table \texttt{ETUDIANT} (structure exo 1, FK vers CLASSE).
    \item Insérer 2 classes : (1, 'Terminale C1', 'Terminale'), (2, 'Terminale D1', 'Terminale').
    \item Insérer élève \texttt{('E20240001', 'MBARGA', 'Jean', '2006-05-12', 'M', 'jean.mbarga@email.cm', 1)}.
\end{enumerate}

\tcblower
\textbf{Solution :}
\begin{lstlisting}[language=SQL]
-- 1. Création base de données
CREATE DATABASE IF NOT EXISTS LyceeDB
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_general_ci;

-- 2. Utilisation base
USE LyceeDB;

-- 3. Table CLASSE (parente, créée EN PREMIER)
CREATE TABLE CLASSE (
    IdClasse INT PRIMARY KEY,
    Libelle VARCHAR(30) NOT NULL,
    Niveau VARCHAR(20)
);

-- 4. Table ETUDIANT (enfant, FK vers CLASSE)
CREATE TABLE ETUDIANT (
    Matricule CHAR(10) PRIMARY KEY,
    Nom VARCHAR(50) NOT NULL,
    Prenom VARCHAR(50) NOT NULL,
    DateNaiss DATE NOT NULL,
    Sexe CHAR(1) NOT NULL,
    Email VARCHAR(100) UNIQUE,
    IdClasse INT NOT NULL,
    CONSTRAINT FK_Etudiant_Classe 
        FOREIGN KEY (IdClasse) REFERENCES CLASSE(IdClasse)
);

-- 5. Données de référence (classes)
INSERT INTO CLASSE (IdClasse, Libelle, Niveau) VALUES
    (1, 'Terminale C1', 'Terminale'),
    (2, 'Terminale D1', 'Terminale');

-- 6. Données transactionnelles (élève)
INSERT INTO ETUDIANT (Matricule, Nom, Prenom, DateNaiss, Sexe, Email, IdClasse)
VALUES ('E20240001', 'MBARGA', 'Jean', '2006-05-12', 'M', 'jean.mbarga@email.cm', 1);
\end{lstlisting}

\textbf{Exécution console :}
\begin{lstlisting}[language=bash]
mysql -u root -p < creation.sql
# ou dans client mysql :
SOURCE /chemin/vers/creation.sql;
\end{lstlisting}
\textbf{Conclusion :} Ordre crucial : Base $\rightarrow$ Tables parentes (sans FK) $\rightarrow$ Tables enfants (avec FK) $\rightarrow$ Données référence $\rightarrow$ Données transactionnelles. \texttt{utf8mb4} gère accents, alphabets locaux, émojis.
\end{exoresolu}

\begin{attention}[Les 5 erreurs qui coûtent des points au Bac]
\begin{enumerate}
    \item \textbf{Oublier \texttt{WHERE} dans \texttt{UPDATE} ou \texttt{DELETE}.} $\rightarrow$ Modification/suppression de \textbf{toutes} lignes. \emph{Réflexe :} Écrire \texttt{WHERE} d'abord, tester avec \texttt{SELECT}.
    \item \textbf{Ambiguïté noms colonnes en jointure.} \texttt{WHERE IdClasse = IdClasse} au lieu de \texttt{WHERE e.IdClasse = c.IdClasse}. $\rightarrow$ Erreur "Column 'IdClasse' in where clause is ambiguous". \emph{Réflexe :} Alias courts (\texttt{e}, \texttt{c}) + préfixer \textbf{toutes} colonnes (\texttt{e.Nom}, \texttt{c.Libelle}).
    \item \textbf{Mauvais format date/chaîne.} \texttt{DateNaiss = 2006-05-12} (soustraction !) ou \texttt{'12/05/2006'} (format FR). $\rightarrow$ Erreur/résultat faux. \emph{Règle :} ISO \texttt{'AAAA-MM-JJ'} entre quotes simples.
    \item \textbf{Ordre création tables (FK).} Créer enfant (\texttt{ETUDIANT}) avant parente (\texttt{CLASSE}). $\rightarrow$ Erreur "Referenced table 'CLASSE' not found". \emph{Règle :} Tables référencées d'abord.
    \item \textbf{Confondre \texttt{DROP TABLE} et \texttt{DELETE FROM}.} \texttt{DROP TABLE} supprime la \textbf{structure} (table disparaît). \texttt{DELETE FROM} supprime les \textbf{données} (table reste vide). "Vider la table" $\rightarrow$ \texttt{DELETE FROM} (ou \texttt{TRUNCATE TABLE}). "Supprimer la table" $\rightarrow$ \texttt{DROP TABLE}.
\end{enumerate}
\end{attention}

\begin{corrige}[Exercice 1 — QCM : SGBD et langage SQL]
\textbf{Réponse exacte : c.}

Un \cle{SGBD} (Système de Gestion de Base de Données) est le logiciel qui assure l'interface entre l'utilisateur (ou les applications) et la base de données physique : il gère le stockage, la sécurité, les accès concurrents et l'intégrité des données. Access et MySQL en sont des exemples.

\textbf{Pourquoi les autres propositions sont fausses :}
\begin{itemize}
    \item \textbf{a. Faux.} MySQL est un \cle{SGBD} relationnel, pas un langage de programmation. Le langage qu'il utilise pour dialoguer avec la base est le SQL.
    \item \textbf{b. Faux.} SQL ne sert pas qu'à interroger : il comprend le LDD (\texttt{CREATE}, \texttt{ALTER}, \texttt{DROP}), le LMD (\texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}, \texttt{SELECT}) et le LCD (Langage de Contrôle des Données / DCL : droits d'accès \texttt{GRANT}, \texttt{REVOKE}).
    \item \textbf{d. Faux.} \texttt{CREATE DATABASE} crée une base de données vide. L'insertion de lignes se fait avec \texttt{INSERT INTO}.
\end{itemize}
\end{corrige}

\begin{corrige}[Exercice 2 — Vrai ou Faux justifié]
\begin{enumerate}
    \item \textbf{Faux.} \texttt{VARCHAR(50)} est une chaîne de longueur \emph{variable} : seuls les caractères réellement stockés occupent de la place (plus un ou deux octets pour la longueur). La valeur \texttt{'ABENA'} n'occupe donc que 5 caractères, pas 50. C'est le type \texttt{CHAR(50)} qui occupe toujours 50 caractères (complétés par des espaces).
    \item \textbf{Vrai.} Une clé primaire identifie de manière unique chaque ligne : ses valeurs doivent donc être uniques et ne peuvent pas être nulles. Déclarer \texttt{PRIMARY KEY} implique automatiquement \texttt{NOT NULL} et \texttt{UNIQUE}.
    \item \textbf{Faux.} \texttt{DROP TABLE} supprime définitivement la structure \emph{et} toutes les données de la table. Aucune sauvegarde automatique n'est créée : c'est une commande irréversible, à manipuler avec la plus grande prudence.
    \item \textbf{Vrai.} Le paramètre \texttt{DISTINCT}, placé juste après \texttt{SELECT}, élimine les doublons : chaque combinaison de valeurs des colonnes affichées n'apparaît qu'une seule fois dans le résultat.
\end{enumerate}
\end{corrige}

\begin{corrige}[Exercice 4 — Calcul direct : cardinalité d'un résultat]
La requête s'exécute en deux étapes logiques.

\textbf{Étape 1 : filtrage par \texttt{WHERE Prix >= 2500}.}

\begin{center}
\begin{tabular}{|c|l|l|r|}
\hline
\texttt{CodeP} & \texttt{Designation} & \texttt{Categorie} & \texttt{Prix} \\ \hline
P3 & Clé USB 16Go & Informatique & 3500 \\
P4 & Souris Optique & Informatique & 2500 \\
P5 & Ramette A4 & Papeterie & 2500 \\
\hline
\end{tabular}
\end{center}

Les lignes P1 (200) et P2 (500) sont éliminées. Attention : la condition est \texttt{>= 2500}, donc P4 et P5 (prix exactement 2500) sont \textbf{retenues}.

\textbf{Étape 2 : projection sur \texttt{Categorie} avec \texttt{DISTINCT}.}

Les catégories des lignes retenues sont : Informatique, Informatique, Papeterie. Après élimination des doublons, il reste : Informatique, Papeterie.

\textbf{La requête renvoie donc 2 lignes.}

\textbf{Point de vigilance :} l'ordre logique d'exécution est \texttt{FROM} $\rightarrow$ \texttt{WHERE} $\rightarrow$ \texttt{SELECT DISTINCT}. Le \texttt{DISTINCT} s'applique \emph{après} le filtrage, sur les catégories des lignes déjà sélectionnées.
\end{corrige}

\begin{corrige}[Exercice 5 — Création de table avec contraintes]
\begin{lstlisting}[language=SQL]
CREATE TABLE ETUDIANT (
    Matricule  CHAR(10)     PRIMARY KEY,
    Nom        VARCHAR(30)  NOT NULL,
    Prenom     VARCHAR(30),
    DateNaiss  DATE         NOT NULL,
    Sexe       CHAR(1),
    Classe     VARCHAR(15)
);
\end{lstlisting}

\textbf{Justifications des choix :}
\begin{itemize}
    \item \texttt{Matricule} est déclaré \texttt{CHAR(10)} car sa longueur est fixe (10 caractères) ; il est \texttt{PRIMARY KEY}, ce qui garantit unicité et non-nullité.
    \item \texttt{Nom} et \texttt{DateNaiss} portent la contrainte \texttt{NOT NULL} car l'énoncé les qualifie d'obligatoires.
    \item \texttt{Sexe} est un \texttt{CHAR(1)} : un seul caractère ('M' ou 'F'). Un \texttt{VARCHAR(1)} serait inutilement complexe.
    \item \texttt{Prenom} et \texttt{Classe} restent sans contrainte : ils peuvent être laissés vides (\texttt{NULL}).
\end{itemize}

\textbf{Points de vigilance :} ne pas oublier la virgule entre chaque définition de colonne (mais jamais après la dernière) ; les noms de colonnes ne prennent pas d'accents ni d'espaces.
\end{corrige}

\begin{corrige}[Exercice 6 — Manipulation de données : INSERT, UPDATE, DELETE]
\textbf{1. Insertion du nouvel employé :}
\begin{lstlisting}[language=SQL]

VALUES (105, 'MBARGA', 'Informatique', 250000, '2023-09-01');
\end{lstlisting}
Les chaînes de caractères et les dates sont encadrées par des apostrophes ; le format de date standard SQL est \texttt{'AAAA-MM-JJ'}.

\textbf{2. Augmentation de 10 \% des salaires du service Comptabilité :}
\begin{lstlisting}[language=SQL]
UPDATE EMPLOYE
SET Salaire = Salaire * 1.10
WHERE Service = 'Comptabilite';
\end{lstlisting}
Augmenter de 10 \% revient à multiplier par $1 + \frac{10}{100} = 1,10$. (On écrit \texttt{1.10} dans le code, \texttt{1,10} en français).

\textbf{3. Suppression des employés embauchés avant 1990 :}
\begin{lstlisting}[language=SQL]
DELETE FROM EMPLOYE
WHERE DateEmbauche < '1990-01-01';
\end{lstlisting}

\textbf{Points de vigilance :}
\begin{itemize}
    \item Sans clause \texttt{WHERE}, \texttt{UPDATE} et \texttt{DELETE} s'appliquent à \textbf{toutes} les lignes de la table : c'est l'erreur la plus grave en manipulation de données.
    \item Les comparaisons de dates fonctionnent directement avec le format \texttt{'AAAA-MM-JJ'} car l'ordre alphabétique y coïncide avec l'ordre chronologique.
\end{itemize}
\end{corrige}

\begin{corrige}[Exercice 7 — Interrogation simple et opérateurs logiques]
\textbf{1. Titre et auteur des livres publiés après 2010 :}
\begin{lstlisting}[language=SQL]
SELECT Titre, Auteur
FROM LIVRE
WHERE AnneeEdition > 2010;
\end{lstlisting}
« Après 2010 » signifie strictement supérieur : un livre de 2010 est exclu.

\textbf{2. Toutes les colonnes, prix entre 3000 et 10000 inclus ET stock > 5 :}
\begin{lstlisting}[language=SQL]
SELECT *
FROM LIVRE
WHERE Prix >= 3000 AND Prix <= 10000 AND Stock > 5;
\end{lstlisting}
L'étoile \texttt{*} sélectionne toutes les colonnes. Les bornes incluses imposent \texttt{>=} et \texttt{<=} ; le stock « strictement supérieur à 5 » impose \texttt{>}.

\textbf{3. Titres distincts des livres de BETI ou OYONO :}
\begin{lstlisting}[language=SQL]
SELECT DISTINCT Titre
FROM LIVRE
WHERE Auteur = 'BETI' OR Auteur = 'OYONO';
\end{lstlisting}
\texttt{DISTINCT} évite d'afficher deux fois le même titre si deux éditions existent.

\textbf{4. Nombre de livres en stock par auteur :}
\begin{lstlisting}[language=SQL]
SELECT Auteur, COUNT(*) AS NombreLivres
FROM LIVRE
WHERE Stock > 0
GROUP BY Auteur;
\end{lstlisting}
Le \texttt{WHERE} filtre les lignes \emph{avant} le regroupement ; \texttt{GROUP BY} forme ensuite un groupe par auteur et \texttt{COUNT(*)} compte les lignes de chaque groupe.

\textbf{Point de vigilance :} ne pas écrire \texttt{Auteur = 'BETI' OR 'OYONO'} : chaque condition après \texttt{OR} doit être complète.
\end{corrige}

\begin{corrige}[Exercice 8 — Jointure entre deux tables]
\begin{lstlisting}[language=SQL]
SELECT CO.NumCom, CO.DateCom, CO.Montant, CL.NomCli
FROM COMMANDE CO, CLIENT CL
WHERE CO.NumCli = CL.NumCli;
\end{lstlisting}

\textbf{Rôle de la condition de jointure :} la condition \texttt{CO.NumCli = CL.NumCli} associe à chaque commande le client qui l'a passée, en évitant le produit cartésien (qui apparierait chaque commande avec \emph{tous} les clients, y compris les mauvais).

\textbf{Points de vigilance :}
\begin{itemize}
    \item Les alias \texttt{CO} et \texttt{CL}, déclarés dans le \texttt{FROM}, allègent l'écriture et lèvent l'ambiguïté sur la colonne \texttt{NumCli} présente dans les deux tables.
    \item Sans la condition de jointure, le résultat contiendrait $n \times m$ lignes (produit cartésien), ce qui est presque toujours une erreur.
\end{itemize}
\end{corrige}

    \item \textbf{LIVRE} (\underline{ISBN}, Titre, Auteur, Categorie, NbExemplaires)
    \item \textbf{ELEVE} (\underline{Matricule}, Nom, Prenom, Classe, DateNaissance)
    \item \textbf{EMPRUNTER} : association entre ELEVE et LIVRE, porteuse des attributs DateEmprunt et DateRetourPrevue. Cardinalités : un élève peut emprunter plusieurs livres et un livre (titre) peut être emprunté plusieurs fois (au cours du temps), donc ELEVE (0,n) --- EMPRUNTER --- (0,n) LIVRE.
\end{itemize}
L'énoncé « un exemplaire ne peut être emprunté que par un seul élève à la fois » ne change pas la cardinalité (0,n) côté livre : sur toute la durée de vie de la bibliothèque, un même titre connaîtra plusieurs emprunts successifs.

\textbf{2. MLD (schéma relationnel) :}
\begin{itemize}
    \item LIVRE(\underline{ISBN}, Titre, Auteur, Categorie, NbExemplaires)
    \item ELEVE(\underline{Matricule}, Nom, Prenom, Classe, DateNaissance)
    \item EMPRUNT(\underline{ISBN\#}, \underline{Matricule\#}, DateEmprunt, DateRetourPrevue) où ISBN référence LIVRE(ISBN) et Matricule référence ELEVE(Matricule).
\end{itemize}
L'association (0,n)-(0,n) devient une table de liaison dont la clé primaire est composée des deux clés étrangères.

\textbf{3. Création de la table LIVRE :}
\begin{lstlisting}[language=SQL]
CREATE TABLE LIVRE (
    ISBN          CHAR(13)     PRIMARY KEY,
    Titre         VARCHAR(100) NOT NULL,
    Auteur        VARCHAR(50),
    Categorie     VARCHAR(30),
    NbExemplaires INT
);
\end{lstlisting}

\textbf{4. Création de la table EMPRUNT :}
\begin{lstlisting}[language=SQL]
CREATE TABLE EMPRUNT (
    ISBN             CHAR(13),
    Matricule        INT,
    DateEmprunt      DATE NOT NULL,
    DateRetourPrevue DATE,
    PRIMARY KEY (ISBN, Matricule),
    FOREIGN KEY (ISBN) REFERENCES LIVRE(ISBN),
    FOREIGN KEY (Matricule) REFERENCES ELEVE(Matricule)
);
\end{lstlisting}

\textbf{Barème indicatif (sur 10 points) :} MCD correct (entités, attributs, clés soulignées, cardinalités) : 3 pts ; MLD avec clés primaires et étrangères bien repérées : 3 pts ; \texttt{CREATE TABLE LIVRE} : 2 pts ; \texttt{CREATE TABLE EMPRUNT} avec clé primaire composée et deux \texttt{REFERENCES} : 2 pts.

\textbf{Points de vigilance :} la table EMPRUNT doit être créée \emph{après} LIVRE et ELEVE (on ne peut référencer que des tables existantes) ; la clé primaire composée se déclare séparément avec \texttt{PRIMARY KEY (ISBN, Matricule)}, pas en répétant \texttt{PRIMARY KEY} sur chaque colonne.
\end{corrige}

\begin{corrige}[Exercice 10 — Sujet Bac : gestion du personnel, requêtes complexes]
\textbf{1. Employés gagnant plus que la moyenne :}
\begin{lstlisting}[language=SQL]
SELECT Nom, Prenom, Salaire
FROM EMPLOYE
WHERE Salaire > (SELECT AVG(Salaire) FROM EMPLOYE);
\end{lstlisting}
La sous-requête calcule la moyenne générale : $(350000 + 280000 + 420000 + 310000 + 290000) / 5 = 1650000 / 5 = 330000$. Seuls FOPA Jean (350 000) et KAMGA Paul (420 000) sont affichés.

\textbf{2. Nombre d'employés par service, services vides inclus :}
\begin{lstlisting}[language=SQL]
SELECT S.NomServ, COUNT(E.Matricule) AS NbEmployes
FROM SERVICE S LEFT JOIN EMPLOYE E ON S.CodeServ = E.CodeServ
GROUP BY S.NomServ;
\end{lstlisting}
La jointure externe \texttt{LEFT JOIN} conserve les services sans employé (qui affichent 0 car \texttt{COUNT(E.Matricule)} ne compte pas les \texttt{NULL}). Résultat attendu : Informatique : 2 ; Comptabilité : 2 ; Ressources Humaines : 1.

\textbf{3. Augmentation de 5 \% ciblée :}
\begin{lstlisting}[language=SQL]
UPDATE EMPLOYE
SET Salaire = Salaire * 1.05
WHERE CodeServ = 'INF' AND DateEmb < '2016-01-01';
\end{lstlisting}
Les employés du service Informatique (\texttt{CodeServ = 'INF'}) embauchés avant le 2016-01-01 sont FOPA Jean (embauché le 2015-01-10) et KAMGA Paul (embauché le 2010-03-15). Les deux sont concernés.
Nouveaux salaires : FOPA $350000 \times 1,05 = 367500$ FCFA ; KAMGA $420000 \times 1,05 = 441000$ FCFA.

\textbf{4. Suppression de MEKONGO Pierre :}
\begin{lstlisting}[language=SQL]
DELETE FROM EMPLOYE
WHERE Nom = 'MEKONGO' AND Prenom = 'Pierre';
\end{lstlisting}
MEKONGO (matricule 105) n'est chef d'aucun service (les chefs sont 103, 102, 104), donc la suppression s'effectue normalement. En revanche, si l'employé supprimé était référencé comme \texttt{ChefServ} dans la table SERVICE, le SGBD \textbf{refuserait la suppression} pour préserver l'\textbf{intégrité référentielle} : on ne peut pas supprimer une ligne tant qu'une clé étrangère d'une autre table pointe vers elle. Il faudrait d'abord modifier ou supprimer la référence dans SERVICE.

\textbf{5. Employé, son service et le nom du chef :}
\begin{lstlisting}[language=SQL]
SELECT E.Nom, E.Prenom, S.NomServ, C.Nom AS NomChef
FROM EMPLOYE E, SERVICE S, EMPLOYE C
WHERE E.CodeServ = S.CodeServ
  AND S.ChefServ = C.Matricule;
\end{lstlisting}
La table EMPLOYE est utilisée deux fois sous deux alias différents (\texttt{E} pour l'employé, \texttt{C} pour le chef) : c'est une \textbf{auto-jointure}.
Résultat attendu :
\begin{itemize}
    \item FOPA / Informatique / KAMGA
    \item NGONO / Comptabilité / NGONO (elle est sa propre chef)
    \item KAMGA / Informatique / KAMGA (il est son propre chef)
    \item ETOUNDI / Ressources Humaines / ETOUNDI (il est son propre chef)
    \item MEKONGO / Comptabilité / NGONO
\end{itemize}

\textbf{Barème indicatif (sur 10 points) :} 2 pts par requête correcte, dont 1 pt pour la justification ou l'explication dans les questions 4 et 5.

\textbf{Points de vigilance :} citer explicitement l'\emph{intégrité référentielle} à la question 4 ; à la question 5, exiger deux alias distincts et deux conditions de jointure dans le \texttt{WHERE}.
\end{corrige}

\begin{corrige}[Exercice 11 — Sujet Bac : débogage et mise en œuvre pratique]
\textbf{1. Les 5 erreurs :}
\begin{enumerate}
    \item \textbf{Ordre de création des tables (bloc \texttt{CREATE TABLE SESSION}) :} SESSION référence CLIENT avec une clé étrangère alors que CLIENT n'existe pas encore. Il faut créer CLIENT \emph{avant} SESSION.
    \item \textbf{Type incohérent (ligne \texttt{Solde INT DEFAULT '0.00'}) :} la valeur par défaut \texttt{'0.00'} est une chaîne décimale entre apostrophes, incompatible avec le type \texttt{INT}. Il faut écrire \texttt{DEFAULT 0}.
    \item \textbf{Format de date (premier \texttt{INSERT}) :} \texttt{'15/01/2024'} n'est pas le format SQL standard ; il faut \texttt{'2024-01-15'}.
    \item \textbf{Violation d'intégrité référentielle (troisième \texttt{INSERT}) :} la session 102 référence le client 2 qui n'existe pas dans CLIENT ; le SGBD rejette l'insertion.
    \item \textbf{Absence de condition de jointure (dernier \texttt{SELECT}) :} \texttt{FROM CLIENT C, SESSION S} sans \texttt{WHERE} produit un produit cartésien ; il manque \texttt{WHERE C.IdClient = S.IdClient}.
\end{enumerate}
(On peut aussi signaler le \texttt{UPDATE} sans \texttt{WHERE}, qui débite \emph{tous} les clients : c'est une erreur logique acceptable comme 5\ieme{} réponse.)

\textbf{2. Script corrigé et ordonnancé (Syntaxe MySQL) :}
\begin{lstlisting}[language=SQL]
CREATE DATABASE CYBERCAFE;
USE CYBERCAFE;

-- Creation de la table parente d'abord
CREATE TABLE CLIENT (
    IdClient INT PRIMARY KEY,
    Nom VARCHAR(30) NOT NULL,
    Prenom VARCHAR(30),
    Solde INT DEFAULT 0,
    DateInscription DATE
);

-- Puis la table qui la reference
CREATE TABLE SESSION (
    IdSession INT PRIMARY KEY,
    DateDebut DATE,
    Duree INT,
    IdClient INT,
    FOREIGN KEY (IdClient) REFERENCES CLIENT(IdClient)
);

INSERT INTO CLIENT VALUES (1, 'ABENA', 'Paul', 5000, '2024-01-15');
INSERT INTO CLIENT VALUES (2, 'NDJOCK', 'Marie', 3000, '2024-01-15');
INSERT INTO SESSION VALUES (101, '2024-01-15', 60, 1);
INSERT INTO SESSION VALUES (102, '2024-01-15', 45, 2);

UPDATE CLIENT SET Solde = Solde - 1000 WHERE IdClient = 1;

SELECT C.Nom, S.DateDebut, S.Duree
FROM CLIENT C, SESSION S
WHERE C.IdClient = S.IdClient;
\end{lstlisting}

\textbf{3. Durée totale des sessions par client en janvier 2024 :}
\begin{lstlisting}[language=SQL]
SELECT C.Nom, SUM(S.Duree) AS DureeTotale
FROM CLIENT C, SESSION S
WHERE C.IdClient = S.IdClient
  AND S.DateDebut >= '2024-01-01'
  AND S.DateDebut <= '2024-01-31'
GROUP BY C.Nom;
\end{lstlisting}

\textbf{Barème indicatif (sur 10 points) :} identification des 5 erreurs : 5 pts (1 pt par erreur correctement localisée et qualifiée) ; script corrigé cohérent : 3 pts ; requête avec \texttt{SUM}, \texttt{GROUP BY} et jointure : 2 pts.

\textbf{Points de vigilance :} l'ordre de création des tables (parente avant fille) est une justification attendue ; le format de date \texttt{'AAAA-MM-JJ'} doit être cité ; la condition de jointure dans le \texttt{WHERE} est indispensable dès que deux tables figurent dans le \texttt{FROM}.
\end{corrige}

\courssub{Définitions clés}

\begin{definition}[Base de Données (BDD)]
Collection structurée de données persistantes, organisées pour un accès, une gestion et une mise à jour faciles. Modélisée par un \cle{MCD} puis un \cle{MLD}.
\end{definition}

\begin{definition}[SGBD (Système de Gestion de Base de Données)]
Logiciel (ex. \texttt{MySQL}, \texttt{Access}, \texttt{PostgreSQL}) permettant de créer, gérer, sécuriser et interroger une BDD. Assure l'indépendance données/programmes.
\end{definition}

\begin{definition}[SQL (Structured Query Language)]
Langage standardisé pour manipuler les BDD relationnelles. Deux sous-langages principaux :
\begin{itemize}
    \item \textbf{LDD (Langage de Définition des Données)} : \cle{CREATE}, \cle{ALTER}, \cle{DROP} (structure).
    \item \textbf{LMD (Langage de Manipulation des Données)} : \cle{INSERT}, \cle{UPDATE}, \cle{DELETE}, \cle{SELECT} (contenu).
\end{itemize}
\end{definition}

\begin{definition}[Clé Primaire (Primary Key -- PK)]
Attribut (ou groupe d'attributs) identifiant \textbf{uniquement} chaque ligne (tuple) d'une table. \textbf{Non NULL, Unique}.
\end{definition}

\begin{definition}[Clé Étrangère (Foreign Key -- FK)]
Attribut d'une table faisant référence à la \cle{PK} d'une autre table. Assure l'\textbf{intégrité référentielle}.
\end{definition}

\courssub{Méthodes express (Syntaxe de référence)}

\begin{methode}[Créer une table (LDD)]
\begin{enumerate}
    \item \texttt{CREATE TABLE NomTable (}
    \item \quad \texttt{col1 TYPE CONTRAINTES,}
    \item \quad \texttt{col2 TYPE CONTRAINTES,}
    \item \quad \texttt{PRIMARY KEY (col1),}  \textit{-- ou inline}
    \item \quad \texttt{FOREIGN KEY (col\_fk) REFERENCES AutreTable(pk)}
    \item \texttt{);}
\end{enumerate}
\end{methode}

\begin{methode}[Modifier une table (ALTER TABLE)]
\begin{itemize}
    \item Ajouter colonne : \texttt{ALTER TABLE T ADD colonne TYPE CONTRAINTES;}
    \item Supprimer colonne : \texttt{ALTER TABLE T DROP COLUMN colonne;}
    \item Modifier type/contrainte : \texttt{ALTER TABLE T MODIFY colonne NEW\_TYPE;} (MySQL) / \texttt{ALTER TABLE T ALTER COLUMN colonne NEW\_TYPE;} (Access/SQL Server)
    \item Ajouter clé étrangère : \texttt{ALTER TABLE T ADD FOREIGN KEY (fk) REFERENCES Parent(pk);}
\end{itemize}
\end{methode}

\begin{methode}[Insérer / Modifier / Supprimer des lignes (LMD)]
\begin{itemize}
    \item \textbf{INSERT} : \texttt{INSERT INTO T (c1, c2) VALUES (v1, v2);} (colonnes optionnelles si toutes fournies dans l'ordre).
    \item \textbf{UPDATE} : \texttt{UPDATE T SET c1 = nv1, c2 = nv2 WHERE condition;} \textbf{\cle{WHERE} obligatoire sauf suppression totale voulue.}
    \item \textbf{DELETE} : \texttt{DELETE FROM T WHERE condition;} (supprime lignes, garde structure). \texttt{TRUNCATE TABLE T;} (vide table, réinitialise auto-incrément, plus rapide).
\end{itemize}
\end{methode}

\begin{methode}[Sélectionner des données (SELECT)]
\begin{enumerate}
    \item \texttt{SELECT \cle{DISTINCT} col1, col2, * FROM Table}
    \item \texttt{WHERE condition} (filtre lignes : \texttt{=, <>, <, >, <=, >=, BETWEEN, IN, LIKE, IS NULL})
    \item \texttt{ORDER BY col1 [ASC|DESC], col2 ...} (tri)
    \item \texttt{LIMIT n} (MySQL) / \texttt{TOP n} (Access) -- pagination
\end{enumerate}
\end{methode}

\begin{methode}[Jointure entre deux tables (Équi-jointure)]
\begin{enumerate}
    \item Donner des \textbf{alias} courts aux tables : \texttt{FROM Eleve e, Classe c}
    \item Préciser la condition de liaison dans \texttt{WHERE} : \texttt{WHERE e.id\_classe = c.id}
    \item Préfixer les colonnes ambiguës : \texttt{SELECT e.nom, c.libelle}
\end{enumerate}
\textbf{Syntaxe canonique :}
\begin{lstlisting}[language=SQL]
SELECT e.nom, e.prenom, c.libelle AS classe
FROM Eleve e, Classe c
WHERE e.id_classe = c.id
  AND c.niveau = 'Terminale'
ORDER BY e.nom;
\end{lstlisting}
\end{methode}

\begin{center}
\begin{tabularx}{\linewidth}{|l|l|X|}
\hline
\rowcolor{popblueL}
\textbf{Catégorie} & \textbf{Opérateur} & \textbf{Exemple / Signification} \\
\hline
Comparaison & \texttt{=, <>, !=, <, >, <=, >=} & \texttt{age >= 18} \\
Logique & \texttt{AND, OR, NOT} & \texttt{ville='Yaounde' AND age>20} \\
Intervalle & \texttt{BETWEEN a AND b} & \texttt{note BETWEEN 10 AND 20} \\

Motif (chaîne) & \texttt{LIKE '\%mot\%'} & \texttt{nom LIKE 'M\%'} (commence par M), \texttt{\_} = 1 caractère \\
